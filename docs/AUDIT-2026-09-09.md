# GrepBot Bug and Optimization Audit - 2026-09-09

## 1. Summary

The current 53-module v6.0.69 tree passes source/artifact parity, duplicate-declaration, const-order, syntax, and ASCII checks, but contains reproducible runtime defects that those gates cannot detect. Highest priorities are recursive ledger persistence and transport outcomes that discard uncertainty; these affect deduplication and military/write behavior. Decision-memory escalation, dry-run collection state, snapshot restoration, and Queue Center positioning also need attention. Rendering and repeated collection scans offer bounded optimization opportunities, but no measured evidence establishes a missed 20-second scheduler budget. This was a read-only source audit with isolated mocked checks, not an es146 gameplay certification. Only this report was added; implementation remains pending review and authorization.

## 2. Critical bugs

Priorities: P1 = high-impact runtime correctness; P2 = functional defect; P3 = lower-impact or latent issue. No P0 found. Suggested directions below are not patches or authorization to implement.

### B1 - P1: Shared ledger save recurses instead of persisting

**Evidence:** `src/core.js:1516`, `src/support.js:142`, `src/support.js:157`, `src/emergency.js:108`, `src/recruit.js:1601`, `src/recruit.js:1690`.

The nested `boundedLedger` function named `save` calls `save(storeKey, ensure())`, resolving to itself instead of the outer storage helper. Every call throws `RangeError: Maximum call stack size exceeded`; an isolated check recorded zero calls to the outer storage stub. Successful support/stash bookkeeping cannot persist through this helper. Support recall throws before reaching its cancellation loop. Recruit pack/target save callers share the same defect. In-memory mutation can survive until reload, making the failure look intermittent from the UI.

**Direction:** Remove the name shadowing and verify actual storage calls plus each consumer's completion path. Pair support validation with B6: repairing persistence exposes an existing overly broad recall selector. The R4/R5 ledger consolidation is marked done in `docs/REDESIGN.md:456`; recursion is not a documented accepted exception. **Needs a dedicated authorized session** because consumer behavior affects military/write modules.

### B2 - P1: Ambiguous network failures become retryable terminal failures

**Evidence:** `src/bridge.js:220`, `src/tx.js:975`, `src/tx.js:996`, `src/tx.js:998`, `src/tx.js:865`.

An XHR watcher status of zero becomes `neterr`. Only the literal `timeout` enters transaction reconciliation; `neterr` takes the generic error path and sets `state='failed'`. The duplicate-intent guard protects unknown/in-flight states but excludes failed transactions. A request accepted by the server followed by a lost response can therefore be sent again on a later attempt. This is a conditional duplicate-write risk, not evidence that a duplicate occurred on es146.

**Direction:** Classify post-send transport uncertainty separately from authoritative rejection and preserve reconciliation/dedup evidence. Include observer cancellation in that classification; cancelling a watcher does not prove gpAjax cancelled the server action. **Needs a dedicated authorized session** for bridge/transaction/write semantics.

### B3 - P1: Captcha response cancels its own result classification

**Evidence:** `src/bridge.js:198`, `src/bridge.js:213`, `src/core.js:2520`, `src/core.js:2531`, `src/core.js:2626`, `src/tx.js:996`.

`ajaxTransportRaw` calls `captchaTrip` before `finish('captcha')`. `captchaTrip` invokes `gbAbortFeature`, which synchronously invokes the current watcher's cancellation callback. That callback settles the request as `cancelled`; the later captcha settlement is ignored. The transaction consequently records an ordinary failure, feeding hard-error accounting instead of the intended captcha result. A mocked execution of the actual transport function reproduced `captcha response settled as: cancelled`. Other already-sent requests cancelled through the same feature sweep also need uncertainty handling under B2.

**Direction:** Ensure one authoritative captcha settlement while retaining uncertain outcomes for other outstanding posts. Preserve the captcha pause itself. **Needs a dedicated authorized session** for bridge/core/transaction behavior.

### B4 - P2: Decision-memory cooldown never advances normally to 15/60 minutes

**Evidence:** `src/journal.js:225`, `src/journal.js:255`.

When a skip expires, `jrnSkipped` decrements `trips` and deletes the first-trip record. The next hard failure then starts from zero again. Under the normal gate-before-attempt flow, a persistent failure repeats five-minute windows instead of escalating through 5/15/60. Isolated execution reproduced two consecutive 300000 ms windows, each with `trips=1`.

**Direction:** Preserve escalation history through ordinary window expiry; define recovery/decay separately from permission to retry. Keep success/reset semantics explicit. **Needs a dedicated authorized session** for journal behavior.

### B5 - P2: Inconclusive reconciliation counts as a hard error

**Evidence:** `src/journal.js:57`, `src/journal.js:61`, `src/tx.js:906`, `src/tx.js:922`.

`jrnPendingResult` recognizes `timeout_unknown`, `pending`, and `unknown outcome`, but not exact `unknown`. Transaction reconciliation emits that exact result. `jrnHard('unknown')` evaluates true, so unresolved checks can accumulate hard-error strikes and open decision-memory skip windows despite no proven server rejection. This also distorts error statistics.

**Direction:** Normalize uncertain result codes consistently across transaction and journal handling. Prove repeated inconclusive reconciliation remains non-hard without weakening true rejection accounting. **Needs a dedicated authorized session** for transaction/journal behavior.

### B6 - P1 latent behind B1: Support recall includes unrelated commands

**Evidence:** `src/support.js:135`, `src/support.js:155`, `src/support.js:157`.

The send ledger stores donor town IDs but not the specific sent command IDs. Recall selects every outgoing support/support_sea movement from those donors, regardless of destination or ownership by the recorded support window. Once B1 is fixed, recalling one window can cancel unrelated manual support or another window's support. Currently the recursive save throws before the recall loop, so this is a latent hazard that must be resolved before that path is re-enabled by a helper repair.

**Direction:** Establish exact command ownership through send/reconciliation evidence and restrict recall to owned commands. **Needs a dedicated authorized military session.** This does not scope the excluded attack/reinforce planner merge.

### B7 - P2: Dry run permanently marks surviving Recoger buttons as collected

**Evidence:** `src/collect.js:52`, `src/collect.js:74`.

The callback marks every eligible button with `dataset.grepbotClicked` on both success and `dryrun`. Later scans skip marked nodes. Turning dry run off therefore leaves those buttons ineligible until the game replaces their DOM nodes or the page reloads. A mocked eligible five-minute Recoger card produced one attempt across a dry-run scan followed by another scan; the marker remained set.

**Direction:** Keep simulated completion separate from confirmed collection state. Validate dry-run ON, dry-run OFF, and successful real collection on the same surviving node. **Needs a dedicated authorized write-module session.**

### B8 - P2: Restoring a snapshot makes the saved snapshot mutable

**Evidence:** `src/diagnostics.js:65`, `src/ui.js:3042`.

`snapshotRestore` assigns payload objects directly to live state. Editing restored target maps mutates the same objects held by the snapshot slot. A second restore in that session no longer recovers the original snapshot. Copying at snapshot creation does not prevent this later alias.

**Direction:** Restore independent copies and prove restore/edit/restore preserves the original slot. This local alias fix has medium risk and needs UI validation.

**Related P1 design risk:** `src/diagnostics.js:70` also replaces current `txState` with historical transaction evidence, while callbacks at `src/tx.js:974` require the original live transaction object. Restoring during an in-flight write can discard its evidence and make its callback return without completion. The UI explicitly confirms overwriting transactions, so this is visible current design, not a hidden new toggle; confirmation cannot restore missing knowledge of server-side effects. Any transaction-safe restore policy **needs a dedicated authorized session**. Do not expand a clone-only fix into that policy implicitly.

### B9 - P2: Queue Center can be dragged mostly outside the viewport

**Evidence:** `src/queue-center.js:13`, `src/queue-center.js:16`, `src/qol.js:55`.

Horizontal drag bounds use viewport width minus CSS maximum width rather than the actual window width. For a 1920 px viewport, a 760 px window, and max-width approximately 1805 px, the calculation permits left approximately 1805 px, hiding most of the window and its close button.

**Direction:** Bound position using actual rendered dimensions, following the existing widget implementation. Validate right-edge dragging, resizing, and narrow viewports. Low risk; local browser validation sufficient initially.

Existing leader, captcha, server-pressure, panic, safe-mode, first-post and optional pause behavior conflicts with a literal interpretation of "only enable can stop"; it is documented behavior and not authorization to remove protection. - **Recruit endpoint / templates:** recruit controller uses barracks/docks, not temple (`src/recruit.js:3`). Support retains its own learned support template (`src/support.js:22`); no attack/support sharing defect was confirmed in the reviewed paths. No default spellPower was found. - **DOM and options:** reviewed UI sinks use literal `gbLit` or `textContent`; HUD and research-picker `replaceChildren` hits clear detached construction stages. - **Locks and scheduling:** helper-owned timer/leadership bookkeeping is not automatically a feature in-flight lock violation. No new feature-local econ interval duplicating orch was established in the inspected paths.
