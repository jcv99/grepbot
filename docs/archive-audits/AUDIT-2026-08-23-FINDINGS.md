# GrepBot Audit — 2026-08-23

Generated by a 4-agent parallel audit (`AgentSwarm`) + an implementation pass
that patched every CRITICAL, every HIGH, and the easy MEDIUM items. Scope:
the assembled `grepbot.user.js` (51 modules, ~27.5k stripped lines, one IIFE)
plus the per-module `src/*.js` when context was needed.

The build pipeline (`build.py`) already catches: duplicate top-level
declarations, `node --check` syntax, ASCII escape integrity, and version
bump requirements. This audit looks past those gates for **logic errors,
cross-module bugs, error-handling gaps, duplications, and state/ordering
issues** that only surface at runtime or across module boundaries.

## CRITICAL — fixed

### #1 `gbLockTouch` return ignored, 15 sites

When a captcha trips the unlock, the next pending `next()`/`step()` IIFE
fires anyway, calling `gbLockTouch` but ignoring its false return, and posts
a new send without the lock. towns.js:223 was the only call site that
checked the return. Fix: add `if (!gbLockTouch(LOCK, token)) return;` to
every other call site.

### #2 `tx.js:656` — dryrun stamp overwrites in-flight real tx

The bail on `state.dryRun` ran BEFORE the existing-tx dedup at line 718, so
a dryrun tick landing on a `sending`/`confirming`/`reconciling`/`unknown`
slot silently replaced the real attempt's `id`. The server callback would
then arrive against a stamp the reconciler no longer recognised, and the
real write was lost. Fix: short-circuit the dryrun branch with the same
in-flight predicate the dedup uses, and return `pending:state` instead of
overwriting.

### #3 `tx.js:820` — commit only on `'applied'`

The post-reconcile branch treated `applied`/`unknown`/`unchanged` as
interchangeable confirmation. A captcha-walled 200-with-error response
(common), a CSRF reject, or a server-side silent drop all parse as a
successful callback but never touch the model — the reconcile says
`'unchanged'` or `'unknown'`, and the code committed the planner ledger
anyway, poisoning a `PLANNER_COMMIT_HOLD_MS` reservation (15s) on a
write that may never have happened. Fix: only `applied` commits; the
other two fall through to the same `'unknown'` outcome the
timeout-reconcile path uses, with `jrnPush('timeout', ...)`. This is the
same pattern the timeout branch (lines 793-804) already implements.

### #4 `dodge.js:87` — own-origin hostile filter dropped raids

The strict `a.is_attack === true || a.is_attack === 1` test dropped
own-origin raids, sieges, and revolts that the client only flagged via
`command_type` (not `is_attack`). The line above (`dodgeIsHostileMovement`)
already classified them as hostile. Fix: re-use the full hostile predicate
on the own-origin branch — `if (myTowns.has(origin) && !dodgeIsHostileMovement(a)) return;`.

### #5 `journal.js:142` — dedup coalesce reused `n`/`x` across distinct tx ids

After a `'reconciled'` row landed, the next call for the same tag with the
same `'ok'` result coalesced against it and reused the same `txId` for `N`
occurrences. External readers counting `n` per `x` got wrong totals. The
40-row loop window was also brittle: a burst tick (bandit+spy+send same
second) could push the same tag past 40 entries and produce a second
counter that should have been one. Fix: include `r.x` (txId) in the
non-provisional match (break on txId mismatch), and walk the full list
capped only by storage.

## HIGH — fixed

### #6 `tx.js:81,94` — quest-clear swallow

`txClearUnknown` and `txClearOne` wrapped the call to
`questClearReviewForTx` in `try { ... } catch (_) {}`. If the clear failed
(stale `state.questRewards`, hot-reload of half the map, prototype
poisoning on `Object.values`), the transaction still flipped to `'aborted'`
but `state.questRewards` kept `claimReview=true` and `claimError` set. The
operator hits "Clear", gets no error, and the stuck "REVIEW" badge remains
in the Quests tab — the next auto-claim scan still refuses. Fix: route
the catch through `gbLogT('quest-clear-err-' + qid, 60000, ...)` so the
operator sees the failure with the offending quest id.

### #7 `journal.js:44` — host-save swallow

`jrnCheckHost` persists the OUTGOING world's journal to its world-scoped
key on hostname change. `try { jrnSaveForHost(jrnHost); } catch (_) {}`
swallowed any `GM_setValue` failure — quota, serialization error, etc. The
next line then loads the NEW world and logs "memory: reloaded for host
<X>" — the operator believes both worlds are healthy. Fix: log the failure
to the journal-log path so the cross-host hop that ate data is visible.

### #8 `recruit.js:1509,1520` — empty catches in batch loop

The `anyTown` probe (1509-1514) and the per-town fire loop (1520-1535)
both wrapped their bodies in `try { ... } catch (_) {}`. If
`batchRecruitAtomicAfford` or `batchRecruitFire` threw mid-loop (e.g.
game model proxy invalidated by an SPA navigation), `count` stayed at 0
and the bottom log line was `batch recruit: idle (scan)` — i.e. the
operator saw "idle" for a feature that just crashed. With
`state.batchRecruit` remaining ON and never re-arming, a single error
could leave the feature silently disabled for the rest of the session.
Fix: replace the empty catches with `gbLogT('batch-recruit-probe-err' | 'batch-recruit-fire-err', 60000, ...)`.

### #9 `dump.js:80,122` — transportBalanceJobs / ironReservedForCave swallow

`pickDumpDestination` (line 80) silently set `jobs = []` on any throw, so
the dump planner "found no destination" for every town for the rest of
the session. `dumpJobs` (line 122) silently fell through to the
non-cave-respecting path, shipping iron the cave wanted. Fix: log both,
and on the iron-reserved throw, skip the iron (treat as "cave wants it")
rather than ship it.

## MEDIUM — fixed

### #10 `orchestrate.js:182` — priorityOrder intra-list dupes

The concat pattern (`mandatory.concat(configured.filter(...)).concat(defaults.filter(...))`)
didn't dedupe duplicates *within* `configured`. If `state.priorityOrder`
had `'farm'` twice, both passed through, both added cadence to the due
list, and `orchTick` fired farm twice per tick. Fix: `[...new Set(mandatory.concat(configured, orchDefaultOrder()))]`.

### #11 `boot.js:103,177` — releaseLocksAt TDZ-adjacent + dedup reset

`let releaseLocksAt = 0;` was declared at line 177, below the `pageshow`
listener registered at line 100. The listener touched it at line 103.
The callback only runs when `pageshow` fires (later than line 177), so no
actual TDZ today — but any future module that moved the listener above
the `let` would hit `ReferenceError` on the first pageshow. Separately,
`releaseLocksAt = 0;` on bfcache restore defeated the `RELEASE_DEDUP_MS`
protection: if the browser fired both `pagehide` and `pageshow(persisted)`
in sequence, both went through the unguarded code. Fix: move the `let`
and `const` to before the first `gbListen` call, and reset to
`Date.now() + 3000` (matching `RELEASE_DEDUP_MS`) so the dedup window is
forwarded, not broken.

## MEDIUM — design / follow-up

These need more than a 1-line patch. Each is documented with the failure
mode and a fix sketch so a follow-up PR can land them.

### #12 `farms.js:1175` — captcha-hot filter is sticky for the whole day

`farmApplyDropPolicies` filters out every village whose `counts[villId] >= 1`
whenever `farmCaptchaHot()` is true. The counts only reset at calendar day
boundary. Under captcha pressure, a village whose 5h/8h timer expired
mid-day is permanently skipped for the rest of the day, even after the
captcha ladder cools. Fix sketch: scope the captcha-hot filter to a TTL
window (e.g. most recent captcha trip), not "claimed any time today". Use
a separate per-cooldown ring buffer that forgets the strike when the
captcha ladder clears.

### #13 `farms.js:1125` — `farmClaimsToday` day-rollover race

`farmClaimsToday()` reads `state.farmClaimsDay`, compares with today's
key, and if different resets BOTH `state.farmClaimsDay` and
`state.farmClaimsToday` then calls `save()` synchronously twice. The
`claim` lock serializes batches but is acquired at the start of
`autoClaimFarms`, not at the start of each individual `claimFarm`. A
batched claim set posts N callbacks concurrently — two callbacks can both
see a stale `farmClaimsDay`, both reset, both write `{}` to storage. The
two `c[villId]++` increments both happen on a fresh empty object, so the
second `saveSoon(FARM_CLAIMS_TODAY, ...)` overwrites the first. Fix
sketch: hold the rollover check inside the lock, or use a single
`saveSoon` after the day-key read without an intervening reset path.

### #14 `farms.js:1303,1642` — `farmScrapeRevive` race on lock expiry

`scrapeAllFarms` takes `gbLock('farm-scrape', 300000)` and `scrapeAllTowns`
takes `gbLock('town-scrape', 300000)`. If the lock expires (long-running
sweep > 5 min), the next sweep can race the still-in-flight sweep. The
deadline stamp `state.nextFarmScrape` is independent of the lock — both
can fire. A stale callback calling `farmScrapeNoteSweep(ok)` can re-trip
the breaker after the new sweep cleared it. Fix sketch: write the same
token into a "scrape in flight" marker the breaker consults before
flipping.

### #15 `farms.js:447` — `farmLoyaltyResearched` writes state as a hidden side effect

`farmLoyaltyResearched()` is named and called like a read-only probe, but
when a match is found it writes `state.farmLoyaltyTech = hit` AND
`save(...)` synchronously. On a quota-exceeded path this can write state
but lose the save; the 60s `farmLoyaltyCache` then answers `val=true`
against the in-memory state, while a reload sees the un-pinned version.
Fix sketch: split into a read-only probe (returns the hit, doesn't write)
and a `farmLoyaltyLearnTech(hit)` function for the persist path.

### #16 `farms.js:1165` — `farmProfitScore` vs `farmDurationPick` loyalty divergence

`farmDurationPick` (picker) uses `loyalty=1.0`; `farmProfitScore` (ranker)
uses `loyalty = farmLoyaltyResearched(tid) ? 1.0 : 0.5`. A village without
loyalty research is ranked high by the score, then the picker chooses a
duration that the score had already discounted — the actual haul lands in
a warehouse that the picker (correctly) thought could hold the 1.0
estimate. Fix sketch: pick one. Either use `1.0` everywhere (matching
picker, losing one rank signal but consistent) or use `?1:0.5` everywhere
and have the picker also clamp via `gbLootEstimate({ ..., loyalty: actual })`.

### #17 — `bandit.js` `banditTimer` cross-module declaration (collect.js)

`let banditTimer = null;` lives in collect.js. bandit.js's
`scheduleBanditScan()` reads + assigns it. On hot-reload or
`__grepbotDispose`, NOTHING clears `banditTimer`. The MO handler does
check `gbInstanceAlive()` inside, so the path is safe in practice today,
but the timer source-of-truth is split across two files. Fix sketch:
move `banditTimer` into bandit.js (the only writer), and wire
`banditClearLoop + banditTimer` cleanup into `__grepbotDispose` alongside
`gbClearTimers` / `gbAjaxDispose`.

### #18 — `bandit.js:357` `banditLoopTimer` not cleared on disable

**Analysis note:** the agent's original claim that the finally-block
re-arms even when `state.autoBandit === false` is incorrect — the
autoBandit false case returns at line 330, before the try/finally. The
real concern is that `banditClearLoop()` is only called from the
auto-bandit toggle in `ui.js:2457`. If a user disables auto-bandit via
`gbMenu` (`GM_registerMenuCommand`) or another route, the pending
`banditLoopTimer` survives until it fires, then `banditScan` returns
without re-arming, and the loop dies. Net effect: one extra useless tick
at most. Fix sketch (if desired): call `banditClearLoop()` from every
disable path, OR add a `if (!state.autoBandit) return;` guard inside
`banditScheduleNext` itself.

### #19 — `farms.js:940` `farmClaimPending` memo holds 3s past lock release

The 3s memo (`FARM_PENDING_MEMO_MS`) returns the cached `val` (true) for
up to 3s AFTER the lock drops, so post-batch `orchFarmFirst()` returns
true → recruit blocked for up to 3s on top of the actual batch time.
Fix sketch: include `gbLocked('claim')` in the memo key so post-batch
the memo expires on lock-drop.

### #20 — `farms.js:1471` `scrapeAllFarms` stamp before lock — **disputed**

The agent's original claim: "stamp `state.nextFarmScrape = Date.now() + wait`
at the top, BEFORE the lock is acquired". Re-reading the code, the stamp
is at line 1471, which is AFTER the `gbLock('farm-scrape', 300000)`
acquisition at line 1468-1469. The only path that returns without
stamping is the `gbLocked('farm-scrape')` early-return at 1467, which is
the correct semantic (we didn't take the lock, don't bump the deadline).
No fix needed; the finding as written is not reproducible against the
current code. **Recommend: close.**

### #21 — `farms.js:1147` `farmApplyDropPolicies` reads `state.farmProfit` mid-iteration

`farmApplyDropPolicies` filters and sorts via `farmProfitScoreOf`, which
reads `state.farmProfit[vill_id]` synchronously. If `farmProfitRefresh`
mutates `state.farmProfit` mid-iteration, the read sees the latest
value. The `farmProfitCache` TTL is 5min for non-blind — so up to 5min
of stale ranking. Acceptable as designed; document the TTL.

### #22 — `boot.js:103` `farmScheduleClaimWake` timer re-checks (verified safe)

The wake timer re-checks `state.autoFarm` and `hostEnabled()` before
firing, but the check happens at fire time inside the closure. The dead
instance check (`!gbInstanceAlive()`) is the FIRST guard. If the user
toggles `autoFarm` OFF between scheduling and firing, the wake returns
without firing. The `state.farmClaimWakeAt/farmClaimWakeTimer` reset
happens BEFORE the return — so a stale wake leaves the slot empty. **Safe.**

### #23 — `dump.js:78` shallow clone of ledger (latent)

`pickDumpDestination` clones the ledger with `Object.assign({}, v)` to
feed `transportBalanceJobs` on a probe. The clone is shallow; nested
objects are shared. `transportBalanceJobs` only writes top-level number
fields today (`src.wood -= ...`), so the latent risk is contained.
Fix sketch: deep-clone the per-town entries, or document the contract
that `transportBalanceJobs` never writes to nested fields and add an
`Object.freeze` assertion when `opts.probeOnly` is set.

### #24 — `ui.js:2998` `.then` w/o `.catch` on `Notification.requestPermission`

`r.then(() => bindConfig())` — if `bindConfig()` throws (the function is
700+ lines with many DOM branches), the rejection becomes an
unhandled-promise warning. Fix: `.then(() => bindConfig(), () => bindConfig())`
or chain `.catch(() => {})`.

### #25 — `ui.js:1002` clipboard path can leak unhandled rejection

`navigator.clipboard.writeText(text).then(() => done(true), fallback);`
If `fallback` itself throws (textarea select on a detached body,
`document.execCommand` removed), the throw becomes an unhandled
rejection because the `.then` second arg is itself a Promise executor. Fix:
wrap `fallback`'s body in its own try/catch and route failures through
`done(false)`.

### #26 — `collect.js:155` `collectAllBackground` lock-release → scheduleCollectBg race

The inner `finish` decrements `pending`, releases the lock, and re-arms
`scheduleCollectBg`. `scheduleCollectBg` checks `collectBgTimer`, then
schedules a new `collectAllBackground`. The new call checks
`gbLocked('collect-bg')` — returns false (lock held by the first). The
lock-release in `finish` happens BEFORE `scheduleCollectBg`, so a
second `collectAllBackground` can squeeze in via the timeout fan-out
after lock-release but before scheduleCollectBg fires. Fix sketch: defer
`scheduleCollectBg` until AFTER `gbUnlock` to close the window.

### #27 — `core.js:43` `gbDomObserver` and `gbListenerAbort` reinit (verified safe)

After `__grepbotDispose` runs `gbListenerAbort.abort()`, the next
instance reassigns `gbListenerAbort = new AbortController()`. `gbDomObserver`
is set to null on dispose and `ensureDomObserver()` re-creates it. The
long-lived panel-internal click handlers stay attached until the panel
itself is GC'd, which is the same as the panel's lifetime. **Safe as designed.**

### #28 — `farms.js:1188` `farmSleepClaimNow` race with `farmTick` claim path

`farmSleepAutoTick` checks `gbLocked('claim')` and returns if held. Then
calls `farmSleepClaimNow` → `autoClaimFarms('sleep ...', sec, onDone)`,
which itself checks `gbLocked('claim')` and returns. So no
double-claim, but `farmSleepAutoTick` doesn't re-check
`captchaPaused('farm')` between the `gbLocked('claim')` check and the
call. Fix sketch: move the captcha check inside the lock acquisition.
