# 1.1 — Panic mode (instant-pause button)

**Bucket:** v4.0 · **Risk:** Low · **Size:** S
**Module:** `core.js` wrapper; wire `qol.js` Actions menu; render in `ui.js`
**Depends on:** none
**Status:** PLANNED — written 2026-08-10 against `src/` @ v3.8.2

## 1. What exists today

- The orchestrator already has a single cadence in `boot.js:105-108`: its recurring callback calls `orchTick()` directly, or queues that same function through `gbWake('orchTick', ...)` during a wake burst. `boot.js:120-121` also runs `farmTick` on its own cadence, and `boot.js:122-123` schedules its deadline wake, so “halt every loop” cannot be implemented by changing only the orchestrator.
- `orchTick()` refuses to dispatch when `automationPaused({})` is true (`orchestrate.js:147-150`), and its delayed per-item `fire` callback checks the same predicate immediately before invoking `ORCH_HANDLERS[item.key]` (`orchestrate.js:184-199`). This is the existing orchestrator skip mechanic; there is no `orchestrator.skip` property or `skip` field in `src/orchestrate.js` (grep over `src/orchestrate.js` finds no such symbol).
- `automationPaused(reasonOut)` currently represents captcha-global, server cooldown, pause-on-user-activity, and night pause (`core.js:572-596`). It does not currently inspect a panic flag. `bumpUserActivity()` only extends the in-memory `userPausedUntil` deadline when `state.pauseOnActivity` is enabled (`core.js:598-601`); `qolBindActivityPause()` installs the activity listeners (`qol.js:1-10`), and `boot.js:116` invokes that binder once.
- Most autonomous paths already call `automationPaused({})` before scanning or posting: collection (`collect.js:29-30,107-108`), farms (`farms.js:488-493`), build (`build-auto.js:268-272`), culture (`culture.js:94-96`), research (`research.js:416-417`), trade (`trade.js:351-352`), recruit (`recruit.js:266-267`), and other action modules found by the same `src/*.js` grep. `txRun()` independently checks `automationPaused(pauseInfo)` before a transaction and returns `paused:<reason>` (`tx.js:524-532`), so adding panic to that shared predicate covers delayed and direct write paths that reach `txRun`.
- Locks are centralized in `core.js`: names and TTLs are declared in `GB_LOCK_TTL` (`core.js:145-173`), acquisition and ownership are handled by `gbLock()` (`core.js:188-193`), and normal release is token-checked by `gbUnlock()` (`core.js:202-210`). `gbUnlockAll()` deletes the entire current lock registry (`core.js:212-215`); it has no owner-token requirement and is already used during page teardown (`boot.js:120-124).` There is no panic lock name today.
- Wake entries are deduplicated by key and drained serially (`core.js:631-644`). `gbWakeDrain()` stops draining while `automationPaused({})` is true and leaves queued entries in `gbWakeQueue` for later (`core.js:645-655`); this is reusable for panic only if the predicate is extended and recovery explicitly resumes draining. The queue has no public clear function and no `orchestrator.skip` state (`core.js:631-655`).
- `state.dryRun` is loaded from `STORE.DRY_RUN` (`core.js:346`; key declared `header.js:138`), and the transaction layer rejects write execution as `dryrun` before the budget gate (`tx.js:524-532`). DOM fallback is similarly blocked by `gbDomClick()` when `state.dryRun` is true (`core.js:940-950`). The Config checkbox already exposes and persists this field (`ui.js:785`, `ui.js:1311`, `ui.js:1384-1388`).
- The existing footer has status spans and an Actions disclosure menu (`ui.js:872-897`). `updateStatus()` assembles pause reasons from `automationPaused`, captcha breakers, journal skips, circuits, unknown transactions, and dry-run state (`ui.js:1815-1847`), but it has no panic-specific red banner or control.
- The Actions menu already has event delegation that closes the disclosure after a `data-act` button click (`ui.js:898-907`), while individual action listeners are bound later (`ui.js:1012-1116`). This is the correct existing surface to add Panic and recovery controls; no new menu/scheduler is needed.
- Journal skip windows are persisted and pruned by `journal.js`: active skips are enumerated by `jrnActiveSkips()` (`journal.js:231-235`), and `jrnClearSkips()` replaces the skip map, persists immediately, and logs `memory: skip windows cleared` (`journal.js:237-240`). The journal is world-scoped through `STORE.DECISIONS`/`STORE.DECISION_SKIPS` and host-aware save/load (`journal.js:31-52,103-115`); panic therefore must not clear these automatically if “Clear skips” is a separate recovery step.
- Plan 27 §9 explicitly lists pause-on-activity and night pause as already coded (`docs/plans/27-v4-wishlist-2026-08-10.md:239-247`), and lock registry/sweeper plus decision skip windows as already shipped (`docs/plans/27-v4-wishlist-2026-08-10.md:254-255`). Panic is absent from the current tree: no `panic` symbol, storage key, UI control, or footer marker is found under `src/`.

## 2. Gap

The shared pause predicate has no operator-triggered emergency state, and the existing orchestrator/wake/timer paths have no immediate-pause control. The feature must add a transient panic state that is recognized by `automationPaused()` before any new work, forces dry-run, expires existing locks immediately, prevents queued wake work from draining, and exposes a red footer warning plus an Actions-menu recovery flow. Recovery must preserve the existing pause-on-activity/night semantics, wait 30 seconds, then require an explicit Clear skips action before normal automation resumes; it must not silently erase journal skip windows.

## 3. Design

Implement panic as a core-owned transient state, not as a second pause subsystem. `gbPanicActivate()` records an in-memory deadline (`Date.now()+30_000`), sets and persists `state.dryRun = true`, calls `gbUnlockAll()` to expire every current lock, logs `panic: activated`, and refreshes the UI. `automationPaused(reasonOut)` checks panic before the existing captcha/server/activity/night checks and reports `panic` while the deadline is active. That makes `orchTick()` and each delayed orchestrator fire skip through their existing guards (`orchestrate.js:147-150,184-199`), makes `gbWakeDrain()` retain queued work (`core.js:645-655`), and blocks transaction writes through the existing `txRun()` guard (`tx.js:524-532`).

At deadline expiry, panic becomes recoverable but does not resume automation automatically: expose a state/query result such as `panicGraceExpired` (exact name to be chosen locally in the IIFE) and keep the shared predicate paused with reason `panic-grace` until `jrnClearSkips()` has been invoked. The recovery button must perform the explicit Clear skips operation, clear only journal skip windows, release any locks acquired during the grace boundary, log `panic: resumed`, and call `gbWakeDrain()` once. It must not turn `dryRun` off: dry-run was operator state before activation and forcing it ON is safety-preserving; recovery leaves it ON so the operator must deliberately disable it in Config. The footer should distinguish active panic (`⚠ PANIC`, red) from the expired 30-second grace (`PANIC: clear skips to resume`), while `updateStatus()` continues to show existing pause reasons after recovery.

The wishlist names `orchestrator.skip = true`; that symbol does not exist (`orchestrate.js:147-199`). Do not invent a parallel orchestrator flag. If implementation needs an explicit “skip” marker for diagnostics, add a core-owned transient predicate/query and have `orchTick()` continue to use `automationPaused()`; this avoids missing direct loops and avoids duplicate pause semantics.

## 4. Work items

Add module-local IIFE functions (not new top-level declarations that collide under concat) for activation, status, and recovery. Extend `automationPaused(reasonOut)` (`core.js:572-596`) to return `true` with `reasonOut.reason = 'panic'` while active and `reasonOut.reason = 'panic-grace'` after 30 seconds until recovery clears skips. Preserve the current ordering and reasons for captcha, server, activity, and night pause.
2. **`src/core.js` — activation side effects.** On activation set `state.dryRun = true` and `save(STORE.DRY_RUN, true)` using the same storage convention as Config (`ui.js:1384-1388`), call existing `gbUnlockAll()` (`core.js:212-215`), cancel or invalidate any panic-owned recovery timer through `gbClearTimeout()` (`core.js:45-50`), and log exactly `panic: activated` once per activation. Do not clear `state.decisionSkips`; that belongs to the explicit recovery action.
3. **`src/core.js` — wake recovery.** Add a narrowly scoped helper to resume the existing `gbWakeDrain()` (`core.js:645-655`) after successful recovery. Do not add `gbInterval`; the existing boot timers (`boot.js:105-118`) remain the cadence. Queued callbacks must still re-check `automationPaused()` in their feature paths.
4. **`src/core.js` — public wiring.** Include panic helpers in the existing runtime/test exposure block only if the project convention requires UI access through the shared IIFE; otherwise `qol.js` can call the same in-scope functions because it loads after `core.js` (`build.py:31-72`). Add no endpoint, bridge route, payload, or `gbCaptchaPause` key: panic has no post surface.
5. **`src/qol.js` — Actions menu handlers.** Add `data-act="panic"` and `data-act="panic-recover"` buttons to the existing Spanish Actions menu (`ui.js:880-896`; the menu markup is in `ui.js`, not `qol.js`). Add `qolPanicActivate()`/`qolPanicRecover()` as module-local IIFE functions in `qol.js`, or bind directly in the existing UI listener block; activation must call the core helper, and recovery must call the core helper that invokes `jrnClearSkips()` (`journal.js:237-240`). The handler must close the disclosure using existing delegation (`ui.js:898-907`) and render/flash Spanish UI text while machine log messages stay stable per `CLAUDE.md:227-240`.
6. **`src/ui.js` — markup, binding, and footer.** Add the two Actions buttons and bind them beside the existing footer action listeners (`ui.js:1012-1116`). Make Panic visually prominent but not ambiguous: active button label `⚠ PÁNICO`, recovery label `Reanudar (limpiar saltos)`, with the recovery button disabled/hidden until the 30-second deadline has elapsed. Extend `updateStatus()` (`ui.js:1815-1847`) to prepend/replace the status text with a red `⚠ PANIC` indicator while active and a red/amber grace indicator after expiry; update only when the rendered text changes, matching `_statusLast` caching.
7. **`src/ui.js` — refresh controls.** Ensure the existing 5-second `updateStatus` interval (`boot.js:118`) causes the recovery control/footer to transition at 30 seconds without adding a scheduler. If a render helper is needed, call it from `updateStatus()` or the existing panel refresh path rather than adding another interval.
8. **`src/boot.js` — no new cadence; verify teardown.** Do not alter existing periodic cadence except, if required by the chosen core implementation, clear panic state/recovery timers in the existing `releaseLocks` teardown (`boot.js:120-139`). Page teardown already calls `gbUnlockAll()` (`boot.js:124`), so avoid duplicate lock cleanup.
9. **`src/journal.js` — reuse only.** Do not modify journal behavior for activation. Recovery may call the existing `jrnClearSkips()` and must leave the journal decision records intact. If the implementation needs a return value to distinguish “cleared” from “already clear,” add only the smallest return contract and update its callers; otherwise no journal edit is needed.
10. **`src/header.js` — storage decision.** Do not add a `STORE` key unless persistence across reloads is explicitly chosen. This plan deliberately keeps panic transient: a reload already disposes the instance and clears timers/locks (`core.js:114-143`, `boot.js:120-139`), and persisting a panic deadline would need a world-scoped migration and could strand automation after a stale reload. If a developer chooses persistence, add `PANIC_UNTIL` and `PANIC_NEEDS_CLEAR` to `STORE`, add them to `WORLD_SCOPED_BASES` (`header.js:193-216`), and document the migration/config version impact before coding; that is not the recommended delta.

## 5. State & storage

Recommended implementation adds no persisted `state.*` field and no `STORE.*` key: panic is an in-memory safety latch reset by instance teardown/reload, while `state.dryRun` is deliberately persisted through existing `STORE.DRY_RUN` (`core.js:346`, `header.js:138`). No `WORLD_SCOPED_BASES` change or `configVer` bump is required. The 30-second grace is a monotonic timestamp in memory and is pruned naturally when the userscript instance is disposed; no TTL cleanup is needed. Journal skip windows remain persisted and world-scoped via existing `STORE.DECISION_SKIPS` handling (`journal.js:31-52,103-115`) until the operator explicitly chooses Clear skips.

## 6. Config surface

No new Config toggle is recommended. Panic is an always-available low-risk safety control, not an automation preference, and must not be disabled by a preset. The existing `Simulación (registra payloads, no envia nada)` control remains the persisted dry-run control (`ui.js:785,1311,1384-1388`); Panic forces it ON and recovery leaves it ON for deliberate operator review. Existing `pauseOnActivity`, `pauseActivityMs`, `nightPause`, `nightStart`, and `nightEnd` retain their current defaults and semantics (`core.js:305-308`, `ui.js:1307-1311,1367-1378`).

## 7. Post surface & safety

No post surface. Panic uses no game route, no `bridgePost`, no `gameAjaxPost`, no `gbAjaxWatch`, no `TPL_FEATURE_MAP` entry, and no `gbCaptchaPause` feature key. Safety is enforced through the existing shared `automationPaused()` guards (`core.js:572-596`), transaction dry-run gate (`tx.js:524-532`), DOM dry-run gate (`core.js:940-950`), immediate `gbUnlockAll()` (`core.js:212-215`), and wake-drain pause (`core.js:645-655`). No new lock is needed; if any implementation introduces a panic operation lock, it must use `gbLock` plus a `GB_LOCK_TTL` entry rather than an `*InFlight` boolean, but the recommended design uses no lock at all.

## 8. Failure modes

- **Panic activation races a delayed callback.** The callback may already be executing when the click occurs; no JavaScript code can preempt an already-running synchronous section. The invariant is that every later guard reads `automationPaused({})`; `orchTick` and its delayed fire already do so (`orchestrate.js:147-150,184-199`), and `txRun` checks again before writing (`tx.js:524-532`).
- **A getter is unreadable.** Panic itself reads only local timestamps/booleans and must never block on an unread game value. Any future feature guard remains subject to the repository invariant: name the read value; if unreadable, return `blind`, call `gbLogT` once, and let the server decide, rather than treating missing data as safe (`CLAUDE.md:130-132`; existing unreadable-capacity example `orchestrate.js:69-76`).
- **Wake queue remains populated.** `gbWakeDrain()` intentionally leaves entries queued when `automationPaused()` is true (`core.js:645-655`). Recovery must explicitly call the existing drain helper once; do not discard heterogeneous wake entries or invoke them directly.
- **Locks are reacquired during the grace.** All normal action paths should be blocked by the panic predicate, but a stale asynchronous completion may attempt a token release. `gbUnlock()` remains token-checked (`core.js:202-210`); activation/recovery may use `gbUnlockAll()` as the emergency registry reset, never a foreign token.
- **Panic expires while night/activity pause is still active.** Recovery must re-evaluate `automationPaused({})` after clearing skips; if the existing predicate reports `night`, `user`, `server`, or captcha, leave automation paused and do not log a false `panic: resumed`. The status must show the actual remaining reason.
- **Operator clicks recovery early.** Reject with a Spanish flash such as `espera 30 s para reanudar`, keep the grace state, keep dry-run ON, and do not clear journal skips.
- **Operator clicks Panic repeatedly.** Make activation idempotent while active: refresh the deadline only if the product decision explicitly says so; recommended behavior is no-op plus a throttled `panic: already active` log, avoiding an accidental extension that makes recovery unpredictable.
- **Dry-run is already ON before panic.** Preserve the ON value. Recovery must not turn it OFF, because the user may have enabled it deliberately and the feature has no authority to override that choice.
- **Reload during panic.** The transient latch disappears with the disposed instance and existing timers/XHRs are cleaned (`core.js:114-143`); persisted `dryRun` remains ON. This is intentional and must be stated in the UI/log if the implementation chooses to mention reload behavior.

## 9. Validation gate

Low-risk gate from plan 27 §11: run Preflight, then one in-game session with no failure (`docs/plans/27-v4-wishlist-2026-08-10.md:286-296`). Do not run a build or server as part of this planning task; implementation validation remains paste-only/manual per `CLAUDE.md:250-255`.

1. Install the built userscript in a test world with at least one enabled autonomous loop and open the panel. Confirm the Actions menu contains `⚠ PÁNICO` and no post is sent by clicking it.
2. Immediately after activation, confirm the footer is red and contains `⚠ PANIC`; Config's dry-run checkbox is checked; the Log contains exactly `panic: activated`; no new orchestrator action begins after the click.
3. With a wake item pending or a delayed multi-feature tick, confirm the Log does not show a new `ok` action caused by the paused wake drain. Existing queued work must remain pending rather than being dropped.
4. Confirm an already-held lock is absent from the lock/preflight view after activation, and no lock remains indefinitely. The implementation must not introduce a `*InFlight` field.
5. Before 30 seconds, click recovery and confirm it is rejected: no `memory: skip windows cleared`, no `panic: resumed`, and footer remains panic/grace.
6. After 30 seconds, confirm the footer changes to the grace/recovery state and the recovery control becomes available. Click `Reanudar (limpiar saltos)` and verify Log entries `memory: skip windows cleared` then `panic: resumed` (ordering may be documented if asynchronous rendering changes it).
7. Verify the orchestrator and existing loops resume their normal cadence only when no pre-existing pause applies. With `nightPause` active during its configured window, or with activity pause still active, recovery must leave the footer showing the existing `night`/`user` reason and must not claim a false resume.
8. Confirm dry-run remains ON after recovery; manually turning it OFF in Config is the only way to restore live posts. No endpoint guess, bridge payload, or game DOM click should appear in the Panic path.
9. Run Preflight again and inspect the Log/Decisions views for no new hard failures, no unexpected post, and no duplicate scheduler or lock registry entries.

## 10. Out of scope

- No changes to pause-on-activity or night-pause policy; those are already implemented in `core.js:572-601` and exposed by `qol.js:306-353`/`ui.js:1307-1378`.
- No replacement for `orchestrator.skip`: the named property does not exist; shared `automationPaused()` is the real call-chain control (`orchestrate.js:147-199`).
- No automatic clearing of journal decisions or skip windows; recovery explicitly reuses `jrnClearSkips()` (`journal.js:237-240`).
- No automatic disabling/enabling of every individual feature toggle; the shared pause gate is the owner. Existing HIGH-RISK defaults remain governed by current Config/preset rules (`qol.js:272-288`).
- No new `gbInterval`, endpoint, action name, payload field, post template, captcha key, or server integration. Future features own their own bridge-first post plans and depend on this safety latch through `automationPaused()`.
- No persistent panic state in the recommended design. If product requirements later demand panic survive reload, that delta belongs to a separately approved storage/migration change in `header.js` and `core.js`, with world-scoped keys and explicit stale-state recovery.
