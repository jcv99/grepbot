# 7.4 — Mass intel auto-post (Discord digest per spy)

**Bucket:** v4.4 · **Risk:** Med · **Size:** M
**Module:** extend `alerts.js` (no new module) — add `intelDigest` event +
post surface; spool logic in a new IIFE-wrapped section at the bottom of
`alerts.js` (`build.py:54` slot, between `research.js` and `merchant.js`).
**Depends on:** none (2.1 spy report parser deep is the producer; if 2.1 is
absent, the feature still buffers raw `state.findings` ingestions — see §3).
**Status:** PLANNED — written 2026-08-10 against `src/` @ v3.8.2

## 1. What exists today

- **`alerts.js` is 89 lines, all outbound.** Reads: `state.webhookUrl`
  (`alerts.js:29`), `state.webhookEvents[event]` (`alerts.js:39`,
  `ev[event] === false`), `state.dryRun` (`alerts.js:31-34`). Writes
  the key-throttle maps `alertPending` and `alertLastSent` (definitions
  exist but are **not in the 89 lines of `alerts.js`** — grep confirms
  no `let alertPending` / `const alertLastSent` line is reached by the
  Read, so they must be declared in the closure of a sibling module —
  but they are referenced at `alerts.js:43-44`, `alerts.js:66`,
  `alerts.js:75-77`, `alerts.js:80`. The 5-minute per-key dedup
  (`alertLastSent[key] + 5*60*1000 > now`, `alerts.js:44`) only blocks
  the **same key** for 5 minutes; it does **not** enforce a per-day
  limit. This is the gap.
- **The Discord payload cap is at the `slice(0, 1800)` calls**
  (`alerts.js:46,60`). Discord's actual limit is 4096 chars per
  embed description and 6000 per embed (10 embeds/msg, body cap 2000
  chars). The existing 1800-char trim is comfortably below Discord's
  per-embed cap but is silent on oversize — payload gets `slice(0,1800)`
  mid-token and the JSON is corrupted. For digest payloads this matters
  more than for one-liner `attack` events.
- **The Telegram payload cap is `text.slice(0, 3900)`** (`alerts.js:54`)
  and is fine for digests. Telegram path uses `chat_id` resolved by
  `alertTelegramChatId` (`alerts.js:9-18`), `@connect` permits
  `api.telegram.org` (`header.js:19`).
- **Webhook event subscription is configurable but the keys are
  hard-coded.** `state.webhookEvents` default is
  `{ captcha:true, attack:true, warehouse:false, culture:false }`
  (`core.js:313`). The UI renders checkboxes for those four
  (`ui.js:1356-1359`) and `saveWebhookEvents` whitelists those names
  on save (`ui.js:1478-1484`). Adding a fifth event requires UI work,
  not state work. (The assignment cites the read at `ui.js:1168` and
  the save at `ui.js:1246-1253`; the actual locations are `ui.js:1354-1360`
  for the read and `ui.js:1477-1490` for the save — the older lines
  are the generic `setChk` / `bindToggle` plumbing that runs before
  the webhook block. Plan 26 §B2 caught this same drift when the
  `intelSetAllianceNote` line was off by 40 lines.)
- **One outbound webhook, no fan-out.** `alertWebhook` issues exactly
  one `gbXhr({ scope:'external', method:'POST', url, … })`
  (`alerts.js:67-83`) per deduped key. There is no multi-channel
  bridge — Discord + Telegram share one URL slot (`state.webhookUrl`).
- **No inbound side.** `@connect` `header.js:16-19` is
  `grepolis.com + discord.com + discordapp.com + api.telegram.org`;
  no other host is permitted (CLAUDE.md sandbox rule).
- **Findings buffer is `state.findings[]`**, capped at 500 entries
  (`spy.js:250-253`, with a 100-entry tighter cap in
  `core.js:1167-1172` under storage pressure). Each finding has
  `player` / `town` / `alliance` / `attacker` / `defender` /
  `vill_id` / `units` / `wall` / `note` / `allianceNote` / `ts`
  — verified by grepping `f.player`, `f.town.id`, `f.alliance`,
  `f.units` and reading `intelDossiers` (`intel.js:37-70`) and
  `renderIntel` (`intel.js:75-114`). `intel.js:1-10`
  `intelPlayerKey(p)` is the canonical "player identifier" used by
  every existing dossier/intel read; the digest MUST reuse it so the
  throttle keyspace agrees with what the dossier shows.
- **Redaction convention is already in place.** `qolRedactConfigDump`
  (`qol.js:225-247`) is the export-side convention for dumps;
  outbound intel pattern-scans (`intel.js:235-238`) use the inline
  `String(h.name).slice(0, 2) + '***'` form when
  `state.exportRedact !== false`. The digest MUST apply the same
  per-name inline redact so a Discord channel does not become a
  player-name leak.

## 2. Gap

The current `alertWebhook(event, payload)` path will fire an alert
when something dramatic happens (attack arrival, watchlist match,
captcha) but nothing aggregates intel *outward* on a regular
cadence — so an alliance-mate playing on Discord never sees your
spies unless they read the GrepBot panel. Plan 27 §7 closes this by
"Discord digest per spy", throttled to once per player per day,
HIGH-RISK toggle default OFF, since the threat model is **data
exfiltration** (a leaked webhook URL, a leaked player name, a
Discord channel flooded with 500 digests overnight), not game
state mutation.

## 3. Design

A pure **outbound** feature. Reuses `alertWebhook`
(`alerts.js:28-88`) and the existing webhook URL/secret
(`state.webhookUrl`); adds nothing new to `gbXhr`'s transport, no
new `@connect` entry (Discord + Telegram are already
`header.js:16-19`), no new post scheduler.

A new IIFE-local section at the bottom of `alerts.js`
(`build.py:54`, between `research.js` and `merchant.js` in the
concat order — `alertWebhook` is already defined by the time the
new code runs, since the entire file is one IIFE body) adds five
module-local symbols:

```js
const intelDigestState = { queue: [], lastFlushAt: 0 };
const intelDigestPostedToday = {}; // playerKey -> utcDay
function intelDigestKeyFor(f) { return intelPlayerKey(f.player || f.attacker || f.defender) || 'unknown'; }
function intelDigestRedactName(name) { return state.exportRedact === false ? String(name) : String(name).slice(0, 2) + '***'; }
function intelDigestBuildPayload(playerKey, items) { /* see §7 */ }
function intelDigestTick() { /* see §7 */ }
```

The spool is `intelDigestState.queue[]`. Each item is
`{ ts, playerKey, summary }`. Per-spy enqueue happens inside a
small hook appended to `ingestReport` (which lives in
`spy.js:236-257`); the digest runs on:

1. **Burst trigger** — `intelDigestState.queue.length >= 12` (cap per
   digest, see Discord size discipline §7), OR
2. **Time trigger** — `Date.now() - intelDigestState.lastFlushAt >= 30 * 60 * 1000`,
   whichever comes first. The 30-min cadence piggybacks on
   `reportCatchUpRun`'s wake entry (`spy.js:120`,
   `gbWake('reportCatchUp', …, { priority: 80 })`): extend the
   existing done step (after `release()` at `spy.js:174`) to enqueue
   `gbWake('intelDigest', intelDigestTick, { priority: 90 })` so
   this feature has no scheduler of its own. No `gbInterval`.

Per-player-per-day throttle: before calling
`alertWebhook('intel-digest', payload)`, check
`intelDigestPostedToday[playerKey] === utcDay` (where
`utcDay = Math.floor(Date.now() / 86400000)`); if already true,
skip and drop the queued items with a one-line `gbLogT` on
`intel-digest-skip-<playerKey>` (TTL 24h). Mark only after the
underlying `alertWebhook` reaches the `gbXhr` POST (skipping
`pending`/`lastSent` 5-min dedup at `alerts.js:43-44` is *not* a
valid skip reason — a fresh key passes the per-key dedup every
day, so the `utcDay` stamp is the only thing that throttles across
days). The stamp is **not** flipped when `state.dryRun` short-circuits
the webhook at `alerts.js:31-34` (same-day replay against a non-empty
queue is the user's "log the dry run payload" path — see §9).

Storage of the stamp: `wkey(STORE.INTEL_DIGEST_POSTED)` (a new key
defined in `header.js:24-187`, added to `WORLD_SCOPED_BASES`
`header.js:193-215` because it bears player keys). Loaded on
startup as `Object.create(null)`, written only on a state flip.

## 5. State & storage

- `state.intelDigestCfg.autoPost` — boolean, **default OFF**
  (HIGH-RISK rule + the silent-leak risk is real).
- `state.intelDigestCfg.batchMaxFindings` — number, default **12**
  (the Discord embed description cap; the existing
  `slice(0, 1800)` at `alerts.js:60` will trim further if a 12-line
  description overflows).
- `state.intelDigestCfg.batchMaxMinutes` — number, default **30**.
- `state.intelDigestPosted` — `{ [playerKey]: utcDayNumber }`,
  id-bearing ⇒ `WORLD_SCOPED_BASES` entry needed for
  `STORE.INTEL_DIGEST_POSTED`. Loaded via
  `load(STORE.INTEL_DIGEST_POSTED, {})`; written via
  `save(wkey(STORE.INTEL_DIGEST_POSTED), state.intelDigestPosted)`
  inside `intelDigestTick` only when the per-day stamp flips.
- `state.intelDigestState` — in-memory only (not persisted).
  The queue survives no reload, by design — a fresh-day reload
  starts with an empty spool and the next report catches up.
- Prune TTL: 7 days, uniform. After 7d of no flips the map is
  bounded by the number of distinct intel'd players the user has
  seen (commonly <200); no periodic prune is required, but a
  defensive one-shot prune inside `intelDigestTick` drops keys
  whose `utcDay` is `< currentUtcDay - 7` to keep the map tidy.
- `configVer` bump: yes (work item 1).

## 7. Post surface & safety

- **Outbound only.** No `gbDomClick`, no `bridgePost`, no
  `gameAjaxPost`. The whole feature is a thin wrapper around
  `alertWebhook` — `gbXhr({ scope:'external', method:'POST', url,
  headers, data })` is the only network path, and that is already
  gated by `state.dryRun` at `alerts.js:31-34`.
- **`alertWebhook` event name**: `'intel-digest'`. The key under
  `state.webhookEvents` matches (`alerts.js:40`).
- **`alertWebhookKey`** (`alerts.js:19-27`) computes
  `event:cs:id` — `id` is the finding's `report_id` (or
  `report_id` fallback). The 5-min per-key dedup means two
  *different* spy findings on the same player will both pass the
  dedup; the per-day stamp at `state.intelDigestPosted[playerKey]`
  is the only thing that throttles across days.
- **Discord payload shape**:
  ```js
  { content: null,
    embeds: [{
      title: `GrepBot: intel-digest <playerRedacted>`,
      description: lines.join('\n').slice(0, 3500),
      footer: { text: location.host },
      timestamp: new Date().toISOString(),
    }] }
  ```
  The 3500-char pre-trim keeps the existing
  `slice(0, 1800)` (`alerts.js:60`) safely inside Discord's
  4096-char embed description cap. Telegram path uses
  `text.slice(0, 3900)` (`alerts.js:54`) — a long digest will
  trim further there.
- **Discord size discipline**:
  - On overflow, `intelDigestBuildPayload` truncates to the
    first 12 items and appends `(+N more today)`. There is **no
    fan-out** to multiple embeds — the existing single-embed
    shape is reused (no Discord `split` to a second message).
  - If a single finding summary exceeds 200 chars, the summary
    is trimmed to 197 chars + `…`. Player and town names get
    `intelDigestRedactName` regardless.
- **Redaction** (the main failure mode for this feature):
  - `intelDigestRedactName` is called on every player name in
    `alertWebhook`'s payload at composition time (`qol.js:230`).
    When `state.exportRedact === false` the raw name is sent
    (this is the user's explicit "I know what I'm doing"
    override; `qol.js:226-229` warns once).
  - The webhook URL **must never** appear in any log line. The
    `gbLogT` keys used (`intel-digest-*`) carry no URL fragment.
  - `state.captchaBreakers['intel-digest']` (see work item in
    §4) is the only breaker code that *could* land a Discord
    response into the log, and `captchaTrip` already wraps the
    body in `JSON.stringify(data).slice(0, 120)`
    (`spy.js:332`) — that trim is what stops a webhook URL leak
    via captcha detail.
- **`gbCaptchaPause` feature key**: `intelDigest`. Added to the
  captcha breaker registry the same way `'report'` is
  (`spy.js:126`, `spy.js:224`). When `captchaTrip('intelDigest',
  detail)` fires (status >= 400 from the Discord endpoint),
  `captchaPaused('intelDigest')` returns true and
  `intelDigestTick` short-circuits silently for the rest of the
  backoff (`state.captchaLadder`, `core.js:353,367`, default
  `[5, 15, 60]` minutes). Persisted via the existing
  `saveCaptcha` (`core.js:1336`) keyed by `STORE.CAPTCHA`
  (`header.js:200`).
- **Lock**: `gbLock('intel-digest', 60000)` during the flush
  (`GB_LOCK_TTL['intel-digest'] = 60000`, new entry in
  `core.js:145-173`). No new `*InFlight` boolean.
- **Dry-run**: `state.dryRun` already short-circuits
  `alertWebhook` (`alerts.js:31-34`) — the payload is logged as
  `DRY-RUN webhook intel-digest: <pretty JSON>` and nothing is
  sent. The per-day stamp is **not** flipped during dry run
  (work item 3's `state.intelDigestPosted` writer is gated on
  the actual POST reaching `gbXhr`, not on `alertWebhook`'s
  return value).
- **`@connect`**: no change. The `header.js:16-19` allowlist of
  `discord.com + discordapp.com + api.telegram.org` covers
  every destination this feature can post to. If a future
  iteration wants a custom Discord channel-message fetch (as
  the catalog row's literal phrasing tempts), that would need a
  wider allowlist and a Bearer token — out of scope per §10
  and consistent with sibling plan 7.1's
  "Discord channel-message fetch" out-of-scope line.

## 8. Failure modes

- **Webhook URL is empty**: `alertWebhook` returns at
  `alerts.js:30`. The per-day stamp **does** flip on success —
  but for an empty URL, "success" never arrives and we keep
  retrying every 30 min. We log once per session:
  `gbLogT('intel-digest-no-url', 86400000, …)` to keep
  stamp-table noise out of the log.
- **Webhook host is not in `@connect`**: `gbXhr` returns
  `'noajax'` (`core.js:1180-1188`); we never reach
  `alertWebhook` because `intelDigestTick` skips when
  `captchaPaused('intelDigest')`. The breaker opens
  immediately on the first attempt and stays open until
  `state.captchaLadder` (default `[5,15,60]`) decays.
- **`@connect` rejects a URL** because the user pasted a
  Discord channel-message URL (not a webhook endpoint):
  `alertWebhookUrlOk` (`alerts.js:4-8`) rejects the regex; log
  `webhook-url` once per 120s (`alerts.js:36`).
- **Per-day limit fires inside the flush**: `gbLogT`
  (`intel-digest-skip-<playerKey>`, TTL 24h) is the *only*
  log; the spool stays empty afterwards (we drop the
  player's queued items, not the whole queue). A subsequent
  flush for a different player can still fire.
- **Storage prune** during quota alarm
  (`core.js:1087-1140`, `state.findings` cap 100 under pressure):
  `state.findings` drops oldest; the digest spool is in-memory
  and unaffected. If `state.findings` was already pruned before
  the spool saw the entry, we just never get the digest line.
- **Reload in the middle of a flush**: `gbLock` (`core.js:189`)
  holds a foreign-token-aware handle; the foreign instance
  keeps the lock across reload (verified by
  `pagehide`/`beforeunload` both calling `gbUnlockAll()` per
  CLAUDE.md v1.4.0 lock registry).
- **Precondition invariant**:
  - The hook in `ingestReport` checks `state.intelDigestCfg.autoPost`
    *and* `state.enabledHosts[location.host] === true`; if either
    is false, no enqueue (read-from-state, no invented truth).
  - `intelDigestKeyFor` calls `intelPlayerKey` (`intel.js:1-10`),
    which returns `null` for `unknown`; the `|| 'unknown'`
    fallback groups unknown-actor findings under a single
    playerKey — they share the per-day stamp, by design (no
    player-name → no per-player cadence), and the daily
    cadence collapses 12 unknown-keyed items into one message.
  - `utcDay = Math.floor(Date.now() / 86400000)` is local-time
    agnostic (UTC days); the user-visible cadence lands
    whenever their clock rolls past UTC midnight. This is
    deliberate (no tz data in the state; plan 27 §13 says
    world-scoping is per-world not per-tz).

## 9. Validation gate

Per plan 27 §11 Med risk: dry-run + one hand-triggered firing + one
full wake-drain.

- **`state.dryRun` ON, ingest one fake spy finding** (`Log` →
  manual `forceIngestReport({...})` if shipped, or hand-visit
  inbox to make `reportCatchUpRun` actually queue a real one):
  Log shows `DRY-RUN webhook intel-digest: {…}` with the
  redacted payload; per-day stamp is **not** flipped
  (`state.intelDigestPosted === {}`).
- **Toggle `state.intelDigestCfg.autoPost = true`**,
  `state.webhookEvents['intel-digest'] = true`,
  `state.dryRun = false`: ingest 3 findings on player A and 2
  on player B in sequence. After 30 min (or after firing
  `intelDigestTick` from the DevTools console), Log shows
  `webhook: intel-digest` twice — once for player A, once for
  player B. Decisions subview shows two `ok` rows with
  `feature:'alert'`, `action:'webhook'`.
- **Ingest one more finding on player A** within the same UTC
  day: Log shows `intel-digest-skip-<playerA>` once and
  Decisions shows no new entry.
- **Ingest one finding on player C** (new player) right after:
  Log shows another `webhook: intel-digest` line. The
  per-player stamp map now has three keys.
- **Set `state.intelDigestPosted.<playerA> =
  Math.floor(Date.now()/86400000)` (today) and reload**:
  storage round-trips via `wkey()`; the stamp survives.
  On the next ingest of a player-A finding,
  `intelDigestTick` skips again with `intel-digest-skip-<playerA>`.
- **Wait past UTC midnight (or set system clock forward)**:
  `utcDay` increments; `intelDigestTick` fires the next time
  the spool reaches 12 or 30 min elapses.
- **Captcha test**: set
  `state.captchaBreakers['intelDigest'].until = Date.now() + 60000`:
  `intelDigestTick` short-circuits silently via
  `captchaPaused('intelDigest')`. Captcha breaker key works
  because the webhook response path (alerts.js:74) is what
  `captchaTrip` would extend; since the spec is
  "external-only" we mirror the captcha-on-DND pattern by
  detecting the `gbXhr` 429/503 path during `intelDigestTick`'s
  caller (`spy.js:120`'s wake) and calling `captchaTrip`
  directly when the `gbXhr` returns a 429 from the webhook
  — implementation detail belongs in work item 4.
- **Redaction test** with `state.exportRedact === true` and a
  payload with `playerName = 'loremipsum123'`: payload sent to
  Discord shows `lo***`. Flip
  `state.exportRedact = false`; same payload shows the raw
  name (and `qol.js:227`'s one-shot warning fires).

## 10. Out of scope

- **Inbound telegram/discord** (chat → GrepBot). Plan 27 §0 drops
  this; CLAUDE.md "no phone-home" and the lack of a webhook
  receiver in the userscript sandbox make it impossible without
  a server.
- **Fan-out to per-alliance channels.** Each `state.webhookUrl`
  is one destination; multi-channel support would require a
  destination map in `state.intelDigestCfg`. Defer until
  specifically requested (consistent with sibling plan 7.1's
  "cross-alliance auth" out-of-scope).
- **Alliance-digest cadence** (one digest per alliance, not per
  player). Plan 7.6 ("Alliance member activity dashboard")
  owns the read-side; cross-reference, do not duplicate.
- **Cross-alliance auth** on the digest payload. The author of
  the digest is the player who ingested the finding; we redact
  author identity (no payload has an `author` field). Anyone
  reading the Discord channel can correlate `worldKey = X,
  intelPostedBy = null`; that's the threat model.
- **Discord channel-message fetch** (catalog row's "alliance
  intake via webhook" phrasing). Same reasoning as sibling
  plan 7.1's §10. Out.
- **Player notes and `allianceNotes` inclusion in the digest
  payload.** `intelDossiers` already attaches these
  (`intel.js:65-68`), but they are user-private; a digest sent
  to a Discord channel must never carry them. `intelDigestBuildPayload`
  composes the payload from `state.findings` only; the notes
  live in `intel.js`'s render path, never in this payload.
- **A `@connect` host addition for a paste service** that
  might carry the digest to a wider audience. Defer per
  CLAUDE.md sandbox rule; not requested.
