# 5.8 — Booty camp optimizer (bandit ranker)

**Bucket:** v4.2 · **Risk:** Low · **Size:** S
**Module:** extend `src/bandit.js` (unit-picker heuristic) + add a read-only
  rollup row in `src/stats.js` (cycle deltas)
**Depends on:** none
**Status:** PLANNED — written 2026-08-10 against `src/` @ v3.8.2 (header `@version` is `3.9.0`; off by one, harmless)

> The Grepolis booty camp is per-player (one `PlayerAttackSpot` model per
> account, `src/bandit.js:186`), so the "ranker" this plan ships is a **unit
> picker**, not a camp picker. It changes *which* units are payload, not
> *which* camp is attacked. The catalog's "ranker" intent is satisfied:
> the bandit `attack` payload now carries a ranked, capped subset of the
> current town's offense units, and the Stats tab shows the per-cycle mix
> so the player can see why.

---

## 1. What exists today

- `banditAttackUnits(uw, rawUnits)` (`src/bandit.js:24-37`) is the only
  caller-side unit filter. It walks `rawUnits`, deletes `militia` and
  anything whose `GameData.units[id].is_naval` is truthy, then drops
  anything `banditIsOffenseUnit` rejects. The result is the **full**
  remaining map — every eligible offense unit count is sent.
- `banditIsOffenseUnit(uw, id)` (`src/bandit.js:10-23`) is the eligibility
  test. It accepts `godsent`/`hoplite` exceptions, prefers the
  `unit_function` attribute (`off`/`def`/`both`/`none`), and falls back to
  the `BANDIT_OFFENSE_IDS` regex at `src/bandit.js:9` (`slinger|hoplite|
  rider|chariot|minotaur|manticore|cyclops?|zyklop|harpy|erinys|fury|
  centaur|griffin|satyr|giant|godsent`).
- `banditViaGame()` (`src/bandit.js:182-298`) builds the payload from the
  current town only: `t.units()` at `src/bandit.js:273`. There is no
  town-picker branch — picking a different town would require a separate
  bridge call to switch `Game.townId`, which `bandit.js` does not have.
- The "ranker" hook is `banditAttackUnits`. It already runs per cycle and
  is the only place the payload mix is decided.
- `state.banditLog` (`src/bandit.js:347-351`) is a 50-entry ring of
  `{ts, ev}` strings. It is the only bandit-related state. There is no
  cycle-by-cycle history of the payload mix.
- `logBandit('attack')` (`src/bandit.js:291`) is the only place the
  payload is journaled — and it stores the *string* `attack`, not the
  units. So after the fact, no record shows which units were sent.
- Defaults: `state.autoBandit` defaults to `false` (`src/core.js:247`),
  HIGH-RISK per CLAUDE.md. Stats surface for the bandit is one
  Preflight row at `src/stats.js:234-238` (`bandit camp`) and the
  per-feature rollup line in `renderStats` (`src/stats.js:294-309`,
  derived from `jrnStats`).
- Plan 26 §C2 added the scope-aware budget line at `src/stats.js:339-344`.
  The per-feature rollup already lists `bandit` rows under the existing
  `feature ok err tout pend cap skip rate` table (`:294-309`); the
  ranker HUD goes inside the same per-feature block, not next to it.

## 2. Gap

Today the bot sends every offense unit from the current town. Three
failure modes follow:

1. **Donate the defenses.** A balanced town that happens to be the
   current town during the bandit cycle loses its offense reserve with
   no warning. The dodge floor (`state.dodgeFloor`, `src/bandit.js:117`
   and `src/core.js:324`) is checked by the **favor** scanner but is
   **not** checked by `banditAttackUnits`.
2. **No cycle history.** The payload disappears once `bridgePost` is
   called. The player (and the validation gate) cannot tell whether the
   last 3 attacks all sent the same 80 hoplites or whether the unit
   mix shifted.
3. **No opt-out for one cap.** The catalog description is "ranker" but
   the only knob today is the binary enabled toggle. There is no way
   to say "send at most 50 of each unit type" without rewriting the
   picker.

The ranker closes those three.

## 3. Design

Two changes, both inside the existing schedule:

1. **Unit-picker with rank + cap.** New module-local IIFE
   `banditRankUnits(uw, rawUnits, cfg)` returning the post-map. The
   shape is unchanged (`{ unitName: count }`); the contents are
   different. Default `cfg` is the empty object — the picker falls back
   to today's "send all" behaviour, so the ranker is **off** by default
   (no change in v3.8.2 behavior).
2. **Stats readout.** New module-local `banditAttackHistory` (plain
   array, **not** persisted; pruned module-local to 20 entries). Each
   successful `post('attack', ...)` callback at `src/bandit.js:275`
   pushes `{ts, units}` onto the array, and `renderStats` prints the
   last 3 cycles.

Both changes are gated by `state.autoBandit === true`; with the master
toggle off (default), the code path is identical to today.

### Ranker contract

`banditRankUnits(uw, rawUnits, cfg)`:

- Apply the existing legality filter the same way `banditAttackUnits`
  does today (delete `militia`, drop naval, drop `banditIsOffenseUnit`
  rejects). After this: `map = { unit: count }` containing only offense
  units.
- If `cfg.smartCap` is not set or `cfg.smartCap <= 0`, return `map`
  unchanged. This is the v3.8.2 baseline.
- Else for each entry, compute `rank = (units[unit].cost?.iron ?? 0) +
  (units[unit].cost?.wood ?? 0) + (units[unit].cost?.stone ?? 0)` —
  i.e. the unit's total resource build cost, a proxy for "productive
  per unit" under the catalog's "ranker" rubric. The rank window is
  sorted once descending.
- For each unit in rank order, cap to `Math.min(count, cfg.smartCap)`.
  One floor: `cap = Math.max(1, Math.min(+cfg.smartCap, count))` —
  never zero out a unit the player bought (the ranker is a *cap*, not
  a *filter*).
- Optionally subtract `state.dodgeFloor` for each unit type that
  matches `dodgeFloorUnits` (default empty array — opt-in). Plan 27
  says Low risk for this cluster; the dodge floor carve-out is
  intentionally NOT active by default because it interacts with the
  `dodge.js` reserve pipeline and changing that would be Med risk.
- Return the capped map.

The picker's `cfg` is read from `state.banditCfg` (new, see §5).

### Stats readout

`renderStats` at `src/stats.js:280-355` already iterates the per-feature
rollup table. We add a sub-table after the `bandit` feature row in the
loop at `src/stats.js:297-309`:

```
  bandit        12   1   0   0   0   4   92%
    ult envio  hoplite:30  rider:12  manticore:2
    anterior  hoplite:35  rider:10  manticore:4
    -3h        hoplite:24  rider:14  manticore:1
```

The Stats row is read-only and reuses the existing `bandit` feature key
in `state.banditLog` decisions. The dedupe pattern follows
`jrnStats(...).byFeature` which already keys `bandit` (`src/stats.js:295`).

### Post volume

**Unchanged.** The send cadence is `banditScheduleNext` (`src/bandit.js:328-338`)
gated by `banditIdleUntil`, `state.autoBandit`, and `gbLocked('bandit-reward')`.
The ranker only changes the units inside the payload. The dry-run gate
already covers `bridgePost('bandit', ...)` at `src/bandit.js:190-193` per
CLAUDE.md "v1.4.0 dry run: `state.dryRun` short-circuits inside
`bridgePost` / `gameAjaxPost` only." No new dry-run gate is needed.

## 6. Config surface

Two new fields with text labels (Spanish, per CLAUDE.md):

- **Cap por unidad (0 = desactivado).** Number input, default `0`,
  stored in `state.banditCfg.smartCap`. When `0`, the ranker is a
  pass-through and v3.8.2 behavior is preserved.
- **Reservar para defensa.** Number input, default `0`, stored in
  `state.banditCfg.dodgeFloor`. When `0`, the dodge floor carve-out is
  skipped. (Distinct from `state.dodgeFloor` for favors: that one is
  read by `favor.js:117` and is per-favor-unit; this one is per-bandit
  unit.)

Both fields are **OFF** by default. LOW risk — the ranker only takes
effect when the master `Banda automática` toggle is ON, and that toggle
is already HIGH-RISK OFF default per CLAUDE.md.

## 8. Failure modes

- **`GameData.units[id].cost` is undefined** — the ranker falls back to
  cost `0` for that unit, which puts it at the bottom of the rank
  order but never excludes it. The cap is applied on count, not on
  rank, so the unit still ships.
- **`rawUnits` is `null` or `undefined`** — the existing
  `banditAttackUnits` early-out at `src/bandit.js:25` is
  `Object.assign({}, rawUnits || {})`. The ranker inherits that.
- **`cfg.smartCap` is non-numeric** — coerced via `+cfg.smartCap` and
  `Math.max(1, Math.min(...))`. Non-numeric input becomes `NaN`,
  `Math.min(NaN, …)` is `NaN`, `Math.max(1, NaN)` is `NaN`, which
  passes through to `Math.min(count, NaN)` = `NaN`. The fix is
  `const cap = Math.max(1, Math.min(+cfg.smartCap || count, count))` —
  fall back to "no cap" if `+cfg.smartCap` is `NaN` or `0`.
- **`banditAttackHistory` overflow** — capped at 20 module-local
  entries, push-then-shift is O(n) on 20 elements, well below
  noticeable.
- **Sub-camp not present (`m.getLevel() == null`)** — the existing
  early-return at `src/bandit.js:195` runs before the ranker; no
  change.

## 9. Validation gate

Manual, per plan 27 §11 Low class (Preflight + one in-game session, no
failure).

- Build (`python3 build.py`), open the Config tab. The new bandit
  block shows two new inputs under the existing `Banda automática`
  toggle. Leave both at `0` (default).
- Open the Stats tab, click the `Banda ahora` … wait, there is no
  manual-fire button. Trigger the scheduler by waiting for the next
  bandit cycle (every ~30s when idle, per `bandit.js:251` and the
  cooldown branch). The per-feature table's `bandit` row now has 2-3
  indented sub-rows showing the last attack mix.
- Set `Cap por unidad` to `5` in Config, wait for the next attack, and
  confirm the next sub-row shows at most 5 of each unit.
- Set DRY-RUN on (`state.dryRun` in Config), trigger a cycle, and
  confirm the Log shows `DRY-RUN bandit: {...}` with the new
  capped payload (the existing dry-run gate covers this; nothing to
  add).
- Preflight (`Comprobar sistema`) — the existing `bandit camp` row at
  `src/stats.js:234-238` still passes; no new row is needed.

## 10. Out of scope

- **Town picker.** Picking the *best* town to attack from would require
  a separate `bridgePost` to switch `Game.townId`, which is not in
  `bandit.js` and would change post volume. The catalog says "Low/S"
  for this row; an inter-town ranker is a future Med-risk item.
- **Reward-rank by power id.** The reward pick at `src/bandit.js:208-209`
  uses `pid.includes('instant')` to pick `useReward` vs `stashReward`
  based on the catalog key. The full set of reward power ids is *not*
  enumerated in `src/`; extending the picker to rank by reward type is
  a separate work item.
- **Per-island group optimization.** `banditWrongIsland` at
  `src/bandit.js:160-181` is a hard skip; the ranker does not change
  it.
- **Auto-bandit v3 (different cadence).** Not this plan. The catalog
  entry is the ranker, not a redesigned cadence.
