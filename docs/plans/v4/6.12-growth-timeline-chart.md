## 1. What exists today

- The only per-town snapshot storage is `state.townResources[id]` (`src/core.js:230`,
  `src/towns.js:163-167, 210-213`). It carries exactly **one** entry per town
  (`{ts, wood, stone, iron, pop, cap, ok, action}`) and is **overwritten**
  on every scrape. There is no append, no ring, no history. Confirmed by
  ripgrep over `src/`: zero hits for `townGrowth`, `growthHist`,
  `popHist`, `appendSample`, `sampleLog`.
- `state.findings` is the closest existing time-indexed series
  (`src/core.js:228`, pruned by `storagePruneForQuota` at `core.js:1188-1190`).
  It is **intel reports**, capped at 100 entries FIFO-dropped on quota, not
  town growth. Using it as a growth source would conflate two signals and
  still lose older entries on quota.
- The closest "history" stores are `state.attackHistory`, `state.attackRecent`,
  `state.questHistory`, `state.banditLog` (all `src/core.js:280-298`). None is
  per-town population / resources.
- `townResState(townId)` (`src/bridge.js:235`) returns the **live** snapshot
  via `ITowns.getTown(id).resources()` with a 3s in-memory cache. It is the
  read path the sampler must call — already proven safe by
  `src/preflight.js` probe `cost reads` at `stats.js:188-209`.
- `state.towns` (`src/core.js:229`, set at `towns.js:71, 122, 197`) is the
  canonical town list (`{id, name, x, y, island}`). The chart needs one
  selector entry per `state.towns[i].id`.
- `renderStats` (`src/stats.js:280-355`) is the existing Stats renderer. It
  writes to `panel.querySelector('.stats-body')` via `textContent`
  (`stats.js:354`). A new `.growth-panel` `<pre>` sibling can be added in
  the same section without touching the existing `stats-body`.
- The Stats tab HTML lives in `src/ui.js:847-853`: window buttons
  `[data-stats="1h|24h|7d"]` already exist; the section is hidden until
  the tab is opened (`ui.js:373, 394` re-renders on tab switch).
- `worldKey` / `wkey()` is applied by `load()` / `save()` for any key in
  `WORLD_SCOPED_BASES` (`src/header.js:193-215`, `src/core.js:1100-1116`).
  A new `STORE.TOWN_GROWTH_HIST` key with id-bearing payload must be added
  to that set.
- `storagePruneForQuota` (`src/core.js:1129-1207`) is the last-resort
  pruner for `QuotaExceeded`. Plan 20 (CODED, `core.js:1187`) ships it;
  the new key's append path must respect its cap (see §5).

## 2. Gap

The catalogue asks for "city growth timeline chart (mermaid line)". The
player-visible question — *"is my main town still growing, and at what
rate?"* — has no answer in the panel today, because no time-series exists.
The honest deliverable is: **(a) add a per-town daily sample of population,
wood, stone, iron totals, warehouse capacity, and building count** (a
single append per town per local day, capped), and **(b) render an ASCII
sparkline of those samples inside the existing Stats tab** so the player
can read growth at a glance.

## 3. Design

Read-only HUD. No post surface, no captcha breaker, no lock, no
scheduler entry, no `gbInterval`. The sampler runs inline off the
existing `scrapeAllTowns` cadence (every 6–7 min) — see §3.2 below for
why no new scheduler is added.

### 3.1 Renderer

Add a new block to `renderStats` (`src/stats.js:280-355`) after the
deadlock notice (`stats.js:326-330`) and before the orchestrator rollup
(`stats.js:331`). The block renders only when `state.towns.length > 0`
AND `state.townGrowthHist` has at least one entry for the selected town.

Per render, for the **selected town id** (default `state.towns[0].id`):

```
crecimiento — Aldea <name> (id <id>)   ult. <N> muestras (max 7d)
  pob    <mini-sparkline>   <first> → <last>   Δ <delta> / <spanDays>d
  wood   <mini-sparkline>   <first> → <last>   Δ <delta> / <spanDays>d
  stone  <mini-sparkline>   <first> → <last>   Δ <delta> / <spanDays>d
  iron   <mini-sparkline>   <first> → <last>   Δ <delta> / <spanDays>d
  cap    <mini-sparkline>   <first> → <last>   Δ <delta> / <spanDays>d
```

Sparkline glyph set: `▁▂▃▄▅▆▇█` (Unicode U+2581..U+2588). Render is the
existing `textContent` discipline: each line is a string, joined with
`\n`, assigned to `box.textContent`. **No** `innerHTML`. This is the
same discipline as `intel.js:112` and `stats.js:354`. The audit I15
record (zero `innerHTML` in quests.js, plan 26) sets the rule.

Sparkline math: bucket the samples into ≤ 24 columns (one column per
hour across the visible 7d window, or one per day if the span is < 24h),
take the mean per bucket, normalize to `[0..7]` over the per-row min/max,
emit one glyph per bucket. Two or fewer samples render `—`. Samples
where the value is `null` (unreadable that day) render `·` and are
excluded from min/max.

### 3.2 Sampler hook

Wire into `scrapeAllTowns` (`src/towns.js:181-228`), not into a new
`gbInterval`. The function already runs every 6–7 min per town and
holds the `town-scrape` lock (`towns.js:183-184`). The sampler is one
call at the end of the `finish()` path (after the per-town writes at
`towns.js:163-167, 210-213`):

```js
function townGrowthSample() {
  if (!Array.isArray(state.towns) || !state.towns.length) return;
  const today = new Date().toISOString().slice(0, 10); // YYYY-MM-DD, local day
  const hist = state.townGrowthHist || (state.townGrowthHist = {});
  for (const t of state.towns) {
    const r = state.townResources[t.id];
    if (!r || r.ok !== true) continue;
    const entry = { ts: Date.now(), day: today,
      pop: r.pop ?? null, wood: r.wood ?? null, stone: r.stone ?? null,
      iron: r.iron ?? null, cap: r.cap ?? null };
    const arr = hist[t.id] || (hist[t.id] = []);
    const last = arr[arr.length - 1];
    if (last && last.day === today) continue; // one per local day
    arr.push(entry);
    while (arr.length > TOWN_GROWTH_MAX) arr.shift();
  }
  save(STORE.TOWN_GROWTH_HIST, state.townGrowthHist);
}
```

Cap constant `TOWN_GROWTH_MAX = 7` (one entry per local day, 7-day
window). The store key goes in `WORLD_SCOPED_BASES` (id-bearing, see §5).

The sampler is called from `scrapeAllTowns`'s `finish(fromGame, fromHttp)`
(`towns.js:188-193`) **after** `pruneMapsToIds(state.townResources, ids)`
(`towns.js:191`). That way stale towns do not produce new samples and a
town that has been transferred out does not leave a phantom row.

### 3.3 Selector

The Intel / Overview tabs already have town selectors (see
`ui.js:587`, the Attack planner's `data-atk="pick"`). The Stats tab does
not. The plan adds one `[data-growth="town"]` `<select>` inside the
Stats section header (`ui.js:847-853`), populated from `state.towns` on
each `renderStats`. Default selection is the first town; switching the
selector re-renders only the growth block. The selector is built with
`document.createElement('option')` and `appendChild` — no `innerHTML`.

### 3.4 Window parity

The existing `[data-stats="1h|24h|7d"]` buttons (`ui.js:847-849`) drive
`statsWindow` (`ui.js:939` → `military.js:257-258`). The growth chart
ignores `statsWindow` and uses its own 7d window, because the underlying
sample is daily. This is honest: a 1h window over a daily sample is
always one column. A short note in the block header makes the window
explicit (`max 7d`).

## 5. State & storage

- New `state.townGrowthHist` (`{}`, id-keyed), `STORE.TOWN_GROWTH_HIST`
  in `WORLD_SCOPED_BASES` (id-bearing payload ⇒ yes, per CLAUDE.md
  "World-scope id-bearing storage").
- Per-town array `{ts, day, pop, wood, stone, iron, cap}`, capped at
  `TOWN_GROWTH_MAX = 7` entries; ring shift in `townGrowthSample`
  (`while (arr.length > TOWN_GROWTH_MAX) arr.shift()`).
- **Size estimate.** Worst case: 12 towns × 7 entries × ~80 bytes
  (serialized JSON with `day` + 6 numbers) ≈ **6.7 KB** world-scoped.
  Cross-ref plan 20 (CODED, `core.js:1187` storage quota alarm): a new
  ~7 KB key is < 0.1% of the typical `GM_setValue` quota headroom and
  is the right size for plan 20's alarm to ignore without false
  positives. The 7d cap matches plan 27 §13 ("Storage prune TTL: 7d
  uniform unless the slice needs longer").
- `configVer` bump to 11 (see §4.1) so existing users pick up the new
  field without a state-shaped migration.
- No `gbLock`, no `GB_LOCK_TTL` entry. The sampler is inline in an
  already-locked path (`towns.js:184` `gbLock('town-scrape', 300000)`).

## 8. Failure modes

- **`townResState(id)` unreadable** — `townGrowthSample` skips towns
  where `state.townResources[id].ok !== true` (§3.2). Sparkline cells
  with `null` samples render `·` and are excluded from min/max; the row
  still renders the other numeric columns. No silent dead row.
- **Selector on a town with no samples** — `growthBlock` returns `[]`
  and the chart emits one line `crecimiento — sin muestras para <name>`
  instead of a partial sparkline. The precondition invariant: every
  block guard reads the value it gates on.
- **Quota pressure** — `townGrowthHist` is small (~7 KB worst case, §5)
  but `storagePruneForQuota` (`core.js:1129-1207`) trims it implicitly
  via `SAVE` retry on `QuotaExceeded`. The cap at 7 entries per town
  already matches the journal/decision pattern (`journal.js` 7-day TTL
  per plan 27 §13).
- **Sampler race** — the sampler is called from inside the held
  `town-scrape` lock (`towns.js:184`), so a second `scrapeAllTowns`
  cannot double-append. If `hostEnabled()` is false the sampler is
  a no-op.
- **Day rollover at the seam** — `new Date().toISOString().slice(0, 10)`
  is UTC. The bot's local-day rollover differs from UTC at most by a
  few hours; if the user cares, they can flip to a local-day string.
  The off-by-one is documented; it does not lose data (the `day !==
  today` guard would just delay the next append by up to 24h on the
  seam, which is invisible at the daily cadence).
- **Time-zone change** — same as above; the `day` field is a string,
  the chart sorts by `ts` for display.

## 10. Out of scope

- **Per-building growth.** Building levels would need a separate
  sampler keyed by `ITowns.town(id).buildings()`; that is a future plan
  (cross-ref plan 27 §6.11 "real-time production overlay" — its data
  layer is the same `ITowns` model, but the read paths differ).
- **Mermaid / SVG / canvas.** Rejected by §3.1. If a future plan needs
  pixel rendering, it ships its own bundled renderer in `src/` and
  pays the size cost itself; the build's ASCII-escape gate
  (`ascii_escape_artifact`, CLAUDE.md) makes it tractable.
- **Alliance / cross-city view.** Cross-ref plan 6.13
  (`6.13-alliance-intel-heatmap.md`); the data sources do not overlap.
- **Trade-route / transport growth.** Plan 27 §1.3 owns transport
  automation. Once 1.3 ships, an extra sparkline row for transport
  events can be added without a separate plan.
- **Real-time per-tick update.** The current cadence is the daily
  append; a per-tick append would cost a write per town per 6–7 min,
  i.e. ~100 KB/day for the same chart. Not justified at the current
  sample size.
- **Auto-export of growth as webhook / Discord attachment.** Out of
  plan 27 §0; webhooks are for events, not bulk data dumps.
