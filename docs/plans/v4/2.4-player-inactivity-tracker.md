# 2.4 — Player inactivity tracker

**Bucket:** v4.0 · **Risk:** Low · **Size:** S
**Module:** extend `src/intel.js` (additive) + small markup addition in `src/ui.js` intel section
**Depends on:** none
**Status:** PLANNED — written 2026-08-10 against `src/` @ v3.8.2

## 1. What exists today

- `intelPlayerKey` (`src/intel.js:1-10`) is the canonical string key for a player. Object-with-id ⇒ `'id:<n>'`; bare string ⇒ trimmed; object with name only ⇒ `String(name)`. Used by `intelDossiers` (line 34-71) and `intelPatternScan` (line 206-245).
- `intelDossiers` (intel.js:34-71) already aggregates findings by player and surfaces `last` (max ts) per player, plus `reports`, `units[]`, `towns[]`, `walls[]`, and the player note from `state.playerNotes[name]` (line 65). It does **not** score inactivity — a player last seen 30 days ago and a player last seen 30 minutes ago are both rendered with the same flat `reports: N` line.
- `intelPatternScan` (intel.js:206-245) groups findings by attacker in a 24h window, fires a webhook at `hits >= 3`, and writes `state.attackPatternNote`. It is the **opposite** signal (active recently) and uses a different window (24h, hard-coded at line 208).
- `watchMatch` (intel.js:145-184) + `intelWatchlistScan` (intel.js:186-205) tracks a saved list of players/towns and fires `alertWebhook('attack', …)` when a new finding matches. Bookkeeping: `state.watchHits[m.rule] = Date.now()` (line 199), persisted via `STORE.WATCH_HITS` (header.js:170, in `WORLD_SCOPED_BASES` line 211). This is a "still active" signal, not an inactivity one.
- 2.2 Enemy city timeline introduces `const INTEL_HISTORY_TTL_MS = 7 * 86400000;` in `intel.js`. 2.4 reuses it.
- Plan 27 §9 already-shipped list does **not** mention a player inactivity tracker. The closest is the `attackPatternNote` (intel.js:109-110) which is the active-player signal. 2.4 is net-new and the inverse view.

## 2. Gap

`intelDossiers` answers "who do we know?" and `intelPatternScan` answers "who is hitting us right now?". Neither answers "who has gone quiet?" — the player we used to see every day, who stopped two weeks ago, who is worth a re-spy because they may have gone on vacation or been replaced. A scout who farms 20 nearby players needs that signal: prioritise re-spy on the inactive, leave the active ones alone. 2.4 closes the gap with a per-player last-seen view, grouped by both attacker and defender axes so the user can see "incoming is quiet" *and* "outgoing scouts are quiet" independently.

## 3. Design

- New function `intelPlayerInactivity(opts)` in `intel.js`. Reads `state.findings` only — no new storage.
- For each finding, contribute to **two** player-keyed maps:
  - `attackerMap[key]` — bumped when `intelPlayerKey(f.attacker)` is not null. Captures "this player attacked".
  - `defenderMap[key]` — bumped when `intelPlayerKey(f.defender)` is not null. Captures "this player was attacked".
  - Skip the `me`-self signal: `intelActorIsMe(actor, me)` (`src/intel.js:28-33`) — if either side resolves to `intelMyIdentity()` (intel.js:17-27), do not count it as "other-player activity". The same self-discard rule `intelDossiers` uses at intel.js:40-44.
- Filter both maps to entries with `lastTs >= now - INTEL_HISTORY_TTL_MS` (7d), so a player who vanished two months ago does not pollute the list. 2.2/2.3 set this constant; this is the third consumer.
- Score per player per axis:
  - **inactive** if `now - lastTs >= PLAYER_INACTIVE_MS` (default 5 × 86400000 = 5 days). The 5d default sits between the 3d ghost-town window (2.3) and the 7d retention ceiling — players who go on vacation usually take 5-14 days off; 5d is the actionable threshold for "re-spy them".
  - **disappeared** if `now - lastTs >= PLAYER_DISAPPEARED_MS` (default 14 × 86400000 = 14 days). Hard cutoff above which re-spying is wasteful — the player is most likely gone for good.
- Output: two tables.
  - `Attackers` (offense axis): rows = sorted by `(inactive-desc, lastTs-asc)`. Capped at 30.
  - `Defenders` (defense axis): same shape, capped at 30.
  - Each row carries `player` (from `intelPlayerLabel`, intel.js:11-16), `lastTs`, `ageMs`, `n` (report count), `inactive` flag, `disappeared` flag, and the `intelPlayerLabel`-derived `note` if `state.playerNotes[noteKey]` is set (matches `intelDossiers` line 65).
- Render: a single sibling `<div class="intel-inactive">` containing two sub-tables (`intel-inactive-atk` and `intel-inactive-def`), each built via `tableShell` + `makeSortable` with the sticky-sort `state.tabFilters` key already wired (`src/ui.js:1-13`).
- No scheduler. No `gbInterval`. No `GB_LOCK_TTL`. No `STORE` / `WORLD_SCOPED_BASES` entry. No `configVer` bump. No `alertWebhook` (passive view; the user is the consumer).

## 5. State & storage

- No new `state.*` fields.
- No new `STORE.*` keys.
- No `WORLD_SCOPED_BASES` entry.
- No `configVer` bump.
- Retention: reuses `INTEL_HISTORY_TTL_MS` (7d) from plan 2.2. **One** retention policy for the read trio. The `PLAYER_INACTIVE_MS` (5d) and `PLAYER_DISAPPEARED_MS` (14d) are *score* thresholds, not retention TTLs — a player who vanished 20 days ago is still represented in the source data (up to 7d) but excluded from the inactive output by the retention filter, which is the correct behaviour.

## 6. Config surface

None. The two score thresholds are hard-coded defaults in `intel.js`. If a user wants a stricter "inactive" definition, they edit the constant. Same rationale as 2.3: knobs that nobody has asked for do not earn Config rows. Comment each constant with the heuristic ("5d = typical Grepolis vacation cap floor; 14d = likely abandoned").

## 7. Post surface & safety

**No post surface.** Read-only. Skips the rest of §7 per `docs/plans/v4/README.md` and plan 27 §13. Never invents a game endpoint. Reads `state.findings` only.

## 8. Failure modes

- **Self-pollution:** if `intelMyIdentity()` is unreadable (the `try { … } catch { return { id: null, name: null } }` at `src/intel.js:18-26`), `intelActorIsMe` returns `false` for everything and the user's own attacks/incidents show up in the tables. Acceptable: the rule degrades to "show everything" when the identity is blind, not "silently drop". The precondition invariant in CLAUDE.md says exactly that — never silently dead.
- **Empty `state.findings`:** empty-state rows, no log.
- **All findings filtered by 7d:** `gbLogT('intel-inactive-empty', 300000, …)` fires once; empty-state rows render.
- **Player name collision across worlds:** not a concern here because the function reads `state.findings` which is **already** world-scoped via `STORE.FINDINGS` in `WORLD_SCOPED_BASES` (`src/header.js:194`). No additional scoping needed.
- **`intelPlayerKey` returns null** (no id, no name — `nameOf` saw a player block with neither): finding is dropped from the map. The active-player `intelPatternScan` has the same drop at intel.js:214 (`if (!key || key === 'unknown') return;`). Consistent.
- **No `note` in `state.playerNotes`:** render the empty cell, do not fabricate a placeholder. Same as `intelDossiers` (line 65: `if (state.playerNotes && state.playerNotes[noteKey]) d.note = …`).

## 9. Validation gate

Per plan 27 §11 (Low risk) — Preflight + one in-game session, no failure.

1. Build, install, open a world with a mix: a player who attacked you yesterday, a player who attacked you 6 days ago, a player you attacked 20 days ago, the `me` player (self).
2. Open the Intel tab. The new "Atacantes" sub-table shows the 6-day-ago attacker as `inactivo`, the yesterday attacker absent (`< 5d`). "Defensores" sub-table shows the 20-day-ago defender absent (filtered by 7d retention). Self is absent from both.
3. Click a row in "Atacantes" — no nav, no post. The note column reads the existing `state.playerNotes[name]` if set; empty otherwise.
4. Sort by `Edad` desc; close+reopen the panel — sort survives via `state.tabFilters.sort:intel-inactive-atk` and `sort:intel-inactive-def`.
5. Force self-pollution: from console, `state.findings[0].attacker.name = '<my name>'`; reopen. The row now shows up — confirms the self-discard rule works (and degrades cleanly when identity is blind).
6. Preflight row "findings schema" still passes; journal still silent (no entries).

- **Auto-fire a re-spy on inactive players.** Plan 4.1 (auto-spy scheduler) with per-target cadence. Out of scope — 2.4 is read-mostly.
- **Webhooks / alerts on inactivity transitions.** No event surface. If a user wants it, add `alertWebhook('inactive', payload)` behind a `state.intelInactiveAlert === true` toggle. Defer.
- **Alliance-level inactivity aggregation.** Owned by 7.5 (NAP / war tracking) and 7.6 (alliance member activity). Different grouping axis, different view.
- **Activity heatmap by hour-of-day.** The data shape is there (`f.ts`), but the visualisation is owned by 6.12 (city growth timeline chart) and 6.13 (alliance intel heatmap). Reusing a chart widget belongs in those plans.
- **Player notes setter.** Already coded at `intelSetNote` (`src/intel.js:115-120`) and wired at `ui.js:997-1001`. 2.4 only reads `state.playerNotes`; never writes.
