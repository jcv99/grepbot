## 1. What exists today
- `research.js` already has a persisted ordered target map: `researchEnsureTargets` seeds `RESEARCH_CS_FAST`, writes `STORE.RESEARCH_TARGETS`, and returns it (`src/research.js:1-7`). The actual list is not a verified research graph; the symbol is referenced by the seed loop but its definition is outside this file and must be inspected before implementation (`src/research.js:4`, `src/research.js:537-543`).
- The current planner sorts target keys by configured `order`, skips researched/queued entries, checks dependencies, affordability, and queue capacity, then selects one job (`src/research.js:450-489`). Thus a first eligible target is already selected, but no shortest-path or “missing prerequisite closure” calculation is present in that call chain (`src/research.js:450-489`).
- Dependency truth currently comes from each live `GameData.researches[tech]` definition (`src/research.js:326-338`), including `research_dependencies`; unknown definitions are rejected as `tech unknown` (`src/research.js:329-332`). This is the only verified source of dependency data in `src/`.
- Research ids are not hardcoded by this plan. The existing code accepts only keys present in the game model (`src/research.js:135-139`) and loads the named CS-fast list (`src/research.js:537-543`); no complete id inventory is present in the requested source tree evidence.
- Research automation is already opt-in via `state.autoResearch`, defaulting false (`src/core.js:303`), and the orchestrator already enables and schedules the research handler (`src/orchestrate.js:1-17`, `src/orchestrate.js:147-195`).
- The catalogue’s module hint is directionally correct but incomplete: `research.js` owns the selection loop (`src/research.js:450-489`), while a new graph module must load before it. `build.py` is the source-of-truth concatenation order (`build.py:31-72`), and currently places `research.js` after `rural.js` (`build.py:51-54`).

## 2. Gap
Add a read-only path analysis over ids that are actually present in `GameData.researches`, without adding a post path or changing the existing opt-in automation. The graph must be obtained from the live game model at runtime, not guessed game data: `research-graph.js` supplies pure graph/closure/ranking helpers, while `research.js` feeds it verified definitions and current town completion/queue state. A hardcoded static table is explicitly not acceptable unless a future maintainer supplies a separately verified capture and documents its provenance; the game model is authoritative today.

## 3. Design
`researchGraphBuild()` iterates `Object.keys(gameUw().GameData.researches)` and reads only each definition’s existing `research_dependencies` (the same shape already consumed by `researchDepsVerdict`, `src/research.js:334-338`). Missing/non-array dependency values become an unreadable/partial graph, never invented edges. For a selected target, `researchPathFor(townId, target)` reads `researchTownTechs(townId)` (`src/research.js:56-107`), removes researched and known queued ids, recursively computes missing prerequisites, and topologically orders the result; cycles, unknown dependency ids, and unreadable state produce a `blind`/incomplete result and no recommendation. `researchScan` may use the result only to rank already configured targets; it must not silently enqueue prerequisites or alter the existing write behavior (`src/research.js:468-487`). UI presents a read-only path/status in the existing research/config surface owned by `ui.js`; no game action is emitted.

## 8. Failure modes
Every graph read must name the value read. Missing `GameData.researches`, malformed dependency arrays, missing target definitions, and cycles return `blind`/incomplete and render “camino no legible”; they must not mean “no prerequisites.” A missing `researchTownTechs`/orders read follows the existing conservative shape (`src/research.js:378-388`): do not claim a free slot. Log once with `gbLogT` for repeated blindness. Never fabricate an id from a label, numeric index, CSS class, or wishlist text.
