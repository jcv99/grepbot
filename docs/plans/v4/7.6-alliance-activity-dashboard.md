# 7.6 — Alliance member activity dashboard

**Bucket:** v4.4 · **Risk:** Low · **Size:** M
**Module:** extend `src/intel.js`; no new module, no new state, no `build.py` MODULES change
**Depends on:** plan 6.13 (`[data-intel="view"]` selector chrome — same dependency rule as plans 7.2 §3.4 and 7.3 §3.4)
**Status:** PLANNED — written 2026-08-10 against `src/` @ v3.8.2

> Read-mostly per plan 27 §7. The dashboard is a per-client view of
> player activity the bot has *observed* — spies seen, attacks
> received, watchlist hits, pattern hits — grouped by player name
> with optional alliance filter. The bot cannot enumerate the
> alliance roster (see §1.5), so "member" here means "any player who
> has shown up in a report the bot ingested", filtered by the
> alliance string the user types.

---

## 1. What exists today

- `state.findings[]` (`src/core.js:221`, capped at 500 by
  `spy.js:250-253` then pruned to 100 by `core.js:1167-1172`) holds
  every parsed report. Per-finding shape (`parse-inline.js:39-100`):
  `{id, ts, type, attacker:{id,name,alliance,...}, defender:{...},
  town:{id,name,x,y}, units, resources, alliance, ...}` — exactly
  what the dashboard reads.
- `intelDossiers()` (`src/intel.js:34-71`) already aggregates findings
  **per-player** (`intelPlayerKey` at `intel.js:1-10`) with
  `reports, units, towns, walls, last, note, allianceNote`. The
  dashboard extends this with two extra counts: `attacksOnMe`
  (defender is me) and `attacksByMe` (attacker is me).
- `intelMyIdentity()` (`intel.js:17-27`) reads the player's id/name
  via `MM.getModelByNameAndPlayerId('Player')` with `Game.player_id`
  as fallback (`intel.js:23`). Used by `intelActorIsMe`
  (`intel.js:28-33`), the existing "who is me" gate.
- `intelPatternScan()` (`intel.js:206-245`) already groups findings
  by player (24h window) and emits `attackPatternNote`. The dashboard
  reuses the same grouping with a wider window (default 7d) and an
  alliance filter.
- `state.watchHits` (`core.js:373`, key `STORE.WATCH_HITS` at
  `header.js:170`) records watchlist-rule hits by rule string.
  Already world-scoped.
- `state.allianceNotes` (`core.js:341`, `STORE.ALLIANCE_NOTES`,
  `WORLD_SCOPED_BASES` at `header.js:206`) is the per-alliance
  free-text map. The dashboard reads it to attach the same
  `[aliado: ...]` suffix the existing dossier line carries at
  `intel.js:96`.
- The session-local `intelView` flag (owned by plan 6.13 §3.3, with
  contributions from plans 7.2 §3.4 and 7.3 §3.4) lives in
  `renderIntel` (`intel.js:75-114`).

### 1.5 Game model: what is NOT reachable

Same honesty boundary as plan 7.3 §1.5: the bot does not have access
to the alliance roster. The dashboard's "member" set is the union of
player strings seen in `state.findings[i].attacker.name` or
`defender.name`, filtered by the alliance string the user types into
a small filter input. A real "list every member of alliance X with
their last login" needs the alliance forum or another player's
client — both out of plan 27 §0.

## 2. Gap

`renderIntel` (`intel.js:75-114`) emits one line per dossier
(`intel.js:93-97`), but the per-player row carries only
`reports, note, allianceNote` — no notion of *role* (attacker vs
defender vs both), no window filter, no alliance filter, no
watchlist/pattern overlay. When a player wants to answer "who in
alliance X has been most active against me in the last 7d?" they
have to mentally aggregate the raw findings tab. Plan 7.6 gives them
that view without inventing data.

## 3. Design

One aggregator, one renderer, one filter input, no post surface.

### 3.1 Aggregator

Add `intelMemberActivity(opts)` to `src/intel.js`, placed next to
`intelDossiers` (`intel.js:34-71`). It returns
`Array<{player, alliance, key, reports, attacksOnMe, attacksByMe,
spiedByMe, towns, firstTs, lastTs, allianceNote}>` sorted by
`lastTs` descending:

```js
function intelMemberActivity(opts) {
  opts = opts || {};
  const filter = String(opts.alliance || '').trim().toLowerCase();
  const cut = Date.now() - ((Number.isFinite(opts.windowHours) ? opts.windowHours : 24 * 7) * 3600000);
  const me = intelMyIdentity();
  const byPlayer = {};
  const inFilter = (s) => s && String(s).toLowerCase() === filter;
  (state.findings || []).forEach(f => {
    if (!f || !(f.ts >= cut)) return;
    const atk = f.attacker || null, def = f.defender || null;
    const atkA = (atk && (atk.alliance || atk.alliance_name)) || f.alliance || null;
    const defA = (def && (def.alliance || def.alliance_name)) || null;
    if (filter && !inFilter(atkA) && !inFilter(defA)) return;
    const add = (p, alliance) => {
      if (!p) return;
      const key = intelPlayerKey(p) || ('name:' + p);
      let r = byPlayer[key];
      if (!r) { r = { player: intelPlayerLabel(p, key), key, alliance: alliance || null, reports: 0, attacksOnMe: 0, attacksByMe: 0, spiedByMe: 0, towns: new Set(), firstTs: f.ts, lastTs: f.ts, allianceNote: null }; byPlayer[key] = r; }
      r.reports++;
      if (intelActorIsMe(def, me)) r.attacksOnMe++;
      else if (intelActorIsMe(atk, me)) r.attacksByMe++;
      else r.spiedByMe++;
      if (f.town && (f.town.id != null || f.town.name)) r.towns.add(String(f.town.id || f.town.name));
      if (f.ts < r.firstTs) r.firstTs = f.ts;
      if (f.ts > r.lastTs) r.lastTs = f.ts;
      if (state.allianceNotes && r.alliance && state.allianceNotes[r.alliance]) r.allianceNote = state.allianceNotes[r.alliance];
    };
    if (atk) add(atk, atkA);
    if (def && !intelActorIsMe(def, me) && !intelActorIsMe(atk, me)) add(def, defA);
  });
  return Object.values(byPlayer).map(r => ({ ...r, towns: r.towns.size })).sort((a, b) => b.lastTs - a.lastTs);
}
```

Notes: the aggregator never *invents* a roster — a player appears
only when at least one finding names them. The `key` is
`intelPlayerKey(...)` (same discipline as `intelDossiers` at
`intel.js:45`). Role counts come straight from `intelActorIsMe`
(`intel.js:28-33`), no second implementation. Alliance attribution
falls back to `f.alliance` (`parse-inline.js:89`) when the player
object does not carry one.

### 3.2 Renderer

Append a new branch to `renderIntel` (`intel.js:75-114`) gated by
`intelView === 'activity'` (same module-local `let` plans 6.13, 7.2,
7.3 share):

```js
if (intelView === 'activity') {
  const alliance = (document.querySelector('#gb-intel-alliance-filter') || {}).value || '';
  const rows = intelMemberActivity({ alliance, windowHours: 24 * 7 });
  let html = '=== Actividad por miembro (7d, vista local) ===\n';
  if (!rows.length) html += '(sin actividad en la ventana)\n';
  else for (const r of rows) {
    const last = new Date(r.lastTs).toLocaleString();
    html += `${r.player} (${r.alliance || '?'})${r.allianceNote ? ` [aliado: ${r.allianceNote}]` : ''}: ${r.reports} informe(s), me-ataca ${r.attacksOnMe}, yo-ataco ${r.attacksByMe}, espiado-por-mi ${r.spiedByMe}, ${r.towns} ciudad(es), ultima ${last}\n`;
  }
  box.textContent = html;
  try { intelPatternScan(); } catch (_) {}
  return;
}
```

`box.textContent` is the only safe assignment (audit-I15; player
names and alliance strings are attacker-controlled).

### 3.3 Filter input

Append a single text input to the Intel section chrome
(`ui.js:692-708`) below the alliance-note editor row:

```js
const f = document.createElement('input');
f.id = 'gb-intel-alliance-filter';
f.placeholder = 'alianza (filtro)';
f.style.cssText = 'width:160px;background:#111;color:#cfc;border:1px solid #333;padding:2px 4px;font-size:11px';
f.addEventListener('input', () => renderIntel());
```

The renderer reads the input's current value on every render
(§3.2); no state field is added. The input persists for the session
because the Intel section is rebuilt only on tab switch.

## 7. Post surface & safety

**No post surface.** No `bridgePost`, no `gameAjaxPost`, no
`gbDomClick`, no `gbAjaxWatch`, no `gbLock`, no `GB_LOCK_TTL` entry,
no `gbCaptchaPause` key.

The renderer uses `box.textContent = html`. The filter input uses
`createElement('input')` + `placeholder` attribute (text content only).
Audit-I15 XSS discipline: zero `innerHTML` for attacker-controlled
strings. Player names (`f.attacker.name`, `f.defender.name`) and
alliance strings (`f.alliance`, `f.attacker.alliance`) come from
`parse-inline.js:39-100` and are attacker-controlled; `textContent`
is the only safe assignment.

## 8. Failure modes

- **`state.findings` empty**: `byPlayer` is `{}`, output is `[]`,
  renderer emits `(sin actividad en la ventana)`. Fresh-install safe.
- **`intelMyIdentity()` returns `{id:null, name:null}`** (`intel.js:26`):
  `intelActorIsMe(...)` returns false in both directions (`intel.js:28-33`);
  every finding falls into the `spiedByMe` bucket.
- **Window cut before earliest `ts`**: that finding is filtered out;
  widen `windowHours` to recover.
- **Alliance case mismatch**: comparison is
  `String(...).toLowerCase() === filter` on both sides — matches.
- **`f.alliance` null on a finding**: `r.alliance` stays `null`,
  label renders `?`. Player still appears if the filter is empty.
- **`state.watchHits` empty**: the dashboard does not currently
  surface a `[W]` marker for watched players; follow-up work.
- **`intelView` undefined** (selector not landed per §3.4): branch
  never fires; falls through to existing dump blocks. No crash.

## 9. Validation gate

Manual, per plan 27 §11 Low class (Preflight + one in-game session,
no failure).

- Build (`python3 build.py`), install, open the Intel tab. The
  `[data-intel="view"]` selector shows `Resumen` (default),
  `Actividad 7.6`, and the other views from plans 6.13 / 7.2 / 7.3
  if they have landed.
- With `state.findings` containing at least one enemy attack on an
  own town (a real bot has this within minutes of opening the
  inbox): the dashboard emits one row per attacker with
  `me-ataca ≥ 1`, `yo-ataco = 0`, `aliado: <note>` if
  `state.allianceNotes` has the alliance.
- Type `WoodFaction` into the alliance filter; rows collapse to only
  attackers whose `f.attacker.alliance === 'WoodFaction'`
  (case-insensitive). Clear the filter; rows return.
- Switch `intelView` between `Resumen` and `Actividad 7.6`; the
  filter input value persists in DOM. Reload → filter returns empty
  (session-local, not persisted).
- Preflight → new `alliance activity` row; pass when `members > 0`;
  warn when 0.
- `state.dryRun = true` → dashboard still renders; no new posts in
  Log tab; journal `mem:<n>` does not increment.

  (no server, no `@connect` host beyond `discord.com` /
  `api.telegram.org` at `header.js:16-19`).
- **Auto-publishing the dashboard.** Out of plan 27 §7.1 / §7.4
  territory (the `alerts.js` Discord-webhook path).
- **Filter persistence.** Session-local DOM only; a follow-up plan
  can add `state.intelFilter` with a `WORLD_SCOPED_BASES` entry.
- **`watched` / `inPattern` marker display.** Aggregator computes
  both; renderer does not yet emit `[W]` / `[P]` suffixes — follow-up.
- **Cross-alliance auth.** Plan 7.3's resource-pool tracker is the
  companion piece that aggregates by alliance; this plan aggregates
  by player. Together they cover the read-mostly alliance views
  promised in plan 27 §7. Anything beyond read-mostly is out per
  plan 27 §0.
- **Plan 6.13 dependency.** If plan 6.13 has not landed, the
  `[data-intel="view"]` selector does not exist and §3.4 has nothing
