# 4.5 — Wall auto-repair

**Bucket:** v4.5 · **Risk:** Med · **Size:** M
**Module:** extend `src/build-auto.js` + `src/build-targets.js` (NOT a new
`wall.js` — see §3 why the plan-27 hint is wrong).
**Depends on:** none.
**Status:** PLANNED — written 2026-08-10 against `src/` @ v3.8.2

## 1. What exists today

Verified against `src/goals.js`, `src/build-auto.js`, `src/build-targets.js`,
`src/core.js`, `src/parse-inline.js`.

- **Wall is already a first-class building in the auto-queue.**
  `AB_BUILDINGS` (`goals.js:127`) is `[..., 'wall', ...]` and
  `AB_CS_FAST` (`goals.js:139`) sets the default target to `wall: 10`.
  `abCurrentLevels` (`build-auto.js:14-33`) reads the live level from
  `t.getBuildings()` and accounts for **negative deltas** when a queued
  order carries `tear_down: true`: `if (a.tear_down) levels[type] =
  Math.max(0, levels[type] - 1)` (`build-auto.js:28`). The same model
  attribute `tear_down` is what carries the rebuild action in the
  game's queue representation.
- **The post surface is `BuildingOrder` / `buildUp`** with payload
  `{building_id: building}` (`build-auto.js:246-247`). The same
  payload builds a fresh level and rebuilds a damaged wall back to
  its previous level; the bridge does not have a separate `repair`
  action. The `tear_down` attribute only appears in queue-row
  introspection (`build-auto.js:28, 54`), not in the post payload.
- **No wall-damage model is currently read.** `parse-inline.js:88`
  parses `wall` out of incoming spy reports
  (`r.wall ?? r.wall_level ?? r.defender_wall ?? (r.defender &&
  (r.defender.wall ?? r.defender.wall_level))`) for intel/dossier
  views only; nothing in `build-auto.js`, `core.js`, or `intel.js`
  reads the wall-damage percentage off the home-town model. Plan 27
  §4.5 names "auto-repair" but the wall-damage getter is **unknown**
  to the tree.
- **`abPickNextFromLevels` is the loop that decides what to build.**
  `build-auto.js:178-202` resolves prerequisites, reads
  `goalEffectiveBuildTargets(townId)` (which is `state.abTargets`,
  `build-targets.js:19-27`), and emits the next building to queue.
  `abFinalValidate` (`build-auto.js:204-224`) re-reads the live queue
  and the live levels before posting — so a wall drop between scan
  and post is caught.
- **`abCanAfford` (`build-auto.js:105-119`) reads the cost margin
  honestly** via `t.resources()` and `t.getAvailablePopulation()`,
  with a 10-resource margin. Wall costs are read from
  `BuildingBuildData` (`build-auto.js:58-74`, `abBuildingCost`) — no
  hardcoded cost table.
- **A new module is NOT justified.** Plan 27 §4.5 says "new
  `wall.js`", but the build path already iterates every
  `AB_BUILDINGS` entry and `wall` is in that list; adding a parallel
  module would (a) duplicate the prerequisite resolver,
  `abFinalValidate`, the queue-max reader, the cost reader, and the
  `bridgePost('build',...)` call; (b) split wall into two posts with
  different feature keys (`'build'` vs `'wall'`) which would double
  the captcha-breaker surface and confuse the journal rollups; (c)
  violate the "do not add per-feature loops" rule
  (`orchestrate.js:1-20` is the sole econ scheduler). The honest
  shape is **a rule in the existing loop** plus a small read of the
  damage signal.

## 2. Gap

`abPickNextFromLevels` decides "build X next" from a target-vs-current
comparison (`build-auto.js:186-187` `if (want <= 0 ||
+(levels[target] || 0) >= want) continue;`). When the wall is
damaged, the **level is still the level** — only a separate damage
attribute decreases. So the loop happily leaves a level-20 wall
sitting at 0% integrity, with `levels.wall === 20` and `want ===
20` and no work to do. The user-visible symptom is a wall that does
not get rebuilt after a hit. The fix is (a) detect wall damage from
a model getter that is unknown today (this plan flags the unknown
honestly and writes the read with a fallback to "no damage" =
"no repair needed"), and (b) make the build picker treat
"effective wall level = current level − damage" when the
`autoWallRepair` toggle is on, so a damaged wall falls below the
target and the loop picks it up on the next cadence.

## 3. Design

Extend the existing `abCurrentLevels` (and its prerequisite resolver
sibling `abPickNextFromLevels`) with a per-town wall damage offset
that subtracts from `levels.wall` when `state.autoWallRepair` is on
and the damage is readable. When the damage is unreadable the
picker must log once per town and continue without the offset
(precondition invariant — never block on an unreadable getter).
Everything else (prerequisite resolve, queue-max check, cost check,
`BuildingOrder/buildUp` post) is unchanged and stays on the
`'build'` feature key so the captcha breaker, journal, and
template-health rules continue to cover wall repairs exactly the
same way they cover normal builds.

**No new module.** A `wall.js` would have to reimplement
`abFinalValidate`, `abQueueInfo`, the cost read, the
`bridgePost('build',...)` call, and a lock to coexist with
`abScan`'s `gbLock('ab', ...)` — and any second lock would race
with `abScan` for the same town, since `abScan` walks towns
sequentially (`build-auto.js:312-368`). The right shape is "extend
the existing loop", not "add a parallel loop". Plan 27's hint is
explicitly rejected here.

## 4. Work items

1. **`src/build-targets.js`** — add `autoWallRepair` to
   `abDefaultTargets()` (the function at `build-targets.js:1`) as
   a new **toggle** with default `false`. Default-off is required
   for any feature that costs resources without user action (CLAUDE.md
   "HIGH-RISK toggles ... default OFF" — this is Med not High, but
   conservative default still applies because wall repairs consume
   stone/wood). Persist via a new `STORE.AUTO_WALL_REPAIR =
   'grepbot:auto-wall-repair'` key in `src/header.js` and a
   `state.autoWallRepair` field in `src/core.js`'s `state`
   initializer (`core.js:220`-ish, next to `state.abAuto` /
   `state.abOrder`). No `WORLD_SCOPED_BASES` change — the toggle
   is a per-player, not per-world, value.
2. **`src/build-auto.js`** — extend `abCurrentLevels` (lines
   14-33) so the returned `levels.wall` is the effective level
   after subtracting the damage read.
   - Add a helper `abWallDamage(townId)` at module-local IIFE
     scope. It probes a list of candidate getter/method names on
     `gbTownModel(townId)` — `getWallDamage`, `wallDamage`,
     `getDamagePercentForBuilding`, `getDamagePercentage` — using
     `gbProbeNum` (CLAUDE.md "Precondition readers", `core.js`
     precondition reader block). The first finite number in
     `[0, 100]` wins; anything else returns `null`.
   - In `abCurrentLevels`, after the `for` loop that walks
     `buildingOrders`, if `state.autoWallRepair` and
     `abWallDamage(townId)` is finite and `> 0`, decrement
     `levels.wall` by the damage percent of one wall level
     (effectively: `levels.wall = Math.max(0, +(levels.wall || 0)
     - damage / 100 * (current + 1))`). Use **whole-level
     arithmetic** so the picker sees an integer gap and emits one
     `buildUp` per damaged level, not fractional posts.
   - If `abWallDamage` is `null`, do nothing. Never fabricate a
     damage value (CLAUDE.md precondition invariant).
   - `abWallDamage` must also be probed at the
     `abFinalValidate` site (`build-auto.js:204-224`) so the
     effective level at post time still reflects the latest
     damage read; otherwise a wall that takes a hit between scan
     and post posts a stale level.
3. **`src/core.js`** — extend `tplNameFor` / `TPL_FEATURE_MAP`
   (`core.js:778-795`): the wall-repair post uses
   `bridgePost('build', {model_url:'BuildingOrder',
   action_name:'buildUp', arguments:{building_id:'wall'}, ...})`,
   the same payload as every other build. `TPL_FEATURE_MAP['build']`
   is currently `'ibAction'` (`core.js:782`), and
   `tplNameFor('build', ...)` returns `null` when
   `action_name === 'buildUp'` (`core.js:795-800`). That already
   excludes `buildUp` from the health tracker — wall repairs are
   automatically excluded too. **No change** to
   `TPL_FEATURE_MAP`; just confirm by reading that the existing
   `action_name === 'buildUp'` short-circuit at `core.js:798`
   catches wall rebuilds.
4. **`src/ui.js`** — under the existing Build config (the
   `state.abAuto` toggle area), add one checkbox row
   `Reparar muralla automáticamente (auto-reparar al detectar daño)`.
   Bound to `state.autoWallRepair` (default `false`). Place it
   next to the wall target input (the `state.abTargets['wall']`
   row in the queue table) so the meaning is local.
5. **`src/stats.js`** — Preflight row `wall auto-repair`: pass =
   `autoWallRepair` off OR the `abWallDamage` probe finds a
   readable getter; warn = `autoWallRepair` on and no getter
   found; fail = `autoWallRepair` on but the cost read for the
   next wall level is unreadable (the loop would never post — the
   user should turn the toggle off).

## 8. Failure modes

- **Unreadable wall damage** (`abWallDamage` returns `null`): the
  helper logs once per 5min per town via
  `gbLogT('ab-wall-damage-blind-' + townId, 300000, ...)`; the
  level stays at the model-reported value; no repair posts. The
  Preflight row (§4 item 5) surfaces this without spamming the
  log.
- **Wall at max level with damage**: `levels.wall >= abMaxLevel('wall')`
  is checked at `build-auto.js:217`; the picker rejects with
  `why: 'max-level'` unless the damage offset dropped the effective
  level below the max. With the offset, a damaged max-level wall
  has `effective < max` and the loop picks wall — which is the
  intended behaviour.
- **Cost unreadable for the next wall level**: `abCanAfford`
  (`build-auto.js:105-119`) returns `{ok:false, why:'cost
  unreadable'}`; the picker continues to the next priority
  target. No infinite loop, no blind post.
- **Queue full**: `abQueueInfo` returns `len >= max` and the
  picker rejects with `why:'queue-full'` (`build-auto.js:207`).
  The native queue head is marked `waiting-queue` (already wired
  at `build-auto.js:336`).
- **Two builds racing the same slot**: `gbLock('ab', ...)` at
  `build-auto.js:272` plus `txRecentlyCommitted` at
  `build-auto.js:215` already prevent a double-post. Wall repair
  inherits both.
- **Damage changes between scan and post**: the post-time
  re-read at `abFinalValidate` (`build-auto.js:204-224`) re-asks
  `abCurrentLevels` (now damage-aware) and the validate either
  passes (post) or rejects with `why:'levels-unreadable'` /
  `why:'plan-changed:...'` (skip). The native queue head is
  marked `blocked` or `replan` (`build-auto.js:362`).

## 9. Validation gate

Per plan 27 §11 Med row: dry-run + one hand-triggered firing + one
full orchestrator tick. Concrete, in order:

1. **Preflight** `wall auto-repair`: pass with the toggle off;
   confirm warn row appears if the toggle is on and the probe
   finds no readable damage getter.
2. **Damage probe**: in the live console, evaluate
   `gbTownModel(<townId>).getWallDamage()` (or whatever the probe
   finds) on a known-damaged town. If undefined across every
   probe name, **mark this whole feature as BLOCKED** until a
   real getter name is captured; do not invent one.
3. **Dry-run ON**, `autoWallRepair = true`, `abTargets.wall = 20`,
   town with wall at level 18 and 50% damage. Force one
   `abScan('manual')`. Log shows two queued `buildUp` posts
   (`wall: 18→19` and `wall: 19→20`) as `DRY-RUN build: ...`; no
   POST; journal `skip:dryrun`.
4. **Dry-run OFF**, same conditions, manual `abScan('manual')`:
   confirm two `BuildingOrder/buildUp` posts for `building_id:
   'wall'`; confirm the model's wall level advances from 18 to
   20; confirm the damage field clears or stays at 0.
5. **Damage mid-scan**: trigger a hostile attack that drops wall
   to 60% between two scans. The next scan picks wall up
   without manual intervention; journal shows
   `auto-queue: wall +1 in town <N> (prereq for wall)` — note
   the `(prereq for wall)` tag is normal (the loop re-emits wall
   as a prereq for itself at the target level).
6. **Max-level damage**: a wall at level `abMaxLevel('wall')` with
   damage > 0. Confirm the loop still posts `buildUp` until the
   effective level reaches the target.

## 10. Out of scope

- **A new `wall.js` module.** Explicitly rejected in §3. The plan
  follows the build path that already exists; the only addition is
  a damage read and a config toggle.
- **Damage reads from any source other than the live town model.**
  No spy-report-driven wall-damage inference (the parse path at
  `parse-inline.js:88` reads `wall` for intel/dossier views, not
  for build automation). If the live getter probe at §9 step 2
  returns nothing, this feature is blocked — do not fall back to
  spy reports.
- **Auto-cap wall at a damage-driven level.** This plan only
  rebuilds to the existing target in `state.abTargets.wall`. A
  "raise wall target by N when damage exceeds X%" feature is its
  own idea and out of scope.
- **Repair scheduling.** The orchestrator cadence for `build`
  (whatever `ORCH_CADENCE['build']` evaluates to after the
  deadlock widening) already covers wall rebuilds; no new
  scheduler is added (CLAUDE.md "no new schedulers").
- **Skirmisher / Captain wall-specific bonuses.** Those are
  gameplay mechanics in the town model, not GrepBot concerns.
