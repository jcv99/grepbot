## 2. Gap

`renderFarms` is a flat, alphabetical-by-id table with the columns the
bridge scrape used to feed. With the scrape dead (plan 26 §A1), every
row but id/name is `-` most of the time, and the player has no way to see
which of their villages actually pays back the slot against the option
they taught the bot. The data we DO have (x/y, learned durations, loyalty,
town warehouse headroom) is enough to estimate `res/min` per village and
rank by it; we just do not compute or render it today.

## 3. Design

Compute a per-village **expected resource rate** from signals that are
actually in the bridge model, then surface it in `renderFarms` as a
sortable column. The rank is intentionally an *estimate* (the actual
haul per village is unknowable — see §1). The function lives in
`farms.js` as a pure helper; nothing posts.

Inputs (all read-only):

- `farmOptionMap` (`farms.js:325-329`) — longest *learned* duration the
  player has hand-taught (the seed `{300:1}` (`core.js:255`) means 300s is
  always known). This is the longest claim the bot is allowed to fire
  here, capped by `farmDurationPick(townId)` against warehouse headroom.
- `island_x`, `island_y` (`farms.js:230-231`) — village coordinates.
- `islandTownMap()` (`farms.js:270-290`) → `townIdForFarm(f)`
  (`farms.js:291-299`) — owning town id (already used by `claimFarm`).
- `townResState(townId)` (`src/bridge.js:235-273`) — town warehouse
  headroom; used by `farmDurationPick`. **Unreadable ⇒ `null` ⇒ the
  village is excluded from the rank with `score: null`** (precondition
  invariant: do not block on an unreadable value).
- `farmLoyaltyResearched(townId)` (`farms.js:379-409`) — bool with 60s
  cache. Cached lookup, no new I/O.

Formula (single helper `farmProfitScore(farm) → { score, duration, distance, loyalty, headroom }`):

```
const learned  = longest learned option in farmOptionMap (>= 300, <= farmDurationPick cap);
const duration = learned;                            // seconds
const loyalty  = farmLoyaltyResearched(tid) ? 1.0 : 0.5;  // 50% penalty mirrors the in-game multiplier
const headroom = townResState(tid)?.cap - max(wood, stone, iron);  // null ⇒ blind
const expected = (duration / 3600) * ROOM_PER_HOUR * loyalty;      // 8000/h baseline
const distance = euclideanIslandDist(farm, tid);                   // > 0 only if cross-island? same island only.
const travel   = distance * TRAVEL_SEC_PER_UNIT;                   // const, pin in Config
const cycleSec = duration + travel;
const score    = expected / cycleSec;                              // res/sec; higher = better
```

`TRAVEL_SEC_PER_UNIT` defaults to **0.0** and is exposed in Config — the
in-game march formula is client-side and not in the bridge model, so a
*guess* here is the only honest choice; defaulting to 0 makes rank
distance-agnostic (the column says `dist=N/A` until the user pins a
value). On worlds without a pinned travel time the rank reduces to
**expected haul per cycle-second**, which is still useful.

Output is written to `state.farmProfit[farm.vill_id] = { score, duration,
distance, loyalty, ts }` (key in `WORLD_SCOPED_BASES`, `header.js:193-214`).
Pruned alongside `state.farmResources` at `core.js:1177-1182`.

`renderFarms` (`ui.js:122-170`) gets a new `res/min` column between
`pop` and `seen`, computed via `farmProfitScore` lazily inside the row
build (no pre-pass; same loop). Sort key adds the score at the end
(`ui.js:165`) so `sortApplySaved` keeps working.

## 8. Failure modes

- **`townResState(townId)` returns null.** Precondition invariant: the
  rank for that village is `null`, the `res/min` column shows `-`, and
  the row drops to the bottom on default sort. `gbLogT('farm-profit-blind-' + villId, 600000, …)`
  fires once per village per 10min (mirroring `wh-unknown-` at
  `farms.js:307`). The bot never blocks a claim on this signal
  (`farmDurationPick` already handles a null headroom by falling back to
  300s at `farms.js:442`).
- **`farmLoyaltyResearched` cache miss / not researched.** Default
  multiplier is 0.5 (matches the in-game "no loyalty" penalty). On a
  world where the research id is `villagers_loyalty` and the bot's
  `FARM_LOYALTY_RE` (`farms.js:368`) does not match, the bot stays at
  0.5 forever; that is a known failure of the existing detector, not a
  regression of this plan.
- **`farmOptionMap` empty for the village.** Seed `{300:1}` (`core.js:255`)
  guarantees a 5min option is always known. Rank uses 300s in that
  case; res/min is necessarily low.
- **`f.x`/`f.y` null.** `farms.js:292` already drops these in
  `townIdForFarm` (no same-island town). Profit row is excluded
  (`score: null`, log once).
- **Bridge model renames a getter.** `farmLoyaltyResearched` is wrapped
  in `try/catch` (`farms.js:406`); `townResState` does the same
  (`bridge.js:244,250`). Renames surface as `null` and the village
  ranks to bottom; the rank never silently invents a value.
- **`state.farmProfit` bloat.** Capped by `pruneMapsToIds` to the live
  farm id set; one row per village, payload <100 bytes.

## 9. Validation gate

Low-risk (plan 27 §11: Preflight + one in-game session).

- Open a world with ≥3 villages. Verify the Farms tab now has a `res/min`
  column; numbers are stable across reload (memo + persisted). On a
  world with the dead HTTP scrape, the W/S/I columns stay `-` and
  `res/min` is still populated from x/y + durations + loyalty.
- Pin a non-zero `Segundos de marcha por unidad de isla` (e.g. 4). Rows
  reorder; the rank falls as distance grows. Re-pin to 0; rank returns
  to duration-only.
- Hand-teach a 20min option (per plan 26 §C1). Verify a town with
  headroom ≥ ~1.6k re-ranks higher; a near-full town keeps a shorter
  option (`farmDurationPick` already clips it at `farms.js:441`).
- Preflight row `farm profit`: pass when `state.farmParsed.length > 0`
  and at least one row has a numeric score; warn when 0/0; fail never
  (read-only).
- Decisions view must show **no** new feature key (no posts).

## 10. Out of scope

- Per-village current stock (cannot be read; plan 26 §A1).
- Per-village historical yield (claim payload does not return amount).
- Per-village building bonus / hero presence (not in the bridge model
  for `FarmTown`).
- Auto-sorting the claim queue. That is plan **5.2** (adaptive farming)
  which consumes `state.farmProfit` and rotates targets under captcha /
  budget pressure. 2.6 only computes and displays.
- Per-village option index selection (which `option` index the player
  hand-taught for which duration) — that lives in `farmOptionMap`
  (`farms.js:325-329`) and is unchanged.
