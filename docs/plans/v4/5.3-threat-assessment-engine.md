## 1. What exists today

- `defenseAssessment(mov, incoming)` is already implemented at
  **`src/wonder.js:144`** — *not* `src/intel.js` as plan 27 §5.3 hints. Plan 26
  §B2 expected exactly this kind of mismatch: the catalogued module hint says
  `intel.js` but the actual code lives where its caller
  (`defenseShouldDodge`, also `wonder.js:145`) was first needed. The live
  return shape is:

  ```
  { eta: number|null,           // seconds until landing, or null on unreadable arrival
    simultaneous: number,        // other hostile movements destined for the same town
    local: { score, count },     // defenseLocalStrength(townId) result; from wonder.js:142
    supports: [{from, travel, units}], // defenseSupportOptions(townId, eta); wonder.js:143
    safeTown: townId|null,       // dodgeSafeTown(townId, incoming); dodge.js:86
    evac: {ok, why, boats?},     // dodgeSupportValidate(...); dodge.js:157
    militia: {ok, why},          // dodgeCanRaiseMilitia(townId); dodge.js:107
    risk: number,                // 0..N additive score with embedded magic numbers
    hasCs: boolean,              // !!mov.hasCs; dodge.js:73 detector
  }
  ```

  Read by `dodgeTrySend()` (`src/dodge.js:207`), surfaced in the Intel tab at
  `src/intel.js:88-89` (the `riesgo` / `apoyo` / `esquivar` columns), and
  bound to the test hook `GB_ROOT.__grepbotTest.defenseAssessment`
  (`src/boot.js:178`).
- Caller `defenseShouldDodge(mov, incoming)` (`src/wonder.js:145`) already
  implements three modes — `notify` / `safe` / `smart` — keyed by
  `state.defenseCfg.mode` (default `'notify'`, `src/core.js:359`,
  `src/wonder.js:141`). The "smart" branch honors a separate
  `state.defenseCfg.smartAuto` flag (`src/core.js:359`, `src/ui.js:1352`) and
  decides on `a.hasCs || a.risk >= 35`. That single `risk >= 35` magic
  constant is the only place where 5.3's output is currently acted on.
- Weights are **hardcoded** in the additive score at `src/wonder.js:144`:
  `+60` if CS, `+25` if ETA < 15min, `+8…+25` per extra simultaneous hit,
  `+10` if local.score < 200, `-5…-20` for incoming supports. Changing them
  today means editing `wonder.js:144` and re-running
  `python3 build.py`.
- Hostile-movement detector (`src/dodge.js:39-52`,
  `DODGE_HOSTILE_TYPES = /^(attack|attack_sea|raid|siege|revolt|colonize|take_over|conquer|portal_attack)$/`)
  is the canonical input — never `incoming`/`started_at` alone, per CLAUDE.md
  "Dodge / militia / CS" rule.

## 2. Gap

The score has three problems 5.3 must solve cleanly:

1. The additive formula is a magic-number soup glued to one threshold; users
   cannot tune it, and 5.4 Smart dodge will need to consume a richer
   decomposition (per-factor contribution, not a single rolled-up number).
2. The output has no display-stable provenance: a future change to the
   formula quietly changes the `risk` value with no audit row, and 5.4 (smart
   dodge) would inherit those silent changes.
3. The Intel tab (`src/intel.js:75-114`) renders only three of the nine
   fields (`riesgo`, `apoyo`, `esquivar`); the rest (`simultaneous`, ETA,
   militia, supports travel times) are computed but discarded.

## 3. Design

Refactor `defenseAssessment` into a documented scoring primitive whose output
shape is **stable** and consumable by both the Intel tab and a future 5.4
consumer. Schema change is **additive only** — the existing nine fields keep
their names and meanings; new fields and a `factors` block are added.

Stable score schema (the contract 5.4 reads):

```
{
  // unchanged
  eta: number|null, simultaneous: number, local: {score, count},
  supports: [{from, travel, units}], safeTown, evac, militia, hasCs,
  // new (5.3)
  band: 'low'|'med'|'high'|'cs',   // discrete bucket for UI + 5.4
  factors: {                       // per-signal contribution; sum <= risk
    cs: number,                    // +60 if hasCs
    eta: number,                   // +25 if eta<15min
    simultaneous: number,          // +8 per extra simultaneous, capped +25
    weak: number,                  // +10 if local.score<200
    support: number,               // -5 per support, capped -20
  },
  risk: number,                    // semantically = clamped sum(factors); recomputed
  computedAt: number,              // Date.now() at the call site
  weights: {...},                  // the weight set used (see §5)
}
```

The function signature is unchanged (`(mov, incoming) -> ...`); the only
call-site adjustment is to pass `weights` via a new optional third arg
(defaults to `state.predictCfg.threatWeights`, see §5). Boot-time callers
(`src/boot.js:178`) keep working unchanged. The Intel tab gets `band` and the
factor breakdown for free; smart-dodge 5.4 gets a stable shape with
decomposed reasoning and provenance.

Display update in the Intel tab:

```
=== Entrantes ===
[CS] attack → 12345 from 67890 @1742345678 | riesgo high (60=cs,25=eta,0=sim,0=support)
  | ETA 12m30s | apoyo 2 (4-9min) | esquivar no (cannot-evacuate)
```

The `riesgo` label prints the band; the parenthetical exposes factor breakdown
in `cs=N,eta=N,sim=N,support=N` form (sign and rounding preserved). Adds at
most ~30 chars/row.

|---|---|---|---|---|

| `threatWeightSim` | number | 8 | 0..30 | `…threatWeights.simPer` |

  behaviour changes for anyone who does not touch the config.

## 8. Failure modes

- **`dodgeIncomingMovements()` (`src/dodge.js:53`) returns `[]`** —
  `defenseAssessment` (`src/wonder.js:144`) is never called for a movement
  that wasn't already in that collection. The new factor sums all default to
  0, `band` is `'low'`, callers (`src/dodge.js:207`) short-circuit on
  `entry.state` first.
- **`dodgeEtaSec` returns `null`** (`src/dodge.js:175`) — `simultaneous` and
  `local` are still meaningful, `eta` factor stays at 0, and the `eta15`
  weight branch is skipped (per the existing `eta != null && eta < 15 * 60`
  guard at `src/wonder.js:144`). No new failure path.
- **`dodgeSafeTown` returns `null`** (everyone threatened, `src/dodge.js:99-102`)
  — `safeTown` is `null`, `evac.ok` is `false`, the consumer
  (`defenseShouldDodge`) already returns `'cannot-evacuate'` so smart-dodge
  never auto-fires. 5.3 inherits the path unchanged.
- **`unitMeta` returns `null`** — `defenseLocalStrength` (`src/wonder.js:142`)
  is unaffected (it filters `m.is_naval`); the score's `weak` branch reads the
  sum, not the metadata directly.
- **Weights misconfigured** (e.g. `cs: -60`) — `risk` can go negative. Clamp
  `risk` to `[0, 100]` after the additive pass (band still resolves
  correctly: negative → `'low'`). Document the clamp in the schema comment
  block; do not silently drop bands.

## 9. Validation gate

Plan 27 §11 risk class Low: preflight + one in-game session, no failure.

- Preflight row `intel: threat engine weights`: pass when
  `state.predictCfg.threatWeights` reads; warn on shape mismatch (out-of-
  range value from a hand-edited localStorage).
- Manual: with `state.defenseCfg.mode='notify'` and one incoming hostile in
  the Intel tab, the row should print `| riesgo low (cs=0,eta=0,sim=0,

  render: same row reads `| riesgo high (cs=120,...)`. Set back to 60.
- Failure pattern: log shows `threat engine: band=high risk=120 band=` — fix
  the clamp at the engine, not the UI.
- **Cross-feature test**: Config → smartAuto on (still `mode='smart'`),
  trigger a synthetic hostile (`dodgeIncomingMovements` returns an entry with
  `hasCs:true`), 5.4 lands later and will consume `assessment.band`; for
  this plan, verify `defenseShouldDodge` logs `why: 'risk'` exactly as before
  when defaults are restored.
