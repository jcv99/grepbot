# 7.2 — Defense coordination board

**Bucket:** v4.4 · **Risk:** Low · **Size:** M
**Module:** extend `src/intel.js`; add a `[data-intel="view"]` option in `src/ui.js` Intel tab; no `src/header.js` change (no new key)
**Depends on:** none (uses `defenseAssessment` from `src/wonder.js` and `dodgeIncomingMovements` from `src/dodge.js`, both already loaded)
**Status:** PLANNED — written 2026-08-10 against `src/` @ v3.8.2 (header `@version` is `3.9.0`)

> Read-mostly per plan 27 §7. The board is a **per-client** coordination aid:
> the user sees their own towns, their own incoming, and their own support
> options, in a layout meant for copy-paste into alliance chat. It does **not**
> fetch any alliance-side state (no `MM.getCollection('Alliance')` exists —
> see §1.4) and does **not** post outbound messages on the player's behalf.
> Coordination with allies stays in the alliance chat; the bot only formats.

---

## 1. What exists today

- `dodgeIncomingMovements()` (`src/dodge.js:53-84`) is the threat source.
  It walks `MM.MovementsUnits` (`dodge.js:57`), filters by the
  `dodgeIsHostileMovement` rule (`dodge.js:41-52`), keeps only attacks whose
  `destination_town_id` is one of the player's towns (`dodge.js:59-63`), and
  returns `[{id, dest, origin, type, hasCs, arrival, units, model}]`.
  Every field used by the board is already there.
- `defenseAssessment(mov, incoming)` (`src/wonder.js:144`) is the per-threat
  scoring function. It returns `{eta, simultaneous, local, supports, safeTown,
  evac, militia, risk, hasCs}`. Already used by `renderIntel`
  (`intel.js:80-90`) for the existing threat dump. The board reuses the same
  call — no second implementation.
- `renderIntel()` (`src/intel.js:75-114`) already renders the existing threat
  block at `intel.js:83-91` in the format
  `[CS] type → dest from origin @arrival | riesgo <n> | ETA … | apoyo N |
  esquivar si/no`. That is a one-line-per-threat view; the board needs a
  grouped-by-destination view with one row per (own-town, attack-id).
- `state.towns` (`src/core.js:229`, populated by `towns.js:71, 197`) is the
  player town list, shape `{id, name, x, y, island}`. Used for ordering and
  labelling the board columns.
- `state.allianceNotes` (`src/core.js:341`, `intel.js:124-132`) carries
  per-alliance free text. The board looks up the **attacker's** alliance
  string (via `parseReport` → `f.alliance` at `parse-inline.js:89`) and
  appends the note if present — same shape as the dossier line at
  `intel.js:66-67`. **Read path only** for the board; the setter is already
  wired at `ui.js:1002-1007`.
- `defenseMode()` (`src/wonder.js:141`) and `state.defenseCfg`
  (`src/core.js:359`) are the live controls the user sets in Config
  (`ui.js:1350-1353, 1470-1472`). The board reads them; it does not
  duplicate them.
- Plan 6.13 (`docs/plans/v4/6.13-alliance-intel-heatmap.md`) already adds a
  `[data-intel="view"]` selector to the Intel section (`ui.js:693`) with two
  options, `Resumen` and `Heatmap 7d`. The board adds a **third** option,
  `Coord 7.2`. When selected, `renderIntel` emits only the board and skips
  the existing dump blocks (`intel.js:83-111`). The existing
  `intelPatternScan` call at the bottom (`intel.js:113`) still runs on
  either view (orthogonal).
- **No** `MM.getCollectionByName('Alliance')`, `getAlliances()`, or
  `AllianceMembers` reference exists anywhere in `src/` (verified by
  ripgrep — zero hits). Alliance-wide data for **other** members is not
  exposed by the game to a single client. The board does not pretend
  otherwise.

## 2. Gap

`renderIntel` (`intel.js:75-114`) renders one line per incoming attack
(`intel.js:86-90`). When a single town has two incoming commands, the user
has to mentally re-group by destination to plan a defence, and the
existing line does not surface the **own-town summary** (which towns need
help, which towns are safe, where to route the supports). Plan 7.2
delivers that summary without inventing any data — everything the board
needs already exists in the call chain.

## 3. Design

Read-only. No post surface, no captcha breaker, no lock, no scheduler.
The renderer is grouped by `dest` (the attacked town) instead of by
attack `id`. Each group shows local strength, the per-attack assessments,
and the suggested action taken from `state.defenseCfg.mode`.

### 3.1 Aggregator

Add `intelDefenseBoard(threats)` to `src/intel.js`, placed next to
`intelDossiers` (`intel.js:34-71`):

```js
function intelDefenseBoard(threats) {
  const byDest = new Map();
  for (const t of threats || []) {
    const k = String(t.dest);
    if (!byDest.has(k)) byDest.set(k, []);
    byDest.get(k).push(t);
  }
  const ownTowns = (state.towns || []).slice().sort((a, b) => String(a.id).localeCompare(String(b.id)));
  const rows = [];
  for (const t of ownTowns) {
    const incoming = byDest.get(String(t.id)) || [];
    if (!incoming.length) continue;
    const townRow = { townId: String(t.id), townName: t.name, attacks: [] };
    for (const m of incoming) {
      const da = defenseAssessment(m, threats);
      const ass = String(m.units?.colonize_ship || m.units?.colony_ship ? 'CS' : (m.hasCs ? 'CS' : 'attack'));
      townRow.attacks.push({
        id: String(m.id || ''), type: ass, origin: m.origin, arrival: m.arrival,
        risk: da.risk, eta: da.eta, supports: (da.supports || []).length,
        evacOk: !!da.evac?.ok, militiaOk: !!da.militia?.ok, hasCs: !!m.hasCs,
      });
    }
    rows.push(townRow);
  }
  return rows;
}
```

The aggregator reuses `defenseAssessment` (`wonder.js:144`) directly —
**no second risk-score formula**. `rows` is sorted by `townId` ascending,
which keeps a stable order across repaints (the same pattern the World
table uses; `ui.js:165` and the keyed-row rule at `CLAUDE.md` "v1.4.0
render").

### 3.2 Renderer

In `renderIntel` (`intel.js:75-114`), after the existing
`if (intelView === 'heatmap')` branch (added by plan 6.13 §4.2), add:

```js
if (intelView === 'board') {
  const threats = intelThreatBoard();
  const board = intelDefenseBoard(threats);
  let html = '';
  html += '=== Coordinación de defensa (live) ===\n';
  if (!board.length) { html += '(sin amenazas activas)\n'; }
  else {
    for (const row of board) {
      html += `Ciudad ${row.townName || '#' + row.townId}: ${row.attacks.length} amenaza(s)\n`;
      for (const a of row.attacks) {
        const eta = a.eta == null ? '?' : fmtSec(a.eta);
        const action =
          state.defenseCfg.mode === 'safe' ? 'esquivar' :
          state.defenseCfg.mode === 'smart' && (a.hasCs || a.risk >= 35) ? 'esquivar smart' :
          a.supports > 0 ? `apoyar (${a.supports} opcion(es))` :
          'mantener';
        html += `  ${a.type} desde ${a.origin || '?'}${a.arrival ? ' @' + a.arrival : ''} | riesgo ${a.risk} | ETA ${eta} | ${action}\n`;
      }
    }
  }
  box.textContent = html;
  try { intelPatternScan(); } catch (_) {}
  return;
}
```

Each line is exactly one attack on one town. The action text is a pure
function of `state.defenseCfg.mode` and the existing `risk >= 35` /
`hasCs` thresholds that `defenseShouldDodge` already uses
(`wonder.js:145`) — no new thresholds. Empty board ⇒ one
`(sin amenazas activas)` line; **no** `null`s, no `undefined` rendered.

### 3.3 Alliance-note overlay

For every incoming attack the board looks up the **attacker**'s alliance
string by walking `state.findings` once before rendering:

```js
function allianceForAttack(originTownId) {
  if (!originTownId) return null;
  for (const f of (state.findings || []).slice(0, 200)) {
    if (String(f?.town?.id) === String(originTownId) && f.alliance) return f.alliance;
  }
  return null;
}
```

If `allianceForAttack(a.origin)` returns a string present in
`state.allianceNotes`, append ` — [aliado: <note>]` (truncated to 40
chars) to that attack's row. Same `textContent` discipline as the
existing dossier line at `intel.js:96`. **No `innerHTML`**.

The lookup is bounded (`state.findings.slice(0, 200)`) because
`state.findings` is capped at 100 entries by `storagePruneForQuota`
(`core.js:1188-1190`); the `slice` is defence-in-depth, not a quota
control.

### 3.4 View selector integration

Plan 6.13 §3.3 already specifies a `[data-intel="view"]` `<select>` in the
Intel section header (`ui.js:693-704`). Plan 7.2 does **not** add a new
control — it adds a third `<option value="board">Coordinación 7.2</option>`
inside the same selector. Plan 6.13 builds the selector; plan 7.2 assumes
it exists. If 6.13 lands first, this is a one-line `<option>` addition.
If 7.2 lands first, plan 6.13 §3.3 picks up the second option instead of
adding the selector itself.

**Resolving the ordering conflict:** both plans propose a third option for
the same selector. Treat the selector as part of the Intel section chrome
(owned by plan 6.13), and 7.2 only contributes one `<option>` to it.
Concretely: §4.1 of 6.13 says "the renderer checks `state.intelView`";
plan 7.2 does **not** introduce a second renderer-mode variable. The
branch lives in the same `renderIntel` block and reads the same
`intelView` module-local `let`.

## 7. Post surface & safety

**No post surface.** No `bridgePost`, no `gameAjaxPost`, no
`gbDomClick`, no `gbAjaxWatch`, no `gbLock`, no `GB_LOCK_TTL` entry,
no `gbCaptchaPause` key.

The renderer uses `box.textContent = html` (same discipline as today
at `intel.js:112`). The selector uses `createElement('option')` +
`appendChild` (plan 6.13 §4.4). Audit-I15 XSS discipline: zero
`innerHTML` where attacker-controlled strings render. The
`origin`/`alliance` strings are attacker-controlled (they come from
report JSON parsed by `parse-inline.js:89`); the primary defence is
`textContent`, which never parses the string as markup.

The board is **read-mostly** end to end. The copy-paste-to-chat
workflow is the user's keystroke, not the bot's; the bot never calls
`alertWebhook` from the board path (a deliberate non-decision; alliance
chat is out of plan 27 §0).

## 8. Failure modes

- **`dodgeIncomingMovements` returns `[]`** — the board renders one
  `(sin amenazas activas)` line. No `null`s, no crashes.
- **`state.towns` empty** — `byDest` is empty, `rows` is empty, same
  `(sin amenazas activas)` line. Fresh-install safe.
- **`state.allianceNotes` empty** — overlay §3.3 finds nothing;
  attack rows render without the ` — [aliado: …]` suffix. Documented in
  the §9 validation gate.
- **`defenseAssessment` throws on a hostile command with unknown
  fields** — `defenseAssessment` is wrapped today by `try { … } catch
  (_) {}` (`intel.js:113`) and the new branch wraps the same call.
  The aggregator still emits `[{townId, attacks: []}]` with empty
  attacks for the throw site. Better: rebuild the per-attack loop
  inside a single `try { … } catch (_) { row.attacks = []; }` so a
  single broken assessment does not blank the whole row.
- **`origin` not present in `state.findings`** — `allianceForAttack`
  returns `null`; no note appended. Documented. The 200-row cap is
  generous; alliance attribution by origin is best-effort.
- **Mode toggle mid-board** — the user changes `defenseCfg.mode` in
  Config (`ui.js:1470`); the next `renderIntel` call reads the new mode
  and re-emits the action text. No state drift, no stale cache. The
  board never caches `defenseCfg.mode` between renders.
- **Top-N town cap** — `state.towns` is at most ~20 on a single world;
  no cap is needed. The board prints every threatened town, every
  attack. The alliance-chat paste format is plain text, so there is no
  pagination concern.

## 9. Validation gate

Manual, per plan 27 §11 Low class (Preflight + one in-game session, no
failure).

- Build (`python3 build.py`), install, open the Intel tab. The
  `[data-intel="view"]` selector shows `Resumen` (default),
  `Heatmap 7d`, and `Coordinación 7.2`.
- With no incoming attacks (`dodgeIncomingMovements()` returns `[]`):
  the board emits `(sin amenazas activas)` and exits cleanly.
- Seed one attack by hand: open the game, send an attack from an alt
  account (or use the dev console to populate `MM.MovementsUnits` with a
  fake hostile movement), open the Intel tab, choose `Coordinación
  7.2`. Expect one town row, one attack row, the action text matches
  the current `defenseCfg.mode` (try `notify` and `safe` and confirm the
  text flips).
- Add an alliance note via the existing UI (`ui.js:1002-1007`),
  re-open the board; the attacker row gains ` — [aliado: <note>]`. The
  alliance note is set on the **attacker**'s alliance name (the string
  the bot saw in the most recent report involving that origin).
- Switch `state.defenseCfg.mode = 'smart'`; expect rows where
  `risk >= 35` or `hasCs` to read `esquivar smart` instead of `apoyar`.
  Rows below the threshold read `mantener`. Same threshold as
  `defenseShouldDodge` (`wonder.js:145`).
- Preflight (`Comprobar sistema`) — new `defense coordination board`
  row appears; passes when `maxRisk` is finite, warns when the board
  renders but every row's `risk` is 0.
- `state.dryRun = true` — board still renders; no new posts in the
  Log tab. Confirm by reading the journal (Decisions sub-view, `mem`).

## 10. Out of scope

- **Cross-alliance coordination (shared board).** Plan 27 §7.1 owns the
  alliance-side intake via webhook; that is a different feature
  (inbound `planner.js` extension). The 7.2 board is local-only.
- **Auto-escalation.** `defenseShouldDodge` (`wonder.js:145`) is the
  existing auto-escalation path; the board only formats what it would
  do, never triggers it. The `state.defenseCfg.mode = 'smart'` rows
  that read `esquivar smart` are advisory; the user still owns the
  decision.
- **Active alliance chat posting.** Out of plan 27 §0 (no auto-post
  to third-party chat surfaces; the existing `alertWebhook` is
  user-configured, never alliance-targeted).
- **Mermaid / SVG / pixel rendering.** Same justification as 6.13 §3.2
  and 6.12 — `textContent` discipline, no chart renderer in `src/`,
  ASCII is the right tool.
- **CSV export of the board.** Read-mostly means read; exporting is a
  user keystroke (select-all + copy from the `<pre>`). The existing
  `qolExportConfig` (`qol.js:248-253`) does not include intel data; an
  intel export would be a separate plan.
- **Alliance member identity lookup.** Plan 7.6 owns the member-activity
  dashboard; that work is needed before the board can show attacker
  *names* (today it shows attacker `origin` town ids). Out of scope
  here.
- **Plan 6.13 dependency.** If plan 6.13 has not landed, the
  `[data-intel="view"]` selector does not exist and §3.4 has nothing to
  extend. In that case file §10 as **blocked** and land 6.13 first.
