## 1. What exists today
- Academy automation already has a persisted opt-in `state.autoResearch` (`src/core.js:303`) and Config checkbox `data-cfg="auto-research"` (`src/ui.js:778`). The catalogue’s “extend research.js” hint is therefore correct for selection, not for cadence.
- `researchScan` scans towns and sorts each town’s configured targets by `order`, then chooses the first eligible unresearched, unqueued, enabled target (`src/research.js:450-489`). It does not weight targets by slot scarcity, city role, opportunity cost, or path value.
- The current queue limit is read from `GameDataConstructionQueue.getResearchOrdersQueueLength()`, with conservative fallback to curator/base values (`src/research.js:109-123`). Current orders are read through `researchOrdersFor`; unreadable non-current queues are explicitly `known:false` (`src/research.js:19-54`).
- The final precondition validates town state, researched flags, known queue, duplicate queue membership, queue full, dependencies, and affordability before post (`src/research.js:378-395`). The slot optimizer must remain advisory to this invariant, not replace it.
- The actual research post is already bridge-first through `bridgePost('research', researchPayload(...))` (`src/research.js:291-315`), with the verified `ResearchOrder` payload and top-level `town_id` (`src/research.js:295-301`). This plan adds no endpoint or payload.
- Research already receives cadence through the shared orchestrator: `research` is enabled by `state.autoResearch`/native pending state (`src/orchestrate.js:1-17`) and dispatched from `orchTick` (`src/orchestrate.js:147-195`). No `gbInterval` may be added.
- Existing `docs/plan-academy-queue.md` is not an unimplemented prerequisite: it says the queue work is coded except live validation (`docs/plan-academy-queue.md:1-9`) and records the implemented H4/H1/H3/A1 fixes (`docs/plan-academy-queue.md:300-335`). 5.5 must not duplicate those fixes.
- Plan 27’s dependency on 1.2 is real, but no `cityProfiles` implementation is present in the cited current files: `researchTownTechs` exposes academy/research/queue facts only (`src/research.js:56-107`), and `build-targets.js` contains build ordering/targets, not profile weighting (`src/build-targets.js:1-26`). Implementer must consume the 1.2 contract only after that plan lands; do not invent its field names.

## 2. Gap
Add deterministic, read-mostly ranking of candidate research jobs when multiple academy slots/towns compete. The rank should combine verified current eligibility with a city profile supplied by 1.2, target path completion/value, and queue occupancy, while preserving the configured target order as a stable fallback. It must not add a second queue, duplicate the already-coded academy queue plan, or turn Low-risk queue weighting into a new autonomous game action beyond the existing opt-in `autoResearch` path.

## 3. Design
At each existing `researchScan` invocation, gather candidates from the same town/target loop (`src/research.js:450-489`). Read `researchTownTechs` and reject only facts actually read; retain unknown queue handling (`src/research.js:454-459`). For each defined target, compute a score from: profile role weights from 1.2 (exact accessor/fields to be named by that plan), the number of missing prerequisites from the verified game model, configured order, and available queue slots. Lower cost/shorter path may be preferred only when the relevant values are readable; unreadable values are `blind` and fall back to configured order. Sort candidates deterministically by score, then town id, then configured order, and run the existing final validation immediately before `researchPost` (`src/research.js:497-516`). This optimizes selection only; it never guesses research ids or starts prerequisites.

## 8. Failure modes
A candidate with unreadable town, academy, research flags, queue, cost, or profile is marked blind and falls back to configured order; it must not be treated as zero cost, zero queue occupancy, or a preferred role. The existing unknown-queue guard must continue to skip non-current towns (`src/research.js:454-459`). Every hard rejection names the value read, matching the existing `researchCanAfford`/dependency logging (`src/research.js:260-287,370-376`). A missing 1.2 profile accessor is a compatibility condition, not permission to guess a field. Final validation remains mandatory immediately before posting (`src/research.js:497-504`).
