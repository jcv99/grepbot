## 2. Gap

GrepBot's Intel tab shows player notes (`ui.js:696-700`) and alliance notes (`ui.js:701-704`) as free-text fields with no semantic meaning. Two natural extensions are missing:

1. A **typed** diplomatic status store (NAP / war / neutral / ally) keyed by player id and by alliance name, with values that mean something to the player and that the bot can read back to colour its own intel view.
2. A **status overlay** rendering that status back to the player in the most visible place: the dossier rows in the Intel panel, which is the only DOM surface where player + alliance names are already listed by their map presence.

There is no way to add a map-canvas tint (sibling 6.7 §1 + plan 27 §0 already closed that path). The 6.7 context menu already lets the player right-click a town and call `intelSetNote` / `intelSetAllianceNote` — 7.5 reuses the same entry points and adds a **status dropdown** in the same editor row so the player can mark "Bob is at war with me" instead of typing free text.

## 3. Design

Two halves, sharing the same in-memory store. No new post surface, no new `*InFlight` boolean, no new `gbInterval`, no new module.

**Half 1 — store + editor (extend `intel.js` + `ui.js`).**

```
state.napStatus = {
  players: { [playerKey]: 'nap' | 'war' | 'neutral' | 'ally' },
  alliances: { [allianceName]: 'nap' | 'war' | 'neutral' | 'ally' },
}
// playerKey is the same key the dossiers already use:
//   intelPlayerKey(p) at intel.js:1-10 — id:<id> for object players, raw name for strings.
//   This is the rule intelDossiers/intelPatternScan already key by, so the lookup
//   is a single Map-style hit per dossier row.
```

- Three new setters in `intel.js`: `intelSetPlayerStatus(player, status)`, `intelSetAllianceStatus(alliance, status)`, `intelClearStatus(...)`. Status is one of `'nap' | 'war' | 'neutral' | 'ally'`; null/undefined/empty string deletes the entry. Same 200-char note ceiling does not apply — status is a 4-value enum, not free text. Persisted via two new `STORE.*` keys (see §5).
- A new `intelStatusFor(player, alliance)` resolution in `intel.js` — given a player and (optionally) the alliance that owns them, returns the stronger of the two statuses. Strength order for rendering: `war > ally > nap > neutral > unknown`. The function reads `state.allianceNotes` (player-side note does not affect diplomatic status; the new store is the only source of truth for the four enum values).
- A new `intelApplyStatusToDossier(d)` decorator (called from `intelDossiers` at `intel.js:46-72`) sets `d.status = intelStatusFor(...)` and `d.statusSource = 'player' | 'alliance' | null`. Dossier render (`intel.js:92-97`) appends `[WAR]/[NAP]/[ALLY]/[NEUTRAL]` to the row.

**Half 2 — status overlay in the Intel panel (extend `ui.js` + small CSS).**

- `renderIntel` already calls `box.textContent = html` (`intel.js:112`). The current rendering is a `<pre>` with plain text. v4.4 wraps that in a CSS-styled structure so rows can be tinted without breaking the existing `<pre>` contract. **Concretely:** replace the `textContent` write with a DOM-construction loop that builds each row via `document.createElement('div')`, sets its text via `row.textContent = lineText` (so attacker-controlled player / alliance strings from `f.attacker.name` / `f.alliance` / `f.defender.name` / `state.playerNotes[…]` / `state.allianceNotes[…]` are escaped by the browser, never serialized into HTML — same XSS discipline as sibling plans 7.2 / 7.3 / 7.6), and toggles `row.classList.add('gb-intel-row', 'status-' + status, …)` for the accent. No `box.innerHTML = …`. The `<pre>` outer wrapper stays — only the children change. CSS (added inline in `intel.js` via `GM_addStyle` so no `theme.css` regen is needed) is **four** rules: `.gb-intel-row.status-war { background: rgba(255,80,80,0.18) }` and the three analogous rules for `nap`/`ally`/`neutral`. Player Spanish labels live in the row text: `[GUERRA]`, `[PAZ]`, `[ALIADO]`, `[NEUTRAL]`. Theme.css is untouched.
- The status colour comes from the dossier's `d.status` (resolved in the store decorator). Rows with no status set retain today's plain rendering. The legend is a single header line at the top of the panel: `Leyenda: [GUERRA] rojo · [PAZ] verde · [ALIADO] azul · [NEUTRAL] amarillo`. The legend itself is a status-free row.
- The editor row in `ui.js` (next to the existing text-note rows, `ui.js:696-704`) gains two more input groups: a player dropdown + status `<select>` and an alliance dropdown + status `<select>`. The "dropdown" is a `<datalist>` attached to the existing text input so the player can type a partial name and the bot offers the names already seen in `state.findings` (server-rendered, no post). When the player picks a `<option>` from the datalist, the click handler at `ui.js:997-1007` is supplemented with a sibling handler that calls `intelSetPlayerStatus` / `intelSetAllianceStatus`. The existing `intelSetNote` / `intelSetAllianceNote` paths stay — the new editor does not replace them; the player can keep free-text notes.

**Hit-test and teardown (sharing 6.7 + `native-ui.js` patterns):**

- 7.5 does **not** add a sibling popup on the map. The map is canvas (6.7 §1). The 6.7 context menu (if and when it ships) already calls `intelSetNote` / `intelSetAllianceNote` from a right-click; 7.5 adds a new "Diplomacia" item that calls `intelSetPlayerStatus` / `intelSetAllianceStatus` with a 4-button prompt (NAP / WAR / ALLY / NEUTRAL / Cancel). That prompt is a `gameUw().confirm(...)` ring, not a custom DOM popup — no map mutation, no overlay div, no canvas read.
- 7.5 adds **no new DOM mutation** outside the Intel panel. `__grepbotDispose` (`core.js:114-143`) tears the panel down on dispose; the rows are children of the panel `<pre>` and die with it. No `gbListenerBag` entry is added by 7.5 outside the existing `'#gb-note-save'` + `'#gb-anote-save'` handlers, which are already wired by `ui.js:997-1007`.

## 8. Failure modes

- **Editor row receives a name not in `state.findings`.** The datalist is a hint, not a validator. Typing a free-text name and clicking `Guardar` calls `intelSetPlayerStatus(name, status)` with the typed string. The setter stores `state.napPlayers[name] = status` regardless of whether the game knows that player. The dossier render at `intel.js:46-72` only colours rows whose `intelPlayerKey` matches a player in `state.findings`, so free-text names that no report ever carried are stored but never surfaced. This is acceptable: the player may know a player by a name that no report has reached the bot yet. The store stays consistent. The precondition invariant holds — every read goes through a real lookup, no invented id.
- **Player renames / alliance tag changes.** Grepolis allows players to change names; alliances can be re-tagged. The dictionary key is the **typed string** at the moment the editor accepted it, so a renamed player leaves a stale entry. This matches the existing `state.playerNotes` and `state.allianceNotes` policies (`intel.js:115-132`) — those are also typed-string keys with no rename tracking. v4.4 ships the same contract; a future plan could add a `MergedAlliances` map if rename tracking becomes a real player need.
- **Modal window opens over the Intel panel.** The `<pre>` is hidden behind the modal window; `renderIntel` early-returns when the section is hidden (`intel.js:78-79`). The status overlay is then effectively off-screen. The dossier data is intact and re-renders when the panel is shown again. No error, no leak.
- **Datalist never populates.** `state.findings` may be empty on a fresh world. The datalist is empty; the `<input>` becomes a free-text field. The editor still works. The legend is still rendered. Status values set on unknown names are persisted silently (handled above). `gbLogT('nap-datalist-empty', 600000, …)` once per scan if preflight wants to surface it.
- **Status enum drifts.** A new client shape adds a fifth diplomatic enum (e.g. `'non-aggression'`) that the bot does not model. `isNapStatus` returns false for the new value, the setter rejects it, the editor dropdown does not show it. The player cannot set a status the bot does not understand. No silent data corruption.
- **`__grepbotDispose` mid-edit.** The panel is torn down (`core.js:135-136`). The handler never fires; the in-memory state is lost (it would have been persisted to `GM_setValue` only on click). The next session loads the previously persisted state. No partial state — `save` is atomic.
- **Tab leader lost (`gbTabLeader === false`, `core.js:11`).** The editor is local UI; it does not need the tab leader. Reading `state.napPlayers` / `state.napAlliances` is local. No `flash('GrepBot está activo en otra pestaña')` guard is needed (the guard is reserved for post paths; the editor writes only to `GM_setValue`).

## 10. Out of scope

- **Live diplomatic state from the game.** Grepolis exposes `AllianceDiplomacyRelation` / `MEMBER_PROFILE` collections in the modern client; the bridge endpoint is **not** known to this plan and would need a `gbAjaxWatch(sig, settle)` sniff + `TPL_FEATURE_MAP` entry. v4.4 ships the player-managed store. A future plan 7.5b can read the game-side state and reconcile, but **must not** invent the endpoint — the work item is "sniff via `gbAjaxWatch` while a player alliance page is open, capture the template into `TPL_FEATURE_MAP`", not a payload guess.
- **Map-canvas tinting.** The map is canvas. Plan 27 §0 forbids canvas/WebGL fingerprint noise (WebExtension privileges). Sibling 6.7 §10 closed the same path. 7.5 ships the panel dossier overlay only.
- **NAP / war auto-detection from incoming attacks.** `intelWatchlistScan` (`intel.js:186-205`) already fires `alertWebhook('attack', …)` on watchlist hits; that path could in principle auto-set a player to `war` after N hits. That is a separate plan (an "auto-detect" feature) and is **not** in 7.5 — auto-mutation of player-managed state would violate CLAUDE.md "HIGH-RISK toggles default OFF" and would belong in a CONFIRM-gated feature, not in a Low/M read-mostly plan.
- **Player-vs-alliance reconciliation.** Setting a player to `nap` while their alliance is `war` is a conflict the user can resolve manually. v4.4 does not auto-resolve; the strength order (player > alliance) is the only rule.
- **Export/import of diplomatic status.** `qolExportConfig` (`qol.js:248-253`) and `qolImportConfig` (`qol.js:254-268`) do not carry `state.napPlayers` / `state.napAlliances`. Diplo status is per-player knowledge, not a config preset. If a future plan wants to export it, it belongs in a separate "Intelligence transfer" plan.
- **Mobile / touch editor.** The Intel tab editor is mouse-driven (same as the existing note rows). Touch support is whatever the browser provides for native `<select>` + `<input>`.
- **Bulk-set from a treaty page.** A "click a list of N players and set them all to `nap`" UI is a future UX plan. v4.4 ships one-player / one-alliance at a time.
