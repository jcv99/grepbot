> `box.textContent = html` discipline (`src/intel.js:112`). Same
> justification as plan 6.12 §3.1: there is no `<svg>`, `<canvas>`,

## 1. What exists today

- `intelDossiers()` (`src/intel.js:34-71`) is the only per-player
  aggregator in the tree. It walks `state.findings`, picks the
  "other side" via `intelActorIsMe`, and groups by `intelPlayerKey`.
  It reads `f.alliance` (string) on each finding at
  `intel.js:66-67` for `state.allianceNotes[alliance]` lookup. **It
  does not aggregate by alliance** — there is no `byAlliance` reducer.
- `intelPatternScan()` (`src/intel.js:206-245`) aggregates by **player**
  over a 24h window (`windowMs = 24 * 3600000` at `intel.js:208`). The
  same shape can be lifted to alliance-level with no new state.
- `intelSetAllianceNote(alliance, note)` (`src/intel.js:124-132`) exists
  and is wired at `src/ui.js:1002-1007`. Plan 26 §B2 named a missing
  setter; it was added between plan-of-record v2.9.1 and the current
  v3.8.2 (the row in plan 27 §9 also notes this — it is "Coded").
- `state.findings` (`src/core.js:228`) is the only alliance-indexed
  store. It carries one row per parsed intel report
  (`parseReport` at `src/parse-inline.js:36-86`) with `alliance`
  (`parse-inline.js:89`) — the attacker (or defender, if the attacker
  is me) alliance string. **Cap: 100 entries** (`storagePruneForQuota`
  at `core.js:1188-1190`); the array is FIFO-dropped on quota. There
  is **no `MM` Alliance collection** referenced anywhere in `src/`
  (verified by ripgrep — zero hits for `getCollectionByName('Alliance')`,
  `getAlliances()`, `alliancesCollection`). Alliance keys in this
  codebase are **opaque strings seen in report payloads**, not model
  objects.
- `state.allianceNotes` (`src/core.js:341`) is the player's free-text
  notes per alliance (`intel.js:124-132`). Keys are the same opaque
  strings as `f.alliance`. It is already exported with redaction in
  `qol.js:238`.
- `state.watchlist` (`src/core.js:338`, `intel.js:148-181`) can match
  by `entry.alliance` (`intel.js:171-173`) — the heatmap is the natural
  reader of the same key.
- `renderIntel()` (`src/intel.js:75-114`) writes the intel panel via
  `box.textContent = html` (`intel.js:112`). The same function calls
  `intelPatternScan()` at the end (`intel.js:113`). A new alliance
  block slots in before the existing `state.watchlist` block at
  `intel.js:98-102` without changing the existing order.
- The intel tab HTML (`src/ui.js:693-704`) is a single `<pre
  class="intel-panel">` plus two note-save inputs. The plan adds a
  selector inside that section to choose between two views: existing
  `intel-panel` (default) and the new heatmap view. No structural
  change to the panel chrome.
- `redactNotes` (`src/qol.js:230`) already handles `allianceNotes`
  export redaction (`qol.js:238`). The heatmap is read-only so redaction
  is a non-concern.

## 2. Gap

The catalogue asks for an "alliance intel heatmap". Today the only
alliance-aware read is `state.allianceNotes[f.alliance]` on the dossier
line (`intel.js:66-67`), and the alliance-notes dump at
`intel.js:103-108`. The player-visible question — *"which alliances are
spiking, and against which of my towns?"* — has no aggregated answer in
the panel. The honest deliverable is an ASCII grid keyed by (alliance,
my-town-id) where each cell counts reports in the rolling 7-day window
(the same 7-day window the journal TTL enforces, plan 27 §13).

## 3. Design

Read-only. No post surface, no captcha breaker, no lock, no scheduler
entry. The aggregator runs inside `renderIntel` (`intel.js:75-114`),
mirroring the existing `intelPatternScan()` call (`intel.js:113`).

### 3.1 Aggregator

Add `intelAllianceMatrix(windowMs)` to `src/intel.js`, returning:

```js
{
  alliances: ['<name>', …],         // sorted by total desc
  towns: ['<myTownId>', …],         // sorted by id
  totalForAlliance: { name: n },    // row totals
  totalForTown: { myTownId: n },    // column totals
  cells: { '<name>::<myTownId>': n },
  windowMs, cutoffTs,
}
```

Inputs and rules:

- Walk `state.findings` once. For each finding with a string
  `f.alliance` and a `f.town.id` (the defender's town), pick
  `f.town.id` as the column if the town is **mine**, else pick
  `f.town.id` if the attacker is from `f.alliance` and the defender
  is mine. The "is mine" check reuses the existing `intelActorIsMe`
  helper (`intel.js:28-33`).
- Skip findings older than `windowMs` (default 7d). The same
  `windowMs = 24 * 3600000` shape at `intel.js:208` works — just bump
  the default to `7 * 86400000` for this aggregator only.
- Skip findings where `f.alliance` is `null`, `''`, `'?'`, or otherwise
  not a string of length 1–40. The cap is to keep the row labels
  readable and to drop game-client placeholders.
- Sort alliances by `totalForAlliance[name]` desc, then by name asc.
  Cap at 12 rows in the rendered grid (top-12). Smaller alliances
  collapse into one `(+N alianzas)` footer row with its own total.
- The "my town" list comes from `state.towns` (`src/core.js:229`,
  `src/towns.js:71, 122, 197`) filtered to **towns that appear as
  defender in at least one finding with an alliance-attributed
  attacker** — i.e. only the towns that are actually under intel
  pressure, not every own town. Cap at 8 columns; remainder collapses
  into a `(+M ciudades)` footer column with its own total.

### 3.2 Renderer

In `renderIntel` (`src/intel.js:75-114`), insert before the watchlist
block (`intel.js:98-102`):

```
=== Heatmap de alianzas (7d) ===
              Col1  Col2  Col3  …  +M   total
AllyA           3     1     -    …   1     5
AllyB           -     -     2    …   -     2
…
(+N alianzas)    -     -     -    …   1     1
total           3     1     2    …   2     8
```

Each cell renders one density glyph from ` .,:;|+*#@` keyed off
`cells[name::myTownId]`. Mapping: 0 → ` `, 1 → `.`, 2 → `,`, 3 → `:`,
4 → `;`, 5 → `|`, 6 → `+`, 7 → `*`, 8+ → `#`, 20+ → `@` (the upper
band). The exact binning does not matter; what matters is that the
glyph ordering is monotone. Alliance and town labels are truncated to
the first 12 characters with `…` if longer — same shape as the
existing dossier line at `intel.js:93-97`. All output is concatenated
with `\n` and appended to `html` (the `box.textContent = html`
discipline at `intel.js:112`). **No** `innerHTML`.

### 3.3 View toggle

The Intel tab already has two note inputs and one big `<pre>`. Add one
more control: a `[data-intel="view"]` `<select>` with options
`Resumen` (default, today's behaviour) and `Heatmap 7d`. The selector
goes immediately under the section title (`ui.js:693` `<div
style="font-size:11px;color:#f5a623;margin-bottom:4px">Intel /
amenazas</div>`). The renderer checks `state.intelView` (a new field,
**session-local**, see §5) and emits either the existing dump
(`intel.js:83-111`) or the new heatmap block. Switching the selector
calls `renderIntel()` — same call site as the existing watchlist
refresh at `ui.js:1002`.

`state.intelView` is **session-local** (a plain `let intelView = …` in
`intel.js` next to `let questMo = null` at `intel.js:249`). It does
**not** persist. Justification: it is a UI mode, not a configuration;
persisting it would force a `configVer` bump and a new `STORE.*` key
for no observable benefit across reloads. The selector's default is
always the existing dump.

### 3.4 Existing watchlist + notes

The existing watchlist match (`intel.js:171-173`) already keys by
`entry.alliance`. The heatmap surfaces the **same** string, so the two
features compose: a user who adds an alliance to `state.watchlist` as
`{alliance: 'AllyA'}` will see the `AllyA` row of the heatmap light up
in real time (next `renderIntel` cycle). The existing pattern-scan
webhook at `intel.js:241-242` continues to fire on the player-level
threshold (`n >= 3`); the heatmap adds nothing new there.

## 7. Post surface & safety

No post surface. No `bridgePost`, no `gameAjaxPost`, no `gbDomClick`,
no `gbAjaxWatch`, no `gbLock`, no `GB_LOCK_TTL` entry, no
`gbCaptchaPause` key. The aggregator reads only.

The renderer uses `box.textContent = html` (the same call as today at
`intel.js:112`). The selector uses `createElement('option')` +
`appendChild`. Audit-I15 XSS discipline (plan 26): zero `innerHTML`
where a player-controlled string is rendered. The alliance name is
player-controlled (it comes from `f.alliance`, which is parsed from
report JSON by `parse-inline.js:89`). The label truncation to 12
characters (§3.2) is a defense-in-depth; the primary defense is
`textContent`, which never parses the string as markup.

## 8. Failure modes

- **`state.findings` empty** — every row/column total is 0; the heatmap
  renders the header + one `0 totales` line. No `null`s, no crashes.
- **`f.alliance` missing on most findings** — many cells render ` `,
  the row totals are 0; the `+N alianzas` footer row collapses the
  empty ones. The block is still rendered so the user sees "no signal".
- **Top-12 / Top-8 caps clip the user's most-interesting alliance** —
  the footer shows `(+N alianzas)` and a total so the user can spot
  the cutoff. The default cap is generous (12 rows × 8 columns = 96
  cells); a future plan can lift the cap if `state.findings` grows
  past 100 entries.
- **Quota prune drops the oldest findings** — `storagePruneForQuota`
  (`core.js:1188-1190`) caps `state.findings` at 100 FIFO entries.
  The 7-day window in the heatmap header can be a lie if the user's
  reports are old enough that the cap clipped more than 7 days.
  Mitigation: include `cutoffTs` in the block header (`ventana
  2026-08-03 → 2026-08-10, N=87 informes`); if `cutoffTs > 7d ago` and
  the count is at the cap, warn "findings al limite de quota: el
  historial de 7d puede estar incompleto". One line; no separate
  probe.
- **Alliance string drift across parses** — `f.alliance` is a raw
  string from report JSON (`parse-inline.js:89`). Two clients could
  spell the same alliance differently ("AllyA" vs "Ally A"); the
  heatmap would render them as separate rows. This is the existing
  dossier-line behavior (`intel.js:66-67`) — fixing it is a
  string-normalization plan, not this one. Documented.
- **`intelView` survives a reload** — explicitly does **not** survive
  reload (§3.3, §5). The selector defaults to `Resumen` on every page
  load. Documented in the selector's `title` attribute ("se reinicia
  al recargar").

## 9. Validation gate

Manual, per plan 27 §11 Low class (Preflight + one in-game session, no
failure).

- Build (`python3 build.py`), install, open the Intel tab. The
  selector shows `Resumen` (default) and `Heatmap 7d`.
- With `state.findings` empty (fresh world, no reports parsed): the
  heatmap emits one line `sin informes en 7d` and exits cleanly.
- After parsing 3 reports spanning 2 alliances and 2 of my towns: the
  heatmap renders a 2 × 2 grid with one density glyph per cell and
  matching row/column totals.
- Add `state.allianceNotes = { 'AllyA': 'spike' }` via the existing
  alliance-note UI (`ui.js:1002`); reopen the heatmap — the
  `AllyA` row gains the note ` — spike` after the alliance name. The
  truncation rule (12 chars + `…`) applies only to the matrix label,
  not to the note.
- Add a watchlist entry `{alliance: 'AllyA'}` and reload — the
  `AllyA` row still renders in the heatmap, the existing watchlist
  block at `intel.js:98-102` still matches on the next report.
- Preflight (`Comprobar sistema`) — new `intel alliance matrix` row
  appears; passes when `state.findings.length > 0`, warns when the
  matrix renders but every cell is zero.
- `state.dryRun = true` — heatmap still renders; no new posts in the
  Log tab. Confirm by reading the journal (Decisions sub-view, `mem`).

## 10. Out of scope

- **Alliance-member activity.** Cross-ref plan 27 §7.6 ("Alliance
  member activity dashboard"). Its data layer is `MM.getCollection
  ('Alliance')`/`Player`-by-alliance, which is **not** read today.
  Adding that would require the missing `Alliance` collection probe;
  out of scope here.
- **Alliance resource pool.** Cross-ref plan 27 §7.3. Same shape —
  needs an `Alliance` model read path; out of scope here.
- **NAP / war tracking.** Cross-ref plan 27 §7.5. The heatmap is the
  *passive observation* view; a `NAP` toggle would be a separate
  state field. The heatmap surfaces what is in `state.findings`; it
  does not infer relationships.
- **Per-day bucketing in the heatmap.** The current design shows the
  *total* across the window. A future plan can break it into 7 daily
  columns (one per day) at the cost of column count and density —
  not worth the read-path complexity yet.
- **Mermaid / SVG / pixel rendering.** Rejected by §3.2. Same
  justification as 6.12.
- **Cross-alliance attack-pattern detection.** `intelPatternScan`
  (`intel.js:206-245`) already runs a player-level pattern scan and
  fires the `pattern` webhook (`intel.js:241-242`). Lifting that to
  alliance-level is a separate plan; the heatmap is the read-side
  companion, not a writer.
- **Auto-export of the matrix.** Out of plan 27 §0. Webhooks are for
  events; bulk data dumps cross the line.
