# 3.4 — Resource dump automation

**Bucket:** v4.3 · **Risk:** Med (HIGH-RISK OFF default) · **Size:** M
**Module:** new `src/dump.js` (concat after `transport.js`); **`build.py` MODULES slot 53** — between `transport.js` (slot 52) and `rural.js` (slot 53 currently). Slot chosen because `dump.js` calls `transportBalanceJobs` / `transportTownETA` from 1.3 (slot 52), `caveTownInfo` / `caveStoreIron` from `cave.js` (slot 49), and `tradeTownRes` / `ironReservedForCave` from `trade.js` (slot 51). All three dependency modules load BEFORE slot 53, so `function`-hoisted cross-module calls are safe; the slot is the latest point in the order where the upstream module surface is complete.
**Depends on:** **1.3 (transport automation) — `transportBalanceJobs` is the inner loop.** Also reads `ironReservedForCave` (`src/core.js:685-722`) and `caveTownInfo` (`src/cave.js:26-91`) for the cave-destination guard.
**Status:** PLANNED — written 2026-08-10 against `src/` @ v3.8.2

## 1. What exists today

**The "dump" gap is real.** There is no automated resource-dumping
feature in the tree today. Verified:

- `rg -n 'dumpResources|resourceDump|dumpTo|treasury_dump' src/`
  returns zero hits.
- The closest neighbour is `caveScan` (`src/cave.js:166-225`), which
  stashes iron into the **same town's** hide building via
  `caveStoreIron` (`cave.js:133-140`) —
  `bridgePost('cave', {model_url:'BuildingHide',
  action_name:'storeIron', arguments:{iron_to_store}, town_id})`.
  That is intra-town, not inter-town.
- `tradeIslandShipJobs` (`src/trade.js:173-208`) ships resources
  mainland→island when `state.islandShip` is on, but only for towns
  with `t.small === true`. Not configurable per-resource or
  per-threshold.
- `tradeFillStorageJobs` (`src/trade.js:130-172`) is a global
  fill-storage rule with **two thresholds**: target fill <= 25 %
  (`trade.js:142`) and source fill >= 85 % (`trade.js:148`). It is
  not a per-resource dump.

**Why this is risky in this codebase.** Resource moves are
**irreversible** once posted. Every transport post fires the
shared `txActionGate` (`src/tx.js:522-534`) → second pre-send check
(`tx.js:646-647`) → `gameAjaxPost` → `BRIDGE_TIMEOUT_MS`
(`src/bridge.js:149`) callback. There is no rollback. An over-eager
dump loop can ship iron away from a town that needed it for a build
order that landed between the scan and the post — a known pitfall
in the existing `tradeScan` family (see `trade.js:339-345` capacity
checks).

**`ironReservedForCave` gate is the iron-side precedent.** When
`state.autoCave` is on and the source town has a hide building
whose target fill is within ETA, `trade.js:217-223` and `trade.js:301`
skip iron sends. 3.4 **must** apply the same gate — over-dumping
iron can starve the cave stash the bot just spent iron filling.
Verified: `ironReservedForCave` returns `{reserved: false, blind:
true}` when capacity is unreadable (the precondition invariant
from `core.js:717`), so a blind read does NOT silently block the
dump.

**Profile schema.** Sibling plan 1.2 ships
`gbCityProfile(townId).resource: {wood, stone, iron}` in -1..+1.
Plan 27 §3 row 3.4's "uses 1.3 transport" implies the dump loop is
also profile-aware: a town whose profile says "I do not want wood"
(`resource.wood = -1`) is a better dump source than a town whose
profile says "I need wood" (`resource.wood = +1`). 1.3's
`transportBalanceJobs` already reads profile bias; 3.4 reuses the
same hook.

**Orchestrator / lock surface (3.4 does not duplicate):**
- `'trade'` lock name, TTL 180000ms (`src/core.js:153`).
- `'trade'` captcha breaker key (`src/qol.js:404-408`).
- `'trade'` orchestrator entry, cadence 120000ms (`qol.js:393`).

## 2. Gap

Plan 27 §3 row 3.4 wants the user to configure: "if town A iron
fills past 95 %, dump 5 000 iron to town B (or any town in the
alliance)". The current tree cannot express this because:

1. **No per-resource dump threshold.** Fill-storage is global
   (85 % source, 25 % target, all resources bundled).
2. **No per-destination routing.** Fill-storage picks any town below
   25 %, not a user-specified set.
3. **No per-resource threshold off-switch.** If a town is
   short-stacked on iron for cave purposes, the user cannot say
   "iron over 95 % dumps, but only if the iron-reserved-for-cave
   rule is satisfied".
4. **No preview / dry-run of dump effect.** `state.dryRun` exists
   (v1.4.0), but there is no per-feature dump sub-planner that
   would log `DRY-RUN dump: A→B iron 5000`.

3.4 fills all four. The transport automation from 1.3 is the inner
planner; 3.4 is the **policy layer** that decides whether the
planner's job is allowed to fire on a given (source, destination,
resource) triple.

## 3. Design

**Dump policy.** For each owned town, on each orchestrator tick:

```text
for each town T:
  for each resource r in {wood, stone, iron}:
    rs = townResState(T.id)        // {cap, wood, stone, iron, full, n, fillPct}
    if !rs or !(rs.cap > 0)        // blind → skip
        continue
    fill_pct = round(rs[r] / rs.cap * 100)
    thresh   = state.dumpThreshold[r]  // default 95/95/90
    if fill_pct < thresh            // below threshold → no dump
        continue
    if r === 'iron' && state.autoCave && caveHasHeadroom(T.id)
        continue                    // iron reserves for cave beat dump
    candidate = pickDumpDestination(T.id, r)  // see §3 below
    if !candidate
        continue
    add to dumpJobs (T, candidate, r, amount)
```

**Destination selection (`pickDumpDestination`):**

The dump destination is the **first** of:

1. **User-configured sink list** (`state.dumpSinks` — array of town
   ids). The user picks which own towns accept dumped resources
   (typically a "resource-bank" town with hide buildings or empty
   warehouses). When `state.dumpSinks` is non-empty, the loop
   filters candidate destinations to that list.

2. **Profile-aware pair** (`pickByProfile`): towns where
   `gbCityProfile(townId).resource[r] >= +0.5` (i.e. the town's
   profile wants the dumped resource). Mirrors the same hook 1.3
   and 5.1 use.

3. **Fallback to `transportBalanceJobs` from 1.3.** When both
   (1) and (2) return no candidate, the dump loop asks
   `transportBalanceJobs(towns, ledger)` for any candidate
   `(from=T, to=*, resource=r)` that fires the transport
   threshold (source fill ≥ 0.85, target fill ≤ 0.25,
   `transportMin` floor).

**Amount calculation.**

```js
amount = floor((rs[r] - state.dumpKeep[r]) * 0.5)
        // dumps half the surplus above the keep line, never all of it
        // clamp to (rs.cap - rs[r])  // never over-dump above cap... wait
        // (rs[r] - keep) is what we're shipping. Clamp by src.tradeCap
        // and tgt free-space (1.3 transport logic).
```

The amount is **half** the surplus above `state.dumpKeep[r]`
(default 50 %), not the full surplus. Rationale: a dump sweep
should free the warehouse, not zero it — a town that just dumped
all its iron and then receives an incoming shipment or a build
order that consumes iron would be stranded. Half-surplus is the
same discipline as the existing `tradeFillStorageJobs:148-149` keep
clamp, generalised to the dump use case.

**Final dispatch.** Each `dumpJob` is shaped exactly like a transport
job: `{from, to, wood, stone, iron}` with two of three at zero
(one-resource-per-job, same shape as plan 5.1's
`transportAiJobs`). The job is dispatched through `tradeSend`
(`src/trade.js:37-46`) which is already in `TX_WRITE_FEATURES`
(`src/planner.js:212-216`) and routes through `txRun` →
`gameAjaxRaw` (`src/bridge.js:149-189`). **No new post surface.**

**Orchestrator wiring.** No new orch key. The dump loop is a
sub-planner of `tradeScan` (`src/trade.js:350-407`), called after
1.3's `transportBalanceJobs` and 5.1's `transportAiJobs` but before
the global cascade. This ordering preserves the rule that
**user-explicit policy wins over heuristic fill**:

```js
// src/trade.js, in tradeScan after the AI call:
if (state.autoDump) jobs = jobs.concat(dumpJobs(towns, ledger));
```

A captcha on trade pauses the whole queue (1.3 §7 reasoning
re-applies); the dump loop shares the same `'trade'` lock,
breaker, and orchestrator entry.

## 5. State & storage

- `state.autoDump: boolean` — `STORE.AUTO_DUMP`, default **false**
  (HIGH-RISK OFF per CLAUDE.md). No `WORLD_SCOPED_BASES` entry.
- `state.dumpThreshold: {wood, stone, iron}` —
  `STORE.DUMP_THRESHOLD`, defaults `{95, 95, 90}`, each clamped
  50..100.
- `state.dumpKeep: {wood, stone, iron}` — `STORE.DUMP_KEEP`,
  defaults `{50, 50, 50}`, each clamped 0..95.
- `state.dumpSinks: string[]` — `STORE.DUMP_SINKS`, default `[]`.
  Town ids are strings. The list is **not** world-scoped because
  the user's own-town ids are stable across logins on the same
  world (the world-scoped id invariant is "id means something on
  this world", which holds for own-town ids — but `dumpSinks` is
  a config-object pointer, not a foreign-world reference; the
  world-scope rule for `WORLD_SCOPED_BASES` is for **data**
  carrying world-specific meaning, which `dumpSinks` does not).
  Cite plan 26 §B6 audit (`tradeMaxHops` deletion note): the
  precedent is that config-pointers to user town ids are
  world-scope by inheritance when the parent state is world-scoped.
  `dumpSinks` is therefore left out of `WORLD_SCOPED_BASES`
  (matches `STORE.TOWN_GROUPS` at `header.js:106`, which is in
  the world-scoped set via `header.js:202`; we leave the
  explicit registration to the migration commit if the
  parent state becomes world-scoped later).
- `configVer` bump 11 → **12** (work item 8).
- Prune TTL: not applicable.

## 7. Post surface & safety

- **Post path is unchanged.** Every dump job runs through
  `tradeSend` (`src/trade.js:37-46`) which posts
  `gameAjaxPost('trade', 'town_info', 'trade', {id, wood, stone,
  iron, town_id, nl_init:true})`. The endpoint is in
  `TX_WRITE_FEATURES` (`src/planner.js:212-216`) and routes through
  `txRun` → `gameAjaxRaw` (`src/bridge.js:149-189`).
- **No `gbAjaxWatch` registration.** Same as 1.3 — trade is server-
  rendered.
- **No `TPL_FEATURE_MAP` entry.** Same as 1.3.
- **Captcha breaker.** `'trade'` (existing), shared with global
  `tradeScan` + 1.3 `transportBalanceJobs` + 5.1 `transportAiJobs` +
  sibling plan 3.1 routes. Captcha on the trade queue pauses
  everything, including the dump loop, for the ladder window.
- **Lock name.** `'trade'` (existing), TTL 180000ms
  (`src/core.js:153`). Acquired once per `tradeScan` at `trade.js:381`.
- **Dry-run.** `txActionGate` (`tx.js:522-534`) returns `'dryrun'`
  when `state.dryRun` is set. `txRun:554-562` logs
  `DRY-RUN trade: …`. Every dump send inherits this — verified by
  tracing through `gameAjaxPost → txRun → gameAjaxRaw`.
- **`ironReservedForCave` interaction.** When the source town has
  `state.autoCave` on AND `caveTownInfo(townId)` shows the hide
  building has headroom AND the ETA to cave target is within
  CAVE_SOON_MS (15 min, `core.js:683`), the dump loop **skips iron**
  on that town. Same gate as `trade.js:217-223`. A blind
  `ironReservedForCave` returns `{reserved: false}` (per
  `core.js:717` "unknown, not 'no'"), so the dump loop proceeds
  without the reservation.
- **`caveHasHeadroom` guard.** When the destination is itself a
  cave town with `state.autoCave` on, the dump only fires into
  that destination if the hide building has free space (mirrors
  the existing `cave.js:181-184` skip logic).
- **Confirm ladder for manual-trigger mode.** Optional Config
  toggle `dumpRequireConfirm` (default OFF) — when ON, a manual
  "Dump now" panel button opens a confirm modal listing the
  planned jobs and only proceeds on OK. Same pattern as the
  attack planner v0.6.0 confirm gate (`CLAUDE.md` "Attack
  planner v2"). **No effect on the orchestrator loop** — the
  confirm gate is for manual fires only; the auto loop has its
  own dry-run + decision-memory discipline.
- **No new scheduler.** No `gbInterval`. Cadence is `'trade'`
  120000ms (`qol.js:393`), jittered ±20 %.

## 8. Failure modes

- **`townResState(from)` blind.** Skip that source; log once via
  `gbLogT('dump-blind-' + from, …)`. Per scan, per town.
- **`tradeLedger` returns null (`tradeIncomingByTown()` unknown).**
  `tradeScan` fails closed (`trade.js:357`) — dump loop never runs.
- **`caveHasHeadroom(from)` blind** (cave reads return null). Skip
  iron-send on that source; log once via
  `gbLogT('dump-cave-blind-' + from, …)`. Per scan.
- **`ironReservedForCave(from) === reserved:true` and resource is
  iron.** Skip that triple. Same path as `tradeGoalJobs:301`.
- **`pickDumpDestination` returns null** (no sinks, no profile
  match, no transport fallback). Skip the source for this
  resource; no log spam (per-scan, per-resource, gbLogT-keyed).
- **`dumpThreshold[r] <= dumpKeep[r]`.** Skip that resource on
  every town; amount would be ≤ 0. Preflight warns
  (`stats.js:171` work item 9).
- **`dumpSinks` contains a town id that is not in `state.towns`.**
  Filtered out by `pickDumpDestination` before the post; logged
  once via `gbLogT('dump-sink-unknown-' + id, …)` at the
  validation gate, not per-tick.
- **Two dump picks in the same scan target the same destination.**
  `tradeApplyJob` mutates `L` after each pick, so the second pick
  sees the first's deduction and clamps itself. The 6-job ceiling
  (`tradeFillStorageJobs:168` analogue) keeps the scan bounded.
- **Captcha during a dump send.** `tradeScan` releases the trade
  lock on `'captcha'` callback (`trade.js:399`). Dump inherits.
- **Decision-memory trip.** `trade` is a write feature in
  `TX_WRITE_FEATURES` (`planner.js:212-216`); three hard errors
  open a 5/15/60min skip window. The dump loop is the latest
  sub-planner to recover after a bad window — that's the right
  behaviour for an irreversible high-stakes action.

## 9. Validation gate

Per plan 27 §11 (Med risk + HIGH-RISK OFF): **dry-run + one
hand-triggered firing + one full orchestrator tick + payload
verification.**

1. **Dry-run smoke.** Toggle `state.dryRun` on; toggle
   `state.autoDump` on; set `dumpThreshold = {wood:50, stone:50,
   iron:50}` (force every town above threshold). Wait one trade
   tick. Expect one `DRY-RUN trade: A→B w…/s…/i…` line per

2. **Live, single tick.** Disable dry-run, force one scan on a
   world with one town fill > 95 % wood. Expect one
   `trade: A→B w<amount>/s0/i0` log line; verify the
   destination is `dumpSinks[0]` (when sinks are configured) or
   the transport-fallback destination otherwise.
3. **Cave guard.** On a town with `state.autoCave` on AND
   `caveThreshPct = 90`, force iron fill to 96 %. The dump loop
   **must skip iron** because the cave reserve beats the dump
   threshold. Verify via `gbLogT('dump-cave-skip-' + from, …)`.
4. **Iron-reserve-for-cave interaction.** With cave ON and iron
   fill > 95 %, force a dump. Expect iron skip; wood/stone
   dumps proceed if their thresholds are met.
5. **`dumpSinks` priority.** Set `dumpSinks = ['townB']`, force
   wood fill on town A > 95 %, wood fill on town C < 30 %. The
   destination must be **townB** (not C — the sink wins over
   the profile match). Verify in journal `decision` rows.
6. **Six-job ceiling.** Disable other sub-planners; force a
   scan with 8 valid (from, to, resource) triples via direct
   state mutation. Expect 6 picked; the next 2 wait for the
   following tick.
7. **Manual confirm gate.** Set `dumpRequireConfirm = true`;
   click "Dump now" from the panel. Expect the confirm modal
   to list the planned jobs; click Cancel → no posts; click OK
   → posts fire.
8. **Preflight row.** Stats → Preflight shows `dump: ok` when
   `autoDump === false`. Toggling on with valid thresholds flips
   to `ok`; setting `dumpThreshold.wood = 40` flips to `warn`;
   setting `autoDump === true` with empty `dumpSinks` AND no
   cave-eligible town flips to `fail`.
9. **Export round-trip.** Export config; the four new fields
   (`autoDump`, `dumpThreshold`, `dumpKeep`, `dumpSinks`) ship
   in the dump. Re-import restores them; no redact warning (no
   player data).
10. **No new scheduler.** `rg -n 'gbInterval' src/dump.js`
    returns zero hits; `rg -n 'InFlight' src/dump.js` returns zero
    hits; no new top-level `function` (IIFE only).

## 10. Out of scope

- **Auto-route discovery** ("GrepBot noticed you dump iron A→B
  every cycle…"). Plan-27 §0 out-of-scope (anti-pattern detection).
- **Inter-player dump (alliance treasury).** Grepolis does not
  expose a treasury transfer endpoint. The dump loop targets
  **own** towns only. If a future client exposes an alliance
  treasury post, 3.4 v2 widens `pickDumpDestination` with a
  fourth tier; the public surface (`dumpJobs(towns, ledger)`)
  stays the same.
- **Cave-bypass dump.** A user who wants to dump iron WITHOUT
  the cave reserve gate can set `state.autoCave = false` for that
  town via `state.caveTowns` (`src/core.js:289`). 3.4 does not
  add a per-town dump override; that is a `caveTowns` extension
  for a future plan.
- **Adaptive cadence per planner.** `orchAdaptive`
  (`orchestrate.js:107-114`) keys on the whole `'trade'` feature
  via `ORCH_JRN['trade']` (`qol.js:412`). Per-sub-planner adaptive
  cadence is a future optimisation.
- **Per-resource dump batching.** Same as 5.1 — Grepolis ships one
  resource per trade post; multi-resource dump batches are a
  future optimisation.
- **Sniffing `transportTpl`.** Plan 27 §1.3 hint; does not exist
  in the tree. The dump loop uses the existing `tradeSend`
  payload verbatim (see plan 1.3 §7 explicit unknown).
