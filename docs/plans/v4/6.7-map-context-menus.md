# 6.7 — Context menus on the map (right-click)

**Bucket:** v4.1 · **Risk:** Med · **Size:** M
**Module:** new `src/context-menu.js`; **MODULES** slot in `build.py` is **after `ui.js`, before `boot.js`** (panel data shape + tab visibility assumed already loaded; reads `renderAttack`, `applyAttackTarget`, `sendAttackViaBridge`, `fetchReport` from later modules in the IIFE — those names resolve at runtime, not load time, so a slot between `attack.js` and `boot.js` is safe).
**Depends on:** none

## 1. What exists today

Verified against `src/native-ui.js`, `src/core.js`, `src/boot.js`, `src/attack.js`, `src/spy.js`, `src/intel.js`, `src/header.js`.

- **No right-click handler anywhere in `src/`.** A targeted `rtk grep` for
  `contextmenu|context-menu|onContextMenu|right.click|map\.|map_mini|map_main|popup`
  across `src/` returns zero hits (the only matches are the phrase
  "stacking context" in the `gb-native-qctl` stylesheet, `native-ui.js:543,721`).
  The closest analogue is `nativeUiScan` (`native-ui.js:836-876`) which mounts
  small controls inside server-rendered town windows. It does **not** touch
  the in-game map surface at all.
- **The map surface is canvas, not DOM.** Grepolis renders the world map on a
  `<canvas>` overlay with absolute-positioned info-popup tiles for selected
  towns. Verified by `nativeUiScan` (`native-ui.js:838`) querying
  `.window_content,.gpwindow_content,#unit_order` — town *windows*, never map
  tiles. There is no `data-town-id` attribute on the map and no DOM hit-test
  hook for a tile. The `nativeWindowTownId` walker (`native-ui.js:562-589`)
  reads town ids off `data-town-id`/`data-town_id`/`data-townid` attributes
  on focusable windows — none of those exist on the map.
- **Action entry points the menu would call already exist.**
  `sendAttackViaBridge(target, srcTownId, units, mission, onDone)`
  (`attack.js:502-578`); `applyAttackTarget(t)` (`attack.js:272-284`) which
  is the canonical "set the attack plan target" path; `attackRememberTarget`
  (`attack.js:233-242`); `fetchReport(id, hintUrl)` (`spy.js:266-297`); the
  report-driven `ingestReport` → `parseReport` → `state.findings` flow
  (`parse-inline.js:33-93`); the attack planner tab's `renderAttack`
  (`ui.js:370, 388, 392, 237` — exposed via `__grepbotTest` in `boot.js:237`).
- **`gbDomClick(el, feature)` is the only DOM-click path that respects
  `state.dryRun`** (`core.js:941-951`). Any new DOM side effect from a
  context menu item must route through it or `state.dryRun` silently stops
  covering that path (CLAUDE.md "dry-run (v1.4.0)"; `docs/plans/README.md`
  "Conventions every plan follows" line 130).
- **Game context menus on the map are server-rendered.** Grepolis opens a
  popup when a town is right-clicked on the map (e.g. "Atacar / Espiar /
  Vista"). The popup lives outside the panel tree; `nativeUiScan` excludes
  `#grepbot-panel` (`native-ui.js:838`) but the game's own popup is
  positioned at the click coordinates, not inside any selectable window.
  The plan 27 caveat — "respect game context menus; only override GrepBot
  areas" (plan 27 §6) — applies.
- **Lock registry pattern is the only inflight signal.** `gbLock` / `gbUnlock`
  / `gbLocked` + `GB_LOCK_TTL` entry (`core.js:145-215`). Already used by
  every post path (`attack.js`, `spy.js`, `build-auto.js`, etc.). No new
  `*InFlight` booleans (CLAUDE.md "v1.4.0 lock registry: never reintroduce").
- **Disposal hook is `__grepbotDispose`** (`core.js:114-141`). It tears down
  `gbListenerBag`, the panel, the queue center, every `.gb-native-qctl` and
  `.gb-native-panel`. Any new listener registered with `gbListen`
  (`core.js:56-72`) is dropped on dispose automatically.
- **`TPL_FEATURE_MAP`** (`core.js:778-790`) holds the post surface map for
  the `attack` feature: `attack: 'attackTpl'`. `tplNameFor('attack', payload)`
  (`core.js:795-801`) returns `'attackTpl'` for an `attackTpl`-shaped
  payload and `null` for hardcoded `buildUp`/research posts. A new
  `attack-via-context` feature key would be a config-only label unless it
  goes through the same `sendAttackViaBridge` — which is the right choice
  (no new template).
- **Plan 27 §9 lists 15 already-shipped ideas.** None cover a map context
  menu. The "Cancel / recall" row points at `military.js + cancelTpl (10.5)`,
  not a right-click surface. 6.7 is genuinely new.

## 2. Gap

The map is the one game surface the bot currently treats as untouchable.
Every GrepBot action that targets a town — attack send, spy, dossier lookup,
note edit, watchlist add, support/recall (the v0.6.0 cancel path) — currently
requires the player to first navigate to the Attack tab, paste a target id,
or open a separate UI. The player has to leave the map to do anything.

A right-click surface on the map that lists the actions GrepBot can do
*for the town under the cursor* would unify that flow. But the map is
canvas + DOM-popup, and the game's own context menu is also a popup — so
the work is not "intercept the click", it is "render our own popup next to
theirs, only on tiles we can identify, only on hosts we own".

The "Med" risk class is correct: the menu is read-mostly and a single
right-click is cheap, but the *target id* must be resolved without guessing
(map tiles carry no `data-town-id`; only the popup that opens on click does,
and the popup's id source is the same canvas hit-test the game itself runs).

## 3. Design

The new `src/context-menu.js` does **not** intercept any game DOM event.
It runs a 750ms self-rescheduling `gbTimeout` chain (mirrors the 8.2
snapshot pattern — README Hard rule #4 forbids new `gbInterval` /
`setInterval`; only `gbTimeout`/`setTimeout` chains are allowed for new
per-feature polling) that polls `document.body` for the game's own
town-info popup (which is the only piece of map UI that DOM-renders a
town id) and mounts a sibling GrepBot menu next to it. The menu items are
pure links into existing entry points — nothing new gets posted without
going through `sendAttackViaBridge` / `fetchReport` /
`applyAttackTarget` / `intelSetNote` etc.

```
game town popup (canvas + DOM popup, id in popup body)
       │
       │  750ms poll
       ▼
contextMenuScan()
  ├─ find popup by class match (server-rendered, not under #grepbot-panel)
  ├─ read town id from popup's data-id / .town_id / href fragments
  ├─ if popup missing  OR  popup still on the same town as last scan  → return
  └─ otherwise: dispose old menu, build a new one at popup position
                items:
                  • Atacar (engages attack planner: applyAttackTarget + flash)
                  • Espiar (opens a report-fetch for this town)
                  • Añadir a lista de vigilancia
                  • Nota jugador (prompt) → intelSetNote
                  • Nota alianza (prompt) → intelSetAllianceNote
                  • Abrir pestaña Ataque
```

**Hit-test (the decision that decides ours vs. theirs):**

- A GrepBot menu only renders when a *game-rendered* town-info popup is
  present in `document.body` and its tree is **not** a descendant of
  `#grepbot-panel` (mirrors `nativeUiScan:838`). The popup is identified
  by a class match: the standard Grepolis info popup carries
  `.ui-dialog-content` or `.town_name` + a `[data-townid]` (or
  `[data-town-id]`) attribute on the title bar; a class match **or** the
  data-attribute match qualifies. If neither is present, we do nothing.
- A second scan: the popup's anchor in the topmost 1/4 of the viewport
  means the player is mid-click; render the menu. The game's own popup
  continues to be the click target for the GAME's items — we never call
  `e.preventDefault()` on anything. The GrepBot menu is a SIBLING
  `<div class="gb-ctx-menu">` positioned with `style.left/top` matching
  the popup's bounding rect (offset +12px right, +0px down so the menus
  do not overlap the cursor).
- A *defensive* hit-test runs once on mount and every 750ms:
  `document.elementFromPoint(rect.left + 4, rect.top + 4)` MUST be the
  GrepBot menu's first item (the same pattern `nativeQctlHitCheck` uses
  at `native-ui.js:724-734`). If not, `gbLogT('ctx-covered', 300000, …)`
  once and abort. This is the same "stacking context buried us" trap
  `nativeQctlHitCheck` was written to catch (comment at
  `native-ui.js:721-723`). The hit-test fires only while the menu is
  mounted; the chain re-arms the next `gbTimeout(contextMenuScan, 750)`
  only when the previous scan settled, so the chain self-throttles under
  a slow `elementFromPoint`.
- The menu is removed in two cases: (a) the scan finds no game popup, or
  (b) the scan finds a popup for a different town id (menu was stale,
  town changed). Both cases call `contextMenuDispose()` which removes
  the menu, removes its `document`-level click-outside listener
  (registered via `gbListen` so it is dropped on dispose), and clears
  the menu's `dataset.grepbotOn` so the next scan does not double-render.

**The "Atacar" / "Espiar" items route through existing entry points only:**

- Atacar: `applyAttackTarget({ id: <town id>, name: <town name>, x, y, src: 'map' })`
  (`attack.js:272-284`) → which itself only writes to `state.attackPlan` and
  calls `renderAttack`. The actual post is still gated by the
  ATTACK_ROLE_OFFENSE plan, the confirm-gate, and the dry-run path that
  `bridgePost` already provides (CLAUDE.md "Attack planner v2 (v0.6.0)").
  No new template, no new lock, no new post surface.
- Espiar: `fetchReport(id, hintUrl)` (`spy.js:266`) with the town id as
  the report id. The XHR spy (`spy.js:8-112`) will queue the report
  through `parseReport`; the player gets the same flow as a hand-click.
  Already locked by `gbLocked('report-catchup')` when burst-mode is on;
  no new lock entry needed.
- Nota jugador / Nota alianza: `intelSetNote(player, note)` (`intel.js:115-120`)
  and `intelSetAllianceNote(alliance, note)` (`intel.js:124-132`). Setters
  already exist (plan 26 §B2 closed the "no setter" gap).
- Lista de vigilancia: `state.watchlist.push({ id, townId, src: 'map' })`
  plus `save(STORE.WATCHLIST, state.watchlist)`. Read path at
  `watchMatch` (`intel.js:145-185`).

**The menu is a SIBLING, not a parent, of the game popup.** This is the
non-negotiable of plan 27 §6's caveat. We never attach to the popup
itself, never override its `oncontextmenu`, never bubble-cancel any click.
If the game's popup is closed by clicking elsewhere, our menu disposes in
the next scan tick.

post paths:

  Writes `state.attackPlan.targetId/targetType/targetX/targetY` and
  calls `renderAttack`. The actual post (`sendAttackViaBridge` at
  `attack.js:502-578`) is reached only via the Attack tab's
  "Send" button, which still runs the v0.6.0 confirm gate
  (CLAUDE.md "Attack planner v2 (v0.6.0): planner dialog has Copy + **Send

- **Espiar → `fetchReport`** (`spy.js:266-297`): post is `gameAjaxPost`

  not in the table at `core.js:778-790`, so `tplNameFor` returns

## 8. Failure modes

- **Game popup class drifts across client versions.** The
  `contextMenuFindPopup` predicate has two branches (data-attribute,
  class match); if both miss, the menu silently does not render. The
  750ms scan wastes a single `querySelectorAll` (cheap). Symptom
  logged once via `gbLogT('ctx-popup-miss', 600000, …)`.
- **GrepBot menu is covered by a stacking-context ancestor.**
  Hit-test per `nativeQctlHitCheck` (`native-ui.js:724-734`). Symptom
  logged once via `gbLogT('ctx-covered', 300000, …)`. The menu
  remains mounted but a click on it does not reach its handler.
  Defensive: the player can still use the Attack tab.
- **Town id is unreadable from the popup.** `contextMenuFindPopup`
  returns `null`. The menu does not mount. This is the precondition
  invariant: a read that did not return a finite value is unknown,
  the menu does not invent one. `gbLogT('ctx-id-blind', 600000, …)`
  fires once per unknown popup class.
- **Tab leader not held.** `gbTabLeader === false` (`core.js:11, 51-55`):
  every menu action calls a `flash('GrepBot está activo en otra pestaña')`
  guard, mirroring `nativeTownAction` (`native-ui.js:590-592`).
  Inherited from the existing tab-leader contract; the menu does not
  need its own implementation.
- **Stale menu on popup close.** The 750ms scan disposes the menu in
  one tick. Worst-case UX: the menu lingers for 750ms after the
  popup closes; clicking it does nothing because every handler
  re-checks `contextMenuState.townId` against the current popup.
- **SPA navigation re-renders the popup tree.** The scan rebuilds
  the menu from scratch. No `MutationObserver` is needed — the
  750ms poll already covers this (`native-ui.js:555-557` uses the
  same 80ms debounce pattern; we do not need sub-second latency
  for a context menu).
- **Modal window open (report, attack planner, etc.).** The
  game town popup cannot coexist with another full-window
  popup, so the scan returns `null` and the menu does not
  mount. The native queue controls handle the window case
  (`native-ui.js:736+`); no overlap.

## 10. Out of scope

- **Selecting a source town from the map.** The map's "from" side of an
  attack (which of your own cities sends) is not a map right-click
  surface — that is the Attack tab's source selector. Plan 7.1
  (shared attack planner v2) is the right place if a map source-pick
  ever lands.
- **Map tile tinting.** The map is canvas; there is no DOM tile to
  tint, and modifying game canvas bytes is out per plan 27 §0
  ("Shadow-DOM UI hide / variable rename in artifact — would break
  template-sniff contracts"). 6.7 ships right-click only.
- **Touch / long-press context menu.** The Grepolis client is mouse-
  driven; long-press would need a separate gesture path. v4.1 is
  desktop only.
- **Custom user-defined menu items.** The five built-in items are
  the contract for v4.1. A "user item list" belongs in 6.8
  (profile auto-switching) or a future UX feature.
- **Auto-opening the menu on left-click.** The game already
  left-clicks a town to recenter the map; overriding that would
  violate the "respect game context menus" caveat (plan 27 §6).
- **Hotkey trigger (Shift-R to open the menu).** That is 6.3
  (keyboard shortcuts). 6.7 only handles the right-click surface.
