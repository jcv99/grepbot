# 7.3 — Alliance resource pool tracker

**Bucket:** v4.4 · **Risk:** Low · **Size:** M
**Module:** extend `src/intel.js`; **no new module** (plan 27's `alliance-pool.js` hint is wrong for the honest scope — see §1.4)
**Depends on:** plan 03 (`docs/plans/03-alliance-notes-ui.md` — the `intelSetAllianceNote` setter was already added at `src/intel.js:124-132` as the §B2 fix from plan 26, but its UI is owned by plan 03 and we depend on the editor row already living in `src/ui.js:700-704`).
**Status:** PLANNED — written 2026-08-10 against `src/` @ v3.8.2

> Read-mostly per plan 27 §7. The tracker is a per-client aggregation; it
> does **not** reach another player's client and it does **not** auto-post
> to alliance chat. The "alliance resource pool" the bot can show is
> exactly the union of (a) own-towns live stocks, (b) the last-known
> resource lines of towns it has spied, and (c) numbers the user types
> into a self-report editor. No other source exists.

---

## 1. What exists today

- `state.townResources[townId]` (`src/core.js:221` initializer; written
  by `fetchTownResources` at `src/towns.js:155-160`) is the **own-towns**
  resource snapshot. Per-row shape `{ ts, wood, stone, iron, pop, cap,
  ok, action }`. World-scoped via `STORE.TOWN_RES` (`header.js:31`,
  `WORLD_SCOPED_BASES` at `header.js:195`).
- `state.findings[i].resources` and `state.findings[i].town` come from
  `parseReport` (`src/parse-inline.js:39-44, 81-87`) on every ingested
  report (`src/spy.js:248-254`). `resources` carries the last-seen
  wood/stone/iron of the **defender** town; `town` carries
  `{id, name, x, y}`. Capped at 500 by `spy.js:250-253`, then pruned to
  100 by `storagePruneForQuota` (`core.js:1167-1172`).
- `state.findings[i].alliance` (`parse-inline.js:89`) is the **string**
  alliance name attached to attacker/defender — the only alliance
  attribute the bot ever sees.
- `state.allianceNotes` (`core.js:341`, `STORE.ALLIANCE_NOTES` at
  `header.js:131`, in `WORLD_SCOPED_BASES` at `header.js:206`) holds
  per-alliance free text. Read paths at `intel.js:66-67` (dossier
  overlay), `intel.js:103-106` (Intel section dump), `qol.js:238`
  (export redactor). The setter `intelSetAllianceNote`
  (`intel.js:124-132`) was added as plan 26 §B2's fix (the comment at
  `intel.js:121-123` confirms the dead-state history); UI caller at
  `ui.js:1006`, editor row at `ui.js:700-704` (plan 03 wired these).
- **`intelDossiers()`** (`intel.js:34-71`) already aggregates per-player
  findings. The pool tracker uses the same row shape with alliance
  name as the row key.

### 1.4 Module hint disagreement (explicit)

Plan 27 §7 row 7.3 says "new `alliance-pool.js`". That is wrong for
the honest scope of this feature: the tracker is one aggregator + one
renderer inside the existing `intel.js` Intel section (next to
`intelDossiers`, `intelThreatBoard`, `intelPatternScan` — three
siblings that already do the same per-row aggregation). Adding a new
module would require a `build.py:31-72` MODULES slot for ~120 lines
of read-only aggregation logic and one state field. The plan keeps
the feature inside `intel.js`. If a follow-up plan later needs an
*ingestion* path that does justify a module (e.g. scraping the in-game
alliance forum, which plan 27 §0 forbids), that can re-split.

### 1.5 Game model: what is NOT reachable from one client

Verified by ripgrep over `src/` for any alliance-wide accessor:

- **No** `MM.getCollectionByName('Alliance')`,
  `MM.getCollectionByName('AllianceMember')`, `getAlliances()`, or any
  `MM.getModels().Alliance` reference exists (zero hits across all 40
  modules).
- **No** `r.alliance` field other than the per-report alliance *string*
  (`parse-inline.js:89`); a report carries one town's snapshot, not
  the alliance roster.

**Therefore the tracker cannot show real, current resource totals for
alliance members who are not the bot and who have not been spied.**
It shows the union of own-towns + last-seen spied towns + a
user-typed self-report per alliance. Anything beyond that requires
the alliance forum or another player's client — both out of plan
27 §0.

## 2. Gap

A player coordinating an alliance wants one screen that shows where
the bot's own resources sit, what the bot has *seen* in the last
reports (filterable by attacker alliance), and what the user has typed
in as self-report numbers for the rest. `renderIntel` (`intel.js:75-114`)
dumps dossiers, threat board, watchlist, alliance notes, and attack
patterns — it does **not** aggregate resource totals by alliance, and
it does not surface the per-town numbers from `state.townResources`.

## 3. Design

Three inputs, one renderer, no post surface.

### 3.1 Aggregator

Add `intelPoolByAlliance()` to `src/intel.js`, placed next to
`intelDossiers` (`intel.js:34-71`). It returns
`Array<{ alliance, ownTotals, spyTotals, selfTotals, towns }>`:

```js
function intelPoolByAlliance() {
  const et = () => ({ wood: 0, stone: 0, iron: 0 });
  const out = new Map();
  const push = (k) => { let r = out.get(k); if (!r) { r = { alliance: k, ownTotals: et(), spyTotals: et(), selfTotals: et(), towns: 0 }; out.set(k, r); } return r; };
  for (const t of (state.towns || [])) { // (a) own towns — bucket under "__own__"
    const r = state.townResources[t.id];
    if (r && r.ok) { const row = push('__own__'); row.ownTotals.wood += +r.wood || 0; row.ownTotals.stone += +r.stone || 0; row.ownTotals.iron += +r.iron || 0; row.towns++; }
  }
  for (const f of (state.findings || []).slice(0, 200)) { // (b) spy-derived — group by attacker alliance when present
    const a = (f && (f.alliance || (f.attacker && f.attacker.alliance))) || null;
    if (!a) continue;
    const row = push(a); const res = f.resources || {};
    if (res.wood != null) row.spyTotals.wood += +res.wood || 0;
    if (res.stone != null) row.spyTotals.stone += +res.stone || 0;
    if (res.iron != null) row.spyTotals.iron += +res.iron || 0;
    row.towns++;
  }
  for (const k of Object.keys(state.allianceSelfReport || {})) { // (c) self-report
    const row = push(k); const e = state.allianceSelfReport[k] || {};
    row.selfTotals.wood = +e.wood || 0; row.selfTotals.stone = +e.stone || 0; row.selfTotals.iron = +e.iron || 0;
  }
  return Array.from(out.values()).sort((a, b) => a.alliance === '__own__' ? -1 : b.alliance === '__own__' ? 1 : a.alliance.localeCompare(b.alliance));
}
```

All inputs are optional and undefined-safe; no thrown errors. The
200-row cap on `state.findings` mirrors the existing
`intelDefenseBoard` bound at
`docs/plans/v4/7.2-defense-coordination-board.md:177` — defence in
depth, not a quota control (`state.findings` is already capped at 100
by `core.js:1167-1169`).

### 3.2 Renderer

Append a new branch to `renderIntel` (`intel.js:75-114`) gated by a
session-local `intelView === 'pool'` flag (same module-local `let`
that plan 6.13 §3.3 owns — same selector `[data-intel="view"]` that
plan 7.2 §3.4 contributes one option to):

```js
if (intelView === 'pool') {
  const rows = intelPoolByAlliance();
  let html = '=== Pool de recursos por alianza (vista local) ===\n';
  if (!rows.length) html += '(sin datos)\n';
  else for (const r of rows) {
    const lbl = r.alliance === '__own__' ? 'propias' : r.alliance;
    html += `${lbl} (${r.towns} ciudad(es)):` +
      `  propias W${r.ownTotals.wood}/S${r.ownTotals.stone}/I${r.ownTotals.iron}` +
      `  espiadas W${r.spyTotals.wood}/S${r.spyTotals.stone}/I${r.spyTotals.iron}` +
      `  reporte W${r.selfTotals.wood}/S${r.selfTotals.stone}/I${r.selfTotals.iron}\n`;
  }
  box.textContent = html;
  try { intelPatternScan(); } catch (_) {}
  return;
}
```

`box.textContent` is the only safe assignment (alliance strings are
attacker-controlled, audit-I15).

### 3.3 Self-report editor

Append four `<input>` rows + a save button to the Intel section
(`ui.js:692-708`) below the alliance-note editor. Click handler calls
a new `intelSetAllianceSelfReport(alliance, payload)` placed next to
`intelSetAllianceNote` (`intel.js:124-132`):

```js
function intelSetAllianceSelfReport(alliance, payload) {
  const key = String(alliance || '').trim();
  if (!key) return false;
  if (!state.allianceSelfReport || typeof state.allianceSelfReport !== 'object') state.allianceSelfReport = {};
  const clamp = (v) => Math.max(0, Math.floor(+v || 0));
  if (!payload || (payload.wood == null && payload.stone == null && payload.iron == null)) {
    delete state.allianceSelfReport[key];
  } else {
    state.allianceSelfReport[key] = { wood: clamp(payload.wood), stone: clamp(payload.stone), iron: clamp(payload.iron) };
  }
  save(STORE.ALLIANCE_SELF_REPORT, state.allianceSelfReport);
  return true;
}
```

Empty payload deletes the key (mirrors `intelSetAllianceNote`'s
delete-on-empty discipline at `intel.js:128`).

## 5. State & storage

- `state.allianceSelfReport` — `Record<alliance, {wood, stone,
  iron}>` (all integers, ≥0). New key, world-scoped via
  `STORE.ALLIANCE_SELF_REPORT` in `WORLD_SCOPED_BASES` (added in
  §4.5). Default `{}`.
- The session-local `intelView` (plan 6.13 §3.3) gains one extra
  value, `'pool'`. Default `'summary'`. Across reloads the selector
  returns to `Resumen` (same pattern as the existing `statsWindow`
  at `src/military.js:257-258` and the new `'board'` value from
  plan 7.2 §5).
- `configVer` bump 10 → 11 (§4.6) because the schema gains a field.
- No prune TTL needed: the user's own self-report rows should survive
  reloads indefinitely. `core.js:1167-1169` prunes `state.findings`
  to 100; `state.allianceSelfReport` is not subject to that quota.
- No redaction hook needed in `qolRedactConfigDump` (`qol.js:225-247`)
  for this iteration — the self-report is **user-typed**, not a
  player name. Add it to `qol.js` `dump` only if a follow-up plan
  decides to expose alliance-pool data in the export blob.

## 6. Config surface

No new toggle. The pool is gated by the `[data-intel="view"]` selector
(§3.4). The self-report editor is the only new control; it lives next
to the existing alliance-note editor (`ui.js:700-704`) and uses the
same `createElement` discipline.

No HIGH-RISK toggle to set OFF (Low risk; read-only). The tracker
never fires a network request — its only outbound side effect is the
`save(STORE.ALLIANCE_SELF_REPORT, ...)` call, which is local GM
storage, not a post.

## 7. Post surface & safety

**No post surface.** No `bridgePost`, no `gameAjaxPost`, no
`gbDomClick`, no `gbAjaxWatch`, no `gbLock`, no `GB_LOCK_TTL` entry,
no `gbCaptchaPause` key.

The renderer uses `box.textContent = html`. The selector option uses
`createElement('option')` + `appendChild`. Audit-I15 XSS discipline:
zero `innerHTML` for attacker-controlled strings. The
`alliance`/`town.name` strings are attacker-controlled (they come
from `parse-inline.js:89`); `textContent` is the primary defence, the
same as the existing dossier line at `intel.js:96`.

The self-report editor inputs are user-controlled; they pass through
`Math.max(0, Math.floor(+x || 0))` (§3.3) and are written via
`String(...)` coercion in the storage save path. No string is
rendered via `innerHTML`; the read-back path in `intelPoolByAlliance`
only does arithmetic.

## 8. Failure modes

- **`state.townResources` empty**: `ownTotals` is `{0,0,0}`; the
  `propias` row still renders with `0/0/0`. Fresh-install safe.
- **`state.findings` empty**: `spyTotals` is `{0,0,0}`. No nulls, no
  crashes.
- **`state.allianceSelfReport` empty**: `selfTotals` is `{0,0,0}`.
- **Bad input `wood: NaN` etc.**: the `clamp` helper at
  `intelSetAllianceSelfReport` (§3.3) coerces every input on write;
  bad input is silently coerced to `0`. Inputs use `type="number"`.
- **`__own__` collision**: the own-towns bucket uses the literal
  `__own__`, which Grepolis rejects in alliance names (verified by
  inspecting `parse-inline.js:89` alliance fallbacks).
- **Self-report for an unobserved alliance**: row appears with
  `propias 0/0/0`, `espiadas 0/0/0`, `reporte <user-typed>`. Useful
  for "alliance X exists, I want to track totals, I haven't spied
  them yet".
- **`intelView` undefined** (selector not landed per §3.4): branch
  never fires; falls through to existing dump blocks. No crash.
- **`state.findings.length > 200`**: `slice(0, 200)` caps the scan;
  per-finding loop is O(N) on at most 200 rows. Negligible cost.

## 9. Validation gate

Manual, per plan 27 §11 Low class (Preflight + one in-game session,
no failure).

- Build, install, open Intel tab. The `[data-intel="view"]` selector
  shows `Resumen` (default), `Pool 7.3`, and the other views if they
  have landed.
- With `state.towns` populated and at least one own town with
  `townResources[id].ok === true`: the `propias` row shows actual
  wood/stone/iron totals.
- Hand-trigger a spy report whose attacker alliance is known (or
  dev-console-seed `state.findings` with a synthetic entry matching
  `parseReport` schema at `parse-inline.js:39-100`). Open Pool view →
  that alliance gains an `espiadas` row with the defender's
  last-seen `resources`.
- Type `WoodFaction`, `10000`, `5000`, `2000` into the self-report
  inputs, click Guardar → `WoodFaction` row gains
  `reporte W10000/S5000/I2000`. Reload → still there.
- Click Guardar with all three inputs blank → self-report section
  disappears (§3.3 delete branch).
- Preflight → new `alliance pool` row; pass when `ownTowns > 0` or
  `spiedTowns > 0`; warn when both are 0.
- `state.dryRun = true` → pool still renders; no new posts in the
  Log tab; journal `mem:<n>` does not increment.

## 10. Out of scope

- **Alliance-wide resource totals for other members.** Not reachable
  from a single client (see §1.5). A real "alliance pool" would
  require scraping the in-game alliance forum or another player's
  client — both dropped in plan 27 §0.
- **Auto-publishing the pool.** Out of plan 27 §7.1 / §7.4 territory
  (the `alerts.js` Discord-webhook path). The user copies the `<pre>`
  text manually.
- **Cross-alliance auth.** Plan 7.6's member-activity dashboard is
  the companion piece that names the players behind the alliance
  strings; this plan does not name them.
- **Alliance forum scraping.** Explicitly out per plan 27 §0 (no
  `@connect` host beyond `discord.com` / `api.telegram.org` at
  `header.js:16-19`). A self-supplied URL fetch would require an
  `@connect` addition plus a sniff — file as a new plan.
- **Plan 6.13 / 7.2 dependency.** If neither has landed, the
  `[data-intel="view"]` selector does not exist and §3.4 has nothing
  to extend. File this plan as **blocked** and land 6.13 first
  (it owns the selector chrome).
