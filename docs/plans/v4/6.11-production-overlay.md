# 6.11 — Real-time resource production overlay

**Bucket:** v4.1 · **Risk:** Low · **Size:** M
**Module:** extends `ui.js` for the widget body; consumes `culture.js`
`economyProductionRate` + `bridge.js` `townResState` for the data layer. The
plan 27 catalogue says "extend `ui.js`" — correct for the panel/widget shell,
but the **production data lives in `culture.js` and the cached resource state
in `bridge.js`**. Both are already exported and the work item is mostly
wiring, not invention.
**Depends on:** 6.2 (widget system contract)
**Status:** PLANNED — written 2026-08-10 against `src/` @ v3.8.2

## 1. What exists today

The data is already computed, just not surfaced as a real-time overlay:

- `src/bridge.js:235-273` — `townResState(townId)`. Reads
  `t.resources()` for `{wood, stone, iron}`, `t.getStorageCapacity()` for
  cap, returns `{cap, wood, stone, iron, full, n, fillPct}`. **3-second
  memo** (`TOWN_RES_CACHE_MS = 3000`, `bridge.js:234`). Used by 8 modules
  (cave, farms, planner, tx, orchestrate, etc. — `Grep` shows 14 call
  sites). This is the "current" half of the overlay.
- `src/culture.js:211-219` — `economyProductionRate(townId)`. Probes
  `t.getProduction()` first, `t.getResourceProduction()` next, then falls
  back to `t.resources()` reading `wood_production`/`production_wood` and
  friends. Returns `{wood, stone, iron}` per-hour or **null** if no getter
  reads finite. Already exported (`boot.js:176` exposes it on the boot
  surface).
- `src/culture.js:226-232` — `economyForecast(townId, horizonSec)`. Pulls
  `plannerSnapshot(townId)` (the shared warehouse reader at `core.js:687`),
  multiplies production by horizon, subtracts planned demand, returns
  `{projected, overflow, deficit, productionKnown}`. Already used by
  `qol.js:185` for the Overview "AVISO · almacén previsto al límite" line
  and by `qol.js:153` (simulator). The **plan 27 §0 row for 6.11 is "real-
  time production overlay"** — not forecast; we surface the rate directly,
  not the 6h projection, because the rate changes minute-to-minute as
  buildings finish.
- `src/qol.js:185` — Overview "AVISO" text already consumes overflow from
  `economyForecast`, **but** the rate itself (wood/h, stone/h, iron/h) is
  not rendered anywhere in the panel.
- `src/bridge.js:323` — `GB_RES_KEYS = ['wood', 'stone', 'iron']`. Reuse
  this constant rather than re-listing the keys in the widget body.

So the missing piece is **only the visual surface**: a small widget that
shows per-town wood/stone/iron plus the current production rate and the ETA
to cap. Everything else is already there.

## 2. Gap

No user-visible widget shows "this town makes 320 wood/h, 280 stone/h, 250
iron/h, and the warehouse fills in 2h 14m". Players who want this currently
eyeball the game's own building screen, which does not project ETAs to cap
and is hidden behind the Senate panel. The Overview "AVISO" line only fires
when a forecast predicts overflow at horizon (6h by default,
`state.predictCfg.horizonHours`). It does not show the rate live.

## 3. Design

A single widget, mounted via `gbWidget` (plan 6.2). Body renders a header row
"Producción" + a per-town list. The currently selected town is at the top
(driven by `gbCurrentTownId` — same getter the Queue Center uses,
`queue-center.js:336-337`); below it, the other towns in the same row order
the Queue Center tabs use. Each row has six cells:

```
town name | wood cur/rate | stone cur/rate | iron cur/rate | ETA → cap
```

Data flow per refresh tick:

1. Read `townResState(townId)` (`bridge.js:235`) — current stock and cap.
2. Read `economyProductionRate(townId)` (`culture.js:211`) — rate per
   resource, may be null.
3. ETA to cap: `Math.max(0, (cap - current) / rate)` in hours, rendered
   as `h:mm` (1h+ → `2h 14m`, sub-1h → `47m`, capped at `24h+`). Unreadable
   rate or current → render `—`.
4. Patch only the changed cells — same keyed-row pattern the rest of `ui.js`
   uses (`ui.js:92-101` `patchCells` for `tr[data-key]` rows, originally
   added in v1.4.0).

**Refresh cadence**: 1s when widget is open, 0 when closed. The widget owns
its own `gbInterval` (`core.js:23-29`, registered via `gbWidget`'s
`tickMs` option — see 6.2 §3). 1s is the existing cadence of
`gbInterval(renderTimers, 1000)` (`boot.js:66`) so this is not a new
scheduler tier.

**Why 1s will not burn CPU** (cross-ref plan 8.3 profiler):

- `townResState` already memoises for 3s (`bridge.js:234`), so most ticks
  hit the cache and only one Map lookup happens per town. Worst case: N
  towns × 1 cache lookup = `O(N)`. With 10 towns and a cache hit, this is
  trivial.
- `economyProductionRate` is **not** cached today. Cost: 3 method probes
  per town (`getProduction`, `getResourceProduction`, `resources()`). All
  three are model methods on the backbone collection; the game itself calls
  them on every render of the resource bar. At 1s × 10 towns = 30 calls/s,
  this is well below the threshold where the profiler (`stats.js`) flags
  a module. If profiling later shows it does, wrap with a 3s memo mirroring
  `TOWN_RES_CACHE_MS` (out of scope for this plan).
- DOM cost: 6 cells × 10 towns = 60 text nodes per second. Patch only on
  change (`textContent` assignment is cheap when the string is identical
  — the DOM does not reflow). Net: <0.5ms/tick on a modern desktop.
- **Belt-and-braces**: gate the entire render behind a `widget visible`
  check. If the user closes the widget, `gbWidget`'s tick stops firing.

- `Producción: widget visible` — default OFF. Lives under the new
  Config → *Widgets* subsection added by 6.2 step 6. Reads/writes
  `state.widgetGeom['production-overlay'].hidden`.
- `Producción: ETA cap` — select `[1h, 6h, 24h, never]`; default `6h`.

- No HIGH-RISK toggles. No `gbCaptchaPause` key needed.

## 7. Post surface & safety

Read-only. The widget calls `townResState`, `economyProductionRate`, and
reads the DOM. No `bridgePost`, no `gameAjaxPost`, no `gbDomClick`. Skip the
rest of the checklist per the README "Read-mostly features: skip the rest".

## 8. Failure modes

- **`economyProductionRate` returns null** for all towns. The widget must
  not crash; render every rate cell as `—` and the ETA cell as `—`. The
  Overview "AVISO" line in `qol.js:185` already handles this case (it
  reads `productionKnown`), so the pattern is proven.
- **`gbCurrentTownId` unreadable**. The widget falls back to the first town
  id from `Object.keys(gameUw().ITowns.towns)`, same fallback
  `queue-center.js:336-338` uses. No blind post, no crash.
- **Player toggles widget off while it's mid-tick**. `gbWidget`'s `dispose`
  tears down the `gbInterval` via `gbTimerBag` (`core.js:23-29`,
  `core.js:118-121`). No tick survives disposal.
- **N+ towns, 1s tick**. Documented above; the 3s memo on `townResState`
  means we do not re-read the model each tick. If real profiling shows the
  uncached rate probe becomes hot, add a 3s memo to `economyProductionRate`
  in a follow-up (no spec change here).
- **Widget hidden by parent panel collapse**. `gbWidget` mounts at
  `document.body`, so GrepBot panel collapse does not affect it. The user
  can toggle independently.

## 9. Validation gate

Manual, per plan 27 §11 (Low risk). One in-game session on `es146`:

- Toggle `Producción: widget visible` ON. Widget opens at default position;
  rate row appears for every town within 1s.
- Verify a town with full warehouses (`townResState().full.iron === true`)
  shows `iron 0/h` (rate, not current — current is the cap value) and ETA
  `—` (rate exists but current === cap). Log shows no errors.
- Verify a town whose model returns `null` from
  `economyProductionRate` shows `—` in every rate cell. Toggle Config →
  reset widget position, reopen — lands back at default.
- Drag widget to `(400, 300)`, close, reopen. Lands at `(400, 300)`
  (persistence comes from 6.2).
- **Preflight**: `production overlay` row green.
- **Profiler**: with widget open, run `preflightRun` then read the per-
  module CPU row (plan 8.3 — not yet shipped, but `gbLog` already exposes
  module timings via `core.js:516-529`). The overlay module should appear
  under 5ms/tick. If it does not, memo `economyProductionRate` (out of
  scope here, file a follow-up).
