# 8.5 — Replay system (step-through journal)

**Bucket:** v4.1 · **Risk:** Low · **Size:** M
**Module:** extend `src/journal.js` (replay query API) + extend `src/ui.js` (`.jrn-pane` step-through controls + new `renderReplay()`) + minor `src/stats.js` (one-line summary, optional)
**Depends on:** none (plan 27 §8 caveat — 8.6 decision audit trail is **already shipped** in `src/journal.js` v1.1.0; this plan is a **viewer** over that data, not new storage)
**Status:** PLANNED — written 2026-08-10 against `src/` @ v3.8.2

## 1. What exists today

- **Plan 27 §8 row 8.6 explicitly says:** *already in `journal.js` (v1.1.0)*. Plan 27 §9 does not list it among the 15 already-shipped items, but the data backing the replay is fully present:
  - `state.decisions` is a 400-row ring (`JRN_MAX = 400`, `src/bridge.js:446`), 7-day TTL (`JRN_TTL_MS = 7 * 24 * 60 * 60 * 1000`, `src/bridge.js:447`), pruned at `src/journal.js:94-101`.
  - Per-row shape: `{ts, f, a, k, r, n, d?, x?}` — see `src/journal.js:163-165`. World-scoped (`wkey(STORE.DECISIONS)`, `journal.js:112`).
  - **Read APIs already shipped:** `jrnStats(windowMs)` (`src/journal.js:249-293`) for rollups, `jrnCountOk(feature, actionRe, windowMs)` (`src/journal.js:295-304`) for counters, `jrnActiveSkips()` (`src/journal.js:231-236`) for the live skip-windows list. **There is no time-windowed raw-row API** — `renderJournal()` (`src/ui.js:1732-1767`) reads `state.decisions` directly.
- **Decisions sub-view is in the Log tab, not the Stats tab.** Plan 27's hint "extend `stats.js` Decisions sub-view" is half right and half wrong:
  - The **sub-view button** "Decisiones" lives in `.gb-logsub` at `src/ui.js:858`, inside the Log tab (`<section data-tab="log">`, `ui.js:836`). Click handler at `src/ui.js:926-935`.
  - The **body container** is `.jrn-pane` (`src/ui.js:862`) with `.jrn-list` (`src/ui.js:863`) and `.jrn-filter` (`src/ui.js:866`); rendered by `renderJournal()` (`src/ui.js:1732-1767`); last 120 rows, reversed (newest first), filtered by `.jrn-filter` text input (`src/ui.js:1655` debounces the filter via `journalFilterDebounced`).
  - Stats renders **rollups only** via `renderStats()` (`src/stats.js:280-355`); it never iterates individual decisions. The 1h/24h/7d window buttons (`src/ui.js:847-849`) drive `statsWindow` (`src/military.js:258`), not the Log sub-view.
- **Replay semantics already implicit in the journal:**
  - `txId` (`r.x`, set at `src/journal.js:124-144`) reconciles a provisional `timeout`/`pending` result with the terminal one — exactly the "step from provisional to terminal" UX the replay needs. The terminal-row replacement at `src/journal.js:138` is what the replay's *next* button jumps to.
  - Dedup windows (`JRN_DEDUP_MS = 10 * 60 * 1000`, `src/bridge.js:448`) collapse identical decisions inside 10 min — a replay that walks the ring row-by-row will see one *ok* row representing 12 identical successful farm claims in the last 10 min (`r.n = 12`, `src/journal.js:152`). The replay must surface `r.n` so the user understands the collapsed count.
- **Time-window selector already exists in the Stats tab** (`src/ui.js:847-849`), wired to `STATS_WINDOWS = { '1h': 3600000, '24h': 86400000, '7d': 604800000 }` (`src/military.js:257`). The replay needs its **own** selector inside `.jrn-pane` because the Log tab does not share state with the Stats tab.

## 2. Gap

The Decisions sub-view shows the last 120 decisions newest-first, filterable by free-text. There is no way to:

1. **Bound by a time window** (the user has to scroll, and 120 rows at a busy moment is less than 10 minutes of activity).
2. **Step through** one decision at a time — *previous* / *next* over a sorted-by-time walk — so the user can scrub a problematic sequence ("why did farm claims stop at 02:14?").
3. **Highlight provisional→terminal transitions** (the `r.x` reconciliation in `jrnPush` `src/journal.js:117-170`).
4. **Jump to the open skip window** for a row (the `r.f|r.a|r.k` key in `state.decisionSkips` corresponds to a `jrnWhy()` row, `src/journal.js:226-230`).

Plan 27 §8 row 8.5 names this "step-through journal" — the implementation is a viewer over the already-shipped data, no new storage, no new writes, no new post surface.

## 3. Design

Three additions, one optional fourth:

- **Replay query API** (`src/journal.js`). Two new read functions alongside `jrnStats()`:
  - `jrnSlice(opts)` — returns the ring rows that match `{since, until, feature?, actionRe?, keyRe?, result?}`, in chronological order (oldest first), each row carrying `n` so the replay can surface the collapsed count. Backed by the same single-pass loop `jrnStats` already uses (`src/journal.js:256-282`) — copy the pattern, do not refactor `jrnStats`. World-scoping is inherited from `state.decisions` loading (`src/journal.js:48-49`); no new key.
  - `jrnWindowOf(row)` — given a row, returns the corresponding row in `state.decisionSkips` (`src/journal.js:189-201` writes) so the *Why* side panel can render the open skip window if any. Pure lookup, no I/O.
- **Replay UI** (`src/ui.js`). Inside `.jrn-pane`, add:
  - A row of controls **above** the existing `.jrn-list`: a 1h/24h/7d window selector (own copy of the Stats buttons — see §5 for the deduplication note), a *Prev* / *Next* pair, and a *Cursor at: HH:MM:SS* indicator. The cursor is the index into the slice, persisted in `state.replayCursor` while the sub-view is open so flipping tabs does not lose the position.
  - A *Why* side panel to the **right** of `.jrn-list` (or below it on narrow panels — CSS handles the wrap), populated by `jrnWindowOf(currentRow)` plus the row's own `r.d` detail (the hard-error snippet, `src/journal.js:131,143,164`).
  - The replay walks **chronologically** (oldest → newest) — opposite of the existing `.jrn-list` (newest-first). The cursor is the row index; *Prev* decrements, *Next* increments, *End* jumps to the most recent row in the window.
- **Renderer** (`src/ui.js`). New `renderReplay()` function called by the existing `.gb-logsub` button click (`src/ui.js:926-935`) when the active sub-mode is `replay`. The Log tab needs a third sub-mode (`data-logsub="replay"`) — the existing `live`/`mem` pair is hardcoded at `src/ui.js:857-858`; the third button is a one-line addition.
- **Optional stats summary** (`src/stats.js`). A single line added to `renderStats()` before `box.textContent = …` (`stats.js:354`) — `replay: open window N rows, latest row HH:MM:SS` — read from the cursor + slice. This is the only `stats.js` change and it is a courtesy line, not a separate feature; can be dropped without breaking the replay.

Replay semantics: **read-only**. No `bridgePost`, no `gameAjaxPost`, no `state.decisions` writes from the UI. The cursor is a `state.*` field but the replay only reads rows.

## 5. State & storage

- New state: `state.replayCursor` (number, default `0`); `state.replayWindow` (string, default `'1h'`, one of `'1h'`/`'24h'`/`'7d'`); `state.replayOpen` (boolean, default `false`, in-memory only).
- Storage: **none**. The replay cursor is per-session — when the user reloads, they go back to the start of the window. `state.decisions` is already world-scoped (`WORLD_SCOPED_BASES` includes `STORE.DECISIONS`, `src/header.js:209`) and the journal TTL (`JRN_TTL_MS = 7d`) gives the replay its natural outer bound; the in-memory cursor is the only thing that needs to be ephemeral.
- Prune: the replay window selector does not prune the underlying ring — it only filters the read. The existing `JRN_TTL_MS` (7d) and `JRN_MAX` (400) bounds at `src/bridge.js:446-447` apply.
- `configVer` bump: 10 → 11 (header.js:191). Coordinated with 8.3 / 8.4.

## 6. Config surface

- **No new Config toggle.** The replay button is part of the Log tab sub-view (same row as "Registro en vivo" and "Decisiones"). Window selector is inline. No Config checkbox, no `qol.js` registration.
- The 1h/24h/7d selector reuses the Stats tab's window labels but does **not** share `statsWindow` (`src/military.js:258`) — Stats window is the rollup window for `jrnStats()`, the replay window is the read window for `jrnSlice()`. They happen to use the same labels and the same `STATS_WINDOWS` map (`src/military.js:257`); `renderReplay()` reads `STATS_WINDOWS[state.replayWindow]` directly. Two selectors, one source of truth.

## 7. Post surface & safety

Read-only. No `bridgePost` / `gameAjaxPost` / `gbAjaxWatch` / `gbLock` / dry-run. None of the post layer is touched. The replay never writes to `state.decisions` or `state.decisionSkips`; the cursor is the only mutable piece.

## 8. Failure modes

- **Ring is empty** (fresh install, or `jrnClear()` was just called). `jrnSlice()` returns `[]`, the cursor stays at 0, `renderReplay()` shows `(sin decisiones en esta ventana)` (mirroring the empty-state in `renderJournal()` at `src/ui.js:1754`). No crash on `slice[state.replayCursor]`.
- **Cursor out of bounds** (window shrunk under the cursor after a `jrnClear()`). `state.replayCursor` is clamped to `Math.min(cursor, slice.length - 1)` at the top of `renderReplay()`. No throw.
- **World switch mid-replay.** `jrnCheckHost()` (`src/journal.js:39-53`) flushes the old world and reloads the new; the cursor is reset to 0 because `state.replayCursor` is **not** in `WORLD_SCOPED_BASES` and reload wipes it. Acceptable — switching worlds mid-replay is an edge case the user opts into by navigating.
- **Detail string truncation.** `r.d` is already truncated to 80 chars at write time (`src/journal.js:131,143,164`) — no truncation needed in the renderer.
- **`r.x` reconciliation already happened** (the provisional `timeout` row was already replaced by the terminal `ok` row at `src/journal.js:138`). The replay sees only the terminal row, not the provisional one — by design. The *Why* panel calls `jrnWindowOf(row)`; if the skip window already expired, it returns nothing and the panel prints `(sin ventana de memoria abierta)`. No dead guard.
- **Precondition invariant (blind getter).** None — `state.decisions` is the value the replay reads, and it is loaded at `src/core.js:355`. There is no third-party API to probe here.

## 9. Validation gate

Low risk → Preflight + one in-game session, no failure (plan 27 §11).

1. Open Log tab → click *Replay*. The replay pane shows the 1h window selector, *Prev* / *Next* buttons disabled at the start, cursor reads `cursor 0 / N`.
2. With `autoFarm` ON for 5 minutes: at least 1 `ok` row for `farm|claim` appears in the 1h window. *Next* jumps through them; *End* lands on the most recent. The *Why* panel reads `(sin ventana de memoria abierta)` for each `ok` row.
3. Force a hard error: stop the bridge by toggling devtools Network → *Offline* and trigger one `bridgePost`. The replay shows the `err:*` row, the *Why* panel reads the open skip window's `r` + `until`. Restore network; *Next* past the `err:*` row shows the recovered `ok` row (if the feature retries).
4. Switch window to *7d*: the slice grows; cursor remains at its prior index; clicking *End* jumps to the latest. No Log lines.
5. Cross-window: leave the replay pane open, reload the page. Cursor resets to 0 (per-session, §10). The 1h window is preserved by `state.replayWindow` if §10 is changed to persist it later — for now it also resets, which is acceptable.
6. World switch: change `location.host` to another Grepolis world in the same tab (multi-world setup) — `jrnCheckHost()` flushes, the replay pane shows the new world's journal (which may be empty on first switch). No crash.

## 10. Out of scope

- Persisting `state.replayCursor` / `state.replayWindow` across reloads. By design per-session; if users want persistence, add `STORE.REPLAY_CURSOR` + world-scope in a follow-up.
- Stepping through `state.decisionSkips` independently. The skip window is shown as the *Why* side panel; navigating skip windows directly is a separate (and small) feature that belongs to 8.1 circuit-breaker work, not here.
- **Replaying actions** ("re-fire the last 100 farm claims in dry-run"). The replay is a **viewer**, not a replayer. Re-firing would need the original payload, which the journal does not store (`r.a` is the action name, `r.k` is the town/target key, but not the full `arguments`). A re-firing feature would need a separate payload store — that is a different plan.
- Editing `state.decisions` from the replay UI. Even *Delete* / *Mark reviewed* — out. The journal is append-only by design (`src/journal.js:163-165`); mutation belongs in `jrnClear()` (`src/journal.js:242-247`) with a confirm prompt, which already exists.
- Cross-referencing the replay with the **stats-window selector** (a single shared 1h/24h/7d button set across Stats + Log tabs). UX improvement, defer.
- 8.6 decision audit trail is **already shipped** — `src/journal.js` v1.1.0 — and there is no work item for it. The replay reads what 8.6 wrote.
- The optional `stats.js` line in work item 6 is not load-bearing — drop it if the Stats panel gets too dense.
