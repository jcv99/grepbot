# 7.1 — Shared attack planner v2

**Bucket:** v4.4 · **Risk:** Med · **Size:** L
**Module:** extend `planner.js` (state + ingest) + `attack.js` (apply gate) + new `shared-plan.js` for the ingest UI; **no** outbound webhook, **no** server, **no** inbound bot.
**Depends on:** 2.1 spy report parser deep, 6.9 config import/export wizard (JSON paste channel already exists).
**Status:** PLANNED — written 2026-08-10 against `src/` @ v3.8.2

## 1. What exists today

- **Attack plan is local-only.** `state.attackPlan` (`core.js:276`, key
  `STORE.ATTACK_PLAN` in `header.js:58`); schema in `defaultAttackPlan()`
  (`attack.js:204-221`); persisted via `saveAttackPlan()` (`attack.js:230-232`).
  `ensureAttackPlan()` (`attack.js:222-229`) merges defaults, so a missing
  field is recoverable, but the only writer is the Attack tab form
  (`readAttackForm` at `attack.js:959-986`).
- **The v0.6.0 confirm gate is one `confirm()` call.** `fireAttackNow`
  (`attack.js:711-739`) opens the browser confirm at `attack.js:717` and
  refuses to send on cancel. Arming goes through `armAttackWave`
  (`attack.js:611-710`) with no per-target prompt; the only safety
  against an accidental send is that gate. There is no per-target
  confirmation in the arm path — `armAttackWave` fires the bridge post
  when each `gbTimeout` elapses (`attack.js:656-696`).
- **The plan is single-target.** `resolveTarget` (`attack.js:346-392`)
  resolves one `targetId` to either `town` or `farm_town`. Multiple
  source towns ride on the same target (the `rows[]` in
  `buildAttackSchedule`, `attack.js:468-500`). There is no notion of a
  shared alliance plan with N targets across N source towns.
- **No inbound channel exists.** The `@connect` block in
  `src/header.js:16-19` is `grepolis.com` + `discord.com` +
  `discordapp.com` + `api.telegram.org` and nothing else. `alerts.js`
  is fully outbound (`alertWebhook` is the only entry point; verified
  by reading the full 89-line file — it builds a `POST` body and hands
  it to `gbXhr` with `scope:'external'`, never reads anything back).
  Plan 27 §0 explicitly drops "Telegram bot **inbound**" and any
  server. The catalog row text "alliance intake via webhook" therefore
  cannot mean what it sounds like — there is no webhook the bot could
  listen on inside a Tampermonkey userscript.
- **Hook for the planner UI lives in `qol.js:62-95`** (`renderPlanner`,
  `plannerSnapshot`), and the per-town live reserves are already
  factored into `plannerLive`/`plannerSnapshot` (`planner.js:37-81`).
  These do not need to change.
- **The Intel dossier already carries `allianceNote` for ingested
  reports** (`intel.js:66-68`) — read paths exist; the setter was added
  in v3.x to fix the dead-state bug plan 26 §B2 named.

## 2. Gap

The Attack tab can stage one attack at a time from a single account.
Alliance playbooks ("everyone attacks X at HH:MM with the composition
they have available") require *importing* a target list from somewhere
else. Plan 27 §7 resolves this with "ingestion only — no outbound
phone-home" + "Attack planner confirm gate (v0.6.0)". With the
userscript sandbox and CLAUDE.md "no server, paste-only", the only
honest ingestion channel is a **paste-in or user-supplied URL fetch**
of a JSON plan. Everything else is a phone-home or a server.

## 3. Design

Three ingress modes, all client-side. A `shared-plan.js` module hosts
the importer + a per-target confirm overlay.

1. **Paste**: a textarea in the Attack tab accepts a JSON blob copied
   from another GrepBot user (Config → "Exportar plan actual" already
   exists in spirit via `qolExportConfig`, `qol.js:248-253`, though it
   does not yet include `attackPlan`). Schema:
   `{ "v": 1, "targets": [{ "id": "<townId>", "name": "...", "x": N,
   "y": N, "window": { "arriveAt": <unix> | null, "staggerMs": N },
   "intent": "attack|support" }], "author": { "id": "...", "host":
   "<grepolis host>" } }`. Validate per target (see §7) before
   admitting it into `state.attackPlan.targets[]`.
2. **User-supplied URL fetch (opt-in)**: Config field
   `sharedPlanUrl` (default empty). When set and host non-empty, the
   bot performs a **single** `gbXhr({ scope:'external', method:'GET',
   url })`. The host **must** appear in `@connect` in
   `src/header.js:16-19`; a Discord channel-message fetch (`GET
   https://discord.com/api/v9/channels/<id>/messages?...`) requires
   adding `discord.com` paths beyond the webhook endpoint, which the
   current GM_xmlhttpRequest sandbox **does not permit without a
   Bearer token** — so in practice this path only works if the URL is
   a raw paste bin the user controls, and the user must add the host
   to `@connect`. We will not add `@connect` entries speculatively;
   the work item is to add one host per supported paste service at
   the time it is requested, with the host listed in this plan's
   §10 out-of-scope until that is done.
3. **Discord webhook outbound for sharing** (NOT intake): a "Publish
   plan" button writes the current `state.attackPlan` to the existing
   webhook URL via `alertWebhook('shared-plan', payload)` if the
   `state.webhookEvents.sharedPlan` opt-in flag is true. This is the
   only outbound path. It is gated by the same `dryRun` short-circuit
   already in `alerts.js:31-34`.

Per-target apply gate: a target that comes from a shared plan goes
through `resolveTarget` (`attack.js:346-392`) and `attackSendAllowed`
(`attack.js:393-398`) exactly like a manual one, and fires through
the same `sendAttackViaBridge` path (`attack.js:502-578`). The v0.6.0
confirm gate is **per target**, not per plan — every target in the
plan opens its own `confirm()` prompt in the existing
`fireAttackNow` arm path. Auto-arm (`armAttackWave`) is **not**
allowed for shared-plan targets unless the new toggle
`state.sharedPlanAutoArm` is true, and even then only when every
target resolves through `resolveTarget` to `kind:'town'` and is not
an own town (the checks at `attack.js:520-529`).

## 5. State & storage

- `state.attackPlan.targets[]` — array of
  `{ id, name?, x?, y?, intent, arriveAt, staggerMs, src }`. Cap at
  100; over-cap → oldest dropped, log once.
- `state.sharedPlanRecent[]` — last 5 imported plans, world-scoped
  (most alliances play on one world per player).
- `state.sharedPlanUrl` — empty string default.
- `state.sharedPlanAutoArm` — boolean, default **OFF** (HIGH-RISK
  rule: a plan that fires without per-target confirm is high-impact).
- `state.webhookEvents.sharedPlan` — boolean, default false (does not
  opt into publish-by-default).
- Id-bearing ⇒ `WORLD_SCOPED_BASES` entries needed for
  `STORE.SHARED_PLAN_RECENT` only. `STORE.SHARED_PLAN_URL` is not
  id-bearing (it's a URL the user typed) but should still be
  world-scoped so two accounts on one world don't cross-pollute.
- No `configVer` bump on `state.sharedPlanUrl` (UI-only).
- `configVer` bump on `state.attackPlan.targets` shape.

## 7. Post surface & safety

- **Inbound**: none. The plan explicitly does not add a webhook
  receiver, an XHR poll, or a long-poll. The "user-supplied URL
  fetch" is a **single GET** issued only when the user clicks the
  "Fetch" button; not a scheduler.
- **Outbound**: `alertWebhook('shared-plan', payload)` for publish,
  behind `state.dryRun` (already short-circuits at
  `alerts.js:31-34`).
- **gbAjaxWatch**: not applicable — this feature uses `gbXhr` for the
  user-supplied URL fetch (read, not action). No bridge post.
- **gbCaptchaPause feature key**: this feature adds a read-side fetch
  for shared-plan URL. Add `sharedPlan` to the captcha breaker key
  set with a guard: `captchaPausedAny('sharedPlan')` checks in
  `sharedPlanFetchUrl` so a captcha storm pauses the fetch.
  Persisted via `saveCaptcha()` (`core.js:1336`) — already keyed by
  `STORE.CAPTCHA` which is world-scoped (`header.js:200`).
- **Lock**: `gbLock('shared-plan', 30000)` for the fetch path;
  `GB_LOCK_TTL` entry `'shared-plan': 30000` (`core.js:145-173`).
- **Dry-run**: `state.dryRun` already gates `alertWebhook` and
  `bridgePost`/`gameAjaxPost`. The fetcher logs a `DRY-RUN
  shared-plan: GET <url>` line when dry-run is on and posts nothing
  in response (treat the fetch itself as read, but block publish).
- **Redaction**: the published payload and the imported payload
  (when re-shared) use `qolRedactConfigDump` (`qol.js:225-247`).
  Per-player names go through `cut()` (1 char + `...`) unless
  `state.exportRedact === false`.
- **Confirm gate**: per target, the existing `confirm()` in
  `fireAttackNow` (`attack.js:717`) fires once per target. The dialog
  text becomes
  `Atacar #<id> (<name>) desde <sourceCount> ciudades ahora?`. The
  user can answer Cancel to abort the whole plan or OK to fire this
  target (the loop in `fireAttackNow` checks `confirm()` per row;
  change the iteration to abort on Cancel).
- **Precondition invariant**:
  - `sharedPlanValidate` calls `resolveTarget` for each target and
    refuses `kind:'farm_town'` and own-town ids.
  - Each target id must match `/^\d+$/` (the gate at `attack.js:351`).
  - `arriveAt` must be a positive integer when present; otherwise
    null (treated as send-now per row, same as
    `attack.js:484-488`).
  - Unreadable target (`resolveTarget` returns null) → entry dropped
    with `gbLogT('shared-plan-bad-target', 60000, ...)`.

## 8. Failure modes

- **Import JSON fails parse**: `gbLogT('shared-plan-json', 10000,
  'shared plan: JSON parse failed'); flash('plan invalido')`.
  No state change.
- **Import JSON schema missing `targets`**: same path; "plan
  invalido (sin targets)".
- **Single bad target**: drop just that target, continue the rest.
  The plan still applies; the user sees a count line in the log.
- **All targets bad**: refuse the import entirely; do not modify
  `state.attackPlan.targets`.
- **User-supplied URL fetch fails**: `gbLogT('shared-plan-fetch',
  30000, ...)`; flash('fetch fallo'). Captcha on the host →
  `captchaTrip('sharedPlan', ...)` and disable the button until the
  breaker expires.
- **`@connect` rejects the URL**: `gbXhr` returns `'noajax'`; we log
  it once and surface a hint that the host needs to be added to
  `src/header.js` (the script does not auto-edit its own userscript
  metadata). The error code path is the same as the existing
  `farmScrape` no-endpoint log at `farms.js:633`.
- **Own-town target**: `resolveTarget` will resolve it (own towns
  pass `attack.js:357-363`); the runtime guard at `attack.js:525-529`
  refuses the post with `bad-target` and `flash('ataque bloqueado:
  el objetivo es una ciudad propia')`. No special-case needed.
- **Plan references a player id the importer doesn't recognize**:
  ignored — only `author.id` is informational.

## 9. Validation gate

Per plan 27 §11 Med risk: dry-run + one hand-triggered firing + one
full orchestrator tick.

- `state.dryRun` ON, paste a 2-target plan → Log shows
  `DRY-RUN shared-plan: ...` and `DRY-RUN attack: ...` per target,
  and a `skip:dryrun` journal entry per intent. No network
  traffic beyond the read fetcher.
- `state.dryRun` OFF, paste a 1-target plan with a foreign town id
  the test account can resolve → confirm() prompts once; answer OK
  → Log shows `attack bridge: sendUnits town <src> → <dest>
  (attack, ...)` and one `ok` entry in Decisions.
- Fire the same plan with `state.sharedPlanAutoArm = false` → no
  auto-arm, the targets sit until the user manually clicks
  **Armar** in the Attack tab.
- Flip `state.sharedPlanAutoArm = true` → the next timer tick
  arms the targets via `armAttackWave`. Each fires after its
  individual `gbTimeout` elapses; Log shows
  `attack: armed N towns mode=send_now`.
- Captcha test: set `state.captchaBreakers.sharedPlan.until =
  Date.now() + 60000`; the **Fetch** button refuses with
  `captcha-pause`.
- Redaction test: paste a plan with `author.id = 'jdoe12345'`,
  `state.exportRedact = true`; export via `qolExportConfig` →
  blob shows `author: { id: 'j...0' }`.

## 10. Out of scope

- **Discord channel-message fetch** as a default share channel.
  Requires a Discord bot token the user pastes in, and a wider
  `@connect` entry than the current `discord.com` permits. Until
  someone explicitly wants this, it stays out.
- **Auto-publish on every planner change**. Only manual publish is
  wired; auto-publish belongs in plan 8.2 (state snapshots).
- **Cross-alliance auth**. We never validate that the importer is in
  the same alliance as the author; the author tag is metadata.
- **Per-player throttling on publish**. Plan 7.4 owns that; the
  publish path for shared-plan payloads opts into the 7.4 throttle
  when 7.4 lands (a small follow-up).
- **An `@connect` host addition for a paste service**. Defer until a
  specific paste host is requested; the work is a one-line edit to
  `src/header.js:16-19` plus a test against the chosen service.
