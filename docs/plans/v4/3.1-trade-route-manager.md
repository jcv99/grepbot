## 2. Gap

`tradeScan` is algorithmically recurring but conceptually **global** — one
preset rule applies to every owned town pair, every scan. A user who wants
"town 12 → town 7, 1500 wood every cycle, only while town 7 < 60 %"
**cannot** express that: every existing sub-planner either fills warehouses
globally or funds a goal (party/unit). Plan 27's "recurring multi-resource"
means **named user-defined pair routes** that survive reloads, carry their own
amount/cadence/limits, and execute alongside the global planners without
double-allocating from the same shared warehouse.

## 3. Design

A **route** is a stored rule:

```js
{ id: 'r_<short>', from: <townId>, to: <townId>,
  wood: <int|nully>, stone: <int|null>, iron: <int|null>,
  minBatch: 100,           // floor; below this the route skips
  maxPerCycle: <int|0>,    // 0 = no ceiling; otherwise per-orch-tick cap
  trigger: { mode: 'always' | 'belowPct' | 'abovePct',
             resource: 'wood'|'stone'|'iron', value: <int> },
  enabled: true,
  lastFiredAt: 0,          // ms; for stats + per-route cadence throttle
  lastSent: { wood:0, stone:0, iron:0, ts:0 } }
```

Routes live in `state.tradeRoutes` (`{ [routeId]: route }`), stored at
`STORE.TRADE_ROUTES`, world-scoped. One sub-planner
`tradeRouteJobs(towns, ledger)` slots into `tradeScan` **before**
`tradeFillStorageJobs` (so it claims headroom first); `tradeApplyJob` then
makes the global sub-planners see the route's deduction in the same scan, so
they will not double-plan against the same town pair. On a fresh scan (next
orch tick) the ledger is rebuilt from real warehouse state plus in-flight
incoming — so a route that fires on tick *n* is naturally idle on tick *n+1*
until the arrival lands and warehouse state changes. **No extra scheduler** —
the orchestrator's `trade` cadence is the only cadence.

The route's `trigger` is the only policy knob that requires reading a value:
`townResState(target).resource` for `belowPct`/`abovePct`. The invariant from
CLAUDE.md binds — if `townResState` returns no value (blind), the route
**idles** for that scan, logs once via `gbLogT`, and lets the next scan try
again. A route that went silently dead when a getter was renamed would be the
exact precondition-invariant violation §0 forbids.

The trigger rule has one further refinement for the multi-resource case
plan 27 names: when a route specifies all three of `{wood, stone, iron}`, the
"fill" is per-resource (each ≤ its ceiling), but the route only fires when
**the sum meets `minBatch`** AND **every specified resource passes its
trigger**. A `wood`-only route is a pure wood route. This matches the
phoenician.js architecture (`PT_RES`, `phoenician.js:14`) — keep the parallel
small.

The post path (`tradeSend` → `gameAjaxPost('trade', 'town_info', 'trade',
…)`) is unchanged. A route is **not** a separate feature in
`TX_WRITE_FEATURES` — it journals under `'trade'`, same as the existing four
sub-planners, so decision memory, stats, and the captcha breaker continue to
treat the whole trade economy as one unit. That is the point of slotting into
`tradeScan` rather than launching a parallel orchestrator key: a captcha on
the trade queue pauses all of trade, routes included, for the ladder window —
splitting them would let a route burn requests against a paused queue.

## 5. State & storage

- New `state.tradeRoutes: { [routeId]: Route }` — world-scoped, stored at
  `STORE.TRADE_ROUTES`, key added to `WORLD_SCOPED_BASES`.
- New `state.autoTradeRoutes: boolean` — world-scoped, stored at
  `STORE.AUTO_TRADE_ROUTES`; default `false` (HIGH-RISK OFF per plan 27 §3).
- `configVer` bumps 10 → 11 (`core.js:507-511`).
- No prune TTL — the route table is a config object, not a journal. It
  survives reloads until the user removes it.
- Per-route `lastFiredAt` and `lastSent` are in-memory only (not saved) —
  they reset across reloads, which is the right behaviour for a 1-minute
  throttle that should not skip a real opportunity if the user reloaded
  five minutes ago.

## 7. Post surface & safety

- **Post path is unchanged.** Every route fires through the existing
  `gameAjaxPost('trade', 'town_info', 'trade', {…})` (`trade.js:37-46`),
  which is in `TX_WRITE_FEATURES` (`planner.js:213`). No new transport.
- **No `gbAjaxWatch` registration.** Trade is server-rendered, not
  template-learned — every payload is a constant shape. `tplNameFor` returns
  `null` for `'trade'` (no entry in `TPL_FEATURE_MAP`), and the
  `tplHealthOk` gate is skipped (`tx.js:569-573`). This is the same shape as
  `pttrade` was coded in plan 25.
- **Captcha breaker.** `gbCaptchaPause` already covers feature key `'trade'`
  (`qol.js:404-408`). Routes journal and pause under that same key — no new
  breaker entry needed.
- **Lock name.** `'trade'` (`core.js:153`, TTL 180000). Routes share the
  same `gbLock('trade')` taken at `tradeScan:381`. A route sub-planner that
  tried to acquire a different lock would race with the global trade tick.
- **Dry-run.** `txActionGate` (`tx.js:522-534`) returns `'dryrun'` when
  `state.dryRun` is set; `txRun:554-562` logs `DRY-RUN trade: …` and
  journals without posting. Every route send inherits this — verified by
  tracing through `gameAjaxPost → txRun` (`bridge.js:194-197`).
- **`orchDeadlockOpen()` interaction.** Routes fire regardless of the
  deadlock state. A deadlock-only scenario (every warehouse pinned) still
  routes according to its `trigger` — that is the user's explicit override,
  and the `tradeApplyJob` ledger discipline means a route that fires during
  deadlock cannot over-fill a pinned warehouse (the validate step catches it
  before `tradeSend`).
- **Read-only precondition readers.** The route sub-planner reads
  `townResState`, `ledger[from]`, `ledger[to]`, `ironReservedForCave`. None
  of these is a new getter — they all exist and are already precondition-
  invariant safe.

## 8. Failure modes

- **`townResState(tgt)` returns null (unreadable capacity).** Route
  sub-planner logs once via `gbLogT('trade-route-blind-' + route.id, …)`,
  skips that route for this scan, continues to the next. Per scan, per
  route — no exception throw, no silent drop.
- **`tradeLedger` returns null (incoming movements unreadable).** `tradeScan`
  fails closed (`trade.js:357`) — same behaviour as today. No job fires,
  every route is skipped.
- **`ironReservedForCave(from)` is `reserved: true` and the route ships
  iron.** Source iron is reduced by the reserved amount before the cap
  clamp — matches how `tradeGoalJobs` handles the same case (`trade.js:301`).
- **Source warehouse empty / below `minBatch`.** Route skips that scan; not
  an error. No log spam (`gbLogT` keyed by `route.id`, 600s window).
- **Trigger value unreadable (e.g. `belowPct` on a resource whose getter
  the client renamed).** Treat as blind: skip + `gbLogT` once. The trigger
  remains in the saved config but never fires until a future build exposes
  the getter again — same posture as the precondition invariant.
- **Per-route throttle exceeded (`Date.now() - lastFiredAt < 60_000`).**
  Skip; the route remains enabled; next eligible scan may fire it. This
  protects against a fleet of routes ping-ponging the same pair at every
  scan when the warehouses are tight.
- **Two routes targeting the same `to` town in the same scan.** The
  shared ledger discipline (`tradeApplyJob` after each job) means the
  second route sees the first route's deduction and clamps itself. The
  4-job-per-route ceiling (`tradeFillStorageJobs:168` analogue) and the
  overall 6-job scan ceiling (`tradeScan`'s existing `if (jobs.length >=
  4) return jobs;` patterns) keep the scan bounded.
- **Captcha during a route send.** `tradeScan` releases the trade lock on
  `'captcha'` callback (`trade.js:399`) — same as today. Routes inherit
  this; no extra path.
- **`state.tradeRoutes` contains malformed JSON from a manual export.**
  `load(STORE.TRADE_ROUTES, {})` returns the default; UI editor validates
  on read (`saveTradeRoutes` rejects unknown fields).

## 9. Validation gate

Per plan 27 §11 (Med risk): **dry-run + one hand-triggered firing + one full
orchestrator tick.**

1. **Dry-run smoke.** Toggle `state.dryRun` on, enable `autoTradeRoutes`
   on, define one route `{from: <ownTownA>, to: <ownTownB>, wood: 500}`.
   Wait one orchestrator tick (~2 min). Expect exactly one
   `DRY-RUN trade: A→B w500/s0/i0` line; zero real posts; route's
   `lastFiredAt` advances.
2. **Validation precheck.** With dry-run still on, force a `tradeScan('manual')`
   from the panel and confirm `tradeValidateJob` did NOT log
   `trade-stale-A-B`. If it did, the ledger cross-check is broken.
3. **Live, one job only.** Disable dry-run, leave `maxPerCycle: 0` (the
   default), wait one scan. Expect one `trade: A→B w500/s0/i0` log line
   and one `ok` decision journal entry for feature `trade` (Stats tab → top
   errors unchanged).
4. **Coexistence with fill-storage.** With `autoTrade` ON and `preset
   === 'storage'`, add the same route. Fill-storage should *not* plan an
   additional wood haul from A to B in the same scan — the route's job
   consumed the headroom via `tradeApplyJob`. Stats: one `trade` ok per
   scan, not two.
5. **`belowPct` trigger.** Add a route with `trigger: { mode: 'belowPct',
   resource: 'wood', value: 60 }` to a target town whose wood fill is
   45 %. Expect one fire per scan until fill rises above 60 %; then
   silence. Adjust by hand and re-observe.
6. **Multi-resource route.** Define `{from: A, to: B, wood: 200, stone: 200,
   iron: 200, minBatch: 500}`. With B at 40 %/40 %/40 %, expect one fire
   per scan summing to 600. With B at 95 %/95 %/95 %, expect zero fires
   regardless of `trigger`.
7. **Iron-reserve-for-cave interaction.** On a town with `state.autoCave`
   on and `caveThreshPct = 90`, define a route that ships iron from that
   town. The reserved amount must be subtracted; verify by reading the
   panel Log for `trade party: skip town …` analogues — for routes the
   equivalent log is `trade-route-iron-reserved-<id>`.
8. **Disabled route persistence.** Toggle one route `enabled: false`, save,
   reload the page, confirm `state.tradeRoutes[id].enabled === false` and
   the route does NOT fire on the next scan.
9. **World-scoping.** Export config from `es146`, edit the exported JSON to
   point one route's `from` at a town id from `en123`, import. On import,
   the import path (in `qolExportConfig`/`qolImportConfig`) applies
   `wkey()` because `STORE.TRADE_ROUTES` is in `WORLD_SCOPED_BASES`
   (`header.js:193-215`); the bad id is silently dropped by the schema
   validator (target not in `towns`).
10. **Captcha pause inheritance.** Trigger a captcha on the trade queue.
    Confirm `gbCaptchaPause` pauses all of trade for the ladder window —
    the route sub-planner must not bypass it. Decision journal
    `captcha-pause` rows count under `trade`, not under a separate feature
    key.
11. **No new scheduler.** `grep -n "gbInterval" src/trade.js` returns zero
    matches after the change. `orchTick` cadence for `trade` is still
    `120000` (`qol.js:393`).

## 10. Out of scope

- **Cross-island distance capping** (plan 07's `tradeMaxHops`) — the
  underlying field is **already deleted** in v3.4.0 (`BACKLOG.md:96`);
  this plan does not re-introduce it. The route schema's `trigger: always`
  plus the per-scan ledger cap is the new ceiling. If a future plan wants
  per-route `maxDistance`, it lives on the route shape itself, not in
  global config.
- **Resource balancing AI (plan 5.1).** 5.1 reuses `state.tradeRoutes` as
  its planner hook — that work belongs to 5.1's plan, not here.
- **Resource dump (plan 3.4).** Uses `transport.js` (plan 1.3) — separate
  module, separate code path. Out.
- **UI label fix** for *"fiesta (sin implementar)"* / *"unidades (sin
  implementar)"* (`ui.js:765-766`). Plan 01 implemented the presets but
  never updated the labels. Flag separately; if folded into the same PR,
  the change is one-liner per label.
- **Adaptive cadence for routes.** `orchAdaptive` (`qol.js:415-416`) does
  not key on per-route success — it keys on the whole `trade` feature
  (`ORCH_JRN['trade']`). Per-route adaptive is a future optimisation, not
  v4.3.
- **Mobile / native-app variant of the route editor.** Config tab is HTML
  only; a mobile-friendly modal can land in v4.5 alongside the dashboard.
- **Auto-route discovery ("GrepBot noticed you send wood from A→B every
  cycle, want to make this a route?").** Anti-pattern detection is
  plan-27 §0 out of scope.
- **Per-player (not per-world) routes.** Trade routes are meaningless
  across worlds (different town ids); world-scoping is the correct
  granularity.
