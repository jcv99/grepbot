# 2.11 — Unit composition advisor

**Bucket:** v4.0 · **Risk:** Low · **Size:** M
**Module:** extend `src/military.js` (new `militaryCompositionAdvisor`,
new `renderCompositionAdvisor`); consume the existing
`state.recruitTargets` and `state.townGoals[townId].units` per-town maps.
**Depends on:** 1.2 city specialization profiles (the per-town profile is
what `goalEffective` (`goals.js:14-19`) merges with `cfg.units` to produce
the advisor's target row). Falls back to `state.recruitTargets[townId]`
when no profile is set, so this plan ships with no ordering dependency.
**Status:** PLANNED — written 2026-08-10 against `src/` @ v3.8.2

> This plan is **advisory**. It must not change `recruitScan` behaviour.
> Auto-recruit is HIGH-RISK and already gated default OFF
> (`core.js:325`, `header.js:118` `STORE.AUTO_RECRUIT`, Config
> `[data-cfg=auto-recruit]` at `ui.js:1336`/`ui.js:1431`); see §10.

## 1. What exists today

- `unitMeta(id)` (`attack.js:31-34`) reads
  `GameData.units[id]`; returns the full Grepolis unit record
  (pop, `is_naval` / `naval`, `unit_function`, `capacity`, `berth`, `speed`,
  `favor`, `god`, `population`, `resources`, `building_dependencies`,
  `research_required`). This is the metadata every other module shares —
  the advisor re-uses it, never duplicates the lookup.
- `classifyUnitFn(id)` (`attack.js:141-156`) collapses the per-world
  `unit_function` vocabulary to one of
  `offense|defense|both|naval|militia|unknown`. Hoplite is hard-pinned to
  `both`; sundry monstrous units map to offense; the standard
  `sword|archer|hoplite|centaur|pegasus|cerberus|calydonian|medusa`
  set to `defense`. The advisor's function summary uses this verbatim.
- `townLiveUnits(townId)` (`attack.js:35-42`) returns the in-town
  garrison; `goalUnitCounts(townId)` (`goals.js:60-62`) adds
  `t.unitsOuter()` for the queued/away split the recruit scan consumes
  (`recruit.js:299-308`). Both fail closed: a torn model returns `{}`.
- `goalEffectiveRecruitTargets()` (`goals.js:39-44`) merges
  `state.recruitTargets` with the per-town profile's `units` map
  (`state.townGoals[townId].units`, `goals.js:8`) and applies
  `goalOrderIds` (`goals.js:115`) suppression. This is the canonical
  per-town target the recruit scan honours, the same target the
  Queue Center tab's recruit lane consumes. `state.recruitTargets` is
  loaded at `core.js:326` and world-scoped
  (`header.js:205` `STORE.RECRUIT_TARGETS`).
- `recruitAffordableAmount(townId, unit, want)` (`recruit.js:215-238`)
  caps by `wood/stone/iron/pop/favor` and returns `0` on an unreadable
  model — the precondition invariant. The advisor surfaces this verbatim
  as the "what's buildable today" row, never refigures it.
- `recruitCanBuild(townId, unitId)` (`recruit.js:134-181`) blocks on
  research + buildings + (mythical) god/temple/favor; an unreadable god
  is **blind** not "wrong god" (`recruit.js:161-168`). The advisor
  shows the blocker reason as-is.
- `recruitQueueInfo(townId, unitId)` (`recruit.js:182-197`) reports
  `{known, len, max, models}`; `recruitQueuedAmount(townId, unit)`
  (`recruit.js:198-207`) sums queued counts. Both fail closed on a
  missing collection (`known: false`).
- `state.goalProgress(townId)` (`goals.js:124`) returns 0..100 already;
  the advisor adds the per-unit gap so the player sees which unit
  blocked progress.
- `renderMilitaryHelpers(sec, plan)` (`military.js:166-201`) is the
  attack-tab render hook; it owns `.atk-cmds` (outgoing cancel list) and
  `.atk-heroes` (player-hero box). The advisor lives in a new sibling
  box (`.atk-comp`), keeping the existing render path intact.

What is **not** coded:
- There is no view of the gap between `have + queued` and `tgt` per unit.
  The Queue Center lists the *plan* (`goalPlanTown` `goals.js:63-101`),
  but does not summarise "you are missing N hoplites to reach your
  defensive goal".
- There is no per-town composition score (offense / defense / naval /
  mythical split), no `classifyUnitFn`-weighted table, no shortage list.
- There is no town-vs-target diff driven by `tgt - have - queued` over
  the canonical `unit_function` split.

## 2. Gap

The player (and auto-recruit) needs a single panel that, per town,
shows the four things the recruit scan optimises against but does not
visualise:

1. The per-unit gap `tgt - have - queued`, colour-coded by
   `recruitCanBuild` (`requirements` blocker → red, `queue` blocker →
   yellow, `resources/pop/favor` short → orange, ready → green).
2. The composition split by `classifyUnitFn` (offense / defense / both
   / naval), weighted by `unitMeta.population`, so the player can see
   whether the town leans offence or defence.
3. The "buildable today" row — what `recruitAffordableAmount` allows
   right now, separately from the long-term target, so a near-empty
   warehouse does not look like a missing target.
4. A per-town `goalProgress` already exists, but it averages 0..100
   across build/research/units; the unit-composition row strips it to
   the units slice and names the unit pulling the average down.

The plan does **not** change `recruitScan` and does **not** alter the
HIGH-RISK default. It is a read view of the same data `recruitScan`
already reads.

## 3. Design

Pure read. One helper that produces a per-town record, one render
function that paints it into a new `.atk-comp` block on the Attack tab.

Data in, per town (`militaryCompositionRow(townId)`):

```
have        = goalUnitCounts(townId)              // goals.js:60
queued      = sum across unitMeta ids of recruitQueuedAmount(townId, u)
tgt         = (state.townGoals[townId].units merged with
              state.recruitTargets[townId]) filtered to finite > 0
             // mirrors goalEffectiveRecruitTargets output for the town
byFunction  = {offense, defense, both, naval, mythical, militia}
              each = Σ u.population · n  over have (read for the unit
              function classifyUnitFn assigns)
shortage    = [{id, want, have, queued, gap, status, why}]
              want = tgt[u] - have[u] - queued[u]
              status in {'ready','short','queue-full','requirements','blind'}
              why   = the reason string from recruitCanBuild /
                      recruitQueueHasSpace / recruitAffordableAmount
buildableToday = [{id, maxAmount, blind}]
              maxAmount = recruitAffordableAmount(townId, u, want)
              blind     = (recruitAffordableAmount === 0 AND want > 0
                           AND model unreadable)
unitProgress = goalProgress(townId) — passed through unchanged
```

Render (`renderCompositionAdvisor(sec)`):

- A new header `<b>Composición</b>` in the Attack tab below
  `renderMilitaryHelpers` (the existing helpers are unchanged). Markup
  lives in `military.js`; the panel template at `ui.js:578-645` gains
  one new `<div class="atk-comp">…</div>` near the existing
  `.atk-cmds` block (line 639).
- A `<details>` per town: town name (from `state.towns` lookup
  `townNameById`, `attack.js:987-989`), `unitProgress %`, four
  `<span>` cells with the `byFunction` populations (defense, offense,
  naval, mythical), an `<ol>` of shortages (≤8 entries, sorted by gap
  desc), and a one-line `buildableToday` rollup.
- One `gbLogT('comp-advice-<townId>', 600000, …)` per (town, status
  change) per 10min, so a steady-state town stays quiet.
- No state writes except the existing `goalProgress`-equivalent memo:
  the advisor does **not** maintain its own ring buffer — every render
  call recomputes from the model. Cache lives in a single module-local
  `let compCache = Object.create(null)` keyed by `townId`, invalidated
  by the `goalPlanTown` hook `goalPlanAll` already drives
  (`goals.js:102`), or by the `bindAttackTab` refresh button.

Data out:
- The Attack tab `.atk-comp` block.
- A new Preflight row `composition advisor` in `stats.js:248`-ish:
  counts towns with `shortage.length > 0`, warns on
  `shortage[].status === 'blind' > 0` (no model — admit it).

## 5. State & storage

- **No** new `state.*` field. **No** new `STORE.*` key. The advisor
  reads `state.recruitTargets` (world-scoped at `header.js:205`) and
  `state.townGoals` (world-scoped at `header.js:209`). Both are
  already id-bearing; both already pass through `wkey()` via
  `load()`/`save()`.
- **No** `configVer` bump.
- The module-local `let compCache` is non-persistent — wiped on reload
  intentionally, since `goalPlanAll` (`goals.js:102`) re-runs on every
  UI tab open and refresh. No TTL, no prune, no leak.

## 6. Config surface

None. The advisor has no toggles. The user opts in by setting
`state.recruitTargets[townId]` or picking a non-`custom` profile
(via the 1.2 plan). With no per-town target configured, the
advisor shows the by-function split and the goalProgress percent
but no shortage list (no gap to display). That graceful zero-state is
deliberate — a panel that shouts "no data" is the wrong shape for a
read-only advisor.

## 7. Post surface & safety

**No post surface.** The advisor is a pure read of
`unitMeta` + `classifyUnitFn` + `townLiveUnits` + `goalUnitCounts` +
`recruitQueuedAmount` + `recruitCanBuild` + `recruitQueueHasSpace` +
`recruitAffordableAmount` + `goalProgress`. No `bridgePost`, no
`gameAjaxPost`, no `gbXhr`, no DOM click. No `gbCaptchaPause` feature
key, no `gbLock` name, no `GB_LOCK_TTL` entry, no `gbAjaxWatch`
registration, no `TPL_FEATURE_MAP`/`tplNameFor` entry, no dry-run
gate. The `recruitAffordableAmount === 0` short row is honest about
unreadable models; it never fabricates a recommendation.

## 8. Failure modes

- `unitMeta(id) === null` (unit id not in `GameData.units` on this
  world) — the unit is dropped from `byFunction` and from the
  shortage list. One `gbLogT('comp-meta-unknown-<id>', 600000, …)` per
  unknown id per 10min. The advisor never invents metadata.
- `t.units()` throws → `goalUnitCounts` returns `{}`; `have` is
  empty; every shortage row carries `status: 'blind', why: 'model'`.
  The per-town `<details>` shows "(blind — open a town once)" and
  Preflight's `composition advisor` row warns.
- `recruitAffordableAmount` returns `0` for a unit with a positive
  want → `buildableToday` row carries `maxAmount: 0, blind: false`;
  the shortage row's `status: 'short'` carries the `why`
  `resources/pop/favor` from `recruitValidateJob`
  (`recruit.js:239-245`). The advisor does **not** override that.
- `recruitCanBuild` returns `false` on a mythical with an unreadable
  god → `recruit.js:166-168` already logs `recruit-god-blind-<tid>` and
  the advisor surfaces the same blind status; `requirements` vs
  `blind` are distinguished by the explicit boolean the helper
  already returns (the advisor maps the second-class case to `blind`).
- A `state.townGoals[townId].units` typo (`{sworrd: 50}`) is dropped
  by `goalMergeMap` because the value is filtered through
  `Number.isFinite(+n) && +n >= 0` (`qol.js:251` `cleanMap`,
  consumed at `goals.js:123`); the advisor sees the empty value, no
  shortage row, no log spam.
- Profile changed mid-render: the cache is keyed by `townId` only;
  any `goalSetProfile` or `goalSetTownOverrides` call invalidates
  through `goalPlanTown` (`goals.js:103,123`). The advisor does not
  add a separate invalidation hook.

## 9. Validation gate

Per plan 27 §11 Low risk: *Preflight + one in-game session, no failure.*

1. `python3 build.py`, paste, reload `es146`.
2. Open the Attack tab. The "Composición" header and a
   `.atk-comp` block appear below "Enviados / cancelar". No console
   errors.
3. Set `state.recruitTargets = { "<townId>": { sword: 50, hoplite: 30 } }`
   in DevTools (or use the existing Config preset). The town's
   `<details>` opens with two shortage rows; both `status` should be
   either `ready` (green) or `short` (orange) depending on warehouse
   fill. With a near-empty warehouse, both show `short` with
   `resources/pop/favor`.
4. Switch the same town to the `conquest` profile (via the 1.2 plan
   or `goalSetProfile(townId, 'conquest')` in DevTools). The shortage
   list now includes `colonize_ship` and shows the temple
   `requirements` blocker (`recruit.js:56`).
5. Preflight → `composition advisor`: row reads e.g.
   `12 towns, 4 with shortage, 0 blind`. `0 blind` is the
   precondition-invariant check.
6. Open a *new* tab and visit a town, then return. The row counts
   match (the `bindAttackTab` refresh button is the only way to force
   a recompute; the cache hit path is the read path).
7. Set `state.dryRun === true`. The advisor output is byte-identical
   to step 5 — it never posts, dry-run covers nothing here.

Must **NOT** appear anywhere: any new `bridgePost`/`gameAjaxPost`
entry, any `skip:*` decision row, any new lock name in Stats's
"held locks" row, any change to the request budget.

## 10. Out of scope

- **Auto-recruit changes.** `recruitScan` (`recruit.js:264-386`) and
  `goalEffectiveRecruitTargets` (`goals.js:39-44`) are untouched. The
  plan is intentionally read-only; auto-recruit stays HIGH-RISK default
  OFF. Re-routing the advisor's output into the recruit scan's
  shortage list would couple a read view to a HIGH-RISK write — punt to
  a future plan that owns the HIGH-RISK gate.
- **Conquest / cs-fast optimisation.** Profile-driven unit targets
  already exist via `state.goalProfiles[profile].units` and the
  `conquest` profile at `build-tab.js:471`. The advisor consumes
  those but does not extend the profile schema.
- **Per-unit cost forecasting.** `townResState` gives a per-town
  capacity, but not a per-resource ETA, and not a per-unit cost roll-up
  over a planning horizon. That is the **warehouse deadlock
  resolver** (plan 05) and the **resource balancing AI** (plan 5.1).
- **A separate `composition.js` module.** Rejected: the function lives
  entirely on top of `unitMeta` + `classifyUnitFn` + `goalUnitCounts`,
  all of which are shared. Splitting them into a new file means the
  file concatenates after its only caller for no benefit (build.py
  would gain a slot, the gate gains a name to check).
- **Auto-mitigation suggestions** ("you should build barracks first").
  The advisor names the blocker; it does not prescribe the fix.
  Suggestions cross the line into planning and belong to the
  build-queue optimizer (5.6) or the goal planner (`goals.js:63-101`).
