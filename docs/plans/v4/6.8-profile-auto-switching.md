# 6.8 — Profile auto-switching

**Bucket:** v4.1 · **Risk:** Med · **Size:** M
**Module:** `src/qol.js` (profile-rule engine) + `src/ui.js` (Config controls); call the existing `src/orchestrate.js` tick, with no new `build.py` MODULES slot
**Depends on:** none
**Status:** PLANNED — written 2026-08-10 against `src/` @ v3.8.2

## 1. What exists today

- `qol.js` already has three named profiles: `afk`, `farming`, and `war`, with Spanish labels and allowlisted values (`src/qol.js:272-358`). The AFK and farming profiles enable write-capable economy loops such as `autoFarm`, `autoCave`, `abAuto`, `autoTrade`, and `autoResearch` (`src/qol.js:290-336`); the war profile enables a different subset (`src/qol.js:338-356`).
- The existing safety table forces `autoFavor`, `autoRecruit`, `autoDodge`, premium culture, merchant, wonder, wonder-favor, Phoenician trade, and village recruit OFF when a preset is applied (`src/qol.js:277-288`, `src/qol.js:359-371`). It deliberately does not change `dryRun` (`src/qol.js:272-276`).
- Applying a preset is currently a direct synchronous mutation: `qolApplyPreset` assigns `state[key]`, calls `save`, forces the high-risk table, and logs one summary (`src/qol.js:359-381`). It is not routed through `qolImportConfig`, despite the design in plan 16 (`docs/plans/16-config-presets.md:31-48`).
- The only current preset controls are footer buttons wired in `ui.js`; the handler applies immediately, rebinds Config, updates status, and flashes a message (`src/ui.js:1632-1642`). There is no time/condition rule editor or auto-switch toggle in the Config markup (`src/ui.js:706-843`).
- No profile-auto state or storage key exists in the shared key table or state initializer (`src/header.js:24-187`, `src/core.js:220-384`).
- The existing orchestrator is the sole cadence for economy work: `orchTick` checks host and pause state, selects due features, and dispatches up to three per tick (`src/orchestrate.js:147-199`); boot calls it once and then every `ORCH_MS` (`src/boot.js:103-107`). A new `gbInterval` would violate the repository scheduler rule (`src/boot.js:103-107`).
- Existing pause conditions already read local time, activity timeout, captcha, and server cooldown (`src/core.js:572-600`); `gameNow` provides a server-time fallback but the night-pause implementation uses `new Date().getHours()` (`src/core.js:585-590`, `src/core.js:1063-1078`). Hostile incoming movements have a real read path in `dodgeIncomingMovements` (`src/dodge.js:53-83`), and town capacity/fill is centralized in `townResState` (`src/bridge.js:235-235`).

## 2. Gap

There is no persisted rule that selects an existing profile from a time window plus live conditions, and therefore no unattended profile transition. The delta is a default-OFF declarative evaluator that applies only the already-coded preset allow-list, records the active rule and a hold-down period, and runs from the existing orchestrator cadence without inventing a game action or post route.

## 3. Design

1. Store a bounded rule list, not JavaScript. The shape is `{enabled, minHoldMin, rules:[{id, enabled, priority, profile, days, startMin, endMin, when}]}`. `profile` is one of `afk|farming|war`; `days` contains local `Date#getDay()` values `0..6`; `startMin` and `endMin` are minutes `0..1439`; `when` is an AND map with exactly `activity: any|active|idle`, `incoming: any|yes|no`, and `warehouse: any|full|not-full`. No `eval`, arbitrary expression, endpoint, or user-event simulation is allowed.
2. Evaluate rules in ascending `priority`, then `id`, on the local wall clock. A time window with `startMin <= endMin` is half-open `[startMin,endMin)`; one with `startMin > endMin` crosses midnight. An empty `days` list never matches. This mirrors the existing explicit overnight interval logic rather than guessing server time (`src/core.js:585-590`).
3. Read `activity` from `state.pauseOnActivity` and the existing `userPausedUntil`; `active` means the timeout is currently live and `idle` means it is not. Read `incoming` through `dodgeIncomingMovements` (`src/dodge.js:53-83`). Read `warehouse` by enumerating the same owned-town models used by the existing overview (`src/qol.js:97-101`) and calling `townResState(townId)`; `full` means at least one readable town is at or above 97% of capacity, while `not-full` requires every enumerated town to be readable and below 97%.
4. If the first matching rule names the same profile as `profileAutoLast.profile`, do nothing. If it names another profile, require `Date.now() - profileAutoLast.switchedAt >= minHoldMin * 60000` (minimum 15 minutes, maximum 24 hours). If no rule matches, keep the current profile; do not bounce to a default profile.
5. On a transition, call `qolApplyPreset(profile)` once, save `{profile, ruleId, switchedAt}`, refresh the Config controls/status, and emit exactly `profile-auto: switched <old> -> <new> (rule <id>; activity=<...>; incoming=<...>; warehouse=<...>)`. The preset's existing high-risk-off and dry-run-preservation behavior remains authoritative (`src/qol.js:272-288`).
6. Call `QOL_PROFILE_AUTO.tick()` from the start of `orchTick` after the host check and before its pause return (`src/orchestrate.js:147-150`). This lets a scheduled profile change the next dispatch's pause behavior, while retaining the single 20-second cadence and no parallel scheduler.

## 5. State & storage

- Add `state.profileAutoCfg` and `state.profileAutoLast`; both use `STORE.PROFILE_AUTO_CFG` / `STORE.PROFILE_AUTO_LAST` and are world-scoped intentionally (`src/header.js:193-215`). The rule list is capped at 20 entries; each rule has a stable bounded `id` and no town/player identifiers.
- Bump `CONFIG_VER_CURRENT` 10→11 (`src/header.js:189-191`). Migration must run through the existing ordered `<version` blocks and finish through the existing `configVer` save (`src/core.js:394-510`).
- `profileAutoLast` is one record, not a history ring, so it needs no TTL prune. Delete malformed rules on load/import; never delete learned templates, journal entries, or findings.

## 6. Config surface

- `Cambio automático de perfiles`: checkbox, default **OFF**.
- `Permanencia mínima (min)`: number `15..1440`, default `15`.
- Rule rows: `Activa`, `Prioridad`, `Perfil`, `Días`, `Desde`, `Hasta`, `Actividad`, `Incoming`, `Almacén`; defaults for a new row are disabled, priority 100, profile `afk`, all days, `00:00–00:00` (must be edited), and all conditions `any`.
- Existing `Perfil: AFK nocturno`, `Perfil: recoleccion activa`, and `Perfil: guerra` remain manual actions (`src/ui.js:892-894`, `src/ui.js:1632-1642`). Auto-switching never turns a high-risk loop ON because the existing safety map only writes those keys as `false` (`src/qol.js:277-288`).

## 7. Post surface & safety

No post surface, route, payload, `gbAjaxWatch`, `TPL_FEATURE_MAP`, captcha feature key, or lock is introduced: this feature only mutates local config by calling `qolApplyPreset` (`src/qol.js:359-381`). It can indirectly enable existing economy loops, so the feature is default OFF, preserves `state.dryRun`, and leaves all resulting posts behind the existing dry-run gate (`src/core.js:940-946`, `src/tx.js:531-555`). No new lock is needed because the tick is synchronous; do not add an in-flight boolean.

## 8. Failure modes

- Invalid rule/profile/time/day is dropped at normalization and logged as `profile-auto: invalid rule <id>`; it never activates the feature. A missing/unknown condition getter is `blind`, logged once through `gbLogT`, and the rule is not selected; no blind value is allowed to trigger a configuration change (`src/core.js:298-309`).
- Missing `ITowns`, `MovementsUnits`, or capacity data produces a throttled `profile-auto: condition blind` entry and leaves the previous profile untouched. `dodgeIncomingMovements` already filters to canonical hostile types (`src/dodge.js:39-83`); do not infer hostility from an unknown field.
- A dropped SPA callback cannot strand this feature because it has no asynchronous callback or lock; the existing orchestrator catches handler exceptions (`src/qol.js:420-435`) and the evaluator must catch its own reads.
- A profile switch never bypasses `automationPaused`; it only occurs before the existing pause return, and every subsequent write still uses existing precondition readers. Every new write guard must name the value it read; unreadable getter ⇒ `blind` ⇒ `gbLogT` once ⇒ let the server decide (`src/core.js:298-309`).
- Overlapping rules are deterministic by priority/id, and the minimum hold plus no-match no-op prevents time-boundary thrash. A switch failure leaves `profileAutoLast` unchanged and logs `profile-auto: apply failed`.

## 9. Validation gate

Med risk requires dry-run, one hand-triggered firing, and one full orchestrator tick (plan 27 §11.1). With `dryRun` ON (`src/ui.js:1384-1389`), enable auto-switching, create a rule for the current minute with `incoming=any`, and wait for one `orchTick`; the Log must show the exact `profile-auto: switched ...` line and subsequent would-be posts must be `DRY-RUN`, never live requests. Turn dry-run OFF only after comparing one manual preset application against its resulting Config values; then allow one full tick and confirm one switch only, no second switch for 15 minutes, and no high-risk toggle becomes ON. Test an overlapping rule, a midnight interval, an unreadable condition (Log `condition blind` once), reload persistence, and a world change; the other world must not inherit the active rule or last-switch record (`src/core.js:1088-1107`).

## 10. Out of scope

No new profile semantics beyond the three shipped presets, per-town profile balancing, city specialization, activity I/O, user-event simulation, or server sync. City specialization belongs to 1.2; keyboard/widget UX belongs to 6.2/6.3. This plan does not invent an endpoint or change any preset payload; it only schedules the existing local preset mutation (`src/qol.js:359-381`).
