# 2.8 — Resource capping predictor (T-10min pre-warn)

**Bucket:** v4.0 · **Risk:** Low · **Size:** S
**Module:** `culture.js` (extend `economyForecast`); touch `core.js` (state +
webhook event key), `ui.js` (flash trigger), `alerts.js` (event key).
**Depends on:** none (uses already-shipping `economyProductionRate`,
`economyPlannedCost`, `plannerSnapshot`, `alertWebhook`).
**Status:** PLANNED — written 2026-08-10 against `src/` @ v3.8.2

## 1. What exists today

- `economyForecast(townId, horizonSec)` at `culture.js:226-234` already
  returns
  `{townId, horizonSec, snapshot, production, demand, projected, overflow, deficit, productionKnown}`.
  `overflow[k]` is `projected[k] >= cap` (boolean). `deficit[k]` is the
  missing-amount over the same window for **consumption**-side checks.
- `state.predictCfg.horizonHours` (default `6`,
  `core.js:358`, key `header.js:154` `STORE.PREDICT_CFG`) is the
  horizon. So a town whose warehouse fills inside 6h already shows up as
  `overflow[k] = true`.
- Resumen (`qol.js:185`) renders a one-shot `AVISO · almacén previsto al
  límite en <resources>` per town using `f.overflow`. **There is no ETA,
  no countdown, no flash, no webhook.**
- `flash()` is exposed via `ui.js`; it is already used by
  `checkThresholds` (`build-auto.js:458`) and by `circuitNote`
  (`planner.js:193`).
- `alertWebhook(event, payload)` at `alerts.js:28-88` is the dispatcher.
  Rate-limited per `event` key (5min) via `alertLastSent` (`alerts.js:44`).
  Defaults already include a `warehouse: false` event key
  (`core.js:313`), suggesting the catalog anticipated a warehouse sink.
- `state.webhookEvents` is `{ captcha: true, attack: true, warehouse: false, culture: false }`
  (`core.js:313`); Config flips individual events (`ui.js:1478`).

Plan 27 §2.8 says "extend `core.js`". **Wrong module hint.** The
projection logic is in `culture.js` (concat slot 19). `core.js` owns
`state`, `STORE`, and the webhook-events default; the actual computation
belongs with `economyForecast`.

## 2. Gap

- The `economyForecast.overflow` flag is binary — "will this town cap
  inside the horizon?" — and the existing Resumen line lumps together
  multiple resources and does not tell the user **when**. The catalog
  promise is a "T-10min pre-warn": translate `overflow` into a per-resource
  ETA in minutes, alert when the ETA crosses a threshold.
- There is no live pre-warn — the AVISO line is rebuilt only on Resumen
  render (qol.js:185 is inside a function called on demand, not on a
  cadence). The warehouse deadlock detector at `orchestrate.js:64-77`
  reacts to **already-pinned** warehouses (`ratio >= ORCH_PIN_RATIO =
  0.97`) — by then the bot has already lost the loot window.

## 3. Design

Extend `economyForecast` in `culture.js` to also return
`etaMinutes: {wood, stone, iron}` — each ETA is the wall-clock minutes
until `projected[k] >= cap` at the current production rate, **clamped to
the configured horizon**:

```
function etaMinutesToCap(live, projected, cap, prod, deficit, horizonSec) {
  // only valid when projected[k] >= cap && prod[k] > 0
  // returns Math.min(horizonSec, (cap - (live[k] - committed + incoming)) / prod[k]) / 60
  // otherwise null
}
```

Wire a per-town watcher (`townCapWatcher` in `culture.js`). Per Hard rule #4
("no new schedulers — `gbInterval`/`setTimeout` is reserved for the existing
core/orch/ibScan/dodgeScan cadences"), the watcher does **not** introduce a
new interval. Instead it runs as a second pass inside the existing
`cultureScan` body — same cadence, same jitter, same orchestrator tick.
`economyForecast` already runs there every cycle; `townCapWatcher` is a
sibling pass that reads the same cached result, so the only added cost is
the comparison + dedupe map write. Adding a 60s `gbInterval` purely for a
UI/alert side channel would duplicate state and risk drift, so the orbit
stays inside `cultureScan`.

On every tick, for each town in `state.towns`:
- call `economyForecast(townId, horizonSec)`
- for each resource where `etaMinutes[k]` is finite and
  `<= PREWARN_MIN_MIN` (default 10), build a payload
  `{townId, name, resource, etaMin, fillPct}` and dispatch **once** via:
  - `flash('AVISO: <name> <res> en ~<n>min (cap)')` (visual)
  - `alertWebhook('cappingPreWarn', payload)` (if
    `state.webhookEvents.cappingPreWarn !== false`)

Per-town dedupe: keep a module-local `_cappingAlerted` map keyed by
`townId|resource` with a 30min TTL. The webhook's own 5min
`alertLastSent` rate limit is **not** enough — multiple towns can stack
within 5min. The 30min TTL matches the existing `tplHealthOk` invalidation
window (`core.js:857`) so behavior feels uniform.

No new post surface, no `gbLock`, no `gbAjaxWatch`. The watch is a
**read-only second pass** inside the existing `cultureScan` body — no new
scheduler, no cadence drift from the rest of the economy.

## 5. State & storage

- No new `state.*` field.
- No new `STORE.*` key. `_cappingAlerted` is module-local TTL state,
  intentionally not persisted — if the user reloads, the watcher
  re-fires the pre-warn at most once per (town, resource) per 30min.
- No new `WORLD_SCOPED_BASES` entry.
- The `webhookEvents` default gains one boolean (`cappingPreWarn`) but
  it lives under the existing `STORE.WEBHOOK_EVENTS` (`header.js:108`)
  key already in `WORLD_SCOPED_BASES` (`header.js:194` covers the
  `WEBHOOK_EVENTS` storage via the parent Set's existing entries —
  verify during impl that this key is actually included; if not, add it
  alongside the other Config keys).

## 6. Config surface

- **Config → Webhooks → Eventos**: new checkbox `Pre-aviso de almacén
  (~10 min)` (`cappingPreWarn`), default OFF (webhook only — the
  in-panel flash is unconditional).
- **Constant `PREWARN_MIN_MIN`** lives as a module-local `const` in
  `culture.js`, default `10`. Not in Config — the catalog promise is
  the "T-10min" number.
- **Constant `PREWARN_HORIZON_HOURS`** lives next to it, default `2`
  (vs. `state.predictCfg.horizonHours = 6`). Smaller horizon → fewer
  false positives. Not in Config either.

## 7. Post surface & safety

- **No new outbound game post.** The only network call is the existing
  `alertWebhook` → `gbXhr` to the user-configured Discord/Telegram URL.
  That path is already gated by `state.dryRun` (`alerts.js:31-33`) and
  `state.webhookEvents[event] === false` (`alerts.js:39-40`).
- **No new `gbAjaxWatch`** registration needed (this is an outbound
  webhook, not an inbound bridge post).
- **No new `TPL_FEATURE_MAP` entry** — no game template is involved.
- **No `gbCaptchaPause` feature key** — this never touches the bridge.
- **No `gbLock` to add** — the watcher is single-instance and the
  dedupe map prevents double-firing.
- **Read-mostly feature**; the only side effect is a console log + a
  user-configured webhook.

## 8. Failure modes

- **`economyProductionRate` returns `null`** (model doesn't expose
  production on this client build) — `etaMinutes[k] === null` for all
  three resources; watcher skips the town. Pre-warn is silent, not
  blind-firing. Logged once via `gbLogT('capping-prod-blind', 600000)`.
- **Capacity unreadable** (`townResState` returns `null` for this
  town) — `etaMinutes` is `null` for all resources; same path.
- **Watcher interval drift under background tab** (`CLAUDE.md` "Tab
  visibility" — background tabs floor at ~1min) — acceptable: pre-warn
  fires up to 1 min late, not catastrophic.
- **Webhook URL invalid** — `alertWebhookUrlOk` (`alerts.js:4-8`)
  rejects; `gbLogT('webhook-url', 120000, ...)` throttled log; user sees
  no Discord/Telegram ping but still gets the in-panel `flash()`.
- **Dry-run mode** — `alertWebhook` short-circuits at `alerts.js:31`,
  logs `DRY-RUN webhook cappingPreWarn: …`, no outbound POST. The
  in-panel `flash()` still fires so the user can validate the trigger
  condition.

## 9. Validation gate

- Hand-fill one town to 95% wood with `main` and a `lumber` building
  producing ≥100 wood/h. Wait ≤10 min. Log shows one
  `cappingPreWarn` entry; Resumen shows `<name>: wood ~<n>min` with
  `n <= 10`; `flash('AVISO: …')` appears once.
- Repeat within 30 min: no second flash, no second log line for the
  same `(town, resource)` pair (dedupe map working).
- Force the town to cap (let the warehouse fill). `flash` clears;
  next sweep re-arms for the next resource.
- Disable `cappingPreWarn` in Config → webhook stops firing but the
  in-panel flash keeps working.
- Stats → Decisions → `cappingPreWarn` events journaled as `ok`
  (informational journal entries — feature `cappingPreWarn`, no skip).
- Build: `python3 build.py` exits 0; install; no `flash()` spam;
  Log tab shows the pre-warn line.

## 10. Out of scope

- Per-resource ETA on **population** fill (handled by 2.7; population
  growth chain is unreliable on stock clients — ETA already
  precondition-guarded there).
- Auto-dumping before cap (the catalog's 3.4 — HIGH-RISK; defer).
- Slack / SMS sink (only the existing `alertWebhook` Discord / Telegram
  routes ship — adding a new sink is `alerts.js` work owned by 6.4).
- Tighter horizon per resource (e.g., "wood caps faster than iron") —
  not in this plan; the single 2h horizon is the v4.0 minimum.
