# 2.2 — Enemy city timeline (diff reports)

**Bucket:** v4.0 · **Risk:** Low · **Size:** M
**Module:** extend `src/intel.js` (additive) + small markup additions in `src/ui.js` intel section
**Depends on:** none (will consume 2.1 deep-parse fields when that ships, but ships standalone against the fields `parseReport` already returns today)
**Status:** PLANNED — written 2026-08-10 against `src/` @ v3.8.2

## 1. What exists today

- The findings ring buffer lives at `state.findings` (`src/core.js:221`), seeded from `load(STORE.FINDINGS, [])`. It is unshifted in `ingestReport` (`src/spy.js:249-254`) and capped at **500** in memory there (`src/spy.js:250-253`) — quota emergencies trim it to **100** in `storagePruneForQuota` (`src/core.js:1167-1172`). There is **no** 7-day TTL on findings; retention is "keep the N most recent".
- `parseReport` (`src/parse-inline.js:33-93`) returns the shape every diff is computed from: `{ id, ts, type, attacker, defender, town:{id,name,x,y}, units, resources, loot, outcome, wall, alliance, vill_id, vacation }`. The defender block is normalised by `nameOf` (`src/parse-inline.js:1-16`) and includes `vacation` plus `alliance`.
- The intel panel is a **single `<pre class="intel-panel">`** element rendered by `renderIntel` (`src/intel.js:75-114`). It writes `box.textContent = html` — a flat text dump of `=== Entrantes ===`, `=== Fichas ===`, watchlist, alliance notes, pattern note. There is no per-city history view today.
- `intelDossiers` (`src/intel.js:34-71`) already groups findings by player (not by town) and surfaces `reports`, `units[]`, `towns[]`, `walls[]`, `last ts`, plus `state.playerNotes[name]`. `walls` is appended unconditionally for **every** finding (intel.js:62) but no aggregate min/max is computed or rendered. `intelThreatBoard` (intel.js:72-74) and `intelPatternScan` (intel.js:206-245) are sibling read functions, called by `renderIntel` and `boot.js:114`.
- Table rendering helpers exist: `tableShell(list, headers, key)` (`src/ui.js:72-91`) + `makeSortable(table, rowDataFn, key)` (`src/ui.js:45-60`) + `patchCells(tr, cells)` (`src/ui.js:92-110`). They are how Farms (ui.js:130) and World (ui.js:203) render today.
- Sticky sort: `state.tabFilters` (`src/ui.js:1-13`) + `sortApplySaved` (`src/ui.js:38-44`) — every `makeSortable(key)` saves its sort under `sort:<key>` and re-applies it after row-set rebuilds. This is what stops "the chosen sort is lost on repaint" (plan 26 §B4).
- Plan 27 §9 already-shipped list does **not** include enemy-city timeline (it lists "Battle report basics (intel.js 13.x) — extending in 2.5"). 2.2 is net-new.

## 2. Gap

Dossiers tell you "this player has been seen in 8 reports". They do not tell you "this city was at wall 12, is now wall 18, gained 40 hoplites, and switched alliance on `ts` X". The 500-cap ring buffer already contains the raw data — wall per finding is captured (parseReport line 88), units per finding is captured (parseReport line 84), and the intel panel never reads them in a per-city axis. 2.2 closes that gap by grouping findings by `town.id` (or `vill_id` for farm raids) and emitting a chronological diff per town.

## 3. Design

- New function `intelCityTimeline(townKey, opts)` in `intel.js`. `townKey` resolves to one of: `town:<id>` (city reports), `farm:<id>` (village raids where `vill_id` is set), `player:<name>` (aggregate by attacker/defender). The function reads `state.findings` only — no new storage.
- Diff dimensions per adjacent pair (oldest→newest), in order:
  1. `wall` (number) — show `+N`/`-N` only when both sides are finite numbers. Unknown ⇒ `?`.
  2. `units` (attacker for offense, defender for defense) — count per unit key, render `Δhoplite 0→40, Δsword 0→10`. Empty `units` object ⇒ `unidades:?` (parseReport:84 only writes keys with `Number.isFinite && > 0`, so absence is unknown not zero).
  3. `resources.wood/stone/iron` (parseReport:27-31) — show last known with `+N` since prior. Loots seen on offense reports only.
  4. `town.name` change (parseReport:80) — render `nombre: "A" → "B"` only on change.
  5. `alliance` change (parseReport:89) — render `alianza: X → Y` only on change.
  6. `vacation` flag (parseReport:91, normalised at parseReport:14) — render `vacaciones ON/OFF` on transition.
  7. Buildings and hero presence: **not implemented today**; explicitly mark as `—` in the table so 2.1 deep-parse can fill them in later without changing the column layout. Plan 27 §2.1 is the source; once it ships, the diff function reads the new fields if present and shows `?` otherwise. This avoids a brittle v1.0 schema lock-in.
- 7-day soft retention filter at read time: filter `f.ts >= now - INTEL_HISTORY_TTL_MS` before grouping. The constant lives in `intel.js` and is reused by 2.3 and 2.4 (one retention policy for the read trio). This is what plan 27 §13 calls the "7d uniform unless the slice needs longer" convention; the journal already does 7d (`src/bridge.js:447`).
- Per-town hard cap: keep the last **8** reports per town in the diff (oldest trimmed). The 500-cap findings ring already bounds global size; the 8/town cap is a UI/payload cap so the table does not grow unbounded for a noisy target.
- Render path: a new sibling `<div class="intel-timeline">` under the intel section in `ui.js:692-707`. `renderIntel` calls a new `renderIntelTimeline()` that builds a `tableShell(['Fecha', 'Muro', 'Unidades', 'Recursos', 'Nombre', 'Alianza', 'Vac.', '—'], 'intel-timeline')`. The `—` column is the buildings/hero placeholder and the cell renders literal `—` until 2.1 lands.
- No scheduler, no `gbInterval`. Read functions only. Wired into the existing 15s `renderIntel` (`src/boot.js:108-115`) which already runs alongside `intelPatternScan`. No `GB_LOCK_TTL` entry (no write), no `WORLD_SCOPED_BASES` entry (no new storage key), no `configVer` bump (read-only feature with no new Config toggle).
- No `alertWebhook` (read-mostly diff for human eyes; no event surface), no captcha feature key.

**No post surface.** This feature is read-only. No `bridgePost`, no `gameAjaxPost`, no `gbAjaxWatch` registration, no template name in `TPL_FEATURE_MAP`, no `gbCaptchaPause` feature key, no `gbLock`/`GB_LOCK_TTL` entry, no `state.dryRun` interaction, no confirm gate. ## 8. Failure modes

- **Empty `state.findings`:** `renderIntelTimeline` writes the empty-state row. No log.
- **All findings filtered by 7d:** log once via `gbLogT('intel-timeline-empty', 300000, …)`, render the empty-state row. The throttle key keeps it quiet on subsequent renders.
- **Unknown wall/units/resources:** render `?` (not `0`). The diff function treats unknown as "no comparison" and emits `sin cambio` against a known side. Honest unknown beats fabricated zero — same rule as the precondition invariant in CLAUDE.md.
- **`parseReport` shape change in a future release:** the diff function reads named keys directly. If a key disappears, the call site sees `undefined` and renders `?` (per item 4). No throw path. If a key is renamed, the column silently goes empty — caught by Preflight's "findings schema" row, which is already read-only (CLAUDE.md "Preflight ... probes every module's read path only").
- **ts in seconds (legacy / future client):** the `parseReport` heuristic at `parse-inline.js:65` (`if (n < 1e12) n *= 1000`) catches this. The empty-timeline log is the trip wire.

## 9. Validation gate

Per plan 27 §11 (Low risk) — Preflight + one in-game session, no failure.

1. Build, install, open a world with at least 3 reports on the same enemy town.
2. Open the Intel tab. Below the existing `<pre>` text dump, the new `intel-timeline` table lists the town, with rows in ascending `ts` order; first row's `prev` column is empty, subsequent rows show `+N muro` / `unidades: 0→40` / `+5k madera` deltas. Last row `ts` matches the most recent finding's `ts` for that town.
3. Sort by `Muro` desc: top row has the highest `cur` wall across the visible groups. Reload the panel (close+reopen) — sort survives (sticky via `state.tabFilters.sort:intel-timeline`).
4. Force the 7d filter: `state.findings[0].ts = Date.now() - 10*86400000` from console, reopen Intel. The filtered-out town no longer appears; the `gbLogT` log fires once.
5. Preflight row "findings schema" still passes; Stats tab decisions counters unchanged (no journal entries — feature is silent on the journal because it is read-only).

## 10. Out of scope

- **Cross-city aggregate by alliance.** Owned by 2.5 (battle report analyzer) and 5.3 (threat assessment). Reusing `intelDossiers` alliance rollup is the natural place; defer.
- **Tombstone / outpost intel.** No game endpoint exists for it in the bridge model; would be a separate read feature. Out of scope per plan 27 §0 (no new game endpoints invented).
- **Writes.** This plan never posts. Re-introducing writes means a confirm-gate per plan 27 §11 Med and a new `gbCaptchaPause` feature key — both deferred until a real use case lands.
- **Player inactivity tracker (2.4) and ghost-town detector (2.3).** Sibling features with their own plan files; they share `INTEL_HISTORY_TTL_MS` but do not call into `intelCityTimeline`.
