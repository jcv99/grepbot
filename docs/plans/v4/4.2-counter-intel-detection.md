# 4.2 — Counter-intel detection (origin pattern)

**Bucket:** v4.2 · **Risk:** Low · **Size:** S
**Module:** extend `src/intel.js`
**Depends on:** none (consumes `state.findings` and `intelMyIdentity` which
already exist).
**Status:** PLANNED — written 2026-08-10 against `src/` @ v3.8.2

## Policy boundary (read first, before §1)

Plan 27 §0 explicitly bans **"Anti-pattern detection (anti-counter-farm)"**
with the reason "Anti-cheat avoidance; explicit policy ban." That policy row
is about *detecting patterns a player uses to dodge GrepBot*, e.g. looking
for users who go inactive just before an attack or who sit on vacation to
avoid retaliation. **4.2 does not do that.** 4.2 only watches incoming
reports whose `defender` resolves to me — i.e. who is **spying on me** — and
groups them. That is the inverse direction: passive observation of an
inbound signal the game itself delivers as a report. 5.3's threat engine is
also inbound; both are read-mostly, no posts, no fingerprinting of other
players' behaviour.

If a future contributor wants to widen scope (e.g. predict *whether* the
watcher will attack soon, or correlate spy timings with travel patterns)
**that is a new plan and must be re-checked against §0 first**. 4.2 ships
within the policy line.

## 1. What exists today

- `state.findings[]` (`src/spy.js:249`, capped at 500, key
  `STORE.FINDINGS` already in `WORLD_SCOPED_BASES`) is the input set. Every
  parsed report carries `type` (e.g. `'spy'`, `'attack'`, `'support'`,
  `'raid'`, `'conquer'`, `'siege'`, `'revolt'`, `'take_over'`,
  `'colonize'` — see `src/dodge.js:39-40` and `src/parse-inline.js:51`).
- `intelMyIdentity()` (`src/intel.js:17-27`) returns `{id, name}` from
  `MM.getModelByNameAndPlayerId('Player')` and `Game.player_id / player_name`,
  catching all known client variants today (`src/intel.js:23-25`).
  Returns `{id:null, name:null}` on read failure.
- `intelActorIsMe(actor, me)` (`src/intel.js:28-33`) compares by id first and
  name second, exactly the pattern required here.
- `intelPatternScan()` (`src/intel.js:206-245`) is the closest functional
  precedent: 24h rolling window, attacker aggregation, dedup via
  `state.alerted[ak]`. 4.2 follows the same shape and reuses
  `alertWebhook('counter-intel', payload)` — the event name is new but
  reuses the existing event bus in `src/alerts.js:28-87`. The 5-min rate
  limit on webhooks (`src/alerts.js:44`) and `state.webhookEvents[event] ===
  false` opt-out (`src/alerts.js:39-40`) apply unchanged.
- `state.alerted` (`src/core.js:229`) is the existing key-value dedup store.
  Already used by `intelPatternScan` with key shape
  `'pattern:' + key + ':' + bucket` (`src/intel.js:229`). 4.2 mirrors that.
- The intel pattern scan already fires `alertWebhook('attack', …)` for
  watchlist matches (`src/intel.js:202`) and `alertWebhook('pattern', …)`
  for pattern hits (`src/intel.js:242`). 4.2 will fire
  `alertWebhook('counter-intel', …)` — different event label, same bus.
- Plan 27 §9 row "Support ETA, attack pattern, watchlist why" is already
  coded (`src/intel.js:89, 109-111, 133-193`). 4.2 is a **different
  signal** (observation by YOU, not on you) and a different event label.

## 2. Gap

The intel picture answers *who is attacking you* (threat board,
`src/intel.js:72-74`) and *what your own findings say about other players*
(dossiers, `src/intel.js:34-71`). It does not separately answer *who is
watching your towns*. The existing `intelPatternScan` only counts hostile
movements; a sustained spy campaign by another player reads as one-or-more
`'spy'` rows in `state.findings` and is otherwise indistinguishable from
your own scout-on-someone-else reports. The user has to scroll the Findings
tab and filter manually to spot recurring spies on the same town.

## 3. Design

A single scan function `intelCounterIntelScan()` modeled directly on
`intelPatternScan()`. Inputs: `state.findings` + `intelMyIdentity()`. Output:
a `Map<attackerKey, stats>` keyed by the existing `intelPlayerKey`
(`src/intel.js:1-10`) — same key used by `intelDossiers()` so a row can be
cross-referenced.

A finding qualifies when **both** of:

1. `f.type === 'spy'` (with `parseReport` already lower-casing and
   `src/dodge.js:39` enumerating known hostile types, the universe is well-
   bounded; we read `f.type` raw without regex-based classification so a
   future client rename to `'scout'` only breaks the spy filter, not the
   attack filter).
2. `intelActorIsMe(f.defender, me)` — i.e. the report's defender resolves
   to me (or one of my towns). Where the report shape names `f.town.id`
   only and `f.defender` is null, the test extends to "town resolves to
   me"; both nulls ⇒ skip (policy: never infer identity from a missing
   field).

Stats per attacker:

```
{
  key, name,
  reports: number,            // count of qualifying rows in window
  distinctTargets: number,    // distinct town ids targeted
  towns: string[],            // town ids as strings, max 8
  first, last,                // timestamps
}
```

**Threshold + window** — same shape as `intelPatternScan`: 24h rolling
window (`src/intel.js:208`); trip at `n >= 3` matches (configurable, see
§6). A single spy report is not actionable — three in a day is a watch
state, not speculation.

**Webhook payload** — `alertWebhook('counter-intel', {watcher: ..., n: ...,
towns: ...})`. Reuses the existing alert path; the event label is new and
the user's `state.webhookEvents[event]` (`src/core.js:313`, default
`attack:true`) becomes the opt-out gate. Plan 26 §B4-style: the opt-out is
not pre-staged; adding the key to the default object matters — see §5.

**Dedup** — same key shape as `intelPatternScan`:
`'counter-intel:' + key + ':' + bucket` against `state.alerted`. Without
dedup the same attacker would fire a webhook every render (15s loop,
`boot.js:108-115`).

**Display** — extend the existing `renderIntel()` (`src/intel.js:75-114`)
with a `=== Contra-inteligencia ===` block above the `=== Fichas ===`
section, listing the same top-N (cap 5) the pattern scan uses. Reuses the
existing redactor for attacker names (`src/intel.js:235, 238`,
`state.exportRedact !== false`) — the Webhook payload is the one place
that holds the unredacted name because the user opted in via
`state.webhookUrl`.

## 4. Work items

1. **`src/intel.js`** — add `intelCounterIntelScan()`:
   - filter `state.findings` for `f.type === 'spy' &&
     intelActorIsMe(f.defender, intelMyIdentity())`;
   - aggregate by `intelPlayerKey(f.attacker)` over a 24h window;
   - emit a hit when `n >= threshold` (default 3, see §6);
   - dedup via `state.alerted['counter-intel:' + key + ':' + bucket]`;

## 5. State & storage

- **One new field**: `state.intelCounterIntel`, persisted to
  `STORE.INTEL_COUNTER` (`src/header.js`).
- The new key **must** go in `WORLD_SCOPED_BASES` (`src/header.js:193-214`)
  only if it carries id-bearing data. 4.2's key holds a **boolean**, so
  per CLAUDE.md "world-scope id-bearing storage" the key is **not** added
  to `WORLD_SCOPED_BASES`. (It would be wrong to scope a global toggle by
  world and surprising the user when they switch.)
- `state.webhookEvents.counterIntel` — the new event-label gate. Default
  `false`. The default object at `src/core.js:313` is `{captcha: true,
  attack: true, warehouse: false, culture: false}` — extend it to
  `…, counterIntel: false}` (a guarded merge in `migrateConfig`
  `src/core.js:489-505` is **not** required; first run with no stored
  object reads the new default whole). Plan 26 §B6: do not ship a Config-
  shaped field that does nothing — every gate is read by `alertWebhook`
  via `src/alerts.js:39-40`.
- **No `configVer` bump** — adding fields to defaults is additive and the
  loader's `load(..., defaultObj)` merge covers it.
- **No prune TTL for the alert dedup** — handled by
  `core.js:1160-1162` global prune of `state.alerted` already.
- **No new lock**, **no new scheduler** — runs from
  `renderIntel()` cadence at 15s (`boot.js:108-115`).

## 6. Config surface

| Field | Type | Default | Why |
|---|---|---|---|
| `[data-cfg=counter-intel]` | checkbox | **OFF** | Webhook fire opt-in; align with `csAlert` / `culturalGoldBudget` defaults that are read-mostly but still surface to the user. |
| `state.counterIntelThreshold` | number | 3 | Hysteresis — a single spy is noise; ≥3 in 24h is a watch state. Range 2..20, integer. |

The threshold is read-only on the panel today — adding a numeric field is
optional and **deferred** (per plan 27 §13 "Every Config toggle has a
`configVer` bump"; if added it follows the `data-cfg=counter-intel-thresh`
pattern at `src/ui.js:1393-1401`). Default of 3 keeps the scan quiet for
ordinary play.

**HIGH-RISK?** No — read-only aggregation, opt-in webhook.

## 7. Post surface & safety

None. The whole flow is read-mostly over `state.findings`. No
`bridgePost`, no `gameAjaxPost`, no `gbAjaxWatch`, no `gbCaptchaPause`
entry. Plan 27 §7's "no post surface" applies in full — section gets one
honest line by the README §7 rule.

## 8. Failure modes

- **`intelMyIdentity()` returns `{id:null, name:null}`** (`src/intel.js:26`)
  — `intelActorIsMe` returns `false`, the scan filters everything out, no
  webhook fires. Throttle a single `gbLogT('counter-intel-blind',
  600000, 'intel: identity unreadable — counter-intel scan skipped')`
  so the user can tell WHY the panel is empty.
- **`f.defender` is null and `f.town` is null** — skip. Inferred from the
  signature `parseReport` returns (`src/parse-inline.js:77-83`), both fields
  are independently nullable. The "defender resolves to me" test requires at
  least one of them; otherwise the row is invisible to this scan.
- **`state.findings.length > 500`** — already capped at intake
  (`src/spy.js:250-253` and `src/core.js:1167-1171`). Per CLAUDE.md "we
  shall never let a silent re-bind invalidate prior reasoning", the
  threshold check is **post-aggregation**, so a 500-row cap that drops
  older spy findings can only reduce "n" (never artificially *raise* it).
- **`type === 'spy'` case mismatch** (`'Spy'`, `'scout'`) —
  `parseReport` (`src/parse-inline.js:51`) does not lowercase `r.type` and
  on some clients sends title-cased strings. Match `/^spy$/i.test(f.type)`
  instead of strict equality, mirroring how
  `intelPlayerKey` (`src/intel.js:1-3`) trims but does not lowercase.
  Document this as the only normalization step; do not extend silently.
- **Webhook spam** — handled by the dedup key
  `'counter-intel:' + key + ':' + bucket`. The bucket
  `Math.floor(now / windowMs)` rolls at the 24h boundary exactly as in
  `intelPatternScan` (`src/intel.js:228-229`).

## 9. Validation gate

Plan 27 §11 risk class Low: preflight + one in-game session, no failure.

- Preflight row `intel: counter-intel scan`: pass when
  `state.findings.some(f => /^spy$/i.test(f.type || ''))` is true and the
  scan runs; warn when the identity getter is unreadable.
- Manual, Config-driven: enable `[data-cfg=counter-intel]`, point a
  webhook URL at a Discord test channel. Hand-trigger ≥3 spy reports on
  a single town (visit the town with a few scout missions). Expected: one
  webhook fires within 15s of the third report, with redaction off
  (`state.exportRedact !== false`) showing the attacker name. Log shows
  `counter-intel: <player> hit Nx in 24h` once.
- Negative path: enable but rewind one finding (or filter by attacker
  with a watchlist-rule that excludes me). No webhook fires when `n <
  threshold` even with the toggle ON. Log stays empty.
- Policy guard: verify the Log has **no** entry that fingerprints another
  player's behaviour (e.g. "player's session appears tactical"). If a
  contributor ever extends the readout to correlate spy timing with
  attack timing, **stop** — that crosses plan 27 §0's explicit ban.

## 10. Out of scope

- **Threat assessment engine** (plan 27 §5.3 = `5.3-threat-assessment-engine.md`,
  this cluster). Different signal: 5.3 scores *current* hostiles against
  each of **my** towns; 4.2 is who has been *watching* me over a 24h
  window. The schemas do not overlap.
- **Battle report analyzer** (plan 27 §2.5 = `2.5-battle-report-analyzer.md`,
  this cluster). 2.5 reads the same `state.findings` for losses + farms;
  4.2 reads them for spy origins. Re-use the existing collection, no new
  ingestion.
- **Spy report deep parse** (plan 27 §2.1): when 2.1 lands,
  `state.findings[i]` carries more fields per row (buildings, hero). 4.2
  reads only `type`, `attacker`, `defender`, `town`, `ts`. No re-write.
- **Counter-farming / counter-cheat evasion** — explicitly forbidden by
  plan 27 §0. If anyone wants to spot a watcher who is about to attack,
  that's a separate plan that has to clear the policy gate first.
- **Persist per-watch list beyond dedup** — no per-player `watchedAt`
  history. The dedup bucket plus `last-seen` from `intelDossiers()`
  (`src/intel.js:55, 63`) covers the use cases without a new key.
- **Outbound counter-spy auto-response** — out of scope and would
  violate the same §0 line. Inbound spy reports are passive intel.
