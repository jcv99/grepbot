## 1. What exists today

The per-town profile engine is **already largely built**. Plan 27's hint
("profiles already partially exist via `qol.js` templates (9.2)") is
misleading — `qol.js:12-44` (`qolSaveTemplate` / `qolApplyTemplate`) is a
named multi-config snapshot applied to **all** towns at once, not a per-town
profile engine. The real partial feature is in `goals.js` +
`build-tab.js:464-473`:

- `GOAL_PROFILE_DEFAULTS` (`build-tab.js:464-473`) — **8 profiles**:
  `custom`, `economy`, `offense_land`, `defense_land`, `offense_naval`,
  `defense_naval`, `conquest`, `favor`. Each carries `{label, build,
  research, units, reserve:{hard,soft}}`. **No `balanced` key** exists.
- `goalProfiles()` (goals.js:1) merges defaults with `state.goalProfiles`.
- `goalTownCfg(townId)` (goals.js:5-12) returns / lazily seeds
  `state.townGoals[id] = {profile:'custom', build, research, units,
  reserve}`.
- `goalEffective(townId)` (goals.js:14-19) merges override over named
  profile (override > profile > nothing).
- **Read-side contract already in production** (goals.js:21-44):
  - `goalEffectiveBuildTargets(tid)` — `build-auto.js:182`,
    `queue-center.js:246`.
  - `goalEffectiveResearchTargets(tid, globalTargets)` — `research.js:450`,
    `queue-center.js:246`.
  - `goalEffectiveRecruitTargets()` — `recruit.js:270`.
  - `goalReservePolicy(tid)` (goals.js:20) — planner reserve policy.
- `goalPlanTown(townId)` (goals.js:63-101) writes a 40-row virtual plan to
  `state.virtualQueue[tid]` (persisted at `STORE.VIRTUAL_QUEUE`,
  `header.js:151`).
- Writers: `goalSetProfile(tid, id)` (goals.js:103) is the writer the UI
  `<select>` at `qol.js:55` calls; `goalSetTownOverrides(tid, obj)`
  (goals.js:123) is the writer the **Edit** button at `qol.js:52` calls.
- State (`core.js:353-354`), storage (`header.js:149-150`), world-scoping
  (`header.js:209`), migration (`core.js:455-460`, ver=6), config
  export/import (`qol.js:251,256`) all exist.
- `boot.js:160-165` re-exports the public surface onto `gb` — `goalProfiles,
  goalEffective, goalPlanTown, goalPlanAll, goalSetProfile,
  goalSetTownOverrides`.

Plan 27's "9.2" reference does not match any numbered section of plan 27
(§9 enumerates 15 already-shipped features; "city profiles" is not one).
The hint is a misread; the partial feature to widen is `goals.js` +
`build-tab.js:464-473`.

What is **absent** relative to the plan 27 spec:

1. The 5 spec names — `offensive / defensive / resource / balanced / custom`
   — do not exist as keys. Closest mapping is `offense_land` / `defense_land`
   / `economy` / (none) / `custom`.
2. Plan 27 names the read API `gbCityProfile(townId)`. The existing API is
   `goalEffective(townId)`. **No `gbCityProfile` symbol exists** in `src/`
   (verified — zero hits across the tree).
3. **Transport (1.3) read-side** is the only feature plan 27 §1.2 names
   that does not yet read the profile. Since 1.3 is itself planned
   (§10 sequences 1.2→1.3), 1.2 must not block on 1.3 — it must expose
   a stable key on the profile schema so 1.3 hooks the same function
   without a second migration.
4. The `custom` path (goals.js:23,28) deliberately disables the named
   profile when a per-town override is present. Semantically correct but
   invisible to users — no panel hint that "custom = use los overrides JSON
   de esta ciudad".

## 2. Gap

The plan-27 spec needs three things on top of what is already coded:

(a) **A canonical alias surface** — the codebase's long-standing name
(`goalEffective`) is fine internally; the spec asks for `gbCityProfile`.
Ship the alias (one line) and keep the old name as the implementation so
`goalEffectiveBuildTargets` / `goalEffectiveResearchTargets` /
`goalEffectiveRecruitTargets` keep their existing callers in
`build-auto.js:182`, `research.js:450`, `recruit.js:270`,
`queue-center.js:246` untouched.

(b) **The 5 spec category names as aliases on the profile table** — map
`offensive → offense_land`, `defensive → defense_land`, `resource →
economy`, add a new `balanced` entry, and keep `custom`. The
per-town override path on `state.townGoals[townId]` is already the
customization surface; nothing else to build there.

(c) **A transport- and resource-flavoured schema widening** so 1.3 (and
5.1 resource-balancing AI) can read the same `gbCityProfile(townId)`
without re-plumbing. Two new optional sub-keys: `defensive` (a 0–1
wall-priority weight the planner + future 4.5 wall-auto-repair can
read) and `resource` (a `{wood, stone, iron}` direction bias the
1.3 transport loop and 5.1 LP solver will eventually consume).
Adding them in 1.2 means 1.3 ships against a real contract instead of
guessing one. Both are read-only here — no consumer other than
`goalReservePolicy` (which already reads `reserve`) touches them in
1.2's own diff.

No new post surface. 1.2 reads state and feeds existing consumers; the
orchestrator (`src/orchestrate.js`, dispatched via `src/qol.js:421-435`)
already wakes each consumer on its own cadence.

## 3. Design

Data flow — Overview → Goals panel (`qol.js:48-57`):

- `<select>` → `goalSetProfile(townId, name)` (`goals.js:103`) writes
  `state.townGoals[townId].profile`, persists to `STORE.TOWN_GOALS`,
  calls `goalPlanTown(townId)` which writes `state.virtualQueue[tid]`.
- **Edit** button → `goalSetTownOverrides(tid, JSON)` (`goals.js:123`)
  for the same town.

Read-side contract (already in production; no change in 1.2 — verified
each call site against the tree):

| Function | File:line | Called by |
|---|---|---|
| `goalEffectiveBuildTargets(tid)` | `src/goals.js:21` | `src/build-auto.js:182`, `src/queue-center.js:246` |
| `goalEffectiveResearchTargets(tid, globalTargets)` | `src/goals.js:27` | `src/research.js:450`, `src/queue-center.js:246` |
| `goalEffectiveRecruitTargets()` | `src/goals.js:39` | `src/recruit.js:270` |
| `goalReservePolicy(tid)` | `src/goals.js:20` | planner + simulator |

A new alias on `src/boot.js:160-165` export surface —
`gbCityProfile: goalEffective`. Plan 27 names this function literally
and downstream plans 5.5 + 5.6 will read it; ship the name so the spec
holds while keeping the existing callers in
`build-auto.js:182` / `research.js:450` / `recruit.js:270` /
`queue-center.js:246` untouched.

Schema widening — add two optional sub-keys to every entry in
`GOAL_PROFILE_DEFAULTS` (`build-tab.js:464-473`): `defensive: <0..1>`
(wall + dodge weight, 0.5 neutral) and `resource: {wood, stone, iron}`
in -1..+1 each (transport / planner bias). The per-town override
schema widens identically on `state.townGoals[townId]` via
`goalSetTownOverrides` (`goals.js:123`). Defaults of
`defensive: 0.5, resource:{wood:0, stone:0, iron:0}` keep the change
forward-compatible for towns that never set a profile.

## 7. Post surface & safety

**Read-only for the feature itself.** 1.2 adds no posts, no bridge
calls, no `gbAjaxWatch` registration, no `TPL_FEATURE_MAP` entry,
no `gbCaptchaPause` feature key, no `gbLock` name, no `GB_LOCK_TTL`
entry. All downstream posts happen inside the existing four
consumers (`build` / `research` / `recruit` / `transport`); they
already have those entries and continue to use them.

Precondition invariant holds by inheritance: every consumer checks
real game-side values (`abCanAfford`, `recruitCanBuild`,

profile is an *input* to those checks, not a substitute.

## 8. Failure modes

- **Profile id not in `GOAL_PROFILE_DEFAULTS`** — `goalSetProfile`
  (goals.js:103) returns `false` and logs nothing. After this
  change, that check is unchanged. The new `balanced` id is added
  to the defaults, so any user picking it lands on a real entry.
- **`defensive` / `resource` written with bad value** — the new
  `cleanNum` calls in `goalSetTownOverrides` (work item 4) clamp to
  range and drop non-finite. Persisted garbage → defensive read
  returns `0.5` (the seed), which is the documented neutral value,
  so a corrupted town goal never blocks the build/research/recruit
  loops.
- **Town id missing from `state.townGoals`** — `goalTownCfg`
  (goals.js:5-12) lazily seeds the empty object on every call;
  this is unchanged. New sub-keys are seeded the same way
  (work item 2).
- **Per-town override without a named profile** — `cfg.profile ===
  'custom'` already routes the four `goalEffective*` readers
  through the override path (goals.js:23,28,42). The widening
  preserves this: `e.defensive` and `e.resource` still resolve via
  the same merge order (override > profile > 0.5/0).
- **Migration collision** — none. Existing `state.townGoals`
  payloads are objects with `{profile, build, research, units,
  reserve}`. After the bump they will simply lack `defensive` and
  `resource`; `goalTownCfg` re-seeds them on first read.
- **`gbCityProfile` referenced before `boot.js` runs** — exports
  are added in `boot.js:160-165` which runs after all modules
  load (build.py:70). Callers that fire from inside
  `orchTick`-driven consumers (`build-auto.js:182`, etc.) only
  fire after `gbBoot` finishes. No ordering hazard.

## 9. Validation gate

Low-risk. Per plan 27 §11 / `ROADMAP.md` discipline:

1. **Preflight** (Stats → Preflight / Actions → Preflight) reports
   `goal profile: pass` — iterate `Object.keys(state.townGoals)` and
   assert every `profile` id is a key in `goalProfiles()`. Add the
   row to `preflightRun` (`src/stats.js:12-191`). For an upgrade
   this must pass without user action; for an empty install it is
   informational.
2. **One in-game session, no failure.** Open Overview → Goals.
   Pick `defense_land` for town A, leave town B on `custom`,
   press **Recalc** on A. Log shows the profile-set event and the
   next `build: town <A> …` decision references the new targets.
   Town B's decisions are unaffected. Switch A to `balanced` and
   verify the build target order reorders to
   `main → storage → farm → market → …`. **Edit** A's overrides
   JSON to set `defensive: 0.9, resource: {wood:-1, iron:+1}`;
   confirm the values round-trip on a second **Edit**.
3. **Dry-run smoke** — with `state.dryRun` ON, run one build tick
   for town A. Journal shows `build: <building> planned` (not
   `skip:dryrun`). Confirms 1.2 is not silently blocking anything.
4. **Storage redaction** — Copy config (`ui.js:986`); the new
   `defensive` / `resource` keys ship raw (no player data) and
   existing redaction rules in `qol.js:225-247` still apply.

The plan 27 §1.2 validation gate ("pick profile 'defensive' for a
town → Log shows recruit mix bias changed for that town only;
other towns unaffected") is **already met** by `goalEffective*`
plumbing in production — 1.2 only adds the `balanced` key, the
`gbCityProfile` alias, and the schema widening.
