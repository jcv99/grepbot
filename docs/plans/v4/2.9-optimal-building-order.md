# 2.9 — Optimal building order

**Bucket:** v4.0 · **Risk:** Low · **Size:** M
**Module:** extend `goals.js` (the planner hook already lives there); helpers
in `build-targets.js` only if a new priority-knob surface is needed.
`build-auto.js` and `native-ui.js` are consumers, not editors.
**Depends on:** none (consumes `goalProfiles` / `goalEffectiveBuildTargets`
which already exist; the city-profile shape planned by 1.2 is optional, not
required)
**Status:** PLANNED — written 2026-08-10 against `src/` @ v3.8.2

## 1. What exists today

- **Per-town priority order, not a sequence.** `state.abOrder` is a single
  22-element array (initialised by `abDefaultOrder` `build-targets.js:2` from
  `AB_BUILDINGS` `goals.js:127-128`). `abMoveOrder` (`build-targets.js:9-18`)
  reorders it via Config UI buttons; `abEnsureOrder` (`build-targets.js:3-8`)
  re-fills missing slots. `goalBuildOrder(townId, extra)` (`goals.js:116`)
  layers the user's per-town `blocked` / `hidden` / `order` / `mandatory`
  overrides on top of `abOrder` and returns the final per-town ordered list of
  building ids consumed by `abPickNextFromLevels`
  (`build-auto.js:178-202`). This is what plan 27 calls "the priority order";
  it is *not* a build sequence, it is the rank each build target receives when
  competing for the next slot.
- **Goal planner already produces an ordered action list per town.**
  `goalPlanTown(townId)` (`goals.js:63-101`) walks `sim` levels building by
  building, projecting affordability against `plannerAvailable` (the ledger),
  and emits `{actions:[{kind:'build',id,level,forTarget,cost,costExact,status,why}]}`
  sorted by `goalQueueDecorate` (`goals.js:117`). It is what the Queue Center
  `renderQueueCenterResearch` "Próximas investigaciones" card shows and what
  `qol.js:50` (`goalPlanAll`) renders in the QoL preview. Preflight already
  probes it (`stats.js:249`).
- **The user's explicit queue wins.** `abPickNextFromLevels` reads
  `nativeQueueBuildPlan(townId, levels)` first (`build-auto.js:180-181`); if
  it returns `{hasJob:true, plan:...}` the planner uses *that* plan and never
  consults the goal targets. `nativeQueueBuildPlan` (`native-ui.js:337-352`)
  returns the FIFO head with cost / requirement / special-conflict reasons if
  blocked. The legacy path only runs when the town has **no** FIFO job *and*
  its `mode.build` is `legacy` (`native-ui.js:338, hasJob:nativeQueueIsFifo`).
- **No `abCustomQueue`, `abCqPrune`, `abGetPin`, `abQueueStrict`, or
  `buildPlanNext` in `src/`.** Plan 23 ("Custom per-town build queue",
  `docs/plans/23-custom-build-queue.md`) describes a feature whose symbols do
  not exist anywhere — verified by `rg 'abCustomQueue|abCqPrune|abQueueStrict
  |abGetPin|buildPlanNext|AB_CUSTOM_Q' src/` (zero hits). Plan 27 §9 lists
  "Custom build queue + instant precision + phoenician ratio pump | per-town |
  Coded v1.6": only the second half (instant precision) shipped in v1.6; the
  custom queue part was never written. This is the same class of mistake
  plan 26 §B2 caught (`intelSetAllianceNote`). The "explicit queue" we
  actually have is the **native FIFO queue** introduced in v2.5.x and made
  whole in v2.7.0 (`queue-center.js`, `native-ui.js`).
- **`goalQueueDecorate` / `goalBuildOrder` precedence** (`goals.js:115-117`):
  `mandatory` first, then lower `order` index, then profile rank. A user can
  already pin, block, hide, and reorder per-town in the Queue Center (see
  `queueCenterResearchPicker` `queue-center.js:173-195` for the research
  surface; the build surface uses the same plumbing).

## 2. Gap

Today the auto-queue runs `goalBuildOrder` → first target that has a
shortfall → prerequisite walk → post. That gives a **good next build**, not a
**good sequence**: it has no notion of which target to clear first when many
are still in progress, no cross-town view (each town's plan is independent
even though resources are shared via the planner), and no "queue these in
this order" affordance for the user to commit a plan. Plan 27 §2.9 wants
that sequence: an ordered list of `(building, forTarget, level)` per town
that minimises "stuck waiting" time, ranked against the planner's resource
ledger. Plan 23's `buildPlanNext` was the same idea (consume the custom list
at the head of the plan), but with a per-town custom list as input; since
that input does not exist, the feature must work off `state.abTargets` +
profile + planner ledger, and must respect the existing native FIFO head.

## 3. Design

The output is a `state.abOptimalOrder` map `{ [townId]: [{building, forTarget,
level, etaMs, cost}, …] }`, generated by a new `abOptimalOrderFor(townId)`
in `goals.js` that:

1. Reads `levels = abCurrentLevels(townId)` (`build-auto.js:14-33`).
2. Reads `targets = goalEffectiveBuildTargets(townId)` (`goals.js:21-26`).
3. Reads `avail = plannerAvailable(townId, {allowSoft:true})`
   (`planner.js:82-86`).
4. Sorts the build targets with a key that combines:
   - dependency depth (lower first; pull prereqs forward — same walk as
     `nativeQueuePrereqWalk` `native-ui.js:166-188`),
   - affordability gap from `avail` (`cost[k] - avail[k]`; positive = wait,
     zero/negative = go),
   - ETA penalty (`building_time` from `abBuildDataEntry`
     `build-auto.js:58-66`),
   - user's existing `goalQueueRank` tie-break (`goals.js:114`) so the
     reorder UI in Queue Center still wins on equal cost.
5. Walks `sim` exactly like `goalPlanTown` (`goals.js:73-83`), emitting one
   `actions` entry per simulated build until either `actions.length === 40`
   or the next entry is blocked on cost or dependency.
6. Persists the result to `STORE.AB_OPTIMAL_ORDER` (new key, see §5).

The result feeds two consumers:

- **Queue Center — "Secuencia óptima" sub-card** under the live FIFO and the
  plan cards in `renderQueueCenterBuild` (`queue-center.js:116-158`). One
  read-only line per entry (`#1 Senaduría 14→15 · 12m`), with a single
  **"Aplicar a la cola"** button that calls `nativeQueueAddBuild` for each
  entry in order (`native-ui.js:205-269`). The button is a **user-confirmed
  append**, never a silent replace: the user's existing FIFO head is left
  alone, the new jobs go to the tail, and the Queue Center re-renders so
  the user sees exactly what changed.
- **`abPickNextFromLevels` does not consult this.** The plan stays advisory;
  the explicit FIFO head still wins (`build-auto.js:180-181`). The optimal
  order only informs the user; it does not re-route the auto-queue. This is
  the precedence rule plan 27 §2.9 leaves implicit and that §1 of this plan
  makes explicit.

A new `abOptimalOrderOn` Config toggle (`state.abOptimalOrder`, default ON)
lets the user turn the advisory off entirely. Default ON is safe: nothing
posts without an explicit click.

  etaMs, cost}, …] }`. Id-bearing key, **add `STORE.AB_OPTIMAL_ORDER` to
  `WORLD_SCOPED_BASES`** in `header.js:193-214` (next to the existing
  `STORE.AB_ORDER` entry on line 209). Id-bearing ⇒ yes.
- `state.abOptimalOrderOn` (boolean, default true) — Config toggle; not
  id-bearing, no world-scope required.
- `configVer` bump (CLAUDE.md / plan 27 §13).
- Prune TTL: 7d uniform (plan 27 §13). Stale entries are harmless — the
  renderer just hides them — but they accumulate so add `pruneStaleOptimal`

## 6. Config surface

- `state.abOptimalOrderOn` (boolean, default **ON**). Risk is Low because
  nothing posts without an explicit click on "Aplicar a la cola"; this is
  the same posture as the existing `nativeQueueAddBuild` tile control.
- No HIGH-RISK toggle — feature is advisory. (CLAUDE.md HIGH-RISK rule
  does not apply.)
- `abOptimalOrderClear()` exposed as a `qol.js` Config row for parity with
  the other "reset" actions; it just deletes the cache.

## 7. Post surface & safety

- **No new post surface.** The only writer of build posts is still
  `bridgePost('build', …)` in `abBuildUp` (`build-auto.js:246`). 2.9 never
  calls it; the **"Aplicar a la cola"** button routes through
  `nativeQueueAddBuild` (`native-ui.js:205-269`), which itself never posts —
  it only mutates the in-memory FIFO list and re-arms `abScan('native')`
  (line 268).
- `gbCaptchaPause` — no new feature key needed; the post that fires after
  the user confirms already runs under the existing `captchaPaused('build')`
  gate (`build-auto.js:229`).
- `gbLock` — no new lock; `nativeQueueAddBuild` calls `nativeQueueSave`
  which schedules a UI re-scan, not a bridge call. `abScan` itself runs
  under `gbLock('ab', …)` (`build-auto.js:272`) which is reused.
- `gbAjaxWatch(sig, settle)` — no new template; nothing is being sniffed
  (the build post's payload `BuildingOrder/buildUp` is already learned and
  registered, see `core.js` template health row for build).
- `TPL_FEATURE_MAP` — no change.
- Dry-run gate — feature is read-only by design. If a future "auto-apply"
  variant is added it must respect `state.dryRun` (`bridge.js:190`) the same
  way `abBuildUp` does.

## 8. Failure modes

- **Unreadable levels / costs / planner ledger** → `abOptimalOrderFor`
  returns `{townId, error: 'levels-unreadable' | 'planner-unreadable',
  actions:[]}` and the Queue Center card renders `gbOptimalOrderEmpty(why)`
  with the same `abReasonText` strings the build tab already uses
  (`build-auto.js:132-159`). `blind` verdict — never silently pretend the
  sequence is complete.
- **Planner ledger is null** (one of `wood/stone/iron/pop/tradeCap`
  unreadable, `planner.js:42`) → walk stops at the first entry that needs
  the missing resource; the rest stay in the list with `status:
  'waiting-resources'` so the user can see what is gated and why.
- **Dependency cycle** (the walk goes deeper than 50 hops) → return the
  partial chain with `error: 'chain-too-long'`; same defensive superset
  pattern as `nativeQueuePrereqWalk` (`native-ui.js:184-188`).
- **`nativeQueueAddBuild` fails on a `special-conflict`** (`native-ui.js:207`)
  → flash the reason and abort the rest of the sequence; do not retry, do
  not split.
- **The user's existing FIFO head is not touched.** Precedence rule: FIFO
  head wins at `build-auto.js:180-181`; the optimal-order card is advisory
  only, so there is no case where it displaces an in-flight or paused head.

## 9. Validation gate

Manual, per plan 27 §11 Low class: Preflight + one in-game session, no
failure.

1. **Preflight** — Preflight rows:
   - `optimal build order` shows `8 entradas · 0 bloqueadas` for the open
     town; `1 entradas · 2 bloqueadas` after dropping the open town's
     warehouse to 0 via a `plannerCfg.towns[id].hard.wood = 1e9` Config
     edit (and reverting after).
   - `goal planner` row (`stats.js:249`) still passes; the new row does not
     regress it.
2. **Queue Center — Construcción** — for a town with at least one
   `abTargets[b]` shortfall, the "Secuencia óptima" card lists the next
   three builds in dependency-respecting order (a Senaduría 14→15 plan
   surfaces Granja 22→23 before Mercado 9→10 when both are below target).
3. **"Aplicar a la cola"** — click the button; the Queue Center FIFO card
   grows by N entries; the Live Build card (`abQueueInfo` `build-auto.js:45`)
   shows the first N-1 as `pending` and the last as `ready`; `abScan`
   (`build-auto.js:266-369`) fires within ~80ms and the first job lands.
4. **Precedence — FIFO head wins** — populate a town with a `[+]` queue
   that starts with a `Lumber 5→6`; verify `abPickNextFromLevels` picks
   lumber (not whatever the optimal-order card suggests as #1).
5. **Dry-run parity** — with `state.dryRun = true`, the new card still
   renders and "Aplicar a la cola" still works (it does not post). The
   `DRY-RUN build: … buildUp` line appears only after the auto-queue picks
   the head, not when the optimal-order button is clicked.

## 10. Out of scope

- Implementing plan 23's `abCustomQueue` / `abCq*` / `abPin`. Plan 23 is
  aspirational; rebuilding it on top of the native FIFO queue is a separate
  feature whose work plan is owed by plan 23's author. 2.9 here uses
  `state.abTargets` + planner ledger only.
- Cross-town sequence ordering (a single list across all towns). The
  planner ledger is per-town (`planner.js:37-45`); a multi-town solver
  belongs with the transport automation (1.3) and the resource balancing AI
  (5.1), not with 2.9.
- "Best next research" — that is the research lane's analogous problem;
  it is already handled by `goalEffectiveResearchTargets`
  (`goals.js:27-38`) and `renderQueueCenterResearch`'s "Próximas
  investigaciones" card (`queue-center.js:246-272`). Plan 27 lists it as
  5.5, owned by that plan.
- Any post. 2.9 is advisory only; auto-applying the optimal order without a
  user click would require a HIGH-RISK toggle and is deliberately deferred.
