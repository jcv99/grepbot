# 8.2 — State snapshots (5min auto-save)

**Bucket:** v4.1 · **Risk:** Low · **Size:** M
**Module:** extend `src/core.js` (the `save`/`load` pair is at `core.js:1088/1186`; the quota-aware prune is `storagePruneForQuota` at `core.js:1118-1175`); surface in `src/stats.js` (size gauge in Preflight per plan 20) and `src/ui.js` (Config toggle, restore menu).
**Depends on:** none (lives alongside plan 20's quota alarm; **must not** fight it).
**Status:** PLANNED — written 2026-08-10 against `src/` @ v3.9.0

## 1. What exists today

State persistence is **already event-driven, not time-driven** — every save is the immediate consequence of a state mutation. Evidence:

- `core.js:1186-1217` `save(key, val)` writes through `GM_setValue`, catches `QuotaExceededError`, calls `storagePruneForQuota()` (`core.js:1118`), retries once, and on second failure sets `storageWarnUntil/Message` for the footer badge (`ui.js:1839`).
- `core.js:1110-1116` module-level `let storageWarnUntil = 0; let storageWarnMsg = ''` — surfaced by `ui.js:1839` as `!quota:pruned` / `!quota FULL` after the badge.
- `core.js:1118-1175` `storagePruneForQuota`: ring-buffer trims `state.decisions` to 50, `state.seen` to `SEEN_MAX = 2000` (`core.js:299`), `state.alerted` to 3 days, `state.findings` to 100, `state.farmResources` to 24h. Each `try { … storageRawSet(wkey(STORE.…), …); bytes += … }`.
- `core.js:1088-1108` `load(key, fallback)`: world-scoped via `WORLD_SCOPED_BASES.has(key)` (set at `header.js:193-215`); `loadValueOk` rejects > 2 MB (`core.js:1101-1108`, `LOAD_MAX_CHARS`) — refused once, fallback returned, `gbLogT('load-huge', 60000, …)`.

Periodic saving is **already partly there for the journal**: `journal.js:103-114` `jrnSave(immediate)` debounces by `JRN_SAVE_MS = 5000` (`bridge.js:449`) with a `gbTimeout` flush on `pagehide`/`visibilitychange` (`journal.js:306-307`). The decision ring is 400 rows / 7 days (`bridge.js:446-447`). No other slice uses the debounce pattern.

What is **absent** for a 5-min snapshot:

- No whole-state JSON serialisation exists. `gbEvidence` (`stats.js:389-506`) builds an object for **diagnostics export** but never persists it; it omits heavy slices (`state.findings[].raw`, `state.attackHistory` payloads).
- No `state.snapshots` ring, no `STORE.SNAPSHOTS` key, no `gbInterval`-style periodic sweeper for snapshots. The 10s `gbLockSweep` (`boot.js:124`) is the only existing periodic work and it is unrelated.
- No restore path. A corrupted state today is rescued by `LOAD_MAX_CHARS` rejecting the bad key; there is no rolling-buffer of last-known-good copies.
- Plan 20 (Storage quota alarm, `docs/plans/20-storage-quota-alarm.md`) is **adjacent** but distinct: it measures per-key sizes and exposes a manual prune UI; it does not snapshot. Plan 20's `LOAD_MAX_CHARS` is the only thing that catches a corrupt state on read, and a snapshot mechanism would be the write-side complement.

## 2. Gap

A bot that runs for hours accumulates state mutations (every farm scrape `farms.js:869`, every `txSave` at `tx.js:534/547/559/610/627/661/686`, every decision `jrnSave`) without ever rolling a checkpoint. If `GM_setValue` corrupts a key in flight, or a quota prune (`storagePruneForQuota` `core.js:1118`) deletes more than it should, the only recovery is "lose everything since the last successful save" — and there is no way to know which save was last successful.

The catalogue promises a 5-minute auto-save snapshot. That snapshot **multiplies storage usage** (one extra full-state copy per slice per 5min) and **must reconcile with the quota alarm** or it will trip the alarm it is meant to back up. The concrete delta from §1 is a ring of 6 timestamped compact snapshots, kept under a hard byte budget, restored only by explicit user action.

## 3. Design

One ring `state.snapshots = [{ at, sizeBytes, payload }]` with **6 slots × 5min cadence = 30 min rolling window**. Persisted under `STORE.SNAPSHOTS`. Snapshots contain a **whitelist of slices** — never a raw `JSON.stringify(state)` of the whole `state` object — so a snapshot is bounded in size independent of how much unrelated state the bot carries.

- **Cadence.** A `gbTimeout`-driven self-rescheduling timer in `boot.js` (NOT a new `gbInterval`; piggybacks on the existing 10s `gbLockSweep` line at `boot.js:124` by extending the lambda). Snapshot at boot + 5min + 5min + …, flushed on `pagehide`/`visibilitychange` (same hooks `journal.js:306-307` already uses), skipped while `automationPaused({})` or `gbServerPaused()` (a paused bot has nothing new to save — same `dryRun`/`safeMode` posture as plan 22's write soft ceiling).
- **Snapshot shape.** `{ at, sizeBytes, payload }` where `payload = { cs: state.clientFingerprint, cV: state.configVer, cfg: { …whitelisted toggles… }, plans: { abTargets, researchTargets, recruitTargets, merchantWish }, txState, circuits, decisionSkips, farmOptionMap, farmSleepDay, lastSeenTs }`. Heaviest slice (`state.decisions`) is **summarised, not copied** (`{ ok: N, err: N, captcha: N, byFeature: { f: N }, topErrors: [...] }` — same shape as `jrnStats` at `journal.js:249-293`). Heaviest other slice (`state.findings`) is **omitted** unless `state.exportRedact === false` (otherwise included with `raw` stripped, plan 20 win).
- **Byte budget.** Hard cap `SNAPSHOT_BUDGET_BYTES = 200_000` (200 KB) per snapshot; total ring `6 × 200 KB = 1.2 MB`. Within the 5 MB GM budget (plan 20, `docs/plans/20-storage-quota-alarm.md:7`) the ring consumes ≤24% — well below the 70% warn threshold plan 20 proposes. **If** `JSON.stringify(payload).length > SNAPSHOT_BUDGET_BYTES`, the snapshot is dropped and `gbLogT('snapshot-oversize', 60000, …)` fires — never silently grow the ring.
- **Quota interaction.** `storagePruneForQuota` (`core.js:1118`) currently does not know about snapshots. Extend it: when pruning kicks in, drop the **oldest snapshots first** (ring tail) until `GM_setValue` succeeds, **before** touching `state.decisions`/`state.seen`/`state.findings`. This is the right precedence — a snapshot is the recovery artefact, so losing the journal ring to save a snapshot is wrong.
- **Restore path.** Manual only, via menu `GrepBot: restore snapshot N` (`ui.js`-style addition next to the existing `GrepBot: clear circuit breakers` at `ui.js:2020`). Lists the 6 slots with timestamp + size, requires `confirm()` (destructive), then writes the snapshot payload through the same `load`/`save` keys (so `state.abTargets` etc. re-load on next `load()` cycle — no in-place state mutation, no version-bump gymnastics). Disabled in `safeMode` (the existing `state.safeMode` gate at `core.js:471`; restore is a debug tool).
- **Read path.** `state.snapshots` is exposed through `gbEvidence` (`stats.js:432-506`) under a new `snapshots: { count: N, oldestAt: ts, newestAt: ts, totalBytes: N, budgetBytes: SNAPSHOT_BUDGET_BYTES }` block. Preflight `cost reads` (`stats.js:188-209`) gets a sibling `snapshots` row reporting `N/6 slots, M KB total`.

Data flow:

```
boot.js:124 10s sweep  →  if (now - lastSnapAt >= SNAPSHOT_INTERVAL_MS) snapshotBuild()
snapshotBuild()  →  payload = pickSlice(state);  sizeBytes = JSON.stringify(payload).length
                   if (sizeBytes > SNAPSHOT_BUDGET_BYTES) drop + log
                   else push to state.snapshots (ring of 6, head=newest), save(STORE.SNAPSHOTS, …)
save() quota path  →  storagePruneForQuota() drops oldest snapshots first, THEN ring buffers
```

## 5. State & storage

- New `STORE.SNAPSHOTS` (`header.js`) — world-scoped via `WORLD_SCOPED_BASES`.
- New `state.snapshots = [{ at, sizeBytes, payload }]` (`core.js:240-385`). Hard-bounded at `SNAPSHOT_MAX_SLOTS = 6` by `snapshotBuild` itself; never grows unbounded.
- New `state.snapshotEnabled` (default ON), `state.snapshotIntervalMs` (default 300000), `state.snapshotAt` (default 0), `state.snapshotRestoreOnBoot` (default OFF) — four new fields, each `load(STORE.…, default)` and `save(STORE.…)` on toggle.
- New `STORE.SNAPSHOT_ENABLED` / `STORE.SNAPSHOT_INTERVAL_MS` / `STORE.SNAPSHOT_AT` (three keys; `snapshotAt` is just a debounce marker, not a user-visible toggle). All world-scoped for consistency, though none of them carry id-bearing data — keeping world-scope prevents a future config migration surprise.
- New `CONFIG_VER_CURRENT = 11` (`header.js:191`). v11 migration copies nothing; only sets `state.snapshots = []` if undefined.
- Prune TTL: snapshots age out by ring-replacement (every 5min the oldest is overwritten). No time-based prune needed.
- **Size budget reconciliation** with plan 20 (`docs/plans/20-storage-quota-alarm.md`): 6 × 200 KB = 1.2 MB ceiling, ≤ 24% of the assumed 5 MB GM budget. Plan 20's 70% warn threshold (line 41) is not crossed by snapshots alone. When the **combined** size crosses 70%, plan 20's manual prune UI should list `snapshots` first (work item 12 of plan 20's "Files" section calls for per-key sizes — snapshots is just another row). The `storagePruneForQuota` change in work item 5 ensures automatic quota recovery preserves snapshots longer than any other slice.

## 6. Config surface

| Field | Type | Default | Notes |
|---|---|---|---|
| `snapshotEnabled` | bool | ON | Master kill-switch. OFF = never snapshot, never restore. |
| `snapshotIntervalMin` | int 1-60 | 5 | Minutes between snapshots. Lower = more recovery granularity, more storage. |
| `snapshotRestoreOnBoot` | bool | OFF | ON = on the first snapshot of a fresh load, restore the most recent slot if `state.configVer` matches. OFF = pure rollback tool, manual only. |

**HIGH-RISK OFF default**: N/A — snapshots are passive state, never trigger a write to the game. Per `CLAUDE.md` "HIGH-RISK toggles … default OFF" applies to game actions, not to local persistence.

## 7. Post surface & safety

This is **read-only infrastructure**: no new bridge posts, no `bridgePost`/`gameAjaxPost` calls, no `gbAjaxWatch(sig, settle)` registrations, no `TPL_FEATURE_MAP` additions. Snapshots are written **only** to `GM_setValue` (the same storage layer every other slice uses), never to the game.

- `gbCaptchaPause` feature key: not needed (no new post surface).
- `gbLock` name + `GB_LOCK_TTL` entry: not needed (no in-flight coordination).
- Dry-run: not applicable.
- **Bridge-first**: irrelevant.

The restore path is gated by `state.safeMode` (which already defaults `true` after the v3 migration at `core.js:471`). The menu item checks `!state.safeMode` and flashes a refusal otherwise — restore is a debug tool, not a normal action.

## 8. Failure modes

- **Snapshot payload grows past 200 KB.** `snapshotBuild` drops it, logs via `gbLogT('snapshot-oversize', 60000, …)`, leaves the ring untouched. The Preflight `snapshots` row surfaces the drop count via `gbLogT` so a pattern is visible. **Never** silently grow the ring — `state.snapshots.length > SNAPSHOT_MAX_SLOTS` would be a bug, not a feature.
- **`GM_setValue` quota failure during `save(STORE.SNAPSHOTS, …)`.** Goes through the existing `save` wrapper at `core.js:1186`. `storagePruneForQuota` is called first; with work item 5, snapshots are the first to drop. If the prune still doesn't free enough, the second `GM_setValue` retry fails, `storageWarnMsg = 'quota FULL'`, the footer shows `!quota FULL` (`ui.js:1839`), and the snapshot is lost for that tick. **Next** tick the ring still has the prior slots, so recovery is at worst 10min stale — acceptable per the plan's "30 min rolling window" promise.
- **Restoring a snapshot whose `configVer` mismatches the live `state.configVer`.** Plan 8.1 bumps to v11 in the same release; v11 is a no-op for snapshots (only initialises `state.snapshots = []`), so a v11 snapshot is restorable on a v11 build. A pre-v11 build would refuse (`configVer < 11`) and flash a refusal. The restore menu must read `payload.cV` and compare to `CONFIG_VER_CURRENT` before any `save()` call.
- **`pagehide` fires during a snapshot in flight.** The `gbTimeout`-self-rescheduling pattern in work item 6 means the build runs as one synchronous `JSON.stringify` + `GM_setValue`. Both are sync; `pagehide` cannot interleave. If the user navigates mid-`JSON.stringify` the worst case is a half-written payload, which `LOAD_MAX_CHARS` (`core.js:1101`) rejects on next load and falls back to `[]` — same recovery posture as a corrupt slice today.
- **Precondition invariant**: every guard checks a value it read. `snapshotBuild` reads `state.snapshotAt`, `state.snapshotIntervalMs`, `SNAPSHOT_BUDGET_BYTES`, the `payload` object — all in-memory. `snapshotMaybeBuild` reads `Date.now()`, `state.snapshotAt`, `automationPaused({})`, `gbServerPaused()`, `state.snapshotEnabled`. No silent dead guards.
- **Quota alarm interaction.** Plan 20 measures size on demand (`docs/plans/20-storage-quota-alarm.md` "Measuring … not every save"). Snapshots do not add to the measurement — `gbEvidence` is the same on-demand surface, and `storagePruneForQuota` runs only on a write failure. Per plan 20's "Measurement runs on demand only" rule.

## 9. Validation gate

Low risk per plan 27 §11.

1. **Boot snapshot:** install on a fresh world. Reload the tab. Preflight `snapshots` row shows `1/6 slots, K KB total, interval 5m`. `gbEvidence.snapshots.count === 1`.
2. **Cadence:** leave the tab open for 12 minutes. Reload. Preflight shows `3/6 slots` (boot + 5min + 10min; 10s sweep tolerance). Footer shows nothing unusual.
3. **Pause-aware:** enable night pause (`state.nightPause`, `core.js:269`). Reload during the pause window. After 10 minutes, the snapshot count is still ≤ 2 (the boot one + one that fired before pause kicked in). The `snapshotMaybeBuild` short-circuit on `automationPaused` works.
4. **Oversize drop:** in DevTools, `state.findings.push(...1000 dummy rows)`, wait one cadence tick. Log shows `snapshot-oversize …`. Preflight `snapshots` row reports the slot count unchanged. Confirm the ring did not grow past 6.
5. **Quota prune order:** fill `state.alerted` to 5000 keys (`gbLogT('alerted-fill', …, …)` repeatedly). Wait for a save to trigger `storagePruneForQuota` — verify the prune log (if any) shows snapshots dropped before `alerted`. The hard test is harder to script without filling real GM storage; instead, **unit-style** check by reading `storagePruneForQuota`'s effect on a hand-crafted `state.snapshots.length === 6` → assert it drops to 2.
6. **Restore:** take 3 snapshots over 10 min. `GrepBot: restore snapshot` lists the 3 slots with timestamps. Pick slot 0 (oldest). Confirm dialog. Reload. State reflects slot 0's `cfg.toggles` and `plans.abTargets`; `state.snapshots` ring is **not** modified by restore (restore is one-shot, not destructive).
7. **`safeMode` gate:** with `state.safeMode === true`, `GrepBot: restore snapshot` flashes `restore bloqueado (safeMode)` and does nothing. Set `state.safeMode = false` via Config, retry, succeeds.
8. **`configVer` mismatch:** hand-craft `state.snapshots[0].payload.cV = 9`. Reload. `GrepBot: restore snapshot` shows the slot but refuses with `version mismatch (9 < 11)`.

## 10. Out of scope

- **Auto-restore on corruption.** Plan 27 §0 dropped remote-feature-flags / auto-update / cloud sync; auto-restore on corruption is the same family of "the bot silently does something the user did not ask for" risk. Manual menu only.
- **Whole-state `JSON.stringify(state)` snapshots.** `state` includes `findings[].raw`, `attackHistory`, `questHistory` — unbounded in size. The whitelist in `snapshotPick` is the discipline; a generic stringify would breach `SNAPSHOT_BUDGET_BYTES` on the first tick of any active player.
- **Snapshot encryption.** Plan 27 §0 dropped obfuscation / fingerprint noise. GM storage is per-script, per-origin; the threat model is browser-extension side-channel, not local file read.
- **Cloud sync, REST API, plugin hooks.** Dropped by plan 27 §0.
- **Reducing existing journal cadence.** The decision journal at `journal.js:103-114` already runs `jrnSave(true)` every 5s with a debounce + pagehide flush; that is the right grain for per-decision accountability, the wrong grain for whole-state rollback. The two compose: journal lives inside `payload.decisionsSummary` (work item 4), the snapshot keeps the summary, and the live journal keeps the full 400-row ring.
- **Replacing `LOAD_MAX_CHARS` (`core.js:1101`) rejection with snapshot-based recovery.** `LOAD_MAX_CHARS` is the read-side guard; a snapshot is the write-side artefact. They compose (snapshot on every cadence; LOAD_MAX_CHARS rejects on read failure and falls back to `[]`), but neither replaces the other.
