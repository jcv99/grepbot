# 3.3 — Colony ship / revolt tracker

**Bucket:** v4.3 · **Risk:** Low · **Size:** M
**Module:** extend `src/military.js` (new `militaryColonyThreats`,
`militaryRecallOutgoingTo`). The recall half re-uses the **already

`state.cancelTpl` (learned at `farms.js:82-87`); the **tracker**

**Depends on:** 5.4 smart dodge (for the per-type risk bump when the
tracker surfaces a colony/revolt hit to the dodge layer — the
tracker itself does not need it). The recall path is independent
of 5.4.
**Status:** PLANNED — written 2026-08-10 against `src/` @ v3.8.2

## 1. What exists today

**Cancel / recall path** (already coded; this plan only **wires** the
threats to it):

- `state.cancelTpl` is loaded at `core.js:274` from
  `STORE.CANCEL_TPL` (`header.js:56`, world-scoped at `header.js:200`).
  Migration at `core.js:435` resets it to `null` if the persisted
  shape is non-object; the `core.js:441` save is the only persistence
  call.
- `farms.js:79-87` learns the template on a player's hand-click that
  posts `Command/cancelCommand` (or `cancel_command`): the body match
  picks up `action_name`, `model_url`, `arguments`, and the live
  `town_id`, persisting with `version: 1` and a `learned_at` stamp.
- `militaryCancelCommand(commandId, opts, onDone)` (`military.js:45-70`)
  is the firing path. It checks `opts.confirmed`, `hostEnabled`,
  `automationPaused`, `captchaPausedAny('cancel','attack')`, command-id
  format, presence in `militaryOutgoingMovements` (the cancelable
  view), `state.cancelTpl` shape, `txRecentlyCommitted` debounce, and
  `gbLock('cancel', …)`. The `GB_LOCK_TTL.cancel = 120000`
  (`core.js:164`) is the only lock it acquires.
- The Attack tab's `.atk-cmds` panel (`military.js:166-183`) lists
  every cancelable outgoing command and offers a per-row Cancel
  button gated on `state.cancelTpl`. `dodgeReturnTick`
  (`wonder.js:148`) already calls `militaryCancelCommand(...,{confirmed:true,automation:true},…)`
  for support that needs to come back when `state.defenseCfg.returnMarginSec`
  elapses (`state.defenseCfg` at `core.js:359`,
  `STORE.DEFENSE_CFG` world-scoped at `header.js:155`/`header.js:209`).
  The recall hook is therefore live and battle-tested; the tracker
  just needs to point at it.

**Threat read path** (already coded; this plan **consumes** it):

- `dodgeIncomingMovements()` (`dodge.js:53-84`) returns
  `[{id, dest, origin, type, hasCs, arrival, units, model}]` for
  every movement whose `dest` is one of my towns and which passes
  `dodgeIsHostileMovement` (`dodge.js:41-52`). The hostile vocabulary
  `DODGE_HOSTILE_TYPES = /^(attack|attack_sea|raid|siege|revolt|colonize|take_over|conquer|portal_attack)$/`
  (`dodge.js:39`) is the canonical list — `revolt`, `colonize`,
  `take_over`, `conquer`, and `portal_attack` are the five types the
  tracker cares about.
- `hasCs` derivation (`dodge.js:73`):
  `units.colonize_ship || units.colony_ship || /^(revolt|colonize|take_over|conquer)$/.test(type)`.
  The colonize-ship presence is the only place the tracker's
  `isColonize` predicate can fire from; whether the server exposes
  the *attacker's* unit breakdown on an **incoming** movement is
  **not verifiable from `src/` or `archive/captures/`** (see §8 and
  the 3.7 plan §8's parallel finding).
- `dodgeEtaSec(mov)` (`dodge.js:175-180`) normalises `arrival` and
  returns seconds-until-landing or `null`. The tracker re-uses it.
- `intel.js:72-74` already calls `dodgeIncomingMovements` for the
  Intel board; `intel.js:86-90` renders per-movement `risk | ETA` and
  `[CS]` prefix. The tracker's panel sits next to the existing
  "Enviados / cancelar" header on the Attack tab (not on Intel) so
  the recall button is one click away.
- The `DODGE_QUEUE` (`STORE.DODGE_QUEUE`, `header.js:143`, world-scoped
  `header.js:208`) already persists a 1h-TTL queue of incoming
  movements with `{state, ts, notified, militiaState, dest, type, hasCs}`
  (`dodge.js:1-37`). The tracker reads it; it does not write.

What is **not** coded:
- A filter on `dodgeIncomingMovements()` that surfaces only the
  colony/revolt subset, with a canonical per-type label and a single
  recall CTA per destination.
- An Intel-board sub-row keyed to the recall row.
- A Preflight row that names the readable `mov.type` vocabulary.

## 2. Gap

A colony or revolt landing on me is irreversible once it lands — the
town flips ownership. The only honest defence windows are (a) read
the threat, (b) recall any reinforcement I sent to that town before
the wave hits, and (c) let the existing dodge layer decide whether to
evacuate.

Today (a) and (c) are partly handled by `dodgeIncomingMovements` and
`defenseShouldDodge` (`wonder.js:145`), but the Intel board line
collapses five distinct attack types into one prefix (`[CS]` +
`type || 'atk'`), and (b) requires the player to:
1. Notice the Intel row,
2. Switch to the Attack tab,
3. Find the outgoing support command by id (or by destination match),
4. Click Cancel on that row, then confirm.

For a player holding ten towns with a friend, step 3 is "open every
`state.dodgeReturns` line by hand" — `dodgeReturnTick` only catches
support that **this bot** sent in response to a dodge. The tracker
fills the gap by:

- surfacing the colony/revolt subset as a dedicated Attack-tab
  panel with a one-click **Recall** per outgoing support, and
- cross-linking it with the Intel row so the player can read the
  same threat in either tab.

The plan does **not** add a new post: the recall is a hand-confirmed
`bridgePost('cancel', …)` via the same `militaryCancelCommand` path
the existing UI already uses. The only thing the tracker adds is a
narrower view of incoming + a recall CTA that pre-fills
`militaryCancelCommand`.

## 3. Design

Pure read + UI glue. No new post surface.

Data in (`militaryColonyThreats()`, new, in `military.js`):

1. `const incoming = (typeof dodgeIncomingMovements === 'function') ? dodgeIncomingMovements() : [];`
2. For each `mov`, decide `kind` (first match wins):
   - `mov.type === 'revolt'` → `'revolt'`
   - `mov.type === 'colonize'` → `'colonize'`
   - `mov.type === 'take_over'` → `'take-over'`
   - `mov.type === 'conquer'` → `'conquer'`
   - `mov.type === 'portal_attack'` → `'portal-attack'`
   - `mov.units && (mov.units.colonize_ship || mov.units.colony_ship)`
     → `'cs-sighted'` (the unit-breakdown branch from `dodge.js:73`,
     surfaced when the type field is missing or unfamiliar).
3. Filter to `kind != null`. Drop everything else (regular
   `attack`/`raid`/`siege` etc. is the smart-dodge layer's job, not
   this tracker's).
4. `eta = dodgeEtaSec(mov)`, `null` ⇒ `etaKnown: false`.
5. For each threat, scan `militaryOutgoingMovements()`
   (`military.js:17-44`) for support commands whose
   `commandId` is in `state.dodgeReturns` and whose `dest` (note: the
   outgoing record's `target` field, `military.js:27`) matches
   `String(mov.dest)`. Build `{threat, recallCandidates: [{commandId,
   type, until, cancelLeft}]}`.

Data out — three read-only sinks, all existing:

- A new `<div class="atk-colony">…</div>` on the Attack tab, rendered
  by `renderColonyThreats(sec)` (new, in `military.js`). One row per
  threat, three columns: `kind` (Spanish per CLAUDE.md — e.g.
  `revolt|colonización|toma|conquista|portal|nave colonizadora`),
  `town <id>`, `ETA`. If `recallCandidates.length > 0`, an extra
  button **Retirar** per candidate. The button calls
  `militaryCancelCommand(commandId, {confirmed:true}, err => { flash(...); renderAttack(); });`
  — verbatim, same path the existing `.atk-cmds` Cancel button uses
  (`military.js:180`). The threat row's render never calls the
  cancel without `confirmed:true`; it is the same gate
  `militaryCancelCommand` enforces on line 46.
- The Intel board row at `intel.js:86-90`: append
  ` | colonización/revolt` (Spanish) when the matching threat is
  surfaced by the tracker, so the player sees the same label in
  both tabs.
- Preflight `colony threats` row in `stats.js:248`-ish:
  `n threats, k with known ETA, j with recall candidates`. The row is
  `warn: etaUnknown > 0` (matches the 3.7 plan's `incoming` row
  pattern).

Action out (the recall): the button posts **via the existing**
`militaryCancelCommand`. Dry-run applies (state.dryRun short-circuits
in `bridgePost`, `core.js:1187-1188`-style). The `cancel` captcha
feature key is already covered by `gbCaptchaPause` via
`captchaPausedAny('cancel','attack')` at `military.js:48`.

**No new post surface.** The only outbound path is the **already
existing** `bridgePost('cancel', payload, cb)` inside
`militaryCancelCommand` (`military.js:65`), gated on

introduce a new action name.

## 8. Failure modes

- **`hasCs` derivation may not fire for non-CS types.** Per the 3.7
  plan §8: the server may hide the attacker's unit breakdown on
  incoming movements, so the `units.colonize_ship` branch may never
  match. The type-field branches (`revolt|colonize|take_over|conquer`)
  remain as the only honest signal. The tracker must therefore
  classify by `mov.type` first; `cs-sighted` is a fallback for
  unknown `mov.type` values that nonetheless carry a colonize_ship
  in `units` (per `dodge.js:73`). The Preflight row warns on
  `etaUnknown > 0` so the player can spot a torn model.
- **No `MovementsUnits` collection** (e.g. an old client build):
  `dodgeIncomingMovements()` returns `[]`; the panel renders the
  empty state "sin movimientos de colonización/revuelta" and the
  Preflight row reads `0 threats`. No crash path.
- **`militaryOutgoingMovements` returns `[]`** (no outgoing
  commands): `recallCandidates` is empty, no **Retirar** button
  renders, no false positive. The threat row still surfaces.
- **Recall button pressed with no `state.cancelTpl`**: the button
  is disabled at render (`disabled = !state.cancelTpl`); if the
  player uses DevTools to force-click, `militaryCancelCommand` returns
  `'template-required'` (`military.js:54-57`) and logs once via
  `gbLogT('cancel-template', 60000, …)`. No post.
- **Recall while the bot is paused** (`automationPaused({})`):
  `militaryCancelCommand` line 47 returns `'paused'`; the **Retirar**
  button in the UI shows the `flash` text "recall failed: paused".
  No post. The player can resume and re-click.
- **Recall target is the player's own town** (the kind of typo
  where `dest` matches an *incoming* colony target by accident):
  the path runs through `militaryOutgoingMovements` whose filter
  at `military.js:35` already excludes non-cancelable movements,
  and the destination check is on the **outgoing** `target` field,
  not on the threat's `dest`. A typo in the incoming `mov.dest`
  produces a no-op (no outgoing support to that town) — the
  **Retirar** button does not render. No post.
- **Cancel arrives after the wave landed**: the
  `txRecentlyCommitted('cancel:' + cmdId, 120000)` debounce is the
  only defence, plus `militaryOutgoingMovements`'s `until` window
  check at `military.js:34` — the row's `cancelLeft` is already
  `null` past `until`, so the **Retirar** button shows "ok" with
  `cancelLeft` blanked. The hand-click is still gated by
  `militaryCancelCommand`'s `live` check at line 51, which returns
  `'not-cancelable'` once the command is no longer in the cancelable
  view. No post.
- **Cross-reference with `dodgeReturnTick`** (`wonder.js:148`):
  `dodgeReturns[id].commandId` is keyed on the dodge-fired support's
  own id, not on a colony-targeted support. The tracker's
  `recallCandidates` filter is `target === mov.dest`, which is a
  strict subset of the support the bot sent — no overlap with the
  dodge-return queue, no double-recall.

## 9. Validation gate

Per plan 27 §11 Low risk: *Preflight + one in-game session, no failure.*

1. `python3 build.py`, paste, reload `es146`.
2. Open the Attack tab. The "Colonización / revuelta" header and a
   `.atk-colony` block appear below "Enviados / cancelar". No console
   errors.
3. Hand-cancel any outgoing command once to learn `state.cancelTpl`
   (the button hint at `military.js:179` already documents this).
   The **Retirar** button on any future threat row is now enabled.
4. Wait for (or stage) a `revolt` or `colonize` incoming. The panel
   shows one row with the Spanish label, `town <id>`, and `ETA`. The
   Intel board row carries the ` | colonización/revolt` suffix. Log
   shows one `gbLogT` only on a state change.
5. With an outgoing support command to that town, the row gains one
   **Retirar** button per candidate. Click it; confirm the dialog;
   the Log shows `cancel: command <id> OK`; the row disappears
   (the cancel succeeds, the support never lands). The Intel row
   remains (the colony wave is still inbound).
6. With `state.dryRun === true`, repeat step 5. The Log shows
   `DRY-RUN cancel: …` and the Decisions view shows `skip:dryrun`
   for the `cancel` feature. The button is still clickable; the
   dry-run is the operator's friend here.
7. Preflight → `colony threats`: row reads e.g.
   `1 threats, 1 with known ETA, 0 with recall candidates`. With an
   outgoing support to that town, the third number becomes `1`.
8. On a world with no incoming colonies (steady state), Preflight
   reads `0 threats, 0 with known ETA, 0 with recall candidates`.
   The panel renders "sin movimientos de colonización/revuelta".

Must **NOT** appear anywhere: any new `bridgePost`/`gameAjaxPost`
entry beyond the already-coded `cancel` path, any new
`TPL_FEATURE_MAP` key, any new `gbLock` name, any new
`GB_LOCK_TTL` entry, any new `gbAjaxWatch` registration. The
tracker is read-mostly; the only outbound traffic is the
already-coded recall, which fires **only** when the player clicks
**Retirar**.

## 10. Out of scope

- **Predicting colony/revolt composition.** The plan reads
  `mov.units` opportunistically (3.7's §8 finding applies: the
  attacker unit breakdown on incoming movements is not verifiable).
  Any composition-aware score belongs to 4.2 (counter-intel) and
  5.3 (threat assessment), which plan 27 §5 cross-references.
- **Auto-recall.** Per CLAUDE.md "HIGH-RISK toggles ... default OFF"
  and plan 27 §0, an auto-cancel on colony/revolt is HIGH-RISK: a
  late cancel of a support that already delivered is a wasted
  budget slot, and a too-early cancel of a support the town
  actually needed is a lost defence. The plan is read-mostly with a
  hand-confirmed CTA only. Auto-recall is 3.2 (support auto-send)
  territory and would need its own confirm-gate.
- **Interfering with `dodgeReturnTick`.** `wonder.js:148` is the
  auto-cancel for dodge-fired support. The tracker is a separate
  view; it does not enqueue or consume `state.dodgeReturns`.
- **New movement types.** Plan 27's §3 table only lists the five
  types in `DODGE_HOSTILE_TYPES`. Adding `portal_attack` to the
  tracker (already in the regex) is enough; new server types
  belong to a future plan after the live client exposes them.
- **Alliance-wide colony alarm.** A colony against an ally is
  surfaced through the existing `[CS]` Intel board row and the
  `alertWebhook('attack', {…, cs:!!mov.hasCs})` (`dodge.js:191`).
  The webhook payload already covers it; the per-ally filter is
  7.5 (NAP / war tracking) and 7.2 (defense coordination board),
  not this plan.
- **A new `cs-tracker.js` module.** The 3.7 plan rejected the same
  hint for the same reason (`build.py:59` already owns the
  analyzer). The tracker extends `military.js` because the recall
  CTA is the one feature the existing helpers in that file
  (`militaryCancelCommand`, `militaryOutgoingMovements`,
  `renderMilitaryHelpers`) already expose.
