# 4.6 — Favor regen optimizer (HUD only)

**Bucket:** v4.2 · **Risk:** Low · **Size:** S
**Module:** extend `src/stats.js` (render-time only; reads `favorCurrent()` from `src/favor.js`)
**Depends on:** none
**Status:** PLANNED — written 2026-08-10 against `src/` @ v3.8.2 (header `@version` is `3.9.0`; off by one, harmless)

> Plan 27 row 4.6 is explicit: *"NOT a feature, just a stat panel — no posts,
> no automation."* This plan ships a read-only HUD block in the Stats tab. It
> does **not** enable `state.autoFavor`, does **not** unblock `favorScan` (the
> `FAVOR_AUTOMATION_ENABLED = false` flag at `favor.js:8` stays false), and
> adds **no** new state field, lock, or storage key.

---

## 1. What exists today

- The only read path is `favorCurrent()` (`src/favor.js:9-17`). It returns
  `uw.Game.gods.attributes` or the `PlayerGods` model attributes. On any
  failure it returns `{}` — never throws, never `null`.
- `favorScan` (`src/favor.js:52-152`) already enumerates the per-god pool the
  same way a HUD would need to:
  `favor.js:71` `const raw = fav[god] != null ? fav[god] : fav['favor_' + god];`
  `favor.js:72` `const cur = Number(raw);` — this is the precondition invariant
  already in place: if `!Number.isFinite(cur)` the existing scanner logs
  `favor-unreadable` once (`favor.js:73-76`) and bails. The HUD must do the
  same on every cell, not just once.
- `favorCfg` is already in the world-scoped bag (`src/header.js:112`,
  `WORLD_SCOPED_BASES` at `src/header.js:203`). The default god is `athena`
  (`src/core.js:317`). The default threshold `200` is the same one
  `favorScan` already gates sends on (`src/favor.js:62`).
- Stats body is rendered by `renderStats` (`src/stats.js:280-355`). Layout
  blocks in order: per-feature rollup (`:294-309`), `topErrors` (`:310-314`),
  `topPending` (`:315-319`), `topSkips` (`:320-324`), deadlock notice
  (`:326-330`), orchestrator (`:331-334`), budget line (`:339-344`), preflight
  rollup (`:347-353`). Plan 26 §C2 already added the budget line.
- `preflightRun` (`src/stats.js:12-268`) is the read-only sweep. It already
  has a `bandit camp` row at `src/stats.js:234-238`; the favor path has no
  equivalent. Preflight is one-shot (only on `gb-preflight` click or
  `preflightRunAndRender` call), so it is **not** the HUD surface.
- There is **no** regen-rate field surfaced anywhere in `src/`. The model
  attribute names read today are `favor.<god>` or `favor_favor_<god>` for the
  pool; `max_favor` / `favor_<god>_max` are not referenced. The game client's
  exact attribute set is unknown — the only public docs are in
  `archive/captures/grepo-dump/js/game.min.js` and have no labeled regen
  rate.

## 2. Gap

The Stats tab tells the player how many decisions the bot made, but says
nothing about favor accrual. The user-visible question — *"how long until
athena hits 200 so a favor cast is even worth posting?"* — has no answer in
the panel. Plan 27 §4.6 asks for a regen-aware readout; the regen rate is not
in the model, so the honest deliverable is a pool/ETA panel that derives
the rate from a paired-sample window and degrades to "unknown" cleanly.

## 3. Design

Read-only. No post surface, no captcha breaker, no lock, no scheduler entry.

Per render of `renderStats`, walk the same god list the existing scanner
already accepts (`favor.js:66` uses `cfg.god` only, but the panel wants
**all** gods — the model exposes every pool at once). For each god:

1. `p_now = Number(fav[god] ?? fav['favor_' + god])` — same lookup as
   `favor.js:71`. If `!Number.isFinite(p_now)` ⇒ `unreadable` cell, log once
   via `gbLogT('favor-hud-blind-' + god, 300000, …)` matching the existing
   5-min throttle key style at `favor.js:74`.
2. `p_max = Number(fav['max_favor_' + god] ?? fav['favor_' + god + '_max'] ?? 0)`.
   If `!Number.isFinite(p_max) || p_max <= 0` ⇒ `max ?` cell.
3. Regen rate: derived from a paired-sample window keyed by god. New module
   local `favorRateSamples` (plain object, **not** persisted in `state.*` —
   it rebuilds across reloads). On every `renderStats` call, push
   `{ts: Date.now(), p: p_now}` for each god, prune anything older than
   10 min, and compute `rate = (p_now - p_oldest) / (now - oldest.ts)` in
   pool per second. Two samples are needed before the rate is reported;
   the cell renders `…` until then. A negative rate means the player just
   spent favor (treat as `0` for ETA).
4. ETA to threshold: `etaSec = rate > 0 ? (thresh - p_now) / rate : ∞`.
   `thresh` defaults to `state.favorCfg.thresh` (default 200 — same as
   `favor.js:62`). Render as `m:ss` if finite, `—` if not regen'ing or
   already above threshold.

Output is one block between the `topSkips` block (`stats.js:320-324`) and
the deadlock notice (`stats.js:326-330`):

```
favor (gods)        actual  max   rate   eta 200
  athena              412   1500  1.4/m  ?
  hera                118   1500  0.0/m  — (no regen sample)
  poseidon            ?        ?   ?      ? (unreadable)
```

The `"rate"` cell is `pool/min`, rounded to one decimal. The `"eta 200"`
cell is the time the pool will hit `state.favorCfg.thresh` (or `—` if
rate is zero / negative / unreadable).

The block is **always** rendered when the player has at least one readable
god; otherwise one line `favor (gods) unreadable`. No Config toggle, no
`configVer` bump.

## 5. State & storage

None.

The sample window is a JS `Object.create(null)` local to `stats.js`. It is
**not** persisted (`STOR`/`save`/`load` would mean a `WORLD_SCOPED_BASES`
entry and a `configVer` bump — neither justified). Across reloads the
window restarts; the rate cell renders `…` until two samples accumulate
after each fresh load.

## 6. Config surface

None.

The plan 27 row carries no Config label. The HUD is gated by the render
itself: if the model's `PlayerGods` is unreadable, every cell prints `?`
and the block is a single `unreadable` line. No HIGH-RISK toggle, no
default to set.

## 7. Post surface & safety

No post surface. No `bridgePost`, no `gameAjaxPost`, no `gbDomClick`,
no `gbAjaxWatch`, no `gbLock`, no `GB_LOCK_TTL` entry, no `gbCaptchaPause`
key. The HUD reads only.

## 8. Failure modes

- **`favorCurrent()` returns `{}`** — every god cell falls through to `?`;
  the block renders the single-line `favor (gods) unreadable` and logs
  once per god via `gbLogT('favor-hud-blind-' + god, 300000, …)`. The
  precondition invariant is preserved per cell (read each value, log
  once, never block).
- **Regen rate derivation** — if the player spent favor between two
  samples the rate is negative; render as `0.0/m` and `eta —`. If the
  pool increased by less than 1 across 10 min, treat as `0.0/m`. If the
  window has fewer than 2 samples, render `…` for the rate.
- **God list source** — the model exposes a fixed set of gods per world;
  the HUD derives the list from the first `favorCurrent()` call (keys
  matching `/^favor(_|$)/` and `/^max_favor/`), instead of hard-coding
  `['athena','hera','poseidon','hades','zeus','ares','aphrodite',
  'artemis']`. A future god the client adds appears automatically.

## 9. Validation gate

Manual, per plan 27 §11 Low class (Preflight + one in-game session, no
failure).

- Build (`python3 build.py`), install, open the Stats tab. The new
  `favor (gods)` block appears between `topSkips` and the deadlock line.
- Preflight (`Comprobar sistema`) shows a new `favor pool read` row with
  `N gods readable` and no `?`s once `PlayerGods` is populated.
- Open the game's favor panel, click a god — the Stats HUD mirrors the
  pool within one render cycle (the next `renderStats` is fired by the
  15s `renderStats` interval at `src/boot.js:108-115`).
- Manually spend favor in the game; the next Stats render shows the pool
  drop and the rate column stays accurate (or reports `0.0/m` if the
  elapsed since the last sample is small).
- Switch tabs and switch back; the rate `…` shows briefly on the first
  render after a reload and resolves to a number on the next.

## 10. Out of scope

- **Auto-favor.** Plan 27 §4.4 (`favor` toggle, HIGH-RISK OFF) and 4.6 are
  related but separate. The scanner stays disabled because
  `FAVOR_AUTOMATION_ENABLED = false` at `src/favor.js:8` — flipping that is
  a different plan that needs a target contract the catalog explicitly
  defers.
- **Regen rate from the model.** If the game client exposes a regen-rate
  field on `PlayerGods`, that is a future improvement to this HUD — but
  the sniff task is *not* this plan's work. The derived rate is good
  enough; the model field is a "nice to have" tracked in `TASKS.md`.
- **Per-town favor readout.** Favor is a player-level pool, not per
  town. The HUD reads the player's pool once.
- **Wonders / `WonderFavor`.** `state.wonderFavorTpl` and
  `state.autoWonderFavor` (`src/core.js:375-376`) are a separate feature
  (plan 27 §3.1-adjacent). Not this plan.
