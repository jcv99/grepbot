## 1. What exists today

- `dodge.js:107-121 dodgeCanRaiseMilitia(townId)` — checks farm building,
  already-standing militia (`+u.militia > 0`), and free population

  `gameAjaxPost('militia', 'building_farm', 'request_militia',

  slot.
- `dodge.js:195-202 dodgeTryMilitia(mov, entry)` — fires on every
  incoming where ETA ≤ `DODGE_MILITIA_WINDOW_SEC = 15*60` (`dodge.js:181`),
  `state.autoMilitia` is on, and `captchaPausedAny('militia', 'dodge')`
  is false. Acquires `gbLock('militia', 30000)` (per-call shorten of the
  `60000` `GB_LOCK_TTL` at `core.js:168`).
- Toggle default **OFF** (`core.js:334`, `STORE.AUTO_MILITIA`
  world-scoped, `header.js:206`). UI at `ui.js:822`, `ui.js:1334`,
  `ui.js:1429`.
- Audit guarantee (`dodge.js:200-201`): a `timeout` or `timeout_unknown`
  outcome locks the entry for 5min (retry bounded) — **militia consumes
  population and re-firing without resolution is unsafe** (CLAUDE.md
  "v1.5.3 preconditions — militia/dodge").

## 2. Gap

Today `dodgeTryMilitia` raises on **every** incoming whose ETA is
<15min. That includes lone single-attacks that the town's own units
could repel. Militia is irreversible (it consumes a slot of population
that does not regenerate during the wave, and the militia unit itself
becomes the standing garrison) — burning it on noise degrades the town
for the attack that actually matters. The smart delta is: only raise
militia when the *defense assessment* (`defenseAssessment` at
`wonder.js:144`) says the town's local strength cannot absorb the
incoming composition, or the incoming is a CS / siege where militia is
the only free reinforcement that arrives in time.

## 3. Design

Add a single decision funnel between `dodgeTryMilitia` and
`dodgeCanRaiseMilitia`. Keep the existing guards; add a
risk-conditioned gate.

```
incoming movement → dodgeTryMilitia (dodge.js:195)
    │
    ├── existing guards: state.autoMilitia, captchaPausedAny,
    │   entry.militiaState, eta window, nextAt debounce      (unchanged)
    │
    └── NEW: dodgeShouldMilitia(mov, assessment)
            ├── Always raise when:  hasCs OR risk >= M_MILITIA_FORCE
            │                       OR assessment.simultaneous >= 2
            ├── Skip      when:    risk < M_MILITIA_SKIP
            │                       AND hasCs === false
            │                       AND localStrength (assessment.local.score)
            │                           >= M_MILITIA_LOCAL_OK
            └── Else (gray zone):  raise only if entry.militiaState
                                   has not advanced past "pending"
                                   within DODGE_MILITIA_GRACE_MS
```

The constants live in `dodge.js` near `DODGE_MILITIA_WINDOW_SEC` and are
pinned in `state.militiaCfg` (default values below).

Data flow:
1. `dodgeScan` (`dodge.js:252`) loops hostile incoming.
2. For each, it already calls `dodgeTryMilitia(mov, entry)`.
3. `dodgeTryMilitia` calls `defenseAssessment(mov, incoming)` once per
   tick (cached on `entry.dAssessment` if not present) — **re-use** the
   assessment dodgeScan is computing for itself in
   `defenseShouldDodge`, so we don't double-pay for `dodgeSupportOptions`
   (`wonder.js:143`, the expensive call).
4. Apply `dodgeShouldMilitia` decision. If skip, write
   `entry.militiaState = 'skipped'` and `gbLogT('militia-skip-<dest>',
   60000, '<why>')`. The same militia-skipped reason becomes part of the
   `whyLog` (`core.js:365`) so Stats can surface "skipped vs raised".

The retry-bounded timeout branch (`dodge.js:201`) is **unchanged**.
Militia is irreversible, the safety guarantee from v1.5.3 stays.

## 4. Work items

1. In `dodge.js`, right after `DODGE_MILITIA_WINDOW_SEC` (line 181), add:
   - `const M_MILITIA_FORCE = 50` — risk threshold where militia fires
     regardless of local strength.
   - `const M_MILITIA_SKIP = 10` — risk floor below which militia is
     skipped unless `hasCs`.
   - `const M_MILITIA_LOCAL_OK = 400` — local defense score above which
     militia is skipped for risk<50 / non-CS incoming.
   - `const DODGE_MILITIA_GRACE_MS = 3*60*1000` — gray-zone window.

   All four literals are mirrored in the persistent
   `state.militiaCfg = {forceRisk, skipRisk, localOk, graceMs}`
   initializer in `core.js` (`defenseCfg` neighbour, line 359). These
   are starting points — tune via Stats after a few waves of evidence.

2. In `dodge.js`, add `function dodgeShouldMilitia(mov, assessment)`
   returning `{yes, why, group}` where group ∈ `{force, skip, grace}`.

3. In `dodgeTryMilitia` (dodge.js:195), insert **once** at the top:
   ```js
   const a = dodgeAssessmentCached(mov, entry);
   const dec = dodgeShouldMilitia(mov, a);
   if (!dec.yes) {
     entry.militiaState = 'skipped';
     gbLogT('militia-skip-reason-' + mov.dest, 60000,
       `militia: skipped (${dec.why})`);
     return;
   }
   ```
   `dodgeAssessmentCached` is a 1-line memo on `entry.dAssessmentTs`;
   it reuses the call `dodgeShouldDodge` already makes for the dodge
   side of the same loop. Mind `gbLogT` keys — they're time-throttled,
   not feature-locked, so this is safe.

4. In `dodgeCanRaiseMilitia` (dodge.js:107), add a guard against
   raising when `simultaneous >= 2 && hasCs === false` — militia is
   wasted on multiple low-risk raids on the same town. `hasCs` still
   forces raise.

5. Render the four numeric thresholds under `auto-militia` (`ui.js:822`).
   Defaults match the literals above.

6. The militia popup dismissal: when auto-militia fires, the bridge
   post dismisses the in-game "you've been attacked" dialog and the
   militia stands visibly. This plan does not change that visual; the
   operator correlates by `mov.id` + journal entry.

## 5. State & storage

- `state.militiaCfg` — `{forceRisk, skipRisk, localOk, graceMs}` — new
  field in `src/core.js` initializer block (next to
  `state.defenseCfg`, line 359). Default values match the literals in §4
  item 1. Store key `STORE.MILITIA_CFG` (new constant in
  `src/header.js:24-187`), world-scoped (`WORLD_SCOPED_BASES`).
- `state.configVer` bumps from `10` to `11` (`src/header.js:191`); new
  rows render on every existing install.
- World-scoping rationale: two different worlds might run very different
  army compositions, but the *policy* (when to consume pop for militia)
  is per-world. Do **not** add to per-user-only bucket.
- Per-town pop cost is **not** persisted: it is derived from the
  standing garrison model on every read via `dodgeCanRaiseMilitia`
  (`dodge.js:113-118`). The audit's invariant: standing militia is
  read from the model, not stored; if the model is unreadable, the path
  bails (`dodge.js:117-119`).
- `entry.militiaState` semantics gain a new `'skipped'` value (existing
  valid set per `dodge.js:9`: `pending|sending|raised|unknown`). The
  `dodgeQueueLoad`/`dodgeQueueSave` (dodge.js:1-35) already serialise
  arbitrary strings — no schema work needed.

## 8. Failure modes

- Gamebridge not ready → `dodgeRaiseMilitia` returns `'noajax'`
  (`bridge.js:151`); entry stays `sending` for the lock window, then
  reverts to `pending`. Existing flow unchanged.
- `'no free population'` from `dodgeCanRaiseMilitia` (`dodge.js:125`)
  → `dodgeTryMilitia` skips. The smart layer **must not** override
  that — pop is the harder constraint, the smart layer only adds *more
  reasons to skip*, never *more reasons to raise*.
- ETA > 15min → debounced (`dodge.js:197`); the smart layer is moot.
- Two near-simultaneous attacks → `entry.militiaState = 'raised'`
  after the first post (`dodge.js:199`); the second sees the guard. A
  CS second wave still slips through because `hasCs` forces raise
  regardless of skip thresholds.
- Timeout → `militiaState = 'unknown'`, retry bounded to 5min
  (`dodge.js:201`). Smart layer is irrelevant here; the v1.5.3 safety
  guarantee holds.

## 9. Validation gate

Per plan 27 §11 High risk: **payload sniff against live UI + confirm-gate
screen + dry-run + manual re-fire, then still default OFF**. Steps on
`es146`:

1. With `state.dryRun === true`, land a single incoming `attack` on a
   town with local defense < 200. The
   `DRY-RUN militia: building_farm/request_militia town <id>` line MUST
   appear in the Log within 15s. Decisions view shows `skip:dryrun` as
   the **only** result for `militia` in this period.
2. Sniff: hand-fire `request_militia` from the militia UI; compare the
   captured payload against the dry-run Log line. They MUST match
   exactly (`town_id` is the only field).
3. Re-fire manually once with `state.dryRun === false`; verify the
   standing garrison gained one militia unit. Then leave the toggle OFF.
4. Risk calibration: with a `raid` then a `siege` against the same
   defender, the bot MUST skip the first and raise on the second
   (verifiable in journal entries). Repeat three times; record min/max
   risk in Stats.
5. CS path: a `colonize_ship`-bearing incoming (`dodge.js:73 hasCs`)
   → militia MUST fire regardless of risk or local strength.
6. **`auto-militia` ships at default OFF.** Nothing in this plan
   touches the shipping default; do **not** bump it to ON.

## 10. Out of scope

- Attacker army composition prediction (we can't read incoming troops;
  only the `type` string is reliable). Plan 4.2 (counter-intel) covers
  origin patterns; plan 5.4 covers per-type risk.
- Re-calling a dismissed militia spawn — no UI for it in the JS
  bridge; the standing garrison is added immediately.
- A separate "smart militia" toggle. The `auto-militia` switch is the
  only one; the four numeric knobs govern smart behaviour within it.
  Splitting is a UX footgun — punt to plan 6.10 (config undo/redo).
