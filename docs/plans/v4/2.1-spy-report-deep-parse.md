# 2.1 — Spy report parser deep

**Bucket:** v4.0 · **Risk:** Low · **Size:** M
**Module:** extend `src/parse-inline.js` (parser) + `src/spy.js` (call site) + `src/intel.js` (consumer) + `src/ui.js` (render)
**Depends on:** none
**Status:** PLANNED — written 2026-08-10 against `src/` @ v3.8.2

## 1. What exists today

The report pipeline is `XHR spy` (`src/spy.js:37-112`) → `queueReport`
(`src/spy.js:222-230`) → `fetchReport` (`src/spy.js:266-297`) → `ingestReport`
(`src/spy.js:236-257`) → `parseReport` (`src/parse-inline.js:33-93`). Findings
land in `state.findings` (ring buffer 500, `src/spy.js:249-253`) and are
*already consumed* by:

- `renderFindings` row rendering (`src/ui.js:1702-1728`) — flat `.units`
  `Object.entries().map(...)` and `W/S/I` resource string.
- `intelDossiers` (`src/intel.js:34-71`) — aggregates by player key, pushes
  `f.units`, `f.wall`, `f.town` into per-player buckets.
- `watchMatch` (`src/intel.js:145-185`) — uses `f.town.id`, `f.vill_id`,
  `f.attacker`, `f.alliance`, `f.town.x`, `f.town.y`.
- `intelPatternScan` (`src/intel.js:206-245`) — uses `f.attacker`, `f.ts`.
- `intelWatchlistScan` (`src/intel.js:186-205`) — uses `f.vacation`,
  `f.town`, `f.vill_id`.

`parseReport` (`src/parse-inline.js:33-93`) returns exactly:

```js
{ id, ts, type, attacker, defender, town{id,name,x,y},
  units, resources{wood,stone,iron,gold,supply}, loot,
  outcome, wall, alliance, vill_id, vacation }
```

The audit (plan 27 §13 + plan 26 §B6 hot list) re-confirms that the existing
parser is **deliberately strict** — five `return null` paths
(`src/parse-inline.js:34, 48, 50, 54` and the implicit final guard at line 53's
"no type and no attacker and no defender and no units and no outcome" check).
`type` is `r.type || r.report_type || null` (`parse-inline.js:51`) and the
parser used to fall through to `type: 'unknown'`; plan 26 I8 confirmed that
`type: 'unknown'` poisons downstream filters and the catch-all was removed —
any report missing a discriminator now returns `null` and lands in
`reportFetchFail(id, 'unparsed')` (`src/spy.js:258-264`). This plan must
preserve that strictness: a **new** field is added only when the JSON key is
present and finite.

Plan 27 §9 confirms existing report-side work to be coded, not to extend:
"Offline report catch-up `spy.js:117-163`" (already shipped, plan 14),
"Battle report basics `intel.js:13.x`" (already shipped, will be deepened in
2.5). No deep-parse surface ships today.

## 2. Gap

The current parser captures the **shape** of a report (who/what/when, basic
units, basic loot, wall) but not the **content** that turns a report into
useful intel:

- **Building levels** (`buildings['main']=12, 'barracks'=8, 'wall'=15`) are
  nowhere in the parsed object. Without them, plan 2.2 (timeline of growth)
  and plan 5.3 (threat score from garrison size) cannot fire.
- **Troops per type** is partially there (`f.units` is a flat bag) but
  **defender vs attacker split** is lost. `extractUnits` reads
  `r.units || r.attacker_units` and never `r.defender_units`
  (`src/parse-inline.js:18-23`). A spy report with `defender_units` would
  flatten into the attacker bucket.
- **Hero presence** (`hero: {name, level, class}`) is absent. Plan 4.3 (hero
  manager) and the dossier view (`src/intel.js:34-71`) cannot key off it.
- **Resources** are kept as `null` on unknowns (`extractResources`,
  `src/parse-inline.js:25-31`). Plan 27 §2.12 (loot capacity) and the existing
  `W/S/I` row need the same `null` semantics — add `gold` (already half-keyed
  by `r.resources.gold` lookup) and `supply` (already half-keyed) but never
  invent a number.
- **Outcome as boolean vs string** — `outcome: r.outcome ?? r.win ?? null`
  (`src/parse-inline.js:87`) mixes types. Battle-to-win ratio math (plan 2.5)
  needs a normalized boolean.

The 2.2/2.5/5.3 consumer plans exist in `docs/plans/v4/README.md` but have
no-ops today because the parser cannot give them what they need.

## 3. Design

Extend `parseReport` (the only place that turns raw bridge JSON into a
finding) with three new fields, then surface them in two consumers:

1. **`buildings: { [name]: number }`** — collected from `r.buildings ||
   r.building_levels || r.buildings_levels`, keys coerced to lowercase, values
   required positive integers (otherwise dropped one-by-one, never a partial
   bag). The existing `wall` field is **kept** as a top-level convenience
   derived from `buildings.wall` if present, so existing readers
   (`src/intel.js:62`, `src/ui.js:1716-1724`) keep working.
2. **`units_attacker`, `units_defender`** — both objects, replacing the
   current single `units` field only for the case where the JSON has split
   keys. **Backward-compat rule**: `extractUnits` keeps writing `units` as
   the union (current contract — `src/ui.js:1716-1718`,
   `src/intel.js:59`); `units_attacker` and `units_defender` are added
   alongside. When the JSON has only `r.units` (no split), the union goes
   into `units` and the two split fields are `null`. When the JSON has
   `attacker_units` + `defender_units`, both split fields are set and the
   union `units` is the sum. Plan 2.5 (battle report analyzer) reads the
   split fields; the existing dossier aggregator keeps reading `units`.
3. **`hero: { id, name, level, cls } | null`** — collected from
   `r.hero || r.hero_info || r.defender_hero`. All fields optional; the
   whole object is `null` if `r.hero` is falsy or yields zero populated
   fields. Never invent `level=0` or `cls='unknown'`.
4. **`outcome: 'win' | 'lose' | 'draw' | null`** — normalize via a small
   mapping at the parser's existing assignment line. Treat `r.outcome` as a
   string when it is one; treat `r.win` as `win`/`lose`; treat `r.draw` and
   the literal string `'draw'` as draw. Anything else stays `null`.

Normalization is pure read-only — `parseReport` still returns `null` for any
payload missing the discriminator (line 51, line 53-55). The new fields are
**additive**; the existing schema is preserved bit-for-bit.

Consumers:

- `extractUnits` (`src/parse-inline.js:18-23`) splits into three helpers used
  by the new parser block. The existing `units` field keeps the union
  signature for `ui.js:1716-1718` and `intel.js:59`.
- `renderFindings` (`src/ui.js:1702-1728`) adds a third row when
  `f.buildings` has keys, formatted as `bldg: main=12 wall=15 stash=3` (top
  3 by descending level, ellipsis after that). The existing `units` /
  `resources` rows are unchanged.
- `intelDossiers` (`src/intel.js:34-71`) pushes `f.hero` and
  `f.buildings` into per-player buckets next to the existing `units` push.

The parser stays in `parse-inline.js` (called only from `ingestReport` at
`src/spy.js:237`) — there is no second call site to update.

## 4. Work items

1. `src/parse-inline.js:18-23` — replace `extractUnits` with three helpers:
   `extractSplitUnits(r)` returning `{ attacker, defender }` (each `null` if
   the source key is missing or empty), and `extractUnits(r)` rewritten as
   the union of the two for the legacy `units` field. The new
   `extractUnits` reads `r.units` first, then `r.attacker_units`+`r.defender_units`
   — when both split keys exist, the union is the sum (clamped at 0).
2. `src/parse-inline.js:25-31` — extend `extractResources` to honor
   `r.resource_pillage` and `r.haul` as alternate sources, but keep all
   `null`-on-unknown semantics (gold/supply stay nullable).
3. `src/parse-inline.js:33-93` — `parseReport` return object gains:
   - `buildings: { [name]: number }` — sanitized via a new module-local
     `parseBuildings(r)` IIFE that lower-cases keys, casts to integer,
     drops non-positive or non-finite values, returns `{}` when nothing
     survives. The existing top-level `wall` field reads
     `buildings.wall || r.wall || r.wall_level || r.defender_wall || null`
     so `src/intel.js:62` and downstream remain green.
   - `units_attacker`, `units_defender` — both `null` or both objects.
   - `hero: {id, name, level, cls} | null` — populated only from
     `r.hero || r.hero_info || r.defender_hero`. Drop the entire field to
     `null` when no source key is present or yields zero populated fields.
     Never invent a `name='unknown'`.

4. `src/parse-inline.js:53` — keep the existing `return null` strictness

5. `src/spy.js:236-257` — `ingestReport` is unchanged: it already calls

   `bldg: <…>` when `f.buildings && Object.keys(f.buildings).length`,

   order (`meta` → `units` → `res`) so the diff in the Intel tab is local.
7. `src/intel.js:59-71` — `intelDossiers` pushes `f.hero` and
   `f.buildings` into the per-player bucket. The dossier object gains
   `hero` (latest, by `f.ts`) and `buildings` (latest, by `f.ts`) fields.
   The export-redaction path (`src/qol.js:252`,
   `src/ui.js:1798-1808`) does not need to redact these fields in v4.0 —
   document as a follow-up in §10.
8. `src/header.js` — no new STORE key. No new state field. The new fields

   500-row cap (`src/spy.js:250-253`).
9. `src/parse-inline.js` line 1 — header comment for the file notes that

   `null`-on-unknown discipline.

## 8. Failure modes

| Condition | Verdict | Behavior |
|---|---|---|
| Tracker returns `r.buildings` as a string | `null` for the field | `parseBuildings` checks `typeof === 'object' && !Array.isArray(...)`; returns `{}` |
| `r.hero` is a string | `null` for the field | Type guard, no throw |
| `r.outcome` is a numeric (`1`/`0`) | mapped to `win`/`lose` | `parseOutcome` branches: `1 → 'win'`, `0 → 'lose'`, anything else `null` |
| `r.units` and `r.attacker_units` both present | split wins, `units` is sum | Existing readers see the union; 2.5 sees the split |
| `r.buildings` has 200 keys | returned whole | UI render caps at top-3; the dossier pushes the whole map |
| `parser` throws | `ingestReport` returns false → `reportFetchFail(id, 'unparsed')` | Existing path (`src/spy.js:336`, `reportRetry` cap at 3) |

The five `return null` strictness paths remain in place. The precondition
invariant (CLAUDE.md) holds: every new field's verdict is the value the
parser actually read, and an unreadable getter yields `null`/empty, never a
guess.

   `f.hero` is `null`. No regression on the `units` row.

   catch-up` row still green; `report fetch` row still green.
5. `grepbot.user.js` rebuilt. `python3 build.py` exits 0.

  assignment UX lives there.
- Per-field export redaction in `state.findings` JSON export. Follow-up —
  the redactor at `src/ui.js:1798-1808` was written before this parser
  widens; the new `hero.name` field is player text and will be flagged

  object. **Hard rule:** the existing `units` field is preserved bit-for-bit
  to keep `src/ui.js:1716-1718` and `src/intel.js:59` working unchanged.
