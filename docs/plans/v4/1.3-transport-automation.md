# 1.3 — Inter-city transport automation

**Bucket:** v4.0 · **Risk:** Med · **Size:** M
**Module:** new `src/transport.js` (concat after `trade.js`); **`build.py` MODULES slot 52** — between `trade.js` (slot 51) and `rural.js` (slot 53 currently). Slot chosen for three reasons: (1) `transport.js` reads `tradeTownRes`, `tradeLedger`, `tradeIncomingByTown`, `tradeSend` — all in `trade.js`; (2) `transport.js` defines a new orchestrator key in the same way `cave.js`/`culture.js` do — both sit adjacent to `trade.js` in the existing order; (3) sibling plan 3.1 (trade-route-manager) only **extends** `trade.js`, so this slot does not collide with that work.
**Depends on:** none — but is the **prerequisite** for 3.2 (support auto-send), 3.4 (resource dump) and 5.1 (resource-balancing AI). The capacity / ETA model and the public helper signatures in §3 are the contract those three consume.
**Status:** PLANNED — written 2026-08-10 against `src/` @ v3.8.2

## 1. What exists today

**`trade.js` already does inter-city resource moves** — there is no
separate transport post route in the tree. Verified by
`rg -n 'transport|Transport' src/`:

- The only inter-city post is `gameAjaxPost('trade', 'town_info',
  'trade', {id, wood, stone, iron, town_id, nl_init:true})` at
  `src/trade.js:37-46` (`tradeSend`).
- The `'Transport' / 'Transports'` collection probes at
  `src/trade.js:55` are **incoming** movements (a `MM.getOnlyCollectionByName`
  read), not a post. They feed `tradeIncomingByTown()`
  (`src/trade.js:49-69`).
- Plan 27 §1.3's "sniff `transportTpl`" hint names a symbol that **does
  not exist** anywhere in `src/` (`rg -n transportTpl src/` returns zero
  hits). This plan treats that hint as forward-looking and explicitly
  flags it as an unknown in §7 — there is no payload to sniff, the post
  is the constant `tradeSend` shape.

**`islandShip`** (`src/trade.js:173-208`) is the closest analogue plan
27 names. It is a sub-planner inside `tradeScan` (`trade.js:350-407`),
threaded through the same `tradeLedger` (`trade.js:71-83`) and gated by
`state.islandShip` (`core.js:297`). Verified by reading every reference
to `state.islandShip` in `src/`: the only writer is the Config checkbox
(`ui.js:760-771`) and the only reader is `tradeIslandShipJobs` plus the
orchestrator guard at `src/qol.js:407` (`trade: 'trade'` — shared with
global `trade`).

**`tradeLedger`** already does the dual-counting (`+mov +pending`)
called out in audit I9 (`src/trade.js:71-83`). 1.3 reuses this ledger
rather than building a parallel one. Each sub-planner mutates via
`tradeApplyJob` (`trade.js:84-90`) and the next sub-planner sees the
deduction in the same scan.

**Profile schema (1.2)** is the read-side hook. `gbCityProfile(townId)`
is added to `boot.js:160-165` (sibling plan 1.2) and returns
`{build, research, units, reserve, defensive, resource:{wood, stone,
iron}}` where `resource[res]` is in -1..+1. **No `transport.js` reads
this yet**; this plan ships that wire so 5.1 (LP solver) does not have
to plumb the same alias a second time.

**Precondition readers in production:**
- `townResState(townId)` (`src/bridge.js:235-273`) — `{cap, wood, stone,
  iron, full, n, fillPct}`, 3s memo, blind on unreadable capacity.
- `ironReservedForCave(townId)` (`src/core.js:685-722`) — returns
  `{reserved, etaMs, blind}`; **gates iron-sending** for `party`
  preset in `tradeGoalJobs` (`trade.js:217-223`). 1.3 calls the same
  gate, regardless of preset, for **any** iron-sending source town that
  also has `state.autoCave` ON.
- `tradeValidateJob(job)` (`trade.js:331-348`) — runs `gbProbeNum`,
  `plannerAvailable`, `ironReservedForCave`, `tradeIncomingByTown`
  gates. **Already exists** — 1.3 does NOT duplicate validation; every
  transport job runs through `tradeValidateJob` before `tradeSend`.

**Orchestrator / lock surface (1.3 does not duplicate it):**
- `'trade'` lock name, TTL 180000ms (`src/core.js:153`).
- `'trade'` captcha breaker key (`src/qol.js:404-408`).
- `'trade'` orchestrator entry (`src/qol.js:426`), cadence 120000ms
  (`qol.js:393`).
- `tradeScan(reason)` is the only trade dispatcher (`trade.js:350-407`).

**Transport moves real resources irreversibly** — every send fires the
shared `txActionGate` (`src/tx.js:522-534`) → second pre-send check
(`tx.js:646-647`) → `gameAjaxPost` → `BRIDGE_TIMEOUT_MS`
(`src/bridge.js:149`) callback. There is **no** rollback path; an
accepted `trade` post ships iron/wood/stone to the destination, full
stop. This is the reason the feature gets a dedicated dry-run gate,
confirm ladder and HIGH-RISK OFF default for the dump sub-feature
(plan 3.4).

## 2. Gap

Plan 27 §1.3 names four scenarios the current `tradeScan` cannot
express:

1. **A user-configurable balance rule** ("if town A wood is below
   30 % and town B wood is above 80 %, send wood from B to A") that is
   neither fill-storage (always targets emptier warehouses globally)
   nor island-ship (only targets `t.small` towns).
2. **Profile-aware bias** — a `resource: {wood:-1, iron:+1}` profile
   (sibling plan 1.2) should bias the transport loop toward iron, not
   require the user to configure a custom global preset.
3. **An ETA / capacity model** other plans consume. 3.2 (support
   auto-send), 3.4 (resource dump), 5.1 (resource-balancing AI) all
   need to ask "when does town X next get wood?" and "how much headroom
   does town Y have for wood?". The current code answers only the
   second question (`townResState`), and only on the **current**
   warehouse state — not on `tradeLedger`-projected state, not on
   arrival-aware headroom.
4. **A public helper surface** so 3.2 / 3.4 / 5.1 do not all reach
   into `trade.js` internals. Today there is no `transportTownETA`
   symbol anywhere in `src/`. Today there is no `transportProjectHeadroom`.

## 3. Design

The new `src/transport.js` defines four public functions consumed by
this plan, by 3.2, by 3.4 and by 5.1:

```js
// Signature contract — DO NOT break between v4.0 and v4.3.
// All four return null on blind (precondition invariant: a check
// may only block on a value it actually read).

transportTownRes(townId)
  → {wood, stone, iron, cap, tradeCap, etaWoodMs, etaStoneMs, etaIronMs,
     islandType, small, fillPct:{wood,stone,iron}, blind:bool}
  // etaXxxMs is ms until the resource hits cap at current production;
  // 0 means "at cap". blind:true if any of wood/stone/iron is
  // unreadable OR cap is unreadable.
  // Reuses tradeTownRes (src/trade.js:1-22) + townResState + per-
  // resource production read via gbProbeNum(t, ['getProduction', ...]).

transportProjectHeadroom(townId, deltaMs)
  → {woodFree, stoneFree, ironFree, blind:bool}
  // Free space in townId's warehouse deltaMs from now, accounting
  // for current production rate and current incoming movements.
  // Blind on unreadable capacity OR unreadable production.

transportTownETA(townId, resource, targetFillPct)
  → {ms, blind:bool} | null
  // ms until the named resource fills targetFillPct of cap, given
  // current production minus the same drain rate other features
  // (cave/culture/build) are projected to consume. Returns null if
  // the target is unreachable in the visible window (> 24h) or if
  // production is unreadable.

transportBalanceJobs(towns, ledger)
  → [{from, to, wood, stone, iron, reason}]
  // ONE planner that produces a balanced fleet-wide move list,
  // honouring:
  //   - ironReservedForCave on iron sources
  //   - townResState fill >= 0.85 (source threshold) for any send
  //   - target fill <= 0.25 (target threshold) for any receive
  //   - minBatch floor from state.transportMinBatch (default 1000,
  //     reuses state.tradeMinBatch at first; new key after the
  //     schema migrates)
  //   - gbCityProfile(townId).resource[res] bias: towns whose
  //     resource bias is +1 attract the resource; -1 repels it;
  //     0 = neutral. (sibling plan 1.2 ships the schema.)
  // Returns at most 4 jobs per scan, mirroring tradeIslandShipJobs
  // ceiling (trade.js:204) — over-firing is what starves the
  // request budget per audit I9.
```

**Internal architecture:**

- `transportTownRes` reuses `tradeTownRes` (`trade.js:1-22`) and adds
  ETA via `gbProbeNum` on `getProduction()` (same pattern as
  `ironReservedForCave` at `core.js:708-716`).
- `transportProjectHeadroom` calls `transportTownRes` and
  `tradeIncomingByTown()` (`trade.js:49-69`) to compose
  "free-space deltaMs from now".
- `transportTownETA` chains `transportProjectHeadroom` over
  iteratively-spaced samples; implementation is a single
  `while ((now + delta) < end) sample; if (sample[res] >= target) return
  delta;` loop with `delta` doubling (max 8 iterations, max 24h).
- `transportBalanceJobs` is a NEW sub-planner that slots into
  `tradeScan` (next work item).

**Orchestrator wiring:** 1.3 does **not** add a new orch key.
`transportBalanceJobs` is called from `tradeScan` (`trade.js:350-407`)
exactly like `tradeIslandShipJobs` is — a sub-planner of an existing
tick. This is the same discipline sibling plan 3.1 follows for routes:
a captcha on the trade queue pauses all of trade, transport included,
for the ladder window. Splitting them would let a transport burn
requests against a paused queue. **No entry is added to
`PRIORITY_ORDER_DEFAULT`** (`header.js:189-190`).

## 7. Post surface & safety

- **Post path is unchanged.** Every transport job runs through
  `tradeSend` (`trade.js:37-46`) which already posts
  `gameAjaxPost('trade', 'town_info', 'trade', {id, wood, stone,
  iron, town_id, nl_init:true})`. The endpoint is in
  `TX_WRITE_FEATURES` (`src/planner.js:212-216`) and routes through
  `txRun` → `gameAjaxRaw` (`src/bridge.js:149-189`).
- **No `gbAjaxWatch` registration.** Trade is server-rendered, not
  template-learned. `tplNameFor('trade', …)` returns `null`
  (`tplHealthOk` is skipped, `tx.js:569-573`); same as the existing
  trade path.
- **No `TPL_FEATURE_MAP` entry.** Same reasoning — `tplNameFor` is
  bypassed by a constant payload shape. **Plan 27's "sniff
  `transportTpl`" hint is wrong**: there is no separate transport
  post template, and a sniff would either land on the existing
  `'trade'` payload (which is already in use) or land on no payload
  at all. **Explicit unknown: do not invent a transport endpoint,
  payload field, or controller name. Work item 1 of this plan uses
  `tradeSend` verbatim.**
- **Captcha breaker.** Feature key `'transport'` is added to
  `gbCaptchaPause`. Because transport runs through the trade
  sub-planner of `tradeScan`, the breaker key is `'trade'` in
  practice (one captcha trip pauses the whole trade queue, including
  transport). The separate `'transport'` key is a no-op today;
  reserved for the day a transport-specific post is added (none
  planned in v4.x).
- **Lock name.** `'trade'` (`core.js:153`). Routes / transport share
  the `gbLock('trade')` acquired at `tradeScan:381`; do not split.
- **Dry-run.** `txActionGate` (`tx.js:522-534`) returns `'dryrun'`
  when `state.dryRun` is set; `txRun:554-562` logs
  `DRY-RUN trade: …`. Every transport send inherits this — verified
  by tracing through `gameAjaxPost → txRun → gameAjaxRaw`.
- **`ironReservedForCave` interaction.** Source iron is reduced by
  the reserved amount before the cap clamp — same pattern as
  `tradeGoalJobs:301`. A blind `ironReservedForCave` call returns
  `{reserved: false}` (the `core.js:717` "unknown, not 'no'"
  comment), so the transport loop proceeds without the reserve
  deduction. Logged once per scan via `gbLogT`.
- **No new scheduler.** No `gbInterval`. No `*InFlight` boolean.
  Cadence is the existing `'trade'` 120000ms (`qol.js:393`).

## 8. Failure modes

- **`townResState(tgt)` returns null (blind).** `transportBalanceJobs`
  skips that target for this scan, logs once via
  `gbLogT('transport-blind-' + tgt, …)`, continues. Per scan, per
  town — no exception throw, no silent drop.
- **`tradeLedger` returns null (`tradeIncomingByTown()` unknown).**
  `tradeScan` fails closed (`trade.js:357`) — transport loop never
  runs. Same as today.
- **`ironReservedForCave(from)` is `reserved: true` and the source
  ships iron.** Source iron is reduced by `Math.floor(info.cap *
  state.transportReserve / 100)` and again by the cave reserve
  (whichever is larger); the cap clamp in
  `transportBalanceJobs` matches `tradeGoalJobs:301`. Blind ⇒ no
  reserve deduction (cave returns `{reserved:false}` on blind).
- **Profile key `resource` is null (profile not seeded yet).**
  `gbCityProfile(townId).resource` returns `{wood:0, stone:0, iron:0}`
  — sibling plan 1.2's `goalTownCfg` defensively seeds this
  (`goals.js:5-12`).
- **Per-pair source fill < 0.85.** Skip that pair; no log spam
  (`gbLogT` keyed by `from+'-'+to`, 600s window).
- **Per-pair target fill > 0.25.** Skip — mirror of
  `tradeFillStorageJobs:142` ("25%-empty target" rule, plan 26 §B6
  audit kept this as the global default).
- **Job fails `tradeValidateJob`.** Same as today: skipped via the
  `'trade-stale-' + from + '-' + to` log path (`trade.js:394`).
  `transportBalanceJobs` does NOT bypass the validator.
- **Two transport jobs in the same scan claim the same source.** The
  shared ledger discipline (`tradeApplyJob` after each job) means the
  second job sees the first's deduction and clamps itself. The
  4-job-per-scan ceiling (mirroring `tradeIslandShipJobs:204`)
  keeps the scan bounded.
- **Captcha during a transport send.** `tradeScan` releases the
  trade lock on `'captcha'` callback (`trade.js:399`). Transport
  inherits this; no extra path.
- **`state.autoTransport` flipped ON with no profile yet loaded.**
  `gbCityProfile` returns the seed `custom` profile (1.2 seeds
  `{defensive:0.5, resource:{wood:0, stone:0, iron:0}}`), so
  transport fires as the neutral case. Logged once on first tick.

## 9. Validation gate

Per plan 27 §11 (Med risk): **dry-run + one hand-triggered firing +
one full orchestrator tick.**

1. **Dry-run smoke.** Toggle `state.dryRun` on; toggle
   `state.autoTransport` on; wait one trade tick (~2 min). Expect
   exactly one `DRY-RUN trade: A→B w…/s…/i…` line per planned job
   (max 4); zero real posts.
2. **Validation precheck.** Force `tradeScan('manual')` from the
   panel; confirm `tradeValidateJob` did NOT log
   `trade-stale-<from>-<to>` for any transport job. If it did, the
   ledger cross-check is broken.
3. **Live, single job.** Disable dry-run, set `state.transportMin =
   500`, force one scan. Expect one `trade: A→B w…` log line and
   one `ok` decision journal entry for feature `trade`.
4. **Profile bias.** Set town A profile `resource.iron = +1`, town B
   `resource.iron = -1`, fill B above 90 %, A below 20 %. Expect one
   iron send from B to A per tick. Revert bias to 0, expect no
   transport on the same town pair (other sub-planners may still
   fire — verify in journal).
5. **Iron-reserve-for-cave interaction.** On a town with
   `state.autoCave` on and `caveThreshPct = 90`, force a transport
   send that ships iron from that town. The cave-reserved amount
   must be subtracted; verify by reading
   `gbLogT('cave-res-blind-' + from, …)` and by checking the
   `trade-goal-far-` log analogues — transport logs
   `transport-iron-reserved-<from>`.
6. **`transportBalanceJobs` cap.** Disable other sub-planners;
   force a scan with 8 valid pairs (use the same town 8 times in
   the test array). Expect 4 jobs returned; the next 4 wait for the
   following tick. Same discipline as `tradeIslandShipJobs:204`.
7. **No new scheduler.** `rg -n 'gbInterval' src/transport.js`
   returns zero hits; `rg -n 'InFlight' src/transport.js` returns
   zero hits. `orchTick` cadence for `trade` is still 120000ms.
8. **Export round-trip.** Export config (`ui.js:986`), confirm
   `autoTransport` is in the dump. Re-import — feature returns to
   its previous state. No redact warning (no player data in the new
   fields).
