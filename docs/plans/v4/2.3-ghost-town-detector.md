# 2.3 — Ghost town detector

**Bucket:** v4.0 · **Risk:** Low · **Size:** S
**Module:** extend `src/intel.js` (additive) + small markup addition in `src/ui.js` intel section
**Depends on:** none
**Status:** PLANNED — written 2026-08-10 against `src/` @ v3.8.2

## 1. What exists today

- `state.findings` (`src/core.js:221`) is the per-world report ring buffer. Every entry carries `ts` (ms epoch, parsed in `parseReport` at `src/parse-inline.js:56-72` with a `n < 1e12` ms/s heuristic), `town.id` and `town.name` (`src/parse-inline.js:78-83`), and a defender block with `vacation` (`src/parse-inline.js:14`, written by `nameOf`).
- The intel panel today (`renderIntel` at `src/intel.js:75-114`) renders only the **flat text dump** of `=== Entrantes ===` / `=== Fichas ===` / watchlist / alliance notes / pattern note. There is no per-town "is anyone home?" view.
- `intelDossiers` (`src/intel.js:34-71`) groups by **player**, not by town. It captures `reports`, `units[]`, `towns[]`, `walls[]`, `last` (max ts). It does not check staleness, vacation, or any "ghost" signal.
- `intelPlayerKey` (`src/intel.js:1-10`) is the canonical string key for a player (`'id:<n>'` for objects with an `id`, otherwise the name). It is what `intelDossiers` and `intelPatternScan` use; towns in `state.findings` carry `town.id` directly with no equivalent helper. 2.3 needs a town-key helper (see §4 item 2) — same shape, different attribute.
- 2.2 Enemy city timeline (sibling plan) introduces `const INTEL_HISTORY_TTL_MS = 7 * 86400000;` in `intel.js`. 2.3 reuses it — that is the **one** retention policy the read trio shares.
- Plan 27 §9 already-shipped list does **not** mention a ghost-town detector. The watchlist code (`watchMatch` at `src/intel.js:145-184`, `intelWatchlistScan` at `src/intel.js:186-205`) is the closest sibling — it logs a hit and fires `alertWebhook` but only when a new finding matches a saved rule. It does not score "quiet towns" at all.

## 2. Gap

A scout user has 200 reports in `state.findings`. Some of those reports are 30 days old on towns whose defenders went on vacation the next week; some are on towns the defender abandoned. Right now the intel panel only shows "this player exists" (dossiers) or "this is incoming right now" (threats). There is no read path that says "you have not seen activity on this town in N days" or "this town's last defender is on vacation". 2.3 closes that gap with a per-town staleness + vacation view, derived from data that already lives in `state.findings`.

## 3. Design

- New function `intelGhostTowns(opts)` in `intel.js`. Reads `state.findings` only — no new storage.
- Group by `intelTownKey(f)` (the helper introduced by plan 2.2 item 2 — `'town:<id>'` for cities, `'farm:<id>'` for villages). Filter to `f.ts >= now - INTEL_HISTORY_TTL_MS` (7d). For each town, find the **most recent** finding and read:
  - `last.ts` — the timestamp.
  - `last.town.name` — display label.
  - `last.defender.vacation` — true if the defender was on vacation at last sight.
  - `last.wall` — last known wall level (so the user knows whether it is worth a follow-up spy).
  - `last.alliance` — last known alliance (so a player who switched alliance is flagged).
- Score per town (read-only, deterministic):
  - **stale** if `now - last.ts >= GHOST_STALE_MS` (default 3 × 86400000 = 3 days).
  - **vacant** if `last.defender.vacation === true`.
  - **abandoned** if no defender name in the last finding (`last.defender && !last.defender.name`).
- Output: `Array<{ townKey, label, lastTs, ageMs, vacation, abandoned, wall, alliance, reasons: string[] }>` sorted by `ageMs` desc. Rendered as a single table on the intel panel below the dossier pre.
- No scheduler (rendered on `renderIntel()` call from `src/boot.js:108-115` 15s loop). No `GB_LOCK_TTL` entry. No `STORE` / `WORLD_SCOPED_BASES` entry. No `configVer` bump. No `alertWebhook` (this is a passive view; firing a webhook for every "town is quiet" would be noise — that is what a 5.x feature is for).

## 6. Config surface

None. `GHOST_STALE_MS` is a hard-coded default (3 days) inside the module. It is the kind of knob that does not earn its own Config row until someone asks; if a user wants to tune it, they change the constant in `src/intel.js` and rebuild. Document in code comment that this is the "3d default per Grepolis vacation cap norm" — players who go on vacation usually take at least 3-7 days off, so anything silent for longer is the actionable signal.

## 7. Post surface & safety

**No post surface.** Read-only. Skips the rest of §7 per `docs/plans/v4/README.md` and plan 27 §13. Never invents a game endpoint. Reads `state.findings` only.

## 8. Failure modes

- **No findings at all:** empty-state row, no log. `intelGhostTowns` returns `[]`.
- **All findings filtered by 7d:** `gbLogT('intel-ghost-empty', 300000, …)` fires once; empty-state row renders. The trip wire is the same one that catches a ts-in-seconds client.
- **Town seen only in outgoing farm raids (no `defender`):** the `last` finding for that town has `defender = null` and `town.id` set (the raid was on a known city id via `parseReport:79`). `abandoned` flag is **not** set (we have an attacker on record, just not a defender), so the row reads `sin nombre de defensor` only when a defenderless finding is the most recent. Honest unknown — the precondition invariant in CLAUDE.md.
- **`last.wall` unknown:** render `?`, not `0`. Same rule as 2.2.
- **User deletes the intel tab section markup:** `panel.querySelector('.intel-ghost')` returns null; `renderIntelGhost` early-returns. The function never throws on missing DOM (matches `renderIntel` line 76-79 pattern).

## 9. Validation gate

Per plan 27 §11 (Low risk) — Preflight + one in-game session, no failure.

1. Build, install, open a world with at least 5 reports covering a mix: one town last seen today, one town last seen 4 days ago, one town whose last defender was on vacation, one farm village with no defender in the most recent raid.
2. Open the Intel tab. The new ghost-towns table appears below the (eventual) timeline table. The 4-days-ago town shows `Xd` age and `sin actividad 3d` reason. The vacation town shows `defensor en vacaciones`. The defenderless village shows `sin nombre de defensor`. The today town is **absent** (it is not stale — `< GHOST_STALE_MS`).
3. Force a vacation flag in console: `state.findings[0].defender.vacation = true`; reopen Intel. The row reappears with `defensor en vacaciones` reason. (The redaction pipeline at `ui.js:1061` does not touch `vacation`.)
4. Sort by `Edad` desc; close+reopen the panel — sort survives via `state.tabFilters.sort:intel-ghost`.
5. Preflight row "findings schema" still passes; journal still silent (no entries).

## 10. Out of scope

- **Per-building and per-hero "what changed while you were away".** Owned by 2.1 + 2.2. 2.3 only reports the *fact* of staleness; the diff lives in 2.2.
- **Auto-fire a follow-up spy on a stale town.** That is plan 4.1 (auto-spy scheduler) with a per-target cadence. Out of scope here — 2.3 is read-mostly.
- **Webhooks / alerts for ghost detection.** No event surface; would add noise. If a future user wants it, add `alertWebhook('ghost', payload)` behind a `state.intelGhostAlert === true` toggle. Defer until asked.
- **Player-level inactivity.** Plan 2.4 owns that axis (group by `intelPlayerKey`, not by town). Different table, different sort.
- **Tombstone / outpost intel.** No game endpoint exists in the bridge model. Plan 27 §0 — do not invent endpoints.
