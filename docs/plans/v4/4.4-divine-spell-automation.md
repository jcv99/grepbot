# 4.4 — Divine spell automation

**Bucket:** v4.5 · **Risk:** High · **Size:** L
**Module:** split spell mechanics out of `src/recruit.js` into NEW `src/god-spells.js`
(`recruit.js` keeps `recruitBuild` + the recruit gate and consumes the new helpers);
add a new entry to `build.py` MODULES at the slot after `favor.js` (line 57) and
before `wonder.js` (line 58).
**Depends on:** none; sits behind the existing `state.autoFavor` toggle per plan 27
§4.4, HIGH-RISK OFF default, `temple_plunder` research required, target = farm town.
**Status:** PLANNED — written 2026-08-10 against `src/` @ v3.8.2

## 1. What exists today

Verified against `src/favor.js`, `src/recruit.js`, `src/wonder.js`, `src/core.js`,
`src/header.js`.

- **Two spell mechanisms today, both partial.**
  - **Favor-for-attack** lives entirely in `favor.js` and spends units at a farm
    village to generate per-god favor. `FAVOR_AUTOMATION_ENABLED = false`
    (`favor.js:8`) keeps the loop from running; `favorScan`
    (`favor.js:52-152`) is the gate + payload, payload uses `attackTpl`
    (`favor.js:133-139`) — it does **not** cast a spell.
  - **Recruit spells** (`recruit.js:4` `RECRUIT_SPELLS = ['call_of_the_ocean',
    'spartan_training', 'fertility_improvement']`; god map `recruit.js:8-12`
    `RECRUIT_SPELL_GODS`) already implement the full cast path:
    `recruitSpellGateOk` (`recruit.js:55-68`, gates on academy + god),
    `recruitSpellCooldown` (`recruit.js:43-54`, persisted via
    `STORE.SPELL_COOLDOWN` = `'grepbot:spell-cooldown'`, `header.js:177`,
    world-scoped, `core.js:319` loads it into `state.spellCooldown`),
    `recruitHasSpell` (`recruit.js:25-38`, reads the `CastedPowers` MM
    collection), and `recruitCastSpell` (`recruit.js:69-80`,
    `gameAjaxPost('spell', 'town_overviews', 'cast_power', {power_id, town_id}, onDone)`).
- **Recruit spell integration is wired but opt-in.** `recruitScan` only
  attempts a spell when `state.recruitSpells` (`core.js:332`,
  default `false`, `header.js:120`) is true and a `favorCfg.recruitPower`
  is set (`recruit.js:319`); the cast is part of a recruit job's lifecycle,
  not its own loop.
- **No non-recruit power ids are cited anywhere in `src/`.** Grep over
  `power_id|cast_power|RECRUIT_SPELLS|god_power` in `src/` finds the
  recruit spell infrastructure and the quest reward parser
  (`quests.js:66,82-84,94,121,217,294,303`), nothing else. Plan 27 §0
  blocks inventing ids; the only safe enumeration is the recruit spell
  list, with a sniff path for any others.
- **TPL_FEATURE_MAP** (`core.js:778-790`) maps `wonder` → `wonderFavorTpl`
  but has **no** `spell` or `favor` entry. The comment at `core.js:790`
  reads literally: *"Favor is currently disabled in src/favor.js; leave
  it unmapped so re-enable does not poison attackTpl health. When favor
  gets its own learned payload, add a dedicated `favorTpl` here."* A
  `spell` entry is therefore needed if any divine-spell post re-uses
  `recruitCastSpell`'s route.
- **Wonder-favor precedent for HIGH-RISK loops.** `wonderFavorScan`
  (`wonder.js:154-183`) is the only currently-coded "spend a learned
  payload" loop: HIGH-RISK (`autoWonderFavor` `core.js:376`,
  `STORE.AUTO_WONDER_FAVOR` `header.js:172`, default `false`),
  `gbLock('wonder-favor')` (`wonder.js:168`, TTL `180000ms`
  `core.js:160`), `gbCaptchaPause`-style feature key `'wonder'` already
  covers it (`wonder.js:155`). The budget discipline
  (`wonder.js:10-19, 110-114`) is the daily-favor-spend model to copy.
- **Orchestrator** has a `favor` slot (`orchestrate.js:5-20`,
  `PRIORITY_ORDER_DEFAULT` includes `favor` `header.js:190`) but no
  `spell` slot; cadences are declared in `orchestrate.js` and there is
  no per-feature `gbInterval` (CLAUDE.md "v1.1.0 orch is the sole econ
  scheduler").

## 2. Gap

Favor-for-attack is intentionally parked (`FAVOR_AUTOMATION_ENABLED =
false`). What is missing is the **second** divine-spell class: spending
favor on `cast_power` against an enemy / farm town (or, separately, on a
defensive target). Today the only way the bot casts a god power is the
`recruitSpells` accelerator inside `recruitScan`, and it only knows the
three recruit spells. A user who wants to spend favor on a meteor,
earthquake, or any non-recruit spell has no surface. The mechanics
(gate, cooldown, persistence) exist in `recruit.js` but are hard-coded
to recruit and live behind the recruit cadence — pulling them out is
what makes a generic god-spell loop possible without copy-pasting the
gate.

## 3. Design

Split the cast mechanics out of `recruit.js` into a new `src/god-spells.js`,
keep the existing `recruitCastSpell` call path stable, and add a
**separate** orchestrator slot (`godspell`) that fires only when
`state.autoFavor` is true and the existing favor-favor loop is parked
(v4.5 stays HIGH-RISK OFF default per plan 27 §4.4; the existing
`autoFavor` toggle is the gate, since the user's mental model is
"auto-favor" = "let the bot spend favor for me"). The spell scan reads
favor, gates, picks a target, casts, and uses the existing cooldown
registry — no new post class, no new endpoint, no new template
(defaulting to the `cast_power` constant the recruit path uses).

Power id discipline (CLAUDE.md, recruit note): **never default to
`call_of_the_ocean`**. The cast path takes the explicit id from
`favorCfg.spellPower` (a new field on the same config block the
recruit accelerator reads at `recruit.js:319`). An unrecognised id →
log once → no cast. A non-recuit power id (meteor, etc.) is
**unknown** to the tree; the work item to learn it is the standard
hand-cast sniff, not a guess.

  The migration at the import site (`qol.js:267`) needs a one-liner

## 7. Post surface & safety

- **Endpoint** is the existing `town_overviews/cast_power`
  (`recruit.js:76-79`, confirmed in source — **NOT a guess**). Payload
  `{power_id, town_id:+townId}`. Dry-run gate (`state.dryRun`) is
  honoured automatically by `gameAjaxPost` → `txRun` (`tx.js:522-647`,
  dry-run aborts at `txActionGate` before the budget mark).
- **Watch registration**: `gbAjaxWatch('ajax:town_overviews/
  cast_power', settle)` already fires from `gameAjaxRaw`
  (`bridge.js:176`); no new watcher needed. Template name in
  `TPL_FEATURE_MAP` as `spell: 'castPowerTpl'` (key reserved for any
  future learned payload — the current payload is hardcoded).
- **Captcha breaker key**: add `'godspell'` to whatever feature-key
  list the captcha breaker reads (`bridge.js` exposes the registry
  per CLAUDE.md "captcha breakers"). Mirror the existing `'favor'`
  and `'wonder'` entries.
- **Lock name**: `gbLock('godspell', 180000)`, add a `GB_LOCK_TTL`
  entry `godspell: 180000` (`core.js:145-174`, next to `favor` and
  `wonder`).
- **Dry-run behaviour**: `DRY-RUN spell: {power_id, town_id}` log
  line, journal as `skip:dryrun`. The same path `recruit.js:344-351`
  uses today.
- **Favor-spend is irreversible** (CLAUDE.md "favor is irreversible,
  manual review required", `recruit.js:349`): the 30-min cooldown is
  the safety window; a blind timeout stamps it. Do **not** retry on
  `pending` or `timeout_unknown` (`recruit.js:347-348` precedent).

## 8. Failure modes

- **Unreadable god pool** (`favorCurrent()` returns `{}`):
  `gbLogT('godspell-favor-blind', 300000, ...)` once; return. Never
  spend on a blind read (CLAUDE.md precondition invariant, mirror
  `favor.js:73-76`).
- **Unrecognised power id** (`state.favorCfg.spellPower` set to
  something not in `RECRUIT_SPELLS` and not yet hand-sniffed):
  `gbLogT('godspell-badpower', 600000, ...)` once. The cast does
  **not** happen — server-side rejection costs a budget slot and a
  decision-memory strike every cadence (`recruit.js:316-322`
  precedent).
- **Wrong-god cast** (power id's required god ≠ town's god):
  `godSpellGateOk` returns `{ok:false, why:'god-mismatch'}`. Block;
  do **not** post.
- **Academy missing**: `godSpellGateOk` returns `{ok:false,
  why:'no-academy'}`. Block; do **not** post.
- **Below reserve**: `godSpellScan` returns silently; log once per
  10min (`gbLogT('godspell-reserve', 600000, ...)`).
- **Already cast in town** (`CastedPowers` model shows the power):
  `godSpellHasCast` returns `true`; skip. (Prevents the
  double-charge that `recruitHasSpell` was added for at
  `recruit.js:25-38`.)
- **Cooldown active** (`state.spellCooldown[townId][powerId] > now`):
  log once per minute; do not post.
- **Captcha response**: `gbCaptchaPause` breaker opens; loop sleeps
  per `state.captchaLadder` ladder (`core.js:353`,
  `[5,15,60]` minutes default).
- **Decision-memory strike** (`journal.js` v1.1.0): three hard
  errors in a row on the same `feature|action|target` open a 5/15/60min
  skip window (`journal.js:86`-ish, per CLAUDE.md "decision memory").
  Captcha/timeout do not trip it.

## 9. Validation gate

Per plan 27 §11 HIGH-RISK row: payload sniff against live UI +
confirm-gate screen + dry-run + manual re-fire once, **still default
OFF** until per-package exit criteria. Concrete, in order:

1. **Payload sniff.** Open a town's temple in the live UI, hand-cast
   one of the three recruit spells, confirm `gbAjaxWatch` settles the
   watch from the XHR response (`bridge.js:7-19, 36-58`). The
   captured `model_url`/`action_name` must equal
   `town_overviews/cast_power` (already cited from `recruit.js:76-79`,
   this step only confirms the live UI sends that route on this
   world).
2. **Dry-run ON.** Set `favorCfg.spellPower = 'call_of_the_ocean'`,
   `favorCfg.targetId = <farm_town>`, `favorCfg.targetType =
   'farm_town'`. Force one tick. Log must show `DRY-RUN spell:
   {power_id:'call_of_the_ocean', town_id:<N>}`; journal must show
   `skip:dryrun`; no POST.
3. **Reserve honoured.** Set `spellReserve = 90`. Confirm zero casts
   while god pool < 90% of cap.
4. **Wrong-god block.** Configure the power for ares on an
   athena-only town. Confirm `god-mismatch:<athena>!=<ares>` log and
   no POST.
5. **Academy missing.** Configure the power for a town with no
   Academy building. Confirm `no-academy` log and no POST.
6. **Live cast (manual gate).** `dryRun = false`, single hand-triggered
   scan, confirm one POST, one `cast_power` arrives in the temple UI,
   cooldown stamped.
7. **Cooldown persistence.** Reload page; confirm `spellCooldown` is
   still set (via Diag dump) and the next scan skips with
   `skip:cooldown`.
8. **Preflight row** `godspell`: pass = id is in `RECRUIT_SPELLS` or
   academy is readable; warn = id set but god unreadable; fail = id
   set but academy missing for the configured town.

## 10. Out of scope

- **Non-farm-town targets.** Plan 27 §4.4 says "temple_plunder ONLY";
  the `targetType` allow-list at `favor.js:93-96` is reused verbatim.
  A plan for attacking enemy towns with divine spells is its own
  feature (plan 27 §3 movement family, separate risk profile).
- **Sniffing non-recruit power ids (meteor, earthquake, etc.).** The
  three RECRUIT_SPELLS ids are the only power ids cited anywhere in
  `src/`. Adding more requires a hand-cast sniff per id (mirrors
  `wonderFavorTpl` for the wonder path); that is a v4.6+ feature and
  is **explicitly unknown** in this plan. The work item is "player
  hand-casts once; the bot captures the id into a learned payload"
  — not "guess the id".
- **Wonder-favor and recruit-spell flows.** Those are owned by plan
  02 and the existing `recruitSpells` accelerator respectively; this
  plan only factors the shared mechanics out, it does not change
  their behaviour.
- **Favor-spend for attack** (`favor.js` favorScan). Stays parked
  behind `FAVOR_AUTOMATION_ENABLED = false` (`favor.js:8`) until a
  later plan turns it on. This plan only reads `favorCurrent()`;
  it does not enable the favor-favor loop.
- **Auto-recruit god pairing.** The `RECRUIT_SPELL_GODS` map
  (`recruit.js:8-12`) is the canonical god-of-spell authority and
  ships unchanged.
