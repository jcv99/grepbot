## 1. What exists today

Three sub-planners in `src/trade.js` already produce balanced moves;
each is rule-based, not optimisation-based:

- `tradeFillStorageJobs` (`src/trade.js:130-172`) — the global
  fill-storage rule: any town ≤ 25 % empty gets wood+stone+iron from
  any town ≥ 85 % full, capped by `state.tradeReservePct`
  (`core.js:296`, default 20) and `state.tradeMinBatch` (`core.js:297`,
  default 1000). Skips when `tgt` has no room (audit I9 ledger
  discipline).
- `tradeIslandShipJobs` (`src/trade.js:173-208`) — special-case
  fill for `t.small` towns (small-island). Limit 4 jobs / scan.
- `tradeGoalJobs` (`src/trade.js:262-330`) — deficit-driven planner
  for `party` / `unit` preset. Picks donors by per-resource surplus,
  applies deficit + cap clamp + free-space cap. Limit 6 jobs / scan.

**Plan 3.1's `tradeRouteJobs`** (sibling plan, extends `trade.js`)
adds a fourth: user-defined named routes that run before
`tradeFillStorageJobs` and claim headroom first.

**Plan 1.3's `transportBalanceJobs`** (sibling, NEW `transport.js`)
adds a fifth: profile-biased fleet-wide balance, also runs before
the global sub-planners via the same `tradeApplyJob` ledger.

**What is missing** vs. the plan 27 §5 row 5.1 description
("Resource balancing AI, greedy LP solver"):

- **No objective function.** Each existing sub-planner is a single
  heuristic ("send to emptier", "drain pinned resource"). None of
  them considers the fleet-wide balance after this batch lands —
  the system has no notion of an optimal target state.
- **No profile-aware prioritisation.** Plan 1.2 ships
  `gbCityProfile(townId).resource.{wood,stone,iron}` in
  -1..+1. None of the existing sub-planners reads it; the closest is
  `tradeGoalJobs` reading `(state.recruitTargets || {})[townId]`
  for the `unit` preset (`trade.js:242-243`).
- **No cross-resource substitution.** Grepolis has no exchange rate
  between wood and stone (cave only stores iron; build orders need
  each resource independently). A real LP would treat
  `wood + stone + iron` as three independent supply chains. The
  "LP" in plan 27's row name is therefore a **loose** LP — see §3
  for the honest model.

**Precondition readers used today:**
- `tradeTownRes(townId)` (`src/trade.js:1-22`) — per-town
  `{wood, stone, iron, cap, tradeCap, small}`.
- `townResState(townId)` (`src/bridge.js:235-273`) — `{cap, wood,
  stone, iron, full, n, fillPct}` with 3s memo; blind on unreadable.
- `ironReservedForCave(townId)` (`src/core.js:685-722`) — gates iron
  sources when `state.autoCave` is on.
- `plannerAvailable(townId, {allowSoft:false})` — read by
  `tradeValidateJob` (`src/trade.js:338`).

**Hard limits in the post pipeline that constrain any solver:**
- One `trade` post = `gameAjaxPost('trade', 'town_info', 'trade',
  {...})` (`src/trade.js:37-46`). No batched API; every move is one
  post.
- `'trade'` lock name, TTL 180000ms (`src/core.js:153`).
- `'trade'` captcha breaker key (`src/qol.js:404-408`).
- Request budget: `state.reqBudgetPerMin` ×
  `REQ_SCOPE_FRACTION.action = 1.0` (`src/core.js:608-612`), default
  40 / 60s. Each scan costs at most ~6 action slots per
  `tradeFillStorageJobs:168` (6 jobs max).
- `tradeScan` runs on `'trade'` cadence 120000ms (`qol.js:393`),
  jittered ±20 %.

**Post-mortem on a real optimization:** plan 26 §B6 already audited
`tradeScan` end-to-end and noted that the existing heuristics double-
count incoming movements correctly (`trade.js:71-83` comment). The
"I9 ledger threading" is closed; 5.1 inherits it.

## 2. Gap

Plan 27 §5 row 5.1 wants an "AI" planner. The honest reading is:

- **No real LP.** Grepolis has no exchange API between resources;
  wood, stone, iron are three independent supply chains. A linear
  program that models wood→stone substitution would have no slack to
  optimise against. A "greedy" pass that scores each (source,
  destination, resource) triple by a hand-picked objective is the
  most the data structure permits.
- **Greedy is sufficient for the actual win.** The user pain is
  *cross-town imbalance that the global fill-storage rule misses*.
  Fill-storage targets any town ≤ 25 % empty; it cannot express
  "town A is building a farm and will need 6000 wood in 8 minutes".
  A planner that reads ETA + profile bias + iron-reserve can do
  better. Greedy on `O(towns² × resources)` ≤ 64 evaluations per
  scan (8 towns × 8 towns × 3 resources) is sub-millisecond and the
  diminishing-returns ceiling for a userscript scheduler.
- **The objective function lives in the planner, not the post.** The
  post is `tradeSend`. The plan is a `transportAiJobs(towns,
  ledger)` function in `transport.js` that follows the same shape
  as `transportBalanceJobs` from sibling plan 1.3.

## 3. Design

**Objective.** Maximise a fleet-wide balance score after this batch
lands, where balance is:

```
score = Σ over towns of
        Σ over resources r in {wood,stone,iron} of
          w_r(profile[t].resource[r]) × distance_to_target_fill_pct(t, r)
```

Where `distance_to_target_fill_pct(t, r) = |fill(t, r) - target_pct(r)|`
and `target_pct(r)` is **per-resource**:
- `wood: 60%` (build + farm are wood-heavy, see CULTURE_COSTS party
  15000 wood, `src/cave.js:284`).
- `stone: 50%` (less demand than wood).
- `iron: 30%` (cave reserves most; see `caveThreshPct = 90`,
  `core.js:288`).

`w_r(profile[t].resource[r])` is the per-town profile bias from
sibling plan 1.2's `gbCityProfile(townId).resource[r]` in -1..+1,
clamped to a [0.25, 2.0] weight so an extreme ±1 does not 8× the
score of one resource.

**Algorithm.** Greedy one-move-at-a-time on
`{from, to, resource}` triples:

1. **Snapshot.** Build a working ledger `L` from `tradeLedger(towns)`
   (sibling 1.3 / `trade.js:71-83` reuses it).
2. **Score every triple.** For each (from, to, resource) where
   `from !== to` and `from.cap > 0` and `to.cap > 0`:
   - source fill >= 0.85,
   - target fill <= 0.25,
   - source `tradeCap >= transportMin`,
   - `ironReservedForCave(from)` is not reserved (or resource != iron),
   - estimate `delta_score` = `score_after - score_before` for the
     triple, sending `min(transportCap, source[res] - keep,
     target.cap - target[res])`.
3. **Pick the top-N.** Sort by `delta_score` desc; pick the top 6
   (matching `tradeFillStorageJobs:168` ceiling).
4. **Apply sequentially.** For each picked job:
   - `tradeApplyJob(L, job)` mutates the ledger.
   - The next pick sees the deduction — no double-counting.
   - Build the `{from, to, wood, stone, iron}` job object exactly
     like `tradeFillStorageJobs:159-164`; **zero the resource** that
     was not part of this triple (the planner sends one resource per
     job, not a multi-resource haul).
5. **Cap.** 6 jobs / scan. The 7th-best triple returns to the
   queue; the next tick re-scores with the actual warehouse state.

**Why greedy over a real LP.** Three honest reasons:

- **No substitution.** A linear program that has no slack to
  optimise is a single-system of equalities with a unique solution
  per demand vector. The "greedy" pass returns that solution when
  the score function is linear and the constraints are tight. There
  is no second-best world to compare against.
- **Sub-millisecond cost.** 8 × 8 × 3 = 192 triples evaluated;
  each evaluation reads `townResState` (3s memo, free after the
  first call) and `gbCfgNum` (constant-time). Wall cost is
  dominated by `tradeApplyJob`, which is a handful of integer
  arithmetic. A real LP — even a 12-variable one — would cost
  comparable time and ship no additional correctness.
- **No new dependency.** A pure-JS LP solver (`javascript-lp-
  solver`, `glpk.js`, …) is not in the repo today; adding it
  conflicts with CLAUDE.md "No linter, no test runner, no Node
  workflow — paste-only mode" because the user would have to
  validate the solver against fixtures the build pipeline does not
  ship. A greedy pass is reviewable in 30 lines.

**Sub-planner shape:**

```js
// src/transport.js (extends — no new file)
function transportAiJobs(towns, ledger) {
  if (!state.autoTransportAi) return []; // toggle, default OFF
  const L = ledger || tradeLedger(towns);
  if (!L) return [];
  // ... greedy loop as in §3 ...
  return jobs;
}
```

**Orchestrator wiring.** No new orchestrator key. 5.1 is a
sub-planner of `tradeScan` (`trade.js:350-407`), called from the
same insertion point as 1.3's `transportBalanceJobs`:

```js
// src/trade.js, after the tradePreset block (line ~360):
if (state.autoTransport) jobs = jobs.concat(transportBalanceJobs(towns, ledger));
if (state.autoTransportAi) jobs = jobs.concat(transportAiJobs(towns, ledger));
```

The order is **transportAiJobs AFTER transportBalanceJobs**, because
the AI planner is greedy-once and should not be clobbered by the
heuristic's claim first. Both run BEFORE `tradeFillStorageJobs`.

## 8. Failure modes

- **`townResState` blind for any owned town.** Skip that town in the
  scoring loop; logged once via
  `gbLogT('ai-blind-' + townId, …)`. Per scan, per town.
- **`gbCityProfile` returns the seed `custom` profile.** All
  `resource[r] = 0` → neutral weights → AI behaves like
  `transportBalanceJobs` but with the per-resource target (60/50/30)
  applied. Verified: 1.2's `goalTownCfg` defensively seeds
  (`goals.js:5-12`).
- **All three `AI_TARGET_*` are equal.** Degenerate score function —
  every resource weighted equally → equivalent to global fill-storage.
  Preflight warns (`stats.js:171` work item 10).
- **`ironReservedForCave(from) === reserved:true`** on the chosen
  source and the triple's resource is iron. Skip; the AI loop
  re-scores with the next candidate. Same path as
  `tradeGoalJobs:301`.
- **Two AI picks target the same destination with the same
  resource.** `tradeApplyJob` mutates `L` after each pick, so the
  second pick sees the first's deduction and clamps itself. The
  6-job ceiling (`tradeFillStorageJobs:168` analogue) keeps the
  scan bounded.
- **Profile `resource` outside [-1, +1] range.** Clamped on read;
  `gbCfgNum` is for numbers, so this is a `Math.max(-1,
  Math.min(1, +v || 0))` guard in `aiScoreTriple`. No log spam.
- **Scan exceeds `'trade'` lock TTL (180000ms).** Same as today —
  the orchestrator's adaptive cadence widens the gap
  (`orchestrate.js:107-114`). A scan that posts more than the lock
  TTL allows gets truncated by `gbLock`; the AI loop is bounded to
  6 picks (≤ 6 posts), well under 180s at 800ms+600ms jitter per
  post (`trade.js:404`).
- **Captcha during an AI send.** `tradeScan` releases the trade
  lock on `'captcha'` callback (`trade.js:399`). AI inherits.
- **Decision-memory trip.** `trade` is a write feature in
  `TX_WRITE_FEATURES` (`planner.js:212-216`); three hard errors
  open a 5/15/60min skip window (`journal.js` plan 01, §11 of
  plan 27). The AI loop is the slowest of the sub-planners to
  recover after a bad window — that's the right behaviour
  (irreversible action, server is the authority).

## 9. Validation gate

Per plan 27 §11 (Med risk): **dry-run + one hand-triggered firing +
one full orchestrator tick.**

1. **Dry-run smoke.** Toggle `state.dryRun` on; toggle
   `state.autoTransportAi` on; set `state.aiTargetWood = 80`,
   `state.aiTargetStone = 80`, `state.aiTargetIron = 80` (force
   any wood/stone/iron imbalance to be acted on). Wait one trade
   tick. Expect at most 6 `DRY-RUN trade: …` lines; verify the
   per-resource target %s are reflected in the picked (from, to,
   resource) triples by counting the resource breakdown.
2. **Single-tick live.** Disable dry-run, force one scan. Expect
   ≤ 6 `trade: A→B w…/s…/i…` lines where the resource fields are
   mutually exclusive (only one of `wood`/`stone`/`iron` is
   non-zero per job — the AI ships one resource at a time).
3. **Profile bias verification.** Set town A profile
   `resource.iron = +1`; town B fill iron 90 %; town C fill iron
   10 %. The picked triple should be `(B → C, iron)` regardless of
   A. Then set town C profile `resource.iron = -1`; expect the
   triple to flip toward a different destination or be skipped
   entirely.
4. **Objective monotonicity.** Force a state where two triples
   have similar `delta_score` but one is strictly better. Log both
   `delta_score` values; confirm the better one is picked (ties
   broken by lexicographic `from+to+resource`, deterministic).
5. **Iron-reserve-for-cave interaction.** On a town with
   `state.autoCave` on and `caveThreshPct = 90`, set that town's
   profile `resource.iron = +1` (it needs iron) and another
   town's profile `resource.iron = -1` (dump it). AI should
   prefer the `-1` town as the source. Verify via
   `gbLogT('ai-iron-reserved-' + from, …)`.
6. **Six-job ceiling.** Disable `autoTrade`, `islandShip`,
   `autoTransport`. Set `autoTransportAi` on. Set up 12 valid
   (from, to, resource) triples via direct state mutation in
   the panel. Expect exactly 6 picked; the next scan picks the
   next 6.
7. **Preflight row.** Stats → Preflight shows `transport AI: ok`
   when `autoTransportAi === false`. Toggling on with ≥ 2 towns
   flips to `ok`; setting all three targets equal flips to
   `warn`; setting `autoTransportAi === true` with 1 town flips
   to `fail`.
8. **Export round-trip.** Export config; the four new fields
   (`autoTransportAi`, `aiTargetWood`, `aiTargetStone`,
   `aiTargetIron`) ship in the dump. Re-import restores them.
9. **No new scheduler.** `rg -n 'gbInterval' src/transport.js`
   returns zero hits; `rg -n 'InFlight' src/transport.js` returns
   zero hits; no new top-level `function` (IIFE only).

## 10. Out of scope

- **A real LP solver.** Plan 27 §5 row 5.1 names "greedy LP solver"
  in one phrase; this plan ships the greedy half honestly. The LP
  half is not feasible without a substitution rate between
  resources (which the game does not provide). If a future client
  releases a "convert" endpoint, 5.1 v2 swaps the inner loop for a
  single-system solver; the public surface
  (`transportAiJobs(towns, ledger)`) stays the same.
- **Cross-account balancing.** Out — GrepBot only reads towns owned
  by the logged-in player (`state.towns`).
- **Adaptive cadence per planner.** `orchAdaptive`
  (`orchestrate.js:107-114`) keys on the whole `'trade'` feature
  via `ORCH_JRN['trade']` (`qol.js:412`). Per-sub-planner adaptive
  cadence is a future optimisation; not in 5.1.
- **Auto-discovery of optimal target percentages.** A future plan
  could observe 7-day warehouse-fill curves and recommend
  `aiTarget*` values. Not in v4.2.
- **Per-resource send batching.** Grepolis' trade endpoint posts
  one job per resource triple; the AI ships one resource at a time
  for the same reason `tradeFillStorageJobs` ships wood+stone+iron
  in one go — but the AI's score function per resource makes
  one-resource jobs cleaner. A multi-resource AI batch is a future
  optimisation.
- **Sniffing `transportTpl`.** Plan 27 §1.3 hint; does not exist
  in the tree (see plan 1.3 §7 explicit unknown). The AI planner
  uses the existing `tradeSend` payload verbatim.
