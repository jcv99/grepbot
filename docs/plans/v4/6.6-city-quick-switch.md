# 6.6 — City quick-switch (dropdown + hotkey)

**Bucket:** v4.0 · **Risk:** Low · **Size:** S
**Module:** extend `src/ui.js` (the panel header) + a tiny new helper
function in `src/ui.js` (or `src/build-tab.js`, where town resolution

## 1. What exists today

- The town list comes from `gameUw().ITowns.towns` — used by `dodge.js:59`,
  `bandit.js:174`, `recruit.js:297`, `cave.js:30,98`, `build-auto.js:11`,
  `core.js:710,1047`, `qol.js:48,89,101,154,161`, `orchestrate.js:60`,
  `wonder.js:143`, `favor.js:112`, `spy.js:362`, `quests.js:320`,
  `military.js:20`, `build-tab.js:147,204`. Every consumer reads via
  `Object.keys(uw.ITowns.towns)` — there is **no** `getActiveTown()` or
  `switchToTown()` in `src/`.
- The currently-selected town is read by `Game.townId`:
  - `bandit.js:174,271,196`: `uw.Game.townId` (used as the default
    `town_id` payload field for bandit attacks).
  - `build-auto.js:373`: `uw.Game.townId` (default town for the auto-build
    loop).
  - `spy.js:362`: `uw.Game.townId` (fallback when no explicit town is
    given).
  - `queue-center.js:336`: `uw.Game.townId` (the Queue Center's default
    town selector).
  - `collect.js:39`: `gameUw().Game && gameUw().Game.townId` (the
    `currentTownId` captured for the `txDomWrite` `k=` key in the
    auto-collect path).
- There is **no `setTown()` / `switchTown()` / `jumpToTown()` API** in the
  Grepolis client. The only confirmed city-switching surface is the
  in-game **dropdown** the framework renders (its handler updates
  `Game.townId` and re-renders the town view). Cross-world town-id routing
  uses a URL fragment the game sets when a town is clicked from a foreign
  context (e.g. intel pop-ups).
- The Config tab has `state.townGroups = {}` (`core.js:311`) but it is
  loaded and **never read or written** outside of `qolExportConfig`
  (`qol.js:252`) and `qolImportConfig` (`qol.js:256`). It is a dead flag
  carried over from earlier work — plan 26 §B6 lists it explicitly.
- The Queue Center (`queue-center.js:336`) already has a town dropdown
  (`ui.js:527`) and the panel has the `state.townGroups` schema. There is
  no panel-level town switcher.
- The build-tab footer (`build-tab.js:147,204`) reads
  `uw.ITowns.towns` but does not expose a UI switcher.
- The Grepolis client itself does **not** expose a stable public API for
  switching town from script. Confirmed via `grep -rn 'jumpToTown\|switchTown\|setActiveTown\|focusTown\|selectTown\|setTown' src/` — zero hits.

## 2. Gap

There is no first-class way to jump to another of your own towns from
inside the GrepBot panel. Users who want to drill into a different town's
queue center must use the in-game dropdown, which closes the panel's
context. The plan delivers a small dropdown + hotkey that lives in the
panel header and lets the user pick a town to make "active"; subsequent
GrepBot scans (auto-collect's `txDomWrite` `k=`, queue-center default,
bandit fallback) continue to use the game's `Game.townId` once the
selection lands.

## 3. Design

**Dropdown surface:** a `<select data-qs="town">` rendered inside the
existing `panel` header, next to the `gb-pill` status pills at
`ui.js:561`. The select lists every id in `Object.keys(uw.ITowns.towns)`,
with `townId + '  (' + name + ')'` as the option label. The id is pinned
explicitly as `<option value="...">` — Spanish `value` would break
`town_id` payloads (CLAUDE.md "UI language: pin an explicit value"). The
selected option tracks `Game.townId` so the dropdown stays in sync with
the in-game selection.

**Hotkey:** `g` opens the dropdown's option list (focuses the
`<select>`). This plan **does not** build the shortcut infrastructure;
plan 6.3 owns `gbShortcut(name, fn)` and the registration list. 6.6 binds
one shortcut via that helper. If 6.3 has not yet shipped, the dropdown
still works — the hotkey is a progressive enhancement.

**Selection handler:** on `change`, call `jumpToTown(newId)`. The
implementation is the smallest surface that works without inventing a
public API:

```
function jumpToTown(id) {
  // The game's own dropdown updates Game.townId when the user picks one.
  // We mirror that by simulating a click on the in-game town's link, which
  // is the only confirmed way to switch town without a framework API.
  const uw = gameUw();
  if (!uw || !id) return;
  try {
    // The in-game selector renders <a href="?action=town&id=X&town=X"> or
    // sets the same on a button click. The exact selector is intentionally
    // not guessed: see §8 ("Unknown: in-game town-switch selector").
  } catch (_) {}
}
```

This is **deliberately not implemented as a hardcoded DOM click** — the
selector is unknown without a live sample. The plan §8 carries the
unknown explicitly and proposes the sniff path.

**No new post surface.** Switching town is a navigation event, not a
write. The framework handles it (URL change, model reload).

**No new lock / `GB_LOCK_TTL` entry** — switching town is a synchronous
DOM click, not an async post.

## 5. State & storage

- **New `state.lastTownSwitchPick`** (`core.js:~380`, near visual prefs).
  Holds the last id the user picked in the dropdown so the panel restores
  it across reloads even if the actual navigation still goes through the
  in-game dropdown.
- **New `STORE.TOWN_SWITCH_PICK`** (`header.js:64`, next to `PANEL_GEOM`).
  Non-id-bearing (it is the user's *own* active town, which is the same
  scope as the rest of `state.towns`), but it is still per-user-not-per-
  town so it does **not** go in `WORLD_SCOPED_BASES`
  (`header.js:193-214`).
- **No `configVer` bump** if we treat `lastTownSwitchPick` as a UI-only
  affordance (it does not change feature behaviour). If a future version
  starts using the pick to drive an actual `bridgePost`, bump then. v4.0
  ships read-only.
- **No prune TTL.**

## 6. Config surface

- **No Config toggle.** The dropdown is always shown; the placeholder
  `<option value="">ciudades</option>` is what users see when the panel
  loads before towns are populated.
- The `gbShortcut('qs-town', ...)` registration is silent (no Config
  surface) — keyboard-shortcut UI is owned by plan 6.3.

## 7. Post surface & safety

**Read-mostly feature: no post surface.** Town navigation is a framework
event (URL change, model reload); GrepBot does not POST to switch town.

- **No `gbAjaxWatch` registration.** Town switches do not produce a
  bridge payload.
- **No `gbCaptchaPause` feature key.** No writes means no captcha.
- **No `gbLock` / `GB_LOCK_TTL` entry.** Synchronous DOM click; the
  in-game framework handles any async re-render.
- **No dry-run gate.** Nothing posts.

## 8. Failure modes

- **Unknown: in-game town-switch selector.** The plan §3 deliberately
  leaves `jumpToTown(id)` as a stub because the Grepolis client's town-
  switch DOM is **not** in `src/` and is not a stable, documented
  contract. Three paths to fill it (work item 8 in v4.0 is to do this
  sniff; see also §11 below):
  1. Open the game's town dropdown in a live session, inspect the
     rendered `<a>` or `<button>` per town, capture the selector and the
     payload it carries.
  2. Register `gbAjaxWatch(sig, settle)` over the framework's town-
     switch XHR (the URL pattern is `action=town&id=X` per
     `bandit.js:192`-style framing — but the URL itself is not
     confirmed; record the raw signature once observed).
  3. Capture the response template into `TPL_FEATURE_MAP` only if the
     switch produces a bridge-style payload. Most town switches are
     pure navigation; nothing to capture.
  Until this work item is closed, the dropdown records the user's pick
  and the Log says `town switch: use the in-game dropdown until the
  selector is sniffed`. No crash, no half-broken UX.
- **Town list stale across world switches.** `populateTownSwitcher()`
  reads `uw.ITowns.towns` at boot; a `worldId` change between sessions
  rebuilds the option set because `wkey()` keys the persisted pick
  (`STORE.TOWN_SWITCH_PICK` is not world-scoped on purpose — the active
  town is per-user, not per-world). If a town id from world A is
  selected while the user is on world B, `select.value` does not match
  any option and the placeholder is shown — silent degrade, no error.
- **Precondition invariant.** The dropdown reads `Object.keys(...)` and
  `uw.Game.townId` directly; both calls are wrapped in `try { ... } catch
  (_) {}` per the existing pattern at `dodge.js:82-84`,
  `orchestrate.js:60`. If `ITowns.towns` is unreadable, the dropdown
  shows only the placeholder. **No silent dead guard** — `gbLogT` fires
  once via `townswitch-itowns-unreadable` key in the catch, matching the
  plan 26 §A1 pattern.
- **Hotkey conflicts.** Plan 6.3 owns the registration; if `g` is
  already taken (e.g. by the game itself for "select all in chat"), the
  helper returns false and the dropdown still works without a hotkey.
  Plan 6.3's lockable key list will own this conflict.
- **Theme integration (6.1).** The select uses CSS variables; the theme
  plan's `--gb-link`/`--gb-fg` tokens carry over. The `option` element is
  styled by the browser, not the panel — that is acceptable (CLAUDE.md
  treats in-game markup as out-of-scope).

## 9. Validation gate

Manual, per plan 27 §11 (Low risk = Preflight + one in-game session, no
failure).

- Install. Header shows the new dropdown to the left of the `Colas`
  button.
- Open the panel on a 5-town world. Dropdown lists all 5 ids with names.
  The active town is pre-selected.
- Pick a different town from the dropdown. Log shows the
  `town switch: use the in-game dropdown until the selector is sniffed`
  line (one-time per pick via `gbLogT`). The in-game dropdown in the
  game's chrome is **not** auto-clicked by GrepBot in v4.0 (per §8
  "unknown").
- Press `g`. The dropdown opens (focuses + size-expands). Pick a town,
  same log line. Press `g` again — same.
- Reload the page. The last pick is restored as the dropdown's selected
  option (or the placeholder if the pick was for a different world).
- `python3 build.py` passes; install via paste into Tampermonkey.
- Preflight: no new warn rows.

## 10. Out of scope

- **Building the in-game town-switch selector** (work item 8 in §8).
  This plan ships the read-only dropdown + hotkey; the actual click is a
  follow-up that requires a live in-game sniff (§8 step 1).
- **Cross-town "compare" panel.** Show two towns side by side. Out of
  scope; belongs to a different feature.
- **Filtering the dropdown by town groups.** `state.townGroups`
  (`core.js:311`) is a dead field today (plan 26 §B6); wiring it into the
  dropdown would unblock a second dead-flag cleanup but is its own work
  item.
- **Town groups + template hotkeys.** Owned by plans 1.2 / 6.8.
- **Re-specifying the keyboard-shortcut framework.** Plan 6.3 owns it;
  this plan binds one shortcut via that helper and degrades silently if
  6.3 has not landed.
- **Switching to a farm village or to a target town from intel.** Town
  switcher is for **own** towns only; farm villages (`FarmTownPlayerRelation`)
  and enemy towns are not navigable the same way and have their own UI
  (intel pop-up).
