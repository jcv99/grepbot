# 2.7 — Population management (town pop cap + ETA + fill row)

**Bucket:** v4.0 · **Risk:** Low · **Size:** S
**Module:** `bridge.js` (extend `townResState` + add `townPopState`); touch `ui.js`
(`renderWorld` fill row), `towns.js` (parse `pop`/`cap` already in
`parseResourceJson` — only add cap-cache revalidation).
**Depends on:** none (uses already-shipping `gbTownPop` at `bridge.js:302`,
`parseResourceJson` at `parse-inline.js:143`).
**Status:** PLANNED — written 2026-08-10 against `src/` @ v3.8.2

## 1. What exists today

- `townResState(townId)` at `bridge.js:235-273` returns
  `{cap, wood, stone, iron, full, n, fillPct}` for **resources** only — the
  `full` map covers `{wood, stone, iron}` and **does not** include population.
  Memo is 3s (`TOWN_RES_CACHE_MS` at `bridge.js:234`).
- `gbTownPop(townId)` at `bridge.js:302-312` reads
  `getAvailablePopulation`/`getFreePopulation`/`getPopulation` (model fn probes,
  `bridge.js:305`) and falls back to `t.resources().population`. Returns
  `null` (not `0`) when nothing readable — the precondition invariant.
- `parseResourceJson` at `parse-inline.js:143-167` already extracts
  `pop` (current free pop) and `cap` (max pop) from the town JSON. `fetchTownResources`
  (`towns.js:127`) writes them into `state.townResources[townId]` at
  `towns.js:163-166` and `towns.js:210-213`. So **the data is already in
  state**, the bridge just doesn't expose a single helper.
- `plannerLive(townId)` at `planner.js:37-45` returns
  `{wood, stone, iron, population, cap, tradeCap}` — same data, different
  shape, used by the planner only.
- Render: `renderWorld` at `ui.js:193-235` already prints `pop/cap` as a single
  cell (`${fmt(r.pop)}/${fmt(r.cap)}`, `ui.js:220`). No ETA, no fill row, no
  per-town summary above the table.
- `townResourcesFromGame` (`towns.js:11-20`) returns the **whole** resource
  object including `population` and `storage`. The game-data branch of
  `scrapeAllTowns` writes `pop: r.population ?? null, cap: r.storage ?? null`
  (`towns.js:211-212`) — so `pop`/`cap` are populated by **both** the game
  path and the HTTP path, but they land in `state.townResources` only,
  with no separate memoized cache.

Plan 27 §2.7 says "extend `core.js` townResState" — **wrong module hint**.
`townResState` lives in `bridge.js` (concat slot 6), `core.js` is slot 3.
`core.js` has no population reads; it owns `state`, `STORE`, `gbLock`, and
`gbCfgNum` (`core.js:889`, the finite-config helper). Adding to `bridge.js`
preserves the module-locality already used by `gbTownPop`/`gbAfford`.

## 2. Gap

- `townResState` covers resources but **not population** — every call to
  compute "what's the fill ratio" duplicates the probe list.
- `renderWorld` shows `pop/cap` as a cell (`ui.js:220`) but does not show
  fill %, ETA-to-full, or a header-level "X/Y towns near pop cap".
- `gbAfford` at `bridge.js:325-349` has a population branch (line 342-347)
  but it only reads it as a `need`/`have` check inside a single cost — there
  is no top-level "town N has M free pop" reader.

## 3. Design

Extend `bridge.js` with one new helper **next to** `townResState`, sharing
its memo and its 3s TTL:

```
function townPopState(townId) {
  // returns { current, cap, freePct } where:
  //   current = +gbTownPop(townId) or t.resources().population or null
  //   cap     = parseResourceJson-cached pop.cap (already in state.townResources)
  //             or t.resources().population_max or null
  //   freePct = current != null && cap > 0 ? round(current/cap*100) : null
}
```

Cache key is `'pop:' + townId` (separate from `townResState`'s keyspace) so
resource full-state and pop full-state can be invalidated independently.
The helper is **read-only**, returns `null` for any unreadable leg (matches
the precondition invariant — never a silent dead guard).

ETA-to-full is the harder read: the model exposes population growth
indirectly via `t.getPopulationGrow()`/`.population_grow`/`getHappiness()`
(multi-step chain). Treat ETA as **optional** — when unreadable, the cell
shows `—` instead of a number. This is the precondition invariant again:
the helper never blocks on what it didn't read.

UI: extend the existing pop cell at `ui.js:220` from
`${fmt(r.pop)}/${fmt(r.cap)}` to a **three-line cell**:
- line 1 (existing): `pop/cap`
- line 2 (new): fill %, with a CSS class `pop-warn` when `freePct >= 90`,
  `pop-near` when `>= 75`
- line 3 (new): ETA to full or `—` (unreadable).

No new post surface, no new `*InFlight` boolean, no new `gbInterval`.

## 5. State & storage

- No new `state.*` field. Population numbers already live on
  `state.townResources[townId].{pop,cap}`.
- No new `STORE.*` key. Cache is module-local (`_townPopCache`) and lives
  for the lifetime of the page only, by design — population changes when
  the user recruits or attacks, and the 3s TTL on `townResState` is already
  the cadence for related state. Persisting it would just invite staleness
  on reload.
- No new world-scoped base. The two memo caches (`_townResCache`,
  `_townPopCache`) are intentionally non-persistent.
- **`CONFIG_VER_CURRENT` bumps `10` → `11`** in `header.js:191`. This is the
  one Config-shape change: existing installs re-render through
  `migrateConfig()` (`core.js:394`) on next load. No new Config fields
  shipped by 2.7 itself — the bump is consumed by sibling plans 2.11/3.7
  which already gate their migrations on `ver < 11`. Aligns with §4 item 6.

## 6. Config surface

- No new toggle. Population is always visible.
- Threshold constants `POP_WARN_PCT` (default 90) and `POP_NEAR_PCT`
  (default 75) live as module-local `const`s in `bridge.js`, **not** in
  Config. The catalog tags this Low/S — surfacing two more knobs is not
  worth the Config tab real estate.
- Spanish cell label: `población` (matches `marketLocale()` at
  `core.js:1327` for `population` key).

## 7. Post surface & safety

Read-only. **No post surface.** Skips the rest of this section per the
template: there is no `gbAjaxWatch` registration, no `TPL_FEATURE_MAP`
entry, no `gbCaptchaPause` feature key, no `gbLock` to add. The new helper
is called from `ui.js`'s render path and from any future consumer
(`cave.js`, `recruit.js`, `planner.js`) that wants `pop`/`cap` without
duplicating the probe list.

## 8. Failure modes

- **Unreadable population** (`gbTownPop` returns `null`): helper returns
  `null`; the cell renders `—` for fill % and ETA. Never a fake `0`.
- **Unreadable capacity** (no `state.townResources[townId]?.cap` and no
  probe success): helper returns `null`; same `—` rendering. Preflight's
  `cost reads` row (`stats.js:192-210`) already shows "population
  UNREADABLE" — the new helper degrades identically.
- **Stale cache after recruit/dodge**: 3s TTL covers normal cadence; if
  the user spam-recruits, the worst case is one render with the old
  `current` value, which the next `renderWorld` corrects. **No need** for
  a `gbWake`-style invalidate hook.
- **ETA unreadable** (model doesn't expose population growth on this
  client build): the cell shows `—`. Per the precondition invariant: a
  guard may only block on a value it actually read.
- **Cache collision with `townResState`**: separate `_townPopCache`
  prevents a `pop` invalidation from trashing the resource cache or vice
  versa. Verified by inspection — `_townResCache` is keyed by raw
  `townId` (`bridge.js:237`); `_townPopCache` keys with `'pop:' + townId`.

## 9. Validation gate

- Preflight → "cost reads" row reports population + stock OK on a town
  with a known `cap` (i.e., `parseResourceJson` saw `population_max`).
- World tab (`ui.js` `renderWorld`) shows a populated `pop/cap` cell with
  fill % on three of three towns, plus ETA `—` (ETA unreadable by
  default — that is expected, not a failure).
- `gbLogT('orch-deadlock-blind', 600000)` does **not** fire on a town whose
  capacity is now readable through `townPopState` (it was firing before
  only because the deadlock resolver at `orchestrate.js:74-77` did not
  include pop in its blind-tally).
- Build: `python3 build.py` exits 0 (no new top-level declarations);
  install + click World tab; no console errors.

## 10. Out of scope

- Population growth ETA from the model (unreadable on stock client builds
  per probe — would require a `gbProbeNum` over
  `getPopulationGrow`/`population_grow` chain; **deferred**, may move to
  a 4.1 polish if the chain becomes reliable).
- Recruit / dodge auto-pause on pop-near-cap (a separate policy; plan 28+
  once `recruit.js`/`dodge.js` expose their own preconditions).
- Town-level pop cap overrides (Config knob) — would only matter for
  intentional cap targets (e.g., "never fill above 80% before wonder
  day"), which is a planning feature owned by 2.9.
