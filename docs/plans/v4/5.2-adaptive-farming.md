## 2. Gap

Today, when `captchaPaused('farm')` is false and the budget is open, the
claim loop will walk **every** ready village in `farmsFromGame()` order,
including villages whose profitability rank (2.6) is low. Under a tight
budget or a captcha that just tripped and is about to expire, the right
move is to skip the marginal villages for one cycle and spend the slot
on the profitable ones — fewer posts, more loot per request, less
captcha surface. Plan 26 §A1 already showed that every claim slot
counts.

## 3. Design

Re-order `ready` in `autoClaimFarms` by `state.farmProfit[vill_id].score`
descending, and apply three drop policies before the loop:

1. **Drop unknown-rank villages from the claim set when pressure is on.**
   `score == null` (read blind: missing headroom, missing x/y, missing
   loyalty) ⇒ keep if no pressure, skip if pressure. "Pressure" = one
   of: `captchaPaused('farm')` was true within the last 5min (sliding
   via `gbServerCooldown`-shaped log), OR `gbServerPaused({reason:'server'})`,
   OR `reqBudgetSoftDelayMs > 0` (per `core.js:721-728`). Tracked via a
   small `farmPressure` ring (`{at, kind}[]`, 8 entries, 30min TTL).
2. **Drop the bottom quartile when pressure is on.** Sort `ready` by
   score desc, drop the bottom 25% only when pressure is on AND
   `ready.length >= 4`. Configurable via `state.farmDropPressurePct`
   (default 25). Off-pressure ⇒ claim everything (no change from today).
3. **Cap daily claim count per village when captcha is hot.** If
   `captchaPaused('farm')` was tripped in the last hour, drop every
   village whose `state.farmClaimsToday[vill_id]` already ≥ 1 from the
   claim set. Counter lives in `state.farmClaimsToday`, dated key
   (`farmDayKey()` mirrors `farmSleepDayKey` at `farms.js:570-573`),
   reset on day rollover.

All three are **drop policies on the existing claim loop**. They do not
add a post, change a template, or open a new captcha feature key. The
`claim` lock (`farms.js:525`) and the spacing (`farms.js:532`) already
serialize everything correctly.

The pressure-skip logic also **does not run** when `state.adaptiveFarm`
is OFF — the toggle ships OFF, mirroring CLAUDE.md ("HIGH-RISK toggles
default OFF"; this is Med but the precedent holds for any new
target-rotation policy).

## 8. Failure modes

- **`state.farmProfit` empty (2.6 not yet shipped, or all scores
  null).** `farmApplyDropPolicies` falls through to "no-op": keep
  original `ready` order. Log once: `farm adaptive: no profit scores
  yet - rotation disabled`. Precondition invariant: do not invent a
  rank.
- **Pressure ring stale on reload.** `farmPressure` is in-memory only;
  on reload it starts empty, so the first tick runs without pressure
  even if the captcha breaker is still hot. The `gbServerPaused` /
  `captchaPaused` gates still apply; 5.2 only adds a sorting /
  filtering preference, not a hard block.
- **All villages dropped.** If the drop policy empties `work`, the
  existing early-return path at `farms.js:516-524` runs (log + schedule
  wake). No post, no orphan lock.
- **Bottom-quartile drops a single low-rank village by accident.** The
  policy only fires when `ready.length >= 4`. Below that threshold,
  `farmApplyDropPolicies` returns the input unchanged.
- **`state.farmClaimsDay` drift.** Compare at the top of
  `autoClaimFarms`; on rollover, reset both `state.farmClaimsToday` and
  `state.farmClaimsDay` and `save()` both. A clock-skew on day
  boundaries is bounded to one cycle.
- **`farmSleepClaimNow` overlap.** `farmSleepClaimNow` (`farms.js:574-591`)
  shares `autoClaimFarms` with a `durOverride` (`farms.js:589`); the
  sleep path uses `farmSleepDuration` (`farms.js:410-414`), not
  `farmDurationPick`. The drop policy in §3 fires on every entry; if
  `state.adaptiveFarm && state.farmSleepAuto`, the sleep path can lose
  villages. Mitigate by skipping the drop policy when `durOverride` is
  one of `14400`/`28800` (sleep durations) — the sleep claim is a
  full-clear, not a normal cycle.
- **Orphan claim counter.** `state.farmClaimsToday` is keyed by village
  id; `refreshFarmsParsed` (`farms.js:255-268`) prunes unknown villages
  out. Persisted under `WORLD_SCOPED_BASES` so a world switch resets it.

## 9. Validation gate

Med-risk (plan 27 §11: dry-run + one hand-triggered firing + one full
orchestrator tick).

- **Dry-run.** `state.dryRun = true; state.adaptiveFarm = true`.
  Trigger `autoClaimFarms('orch')` (the `ORCH_HANDLERS.farm` key). Log
  shows the drop policy ran; no `FarmTownPlayerRelation/claim` posts
  fired; `state.farmClaimsToday` stays empty.
- **Manual press with pressure off.** Disable adaptive; flip the
  "captcha recently tripped" sentinel (set `captchaLadder`-shaped
  timestamp) and verify the loop claims **all** ready villages in
  insertion order. Then enable adaptive + same sentinel ⇒ log shows the
  bottom quartile dropped, IDs listed.
- **Full tick.** `orchTick` runs; Stats tab `farm adaptive` row reads
  `pass`; journal entries `farm <vill_id>` are the same villages that
  would have been claimed pre-feature, minus the dropped bottom-quartile
  IDs (compare `farm <id>: ok` counts in Decisions view pre/post).
- **Quota discipline.** With `reqBudgetPerMin = 40` and 12 villages, a
  sweep under pressure-on must show fewer claim posts (per journal)
  than pressure-off, and zero `skip:budget` (the global pool already
  covers it).
- **Validation summary:** single claim-cycle delta ≤ 1 village under
  no-pressure; ≤ 25% villages dropped under pressure; sleep-claim
  path unchanged when `durOverride` is 4h/8h.
