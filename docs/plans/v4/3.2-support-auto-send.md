## 1. What exists today

- The **destination-side** support branch already exists in `dodge.js:130-138`:
  `dodgeSendOut(townId, units, safeId, onDone)` posts through `bridgePost('dodge', …)`
  with payload
  `{model_url:'Town/<townId>', action_name:(state.attackTpl?.action_name)||'sendUnits', arguments:Object.assign({id:+safeId, type:'support'}, units), town_id:+townId}`.
  `dodgeSupportValidate` (`dodge.js:157-174`) re-checks live units, transport
  capacity, and god-mix before posting. That is the read-side + post-side
  plumbing **dodge already uses to evacuate**. 3.2 reuses `dodgeSupportValidate`
  as the precondition gate; it does **not** re-implement it.
- **No offensive support feature exists today.** `src/support.js` is absent
  (`ls src/` lists 40 modules, none named `support.js`; `grep -rn 'supportTpl\|src/support.js' src/`
  returns zero hits). `state.supportTpl` does not exist; no `TPL_FEATURE_MAP`
  slot, no Config toggle, no orchestrator handler.
- `state.attackTpl` (`core.js:273`, key `STORE.ATTACK_TPL`, world-scoped in
  `header.js:200`) is the only learned `Town/sendUnits` template. The dodge
  path reuses it (`dodge.js:133`). `TPL_FEATURE_MAP` (`core.js:778-790`) maps
  `attack → attackTpl`. Sharing it with support would re-create the v2.5.7
  favor-vs-attack poison incident documented in the comment at `core.js:785-789`:
  one bad server rejection on `type:'support'` would invalidate `attackTpl`,
  blocking live attacks too. **§4 learns `supportTpl` as a separate template**
  with the same `model_url|action_name` signature, distinguished by
  `arguments.type === 'support'`. `tplNameFor` resolves it before any live
  post.
- `state.cancelTpl` (`core.js:274`, key `STORE.CANCEL_TPL`, world-scoped
  `header.js:200`) and `militaryCancelCommand` (`military.js:45-70`) are the
  **undo path**: recall is `bridgePost('cancel', …)` with the canonical
  template. `cancelTpl` is already required by the render panel
  (`military.js:179`). 3.2's recall is the same call, so the support auto
  path **does not** add a new post surface for recall — it reuses `cancelTpl`
  + `militaryCancelCommand({confirmed:true, automation:true})`. This matches
  how the dodge-return path uses the same primitive (`wonder.js:148`,
  `dodgeReturnTick`).
- **Hostile-only canonical filter.** Per CLAUDE.md "Dodge / militia / CS",
  incoming detection must not use `incoming`/`started_at` alone.
  `dodgeIsHostileMovement` (`dodge.js:41-52`) is the canonical filter: it
  rejects `DODGE_FRIENDLY_TYPES = /^(support|support_sea|trade|return|spy|farm|reward)$/`
  at `dodge.js:40` and accepts only `DODGE_HOSTILE_TYPES` plus `is_attack ===
  true`. 3.2's trigger uses **the same** filter and never inspects
  `a.incoming`/`a.started_at`. Trigger = "there is a hostile on `mov.dest`
  whose ETA is in the support window and no friendly supports already in
  flight" — no second filter.
- `defenseAssessment(mov, incoming)` (`wonder.js:144`) returns
  `{eta, simultaneous, local, supports, safeTown, evac, militia, risk, hasCs,
  band, factors, weights, computedAt}` after plan 5.3 lands (the existing
  9-field shape today; plan 5.3 widens it). `defenseSupportOptions(dest, eta)`
  (`wonder.js:143`) lists candidate donor towns that can land in time — same
  island, defense-class units, transport capacity, travel < ETA. **3.2 reads
  `defenseSupportOptions` rather than re-deriving donor candidates.** This is
  the contract plan 5.3 already documents: "5.3's schema is the contract 5.4
  reads". 3.2 reads it too — no second scoring scheme.
- `dodgeEtaSec(mov)` (`dodge.js:175-180`) is the ETA helper used by every
  defense consumer. `computeTravelSeconds(srcTownId, target, units, requireCanonical)`
  (`attack.js:71-97`) is the canonical travel-time probe; with
  `requireCanonical=true` it returns `null` when no model call succeeds, so
  the support arm path uses it the same way `armAttackWave` does
  (`attack.js:681-687`).
- `state.defenseCfg` (`core.js:359`, key `STORE.DEFENSE_CFG` world-scoped
  `header.js:209`) carries `mode` ('notify'|'safe'|'smart'), `returnMarginSec`,
  and (after 5.3) the factor weights. 3.2 does **not** introduce a parallel
  `state.supportCfg`; it reads `defenseCfg.mode` to decide whether to arm at
  all, and adds **only** the auto-burst toggle + the troop-selection +
  per-window confirm thresholds as new fields under `state.supportCfg`
  (separate world-scoped object — see §5).
- `orchTick` (`orchestrate.js:147-199`) is the cadence-aware scheduler.
  `ORCH_CADENCE` (`qol.js:388-403`) is the per-feature cadence table. **3.2
  does NOT add an orchestrator handler**: support is reactive (one burst per
  detected incoming movement), not periodic. The driver is the same
  5-second `DODGE_CHECK_MS` loop that already runs `dodgeScan`
  (`boot.js:100`, `wonder.js:150`); support arms from a hook inside
  `dodgeScan` after the existing `dodgeTrySend` path returns, not from a
  parallel timer. This avoids the "two timers, two cadences" mistake
  flagged in `CLAUDE.md` "v1.1.0: orchTick is the sole econ scheduler".
- `captchaPaused(feature)` (`core.js:1337`) and `captchaPausedAny(...features)`
  (`core.js:1352`) gate writes. `gbLock('support', 180000)` is the lock name
  plan 3.2 introduces as a **`GB_LOCK_TTL` entry**, not a `*InFlight` boolean.
- `txActionGate` (`tx.js:522-534`) is where the dry-run gate lives for any
  write feature. Support passes through `bridgePost('support', …)` → `txRun`
  (`tx.js:535`) → `txActionGate`; the dry-run short-circuit at `tx.js:554-561`
  handles it for free. The "real troops, irreversible" warning in §0 of the
  assignment is honoured without writing a new gate.
- Plan 27 §9 lists 15 already-shipped items. None of them is "support
  auto-send". `cancelTpl` + `cancel` recall (`military.js:45-70`) is shipped
  but is the **undo** path, not the action — there is no path to *send*
  support automatically today. The feature is genuinely new.

## 2. Gap

Three read paths already produce the inputs 3.2 needs:
`defenseSupportOptions` (`wonder.js:143`) lists candidate donor towns;
`dodgeSupportValidate` (`dodge.js:157-174`) gates transport + units;
`defenseAssessment` (`wonder.js:144`, schema widened by plan 5.3) scores the
threat. What does **not** exist is the policy that decides *when* to arm a
support run, *which* troops to leave at home, and *what* the per-window
confirm gate looks like. Plan 27 §3 requires "confirm gate per window":
when several incoming movements share a destination, the user must see one
aggregate decision ("send X from A, Y from B, Z from C") rather than N
silent fires. There is also no defined "what if the attack lands before
support arrives?" failure mode — recall via `militaryCancelCommand` is the
undo, but the recall cost (loss of troop-pool) and the abort conditions
(threshold for "too late, don't even arm") are not modeled.

## 3. Design

Two coordinated pieces in `src/support.js`, one Config toggle, one confirm
gate. **No new `*InFlight` boolean, no new `gbInterval`, no new
top-level `function` declaration** — module-local IIFE wrapping where
helpers need to stay private. The driver is the existing `dodgeScan` loop
(`boot.js:100`, `wonder.js:150`); support arms from a hook called at the end
of `dodgeScan` after `dodgeTrySend` (`dodge.js:203-251`) returns.

### 3.1 Trigger condition (per incoming movement)

For each entry returned by `dodgeIncomingMovements()` (`dodge.js:53-84`),
`supportTryBurst(mov)` runs once per `mov.id` (TTL = `mov.arrival + 10min`,
keyed on `mov.id`). **All gates must hold** before arming:

1. `state.supportCfg.auto === true` (HIGH-RISK, default OFF — see §6).
2. `hostEnabled()` and `!automationPaused({})` (server pressure bus
   (`CLAUDE.md` "Server pressure bus") — server cooldown already feeds
   `automationPaused` via `noteServerPressure`).
3. `!captchaPausedAny('support', 'dodge')` and `!gbLocked('support')`.
4. The hostile-only canonical filter already passed when `mov` was yielded
   by `dodgeIncomingMovements` (`dodge.js:64`) — no second check.
5. `dodgeEtaSec(mov)` is finite and `>= SUPPORT_MIN_ETA_SEC` (default
   `120` — anything tighter than the existing `armAttackWave`'s 90s max
   window (`attack.js:611`) is too tight to arm reliably).
6. `defenseAssessment(mov, incoming).band ∈ {'high','cs'}` — consumes the
   5.3 schema. A `'med'` band produces a logged advisory only, never an
   arm; `'low'` is silent. **This is the single threshold 3.2 reads**, not a
   re-derived score.
7. `mov.dest` is the player's own town (already guaranteed by `dodge.js:59-63`).
8. No friendly support already en-route to `mov.dest` whose arrival is
   `<= mov.arrival - SUPPORT_OVERLAP_SEC` (default `30`). Friendly detection
   uses `militaryOutgoingMovements()` (`military.js:17-44`) filtered to
   `type ∈ DODGE_FRIENDLY_TYPES` (`dodge.js:40`) whose `target ===
   String(mov.dest)`. A pre-existing friendly makes the support redundant.
9. At least one donor candidate exists in `defenseSupportOptions(mov.dest,
   eta)` (`wonder.js:143`) with `travel < eta` and `boats.ok`. If none, log
   `support: no donor` and bail.

### 3.2 Troop-selection rule (what stays home)

For each donor candidate `d ∈ defenseSupportOptions(...)`, the unit mix to
send is computed by `supportSelectUnits(d.from, mov, plan)`:

- Start with `townLiveUnits(d.from)` (`attack.js:35-42`) filtered to
  defense-class units via `classifyUnitFn` (`attack.js:141-156`) returning
  `'defense'` or `'both'`. `hoplite` returns `'both'` and is included
  (`attack.js:146`); `militia` is filtered out
  (`dodge.js:144`).
- **Floor at home:** subtract `dodgeFloor`-style home reserve — a new
  Config field `state.supportCfg.homeFloor` (default `0`, range
  `0..50`, integer per-unit count) keeps that many of each class behind.
  Reuse `dodgeTownUnits` (`dodge.js:139-156`) as the model; parameterise
  the floor name from `state.dodgeFloor` (`core.js:324`) when
  `state.supportCfg.shareDodgeFloor !== false` (default true), otherwise
  use `homeFloor`.
- **Cap by travel-class:** of the candidates `defenseSupportOptions` lists,
  take the smallest travel-time one first (`out.sort` at `wonder.js:143`),
  then pick the next only if it has a non-empty `units` object after the
  floor pass. `boatCapacityCheck` (`attack.js:106-140`) re-validates the
  composition (cross-island requires boats — same rule dodge applies).
- **Confirmation gate per burst:** if the aggregated send-count across
  donors is `> state.supportCfg.confirmThreshold` (default `100`, range
  `0..10000`), surface a single `confirm()` dialog per **window** (one
  per `mov.dest`, not per donor) listing the donor towns, units, ETA, and
  the projected arrival before the attack. Refusal ⇒ `state.supportLastSkip[movId]
  = {reason:'declined', ts:Date.now()}` and the burst is skipped; no post.
  Acceptance ⇒ proceed.

### 3.3 Anti-flap guard

A per-`mov.id` ledger `state.supportLastSend` (world-scoped, §5) stores
`{ts, expires}` for each burst that armed. A re-pass of `supportTryBurst`
on the same `mov.id` is a no-op while `expires > Date.now()`. `expires` is
the burst's projected arrival (`gameNow() + travel`) **plus** 10 minutes,
matching `dodgeLastStash` TTL precedent (plan 3.5 §5). The ledger is pruned
in `supportScan` on every pass: entries older than `expires + 1h` are
dropped. **No `*InFlight` boolean** — the TTL is the guard. Mirror
`dodgeQueueLoad/dodgeQueueSave` (`dodge.js:1-37`) for the persistence shape.

### 3.4 Attack-lands-first abort (the recall path)

When `mov.arrival - gameNow() <= SUPPORT_NO_ARM_SEC` (default `60`), the
burst is **not armed**: even with a confirmed gate, the canonical travel
probe (`attack.js:682-687`) returns `null` more often as the window closes
and arming reliably is no longer possible. The auto path logs
`support: window closed for <movId> at <sec>s` and exits.

Once a burst is **in flight** and the host learns the attack actually
landed before support arrives (e.g. `dodgeQueue` (`dodge.js:1-37`) shows
the movement resolved while support is mid-transit), `supportRecallWindow`
triggers `militaryCancelCommand(commandId, {confirmed:true, automation:true}, cb)`
(`military.js:45-70`) for each surviving donor command. Recall is gated on
`gbLock('cancel', …)` (`military.js:59`) — the same gate every other recall
honours. The recall is **best-effort**: the server may have already moved
the support into the destination town, in which case `cancelTpl` returns
`'not-cancelable'` (`military.js:52`) and we journal `'support: recall
arrived already'` and move on. Recall **never** blocks on an unreadable
state — the precondition invariant applies.

### 3.5 Confirm gate display

The per-burst confirm message reads (Spanish per `CLAUDE.md` UI-language
split):

```
Apoyo a <townName> (#<destId>)
Ataque hostil: <type> [CS] desde <originId> en <eta_str>
Donantes propuestos:
  - <donorName1> (#<donorId1>): <sword>:<n> <hoplite>:<n> … — llega en <travel1>
  - <donorName2> (#<donorId2>): … — llega en <travel2>
Total: <unitCount> unidades / <donorCount> ciudades
Umbral de confirmación: <confirmThreshold>; envío actual: <total>
¿Enviar? (Cancelar = saltar esta ventana)
```

The gate fires from `gbDomClick`'s `confirm()` (no custom modal — same
discipline plan 3.5 §4.3 uses). With `state.dryRun === true` the
confirmation text gains a `[DRY-RUN] ` prefix and the post is short-circuited
at `tx.js:554-561`.

## 7. Post surface & safety

- **Bridge-first.** Every support post is `bridgePost('support', payload, cb)`
  → `txRun` (`tx.js:535`) → `txActionGate` (`tx.js:522-534`). DOM is
  fallback only and is **not** added in this plan: `bridgePost` already
  covers the action with a learned payload (the same route dodge uses,
  `dodge.js:130-138`).
- `gbAjaxWatch('bridge:Town/<srcId>|sendUnits', settle)` registers
  automatically inside `bridgeRaw` via `bridge.js:131-142`. The discriminator
  `arguments.type === 'support'` is handled by `tplNameFor` (work item 5),
  not by the watcher signature — the signature stays `model_url|action_name`.
- **`TPL_FEATURE_MAP` slot.** `'support': 'supportTpl'` added to
  `core.js:778-790`. `tplNameFor` (`core.js:795-801`) is taught to
  discriminate on `arguments.type === 'support'`. Without this slot the
  support path would share `attackTpl`, and one bad server rejection would
  invalidate live attacks (the v2.5.7 favor precedent). This is the single
  most consequential schema decision in the plan.
- **`gbCaptchaPause` feature key** (`bridge.js`): the existing
  `responseIsCaptcha` (`bridge.js:113`) call site uses the per-post
  `feature` label as the breaker key. Support passes `feature:'support'`
  to `bridgePost`, so `captchaPaused('support')` is the natural key —
  no new key is registered globally; the breaker auto-keys off `feature`.
- **`gbLock` + `GB_LOCK_TTL`.** Add `'support': 180000` to
  `core.js:145-173`. Distinct from `'dodge'` (`dodge.js:227`, TTL 180s) so
  the two paths can run in parallel without each starving the other.
  Distinct from `'cancel'` (`military.js:59`, TTL 120s) so the recall
  path is never blocked by a still-arming burst. No `*InFlight` boolean.
- **Dry-run gate.** Automatic via `tx.js:531` inside `txActionGate`. The
  confirm-gate dialog itself is not gated by `dryRun` — the user can still
  see what *would* be sent; only the post is short-circuited at
  `tx.js:554-561`. The Preflight row surfaces `dryRun: true` as a green
  pass even when `supportCfg.auto` is OFF (correct posture).
- **Recall path.** `militaryCancelCommand` (`military.js:45-70`) is the
  existing primitive; 3.2 calls it with `{confirmed:true, automation:true}`
  after the user clicks the confirm dialog for the burst. Recall cost
  (loss of troop-pool) is logged via `gbLog` and journaled; no silent
  recall.

## 8. Failure modes

- **`supportTpl` is `null`.** `supportBridgePost` rejects the post with
  `'template-required'` and `gbLogT('support-template', 60000, …)` runs
  once. The Preflight row (`stats.js` §4.9) reports `support: auto-send:
  warn (no template, auto ON)`. The auto path never blindly fires; this
  is exactly the dodge path's behaviour at `dodge.js:54-57`. **Do not**
  attempt to learn the template from a same-window hand-click — that races
  the burst and would either fire the burst on a missing template or
  starve the user mid-click.
- **`defenseAssessment` reads `eta:null`.** `supportTryBurst` skips the
  movement — the support window is unknowable. Logged via
  `gbLogT('support-eta-null', 60000, …)`. No post, no confirm.
- **`defenseSupportOptions` returns `[]`.** Logged once per
  `state.supportLastSend` cycle, no post. The defensive posture is the
  same as dodge today when no safe town exists (`dodge.js:99-102`):
  the bot cannot help, the user is informed.
- **`militaryOutgoingMovements()` misses a friendly in flight** because
  the game has not yet published it (the friendly was just sent):
  `supportTryBurst` may over-arm. The anti-flap ledger (`state.supportLastSend`)
  prevents the **same** movement id from firing twice, but does not
  prevent a redundant support from a different donor. The window is small
  (≤ 10s) and the worst case is one extra `Town/sendUnits` post; the post
  is journaled and `jrnSkipped` (`tx.js:530`) closes the decision-memory
  window on the next attempt. **No double-fire inside the same window:**
  the `supportOverlapSec` gate at work item 3.1.8 prevents stacking
  friendlies on the same destination within `30s` of the projected
  attack.
- **The attack lands before support arrives.** `dodgeQueue` records the
  arrival (`dodge.js:289-294`). `supportRecallWindow` runs on the next
  5s pass: it finds the support command still in
  `militaryOutgoingMovements()`, calls `militaryCancelCommand` per donor.
  Recall may fail with `'not-cancelable'` (`military.js:52`) when the
  server has already absorbed the support into the destination town;
  this is logged, not retried. **The recall is irreversible** in the
  sense that troops spent on travel time are lost, but it is bounded by
  `cancelTpl` TTL (120s default) and never blind-fires.
- **Hostile that turns out to be friendly** (e.g. an attack that was
  cancelled before landing, but `mov` still shows in
  `MovementsUnits`). `dodgeIsHostileMovement` (`dodge.js:41-52`) is
  authoritative: once an entry passes, it stays hostile for this plan's
  purposes. The auto path arms; the worst case is a redundant support
  that the recall path may or may not be able to undo. **Do not** add a
  "second-chance hostile check" — that is the v1.5.3 audit rule
  (`CLAUDE.md` "Dodge / militia / CS"): one canonical filter, never
  revisit.
- **`gbLock('support')` contention.** A second burst fires while the
  first is in flight: the lock returns `null`, `supportTryBurst` reschedules
  `nextAt = Date.now() + 2000` (same retry shape `dodgeTrySend` uses,
  `dodge.js:210-214`). The lock's 180s TTL plus the 5s driver means
  contention resolves in well under one minute.
- **`state.dryRun` flipped mid-burst.** `txActionGate` reads `dryRun` on
  every `txRun` call (`tx.js:531`); the gate is per-post. A burst that
  armed with `dryRun:false` and posted before `dryRun:true` is honoured;
  the user's intent at the moment of the confirm dialog is what counts.
  The Log tab records both the `confirm()` and the `DRY-RUN support: …`
  or the live `support bridge: …` line.

## 9. Validation gate

Plan 27 §11 risk class Med: **dry-run + one hand-triggered firing + one
full orchestrator tick**. Plus the payload-sniff pre-flight from §0 of
plan 27 for any new post surface.

1. **Payload sniff against live UI.** With one own town and one own town
   to donate from, click `Send units → Support` in the game's own UI by
   hand once. Open DevTools → Network → filter on `frontend_bridge` →
   capture the request body. The expected body is
   `{model_url:'Town/<srcTownId>', action_name:'sendUnits', arguments:{id:<destTownId>, type:'support', <unit counts>}, town_id:<srcTownId>}`.
   Compare against `supportBridgePost`'s constructed payload. If they
   differ, the template wins and the post is rewritten before any live
   fire.
2. **Build + paste + reload `es146`.**
3. **Stats → Preflight**: new `support: auto-send` row reads
   `auto=OFF, tpl=null` (or `tpl=learned` after step 1) → pass.
4. **Dry-run walk-through.** Set `state.dryRun = true` and
   `supportCfg.auto = true`. Synthesise an incoming attack (or use an
   alt account). Confirm the dialog appears (`support: confirm dialog
   for window …`), accept it. Log shows `DRY-RUN support: …` and a
   `skip:dryrun` journal row. No `bridgePost('support', …)` actually
   fired. Stats Decisions view shows one `skip:dryrun` row.
5. **Hand-triggered firing.** Disable `dryRun`. Re-synthesise the same
   incoming. Accept the confirm dialog. Log shows `support bridge:
   sendUnits town <src> → <dest> (support, N tipos / M unidades)`. Stats
   Decisions shows one `ok` row for `support`. The destination town's
   `Town/units` model (via `gbTownModel`) reflects the new garrison.
6. **Recall path.** Re-arm a burst, then in the game cancel the attack
   from the attacker's side (`MovementsUnits` removes the entry) within
   the support travel window. The next 5s pass fires
   `supportRecallWindow`; `militaryCancelCommand` is called for each
   donor; logs show `cancel: command <id> OK`. Stats Decisions shows
   one `ok` for `cancel` and one `manual`/`done` for the original
   `support` entry (state machine: `supportLastSend[movId].state →
   'recalled'`).
7. **Refusal path.** Same setup; refuse the confirm dialog. Stats
   Decisions shows `skip:declined`; no `bridgePost('support', …)` fires;
   Log shows `support: confirm declined for window …`. Anti-flap ledger
   is **not** updated (no post means no flap risk).
8. **Anti-flap.** Re-fire the same incoming movement twice in 60s: the
   second confirm is suppressed (`state.supportLastSend[movId].expires
   > Date.now()`); Log shows `support: already-sent for <movId>`.
9. **`auto = OFF`.** Confirm dialog never appears regardless of incoming;
   no Log line beyond the orchestrator's quiet cadence.
10. **Captcha breaker.** Trigger a captcha via the dev test page; the
    `support` feature pauses per `gbCaptchaPause`. Auto resumes after
    the ladder expires (`core.js:367`). Log shows `support:
    captcha-pause (5|15|60m)`.
11. **Default OFF in code AND in shipped Config.** The release is invalid
    if any user gets an auto-send-without-clicking path on first install.
    Plan 27 §11 High-risk gate rule applies even at Med-risk for this
    feature, because the cost of error is real troop loss.
12. **One full `orchTick`.** With `auto = ON` and a single synthetic
    incoming, the dodge path may arm *and* support may arm on the same
    movement — verify they coexist (per §3.1, support only arms when
    dodge did not). Stats Decisions shows both rows; the support row
    carries `state: 'sent'` and the dodge row carries `state: 'sent'`
    if and only if `dodgeSupportValidate` cleared (the same path).

## 10. Out of scope

- **Predictive snipe** (plan 3.7): the wave-cluster gap arithmetic
  (`csWaveClusters`) is orthogonal. 3.2 reads the same `defenseAssessment`
  plan 3.7 also reads; the two features can run on the same incoming list
  without coordinating. If they should coordinate, it is a follow-up
  dependency: 3.7 first, then 3.2 consumes its `snipe` field for the
  "covered" case to lower the band threshold. **Not** modelled here.
- **Counter-dodge** (auto-recall without user click): explicitly HIGH-RISK
  and reserved for plan 5.4 (smart dodge) once that lands. 3.2's recall
  is *only* triggered by the confirm dialog having fired; the post-arm
  `supportRecallWindow` is a cleanup, not an autonomous decision.
- **Support via phoenician merchant**: phoenician ships carry units, not
  supports. Different `model_url`/`action_name` entirely; owned by
  `phoenician.js`, plan 25.
- **Cross-alliance support request intake**: that is plan 7.1 (alliance
  webhook for incoming support asks). 3.2 is local-only.
- **Defensive wall repair** (plan 4.5): orthogonal, different building,
  different `model_url`. Reuses the threat-detection path but posts to
  a different endpoint.
- **Auto-dodge resident troop floor conflict** (plan 5.4): the
  `homeFloor` rule interacts with the dodge `dodgeFloor` today. Plan 3.2
  exposes `shareDodgeFloor` (default true) to keep both paths reading
  the same floor; tuning the two independently is plan 5.4's job once it
  lands.
- **Manual support "Send now" button on the Defense Coordination Board**
  (plan 7.2): the board renders read-only. A "Send from this town"
  button on a board row is its own UI surface; owned by plan 7.2's
  follow-up if it ever lands.
