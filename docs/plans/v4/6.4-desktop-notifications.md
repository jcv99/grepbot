# 6.4 — Desktop notifications + sound (per event)

**Bucket:** v4.1 · **Risk:** Low · **Size:** S
**Module:** extend `src/alerts.js` (per-event Notification + Audio) +
`src/core.js` (state initializer) + `src/ui.js` (Config surface).
**Depends on:** none — `alerts.js` already has the per-event fan-out
(`alertWebhook` at `alerts.js:28-88`); this plan adds a sibling fan-out
to the local OS notification surface.
**Status:** PLANNED — written 2026-08-10 against `src/` @ v3.9.0 (`header.js:4`).

---

## 1. What exists today

- `src/alerts.js` is **89 lines total** (`alerts.js:1-89`). All five
  functions in it (`alertIsTelegram`, `alertWebhookUrlOk`,
  `alertTelegramChatId`, `alertWebhookKey`, `alertWebhook`) deal
  exclusively with the outbound Discord/Telegram webhook pipeline.
  There is **no `Notification` API call and no `Audio` usage anywhere in
  `src/`** — verified with
  `grep -n 'Notification\|new Audio\|webkitAudio\|playSound' src/`,
  zero hits.
- `alertWebhook(event, payload)` (`alerts.js:28-88`) is the single
  fan-out point. It is invoked from four call sites:
  `core.js:1379` (`captcha`), `intel.js:202` (`attack`, watchlist),
  `intel.js:242` (`pattern`), `culture.js:198` (`culture`), and
  `dodge.js:191` (`attack` with `cs: !!mov.hasCs`). Plan 27 §9
  already lists "Discord / Telegram webhooks" as shipped in
  `alerts.js` (8.8); this plan extends the same file with a second
  fan-out path, not a third.
- The per-event toggle surface already exists for webhooks:
  `state.webhookEvents` default `{ captcha:true, attack:true, warehouse:false, culture:false }`
  (`core.js:313`), rendered by `ui.js:1355-1359` and saved by
  `saveWebhookEvents()` at `ui.js:1477-1490`. The plan piggybacks on
  this UI — adding `notify:*` toggles next to `wh-*` keeps the user
  model consistent.
- Module-scope `alertPending` and `alertLastSent` are declared in
  `research.js:545-546` and read/written from `alerts.js:43-44,66,75,76,80,85`.
  The dedup is keyed on `alertWebhookKey(event, payload)` (5min TTL).
  The new desktop-notification path **must share that key** so a
  captcha that already fired a notification 2min ago does not fire
  again — duplicating the dedup table would let the two paths race.
- **`@grant` list (`header.js:9-15`)** declares
  `GM_xmlhttpRequest`, `GM_setValue`, `GM_getValue`, `GM_addStyle`,
  `GM_registerMenuCommand`, `GM_unregisterMenuCommand`. The browser's
  built-in `Notification` and `Audio` constructors do **not** need a
  `@grant` — they run in the page context, which a Tampermonkey
  userscript can reach via `unsafeWindow` (the `GB_ROOT` pattern at
  `core.js:3,80,81`). No header change is needed for the Notification
  API itself.
- The `GM_notification` shortcut is available (`TM grants list`),
  but it (a) only renders a chrome-side toast with no per-event
  customisation, (b) bypasses the user's own notification settings,
  and (c) does not play sound. The browser `Notification` constructor
  is the right primitive here.

## 2. Gap

The webhook pipeline only fires when `state.webhookUrl` is set
(`alerts.js:29-30`). When the player is sitting at the game tab and
no webhook is configured, the only signal for captcha / incoming
attack / culture completion is the footer status line
(`updateStatus()` at `core.js:562`) and the panel Log tab. Players
who want to keep GrepBot running in a background tab (a common
"AFK nocturno" preset at `qol.js:290-314`) get nothing for the most
urgent events — captcha and incoming attack.

The plan adds a local notification + chime on the same per-event
fan-out, gated on a default-OFF master toggle so the user has to
opt in (Notification.permission can only be requested inside a
user gesture, and Chrome silently drops auto-prompts).

## 3. Design

Two new functions in `alerts.js`, both called from inside
`alertWebhook` after the existing `state.webhookEvents[event]` check:

```
function alertDesktop(event, payload, key):
  if (!state.notifyEnabled) return;
  if (!state.notifyEvents || state.notifyEvents[event] === false) return;
  // Reuse the webhook dedup key — same 5min window, same suppression.
  if (alertPending[key]) return;
  if ((alertLastSent[key] || 0) + 5 * 60 * 1000 > Date.now()) return;
  const n = buildNotification(event, payload);
  try { new Notification(n.title, { body: n.body, tag: key }); }
    catch (e) { gbLogT('notify-' + event, 60000, 'notify: ' + String(e).slice(0, 60)); return; }
  alertPending[key] = Date.now();
  if (!state.notifyMuted) alertPlayChime(event);

function alertPlayChime(event):
  // Three short WAVs (~1KB each), base64-encoded inside src/.
  // We do NOT load from the network: a backgrounded tab can play
  // cached data: URIs without a permission prompt, and the user's
  // own GrepBot storage is the right scope.
  const map = { captcha: 'chime-captcha', attack: 'chime-attack',
                pattern: 'chime-pattern', culture: 'chime-culture' };
  const url = CHIME_URLS[map[event] || 'chime-default'];
  try {
    const a = new Audio(url);
    a.volume = Math.max(0, Math.min(1, +state.notifyVolume || 0.5));
    const p = a.play();
    if (p && typeof p.catch === 'function') p.catch(() => {});
  } catch (e) { gbLogT('chime-' + event, 60000, 'chime: ' + String(e).slice(0, 60)); }
```

`alertWebhook` is updated so that the existing webhook send becomes
a sibling — `alertDesktop(event, payload, key)` is called **before**
the `gbXhr(...)` block. The dedup table is shared. If the user has
only the desktop path enabled (no webhook URL), the
`alertLastSent[key]` entry is still written by `alertDesktop` (it
sets `alertPending[key] = Date.now()`); the next call to
`alertWebhook` within 5min sees the dedup and short-circuits at
`alerts.js:43-44`. This matches today's "one event, one notification"
behaviour regardless of which channels are enabled.

Permission gate: `Notification.permission` is `'default'` on a fresh
install. The Config panel adds a "Permitir notificaciones" button
that calls `Notification.requestPermission()` from the click handler.
The button is **disabled** when permission is already `'granted'`
or `'denied'`, and shows the current state in its label. Per the
Notification API, `requestPermission()` is only honoured when called
inside a user gesture — a button click is one. **Never** call
`requestPermission()` from `boot.js` or from a `keydown` listener
that the user did not register — Chrome silently rejects it.

   Keep the strings short; the artifact is already ASCII-only after

## 6. Config surface

- Label: `Notificaciones` (notifications). One master toggle + one
  permission button + four per-event checkboxes + one volume slider
  + one mute checkbox.
- Position: just below the existing `webhook-events` block
  (`ui.js:1477-1490`). Rationale: webhooks and desktop notifications
  share the same event taxonomy; the two blocks read as a unit.
- Defaults: master OFF (permission would otherwise auto-prompt
  silently for every install — a hard UX regression); events all
  OFF (the master gate is enough; per-event gating is a follow-up).
  Volume 0.5. Mute OFF.
- No HIGH-RISK toggle involved; risk stays Low. The master toggle
  **defaults OFF** because Chrome's permission auto-prompt is the
  single most intrusive UX event in any userscript and must be
  earned, not assumed.

## 7. Post surface & safety

This feature **does not introduce a bridge / `bridgePost` post
surface**. Desktop notifications are a browser-side OS surface; the
sound chimes are `data:` URIs that never leave the script's own
memory. Both are downstream of the existing `alertWebhook` call,
which already has its own dry-run + URL-validity gates.

- No `gbAjaxWatch` registration needed (no new HTTP path).
- No `gbCaptchaPause` feature key needed (no bridge post).
- No `gbLock` / `GB_LOCK_TTL` entry needed (synchronous).
- No dry-run gate needed — there is no payload to dry-run; the
  chime is a local sound. (The existing `alertWebhook` dry-run gate
  at `alerts.js:31-34` already short-circuits the whole call.)
- **No new `gbInterval`.** Notifications are event-driven from the
  existing webhook fan-out.
- **No new top-level `function` declarations that risk the
  `build.py` duplicate gate** (`build.py:365-378`). Every helper in
  §4.2, §4.3 is at module-indent depth, matching
  `alertIsTelegram` and friends at `alerts.js:1-27`.

## 8. Failure modes

- **`Notification` API blocked by the browser** (rare on Tampermonkey;
  Firefox with strict cookie permissions, Safari with cross-site
  tracking). `new Notification(...)` throws — caught at the
  `try/catch` in `alertDesktop`, logged once per event via
  `gbLogT('notify-' + event, 60000, …)`, and the dedup table is **not**
  marked (so the next event retries). After ~3 retries the throttled
  log keeps the Log tab informative without spamming.
- **`Audio` constructor blocked** (Chrome autoplay policy). The
  first chime after install may be blocked because the gesture that
  granted Notification permission is not the same gesture that
  plays audio. `play().catch(...)` swallows the rejection silently;
  the user can press the volume slider or a "Probar sonido" button
  (added alongside the slider) to play one chime inside a fresh
  gesture. Subsequent notifications in the same tab session usually
  work because the tab has been activated.
- **`Notification.permission === 'denied'`.** The Config button is
  disabled; the master toggle stays OFF; no prompts fire. The user
  must reverse the decision in the browser's site settings.
- **`unsafeWindow.Notification` is not the same as `Notification`.**
  Tampermonkey sandboxes the script. `Notification` is the page
  constructor — reachable through `unsafeWindow` (the `GB_ROOT`
  pattern at `core.js:3,80,81`). The `new Notification(...)` call
  must come from `unsafeWindow.Notification.bind(unsafeWindow)` if
  the constructor references `this`. In practice `Notification`
  does not use `this`, so the call works as written; verify in the
  validation gate by checking the chrome tray on a forced event.
- **Volume slider at 0.** `state.notifyVolume === 0` produces an
  inaudible chime. That is fine — the visual notification still
  fires; the user can move the slider up. The mute checkbox is the
  one that suppresses the chime entirely.
- **Telegram / Discord URL conflicts.** Both webhook and desktop
  paths read `state.webhookEvents[event]`. The webhook path has its
  own URL check at `alerts.js:35-38`; the desktop path does **not**
  care about the URL — it fires even if no webhook URL is set. This
  is intentional: a player can disable webhooks but keep desktop
  notifications for low-latency awareness.
- **Multiple events within the 5min window.** `alertDesktop` shares
  the `alertPending[key]` table with `alertWebhook`, so a captcha
  fires the desktop notification and the webhook **at most once
  per 5 minutes per fingerprint**. Captchas normally come 15+ minutes
  apart; this is not a real loss.

## 9. Validation gate

Manual, per plan 27 §11 (Low risk = Preflight + one in-game session,
no failure).

- Install the new `grepbot.user.js`. Config → Notificaciones → click
  `Permitir notificaciones`. Browser shows the prompt; accept. The
  button label flips to `Permitir notificaciones (actual: granted)`.
- Tick `Notificaciones de escritorio`. Config → Log shows
  `notify-enabled ON`.
- Tick `Notificaciones: captcha`. Trigger a captcha manually
  (visit `/captcha` or run any bridge post 3× in a row — the
  captcha ladder at `core.js:367` opens a window). A chrome tray
  notification appears with body `GrepBot [es146] captcha` and the
  chime plays.
- Config → Notificaciones → drag the volume slider to 0. Re-trigger
  the captcha: notification appears, no sound. Drag to 1: sound
  plays loud. Tick `Silenciar sonido`: re-trigger, no sound even
  at volume 1.
- **Permission denial path.** Open browser site settings, set
  Grepolis to `Block`. Refresh the tab. The Config button is
  disabled with label `(actual: denied)`. Toggling the master
  checkbox has no effect — the `new Notification(...)` call at
  `alertDesktop` throws and the catch path logs once.
- **Webhook / desktop independence.** Set `webhook-url` to a fake
  URL (the URL-validity check at `alerts.js:35-38` rejects it).
  The desktop notification still fires; no `gbXhr` is made.
  Reverse: clear the master toggle, set a real webhook URL — the
  webhook fires; no chime, no chrome notification.
- **Preset test.** Config → Aplicar plantilla → `AFK nocturno`.
  The master toggle flips ON. Visit the game and trigger an
  incoming attack via a friend — the chrome notification appears
  with the attack fingerprint.
- Log tab shows zero new error rows. No new `gbXhr` calls appear
  in the Network tab (only the existing `gbXhr` from
  `alertWebhook` when a webhook URL is set).
- `python3 build.py` passes (no new top-level declarations
  collide); install via paste into Tampermonkey.
- Preflight (Stats → Comprobar sistema) reports no new warn rows.

## 10. Out of scope

- **Per-world / per-event custom sound files.** The four chimes are
  fixed base64 blobs; uploading a custom `.wav` is a much larger UI
  surface and out of scope.
- **In-panel toast** (a GrepBot-internal non-OS notification). Plan
  6.1 already owns visual styling; an in-panel toast would belong
  to that plan or to the broader panel rework in §6.2 (Draggable
  widgets). Out of scope here.
- **Notification click → focus the game tab.** `Notification.onclick`
  can call `window.focus()`, but the browser's own handling already
  focuses the originating tab. Wiring a custom click handler is
  reserved for v4.x when the action target is clearer.
- **iOS Safari.** Safari on iOS still does not ship the
  `Notification` constructor to web apps without a home-screen
  install. The plan degrades silently — the dedup table logs once.
- **Telegram bot inbound** (chat → GrepBot). Plan 27 §0 explicitly
  drops this; outbound webhook is the only direction GrepBot ships.
