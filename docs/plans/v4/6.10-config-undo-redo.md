# 6.10 — Undo/redo for config changes

**Bucket:** v4.0 · **Risk:** Low · **Size:** S
**Module:** `src/qol.js` (snapshot/history/apply contract) + `src/ui.js` (buttons and event boundaries); existing `build.py` MODULES slots `qol.js`/`ui.js` (`build.py:61-70`)
**Depends on:** none; 6.9 should call this transaction boundary when it lands
**Status:** PLANNED — written 2026-08-10 against `src/` @ v3.8.2

## 1. What exists today

- There is no `undo`, `redo`, `configUndo`, or config-history symbol in `src/`; the only existing history-like state is operational decision memory (`state.decisions`/`state.decisionSkips`, `src/core.js:343-345`) and queue/history data for other features (`src/core.js:263-285`).
- The existing config export is a partial allow-list of targets, planner/queue data, profiles/templates, and notes/watchlist (`src/qol.js:248-252`). It is redacted only by the UI export caller (`src/ui.js:985-987`), not by `qolExportConfig` itself.
- Config controls mutate `state` and persist directly in many handlers: early toggles use direct assignments (`src/ui.js:1193-1291`), later toggles use `bindToggle` (`src/ui.js:1364-1392`), and numeric/select/object fields use `saveNum` and direct listeners (`src/ui.js:1393-1533`). No common before/after checkpoint exists.
- Presets also mutate directly through `qolApplyPreset` (`src/qol.js:359-381`), and template application writes targets directly (`src/qol.js:25-44`). Plan 16 proposed snapshot/undo (`docs/plans/16-config-presets.md:45-48`, `docs/plans/16-config-presets.md:65-80`), but that behavior is not present in the shipped functions.
- `configVer` is loaded as world-scoped state (`src/core.js:339-347`, `src/header.js:193-215`), migration is ordered through v10 and ends by saving/logging the new version (`src/core.js:394-510`), and `migrateConfig()` runs during UI startup (`src/ui.js:1992-1997`). An undo implementation that simply writes an old version backward would violate this one-way migration model.

## 2. Gap

Add bounded, local undo and redo for user-facing configuration mutations without treating runtime telemetry, learned templates, journal rows, or credentials as configuration. Every checkpoint must restore a validated current-schema snapshot, preserve the migration version, and handle an old snapshot across a `configVer` boundary without replaying obsolete storage formats or silently disabling dry-run safety.

## 3. Design

1. Define `QOL_CONFIG_HISTORY` as a module-local IIFE in `qol.js`, exposing `snapshot`, `commit`, `undo`, `redo`, `canUndo`, and `canRedo`. A snapshot is `{schema, ver, at, reason, data}`. `data` is a cloned, validated configuration allow-list; it excludes `webhookUrl`, `webhookEvents.telegramChatId`, CSRF, captcha breakers, learned templates, findings, decisions, transport state, and host consent. The existing redaction path remains the export privacy boundary (`src/qol.js:223-246`).
2. Expand the canonical config snapshot/export allow-list to cover every Config-tab field that can alter automation, including the toggles and values rendered at `src/ui.js:1302-1363` and persisted at `src/ui.js:1371-1533`, while keeping sensitive/operational exclusions explicit. Do not infer keys from a deny-list: new config keys remain untouched until deliberately added to the allow-list.
3. `commit(reason, mutate)` clones the canonical `before`, runs the existing mutation synchronously, clones `after`, and pushes `before` only when the canonical JSON differs. It clears redo, caps each ring at 20 entries, stores a 7-day timestamp, and saves one world-scoped undo key. Nested apply calls use a `record:false` guard so import/preset/undo does not create recursive entries.
4. Wrap user-generated Config-tab `change` events at the section capture phase in `ui.js`, before existing handlers mutate state, then compare after the synchronous handler. The event filter is limited to `[data-cfg]` controls plus the existing preset/template/import actions; it must not capture panel navigation, Stats simulation, journal clear, scrape buttons, or runtime callbacks. Explicit `commit` calls remain required for public `qolImportConfig`, `qolApplyPreset`, and `qolApplyTemplate` so non-DOM callers are covered.
5. Undo pops the latest valid undo entry, first commits the current state to redo, then applies the popped data through the same validators/normalizers as `qolImportConfig` (`src/qol.js:254-267`). Redo does the symmetric operation. Refresh Config, Overview, and status after either action; log `config undo: <reason>` / `config redo: <reason>` with stack counts, never raw sensitive data.
6. Migration boundary rule: `ver < state.configVer` is normalized forward into the current schema and applied without lowering `state.configVer`; `STORE.CONFIG_VER` remains the current value. The apply log must say `config undo: normalized v<old> -> v<current>` and the result is not advertised as byte-identical. `ver > state.configVer` is refused and remains on its stack. This is necessary because startup migration can rewrite state and persist v10 (`src/core.js:394-510`) before the UI is available (`src/ui.js:1992-1997`).

## 4. Work items

1. **`src/header.js` — storage constants and scope.** Add `CONFIG_UNDO` and `CONFIG_REDO` keys beside `CONFIG_VER` (`src/header.js:125-140`), and add both to `WORLD_SCOPED_BASES` (`src/header.js:193-215`) so undo data from one world cannot alter another world’s config. No id-bearing key may bypass that set.
2. **`src/core.js` — state initialization.** Load `configUndo` and `configRedo` as bounded arrays in the `state` object (`src/core.js:220-384`). Do not put history into `DECISIONS`; that ring has separate TTL/duplicate semantics (`CLAUDE.md:352-365`).
3. **`src/qol.js` — canonical snapshot and history IIFE.** Implement deep cloning with the repository’s JSON style (`src/qol.js:254-257`), allow-list normalization, ring pruning, save/load, stack operations, and a non-recording apply option. Reuse import validators rather than a second unchecked setter. Preserve the existing preset high-risk-off policy (`src/qol.js:272-381`).
4. **`src/qol.js` — mutation boundaries.** Add `history:false`/`source` options to `qolImportConfig`, wrap `qolApplyPreset`, and wrap `qolApplyTemplate` (`src/qol.js:25-44`, `src/qol.js:254-267`, `src/qol.js:359-381`). A failed/zero-section import must not create an undo entry; a successful preset/template/import creates exactly one.
5. **`src/ui.js` — event capture and controls.** Register one capture listener on `section[data-tab=config]` after the existing controls are bound (`src/ui.js:1137-1540`), identify only config mutations, and close the checkpoint after the target handler returns. Add `Deshacer` and `Rehacer` buttons plus disabled-state/count rendering near the existing profile/config controls (`src/ui.js:883-894`). Clicks call the public history methods, then `bindConfig`/`updateStatus`.
6. **`src/ui.js` — no accidental captures.** Ensure the listener does not checkpoint `clear-captcha`, `research-csfast`, `pt-now`, `pt-copy`, panel navigation, or `gb-sim-run`; those controls are visible in the existing markup (`src/ui.js:779-841`, `src/ui.js:688-690`) and their handlers have non-config side effects (`src/ui.js:1412-1425`, `src/ui.js:1501-1503`).
7. **`src/core.js` — migration compatibility helper.** Extract or add a pure current-schema normalizer for history data from older `ver` values, without decrementing `state.configVer` or re-running world-key migration against arbitrary data. Keep startup `migrateConfig()` as the only state migration entry (`src/ui.js:1992-1997`).

## 5. State & storage

- New fields: `state.configUndo` and `state.configRedo`, each a maximum-20 array of `{schema,ver,at,reason,data}`. New keys are world-scoped (`src/header.js:193-215`) and pruned at 7 days on load/save; malformed or oversized entries are discarded.
- `configVer` remains the current schema after undo/redo. Do not add a separate version history key and do not lower `STORE.CONFIG_VER` (`src/header.js:132`, `src/core.js:507-510`).
- The existing `CONFIG_EXPORT_SCHEMA` is 3 (`src/qol.js:223`). Bump it only if the expanded canonical export changes its shape; record the schema in every snapshot and refuse future schemas using the existing import ceiling (`src/qol.js:254-256`).
- History excludes player/alliance notes, watchlist, webhook URL/chat id, CSRF, learned templates, findings, journal, locks, queues in flight, and host consent. Imported queue entries continue through the existing uncertain-state normalization (`src/qol.js:257-266`); an undo must never resurrect an in-flight job as accepted.

## 6. Config surface

- Add `Deshacer` and `Rehacer` buttons, disabled when their stack is empty, with compact counts `Deshacer (N)` / `Rehacer (N)`.
- Add status text `Último cambio: <reason>` and show migration normalization as `Normalizado: v<old> → v<current>`.
- No new automation toggle. `dryRun` remains user-controlled by the existing Config checkbox and handler (`src/ui.js:785`, `src/ui.js:1384-1389`); if an undo snapshot would change current `dryRun` from ON to OFF, preserve ON and log `config undo: dry-run safety preserved`.
- HIGH-RISK fields are not newly enabled by this feature; presets continue forcing them OFF (`src/qol.js:272-288`). Undo/redo may restore an explicitly user-enabled value already present in a snapshot, but must never synthesize one or accept an unlisted field.

## 7. Post surface & safety

No post surface is introduced: undo/redo only applies local validated configuration. There is no route, payload, `gbAjaxWatch`, `TPL_FEATURE_MAP`, `gbCaptchaPause` key, or lock; existing posts remain behind `bridgePost`/`gameAjaxPost` dry-run and precondition gates (`src/core.js:940-946`, `src/tx.js:531-555`). Do not add a new scheduler or `*InFlight` boolean. The dry-run-preservation rule above prevents the recovery control from turning a safe session live.

## 8. Failure modes

- Empty stack, malformed snapshot, expired entry, or future schema is a no-op with `flash('no hay cambios para deshacer/rehacer')` or `config history: snapshot refused`; it must not mutate state or storage.
- A snapshot whose version is older than current is normalized forward, never written backward. If a field was removed or rewritten by migration, leave the current/default normalized value and disclose that limitation in the Log; do not claim exact equality (`src/core.js:409-510`).
- A snapshot containing an unreadable/invalid value is rejected by the same validator that protects imports (`src/qol.js:254-267`). For any resulting live feature, every guard names the value it read; unreadable getter ⇒ `blind` ⇒ `gbLogT` once ⇒ let the server decide (`src/core.js:298-309`).
- Storage quota failure uses the existing prune/retry path (`src/core.js:1130-1213`); keep the in-memory stacks coherent with the successful write only. If persistence fails, log the failure and disable the corresponding button until the next reload rather than reporting durable history.
- Rapid clicks are serialized by a synchronous `recording` flag and button disable; no asynchronous callback or lock is needed. A failed apply puts the popped entry back on its original stack.

## 9. Validation gate

Low risk requires Preflight plus one in-game session with no failure (plan 27 §11). Change one Config checkbox, click `Deshacer`, verify the checkbox/value and exported canonical settings return to the prior state, then click `Rehacer` and verify the second state returns; Log must contain the reason and stack counts. Repeat with a numeric field, object field, preset button, template apply, and a valid import; each creates one entry, while cancel/invalid import/clear-captcha creates none. Turn dry-run ON, make a snapshot with it ON, change it OFF, undo, and confirm it stays ON. Simulate or retain a snapshot with `ver:9` while current is v10: undo must log normalization, keep `state.configVer` at v10, and leave queue/defense values valid; a `ver:11` snapshot must be refused without mutation. Reload and verify the 7-day bounded history persists, then switch worlds and verify the stacks are isolated. Stats/Preflight must still report normally and no game request may appear from undo/redo.

## 10. Out of scope

No undo for findings, farm scrape data, decision journal, learned payloads/templates, locks, runtime scheduler deadlines, queue outcomes, panel geometry, host consent, or secret-bearing webhook fields. No cross-world history merge, browser storage sync, server backup, test harness, or new scheduler. The Config wizard UI is 6.9; automatic profile rule evaluation is 6.8.
