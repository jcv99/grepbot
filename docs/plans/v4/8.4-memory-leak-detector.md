# 8.4 — Memory leak detector (`performance.memory` + `Map.size`)

**Bucket:** v4.1 · **Risk:** Low · **Size:** S
**Module:** extend `src/stats.js` (renderer + `preflight` row) + extend `src/core.js` (heap reader + map-size sample collector)
**Depends on:** none
**Status:** PLANNED — written 2026-08-10 against `src/` @ v3.8.2

## 1. What exists today

- `performance.memory` is referenced **zero times** anywhere in `src/` (verified with `rg 'performance\.memory' src/`). Plan 27 §8 already flags it as best-effort / Chromium-only — this plan delivers the unavailable-path handling explicitly, not as a footnote.
- The largest bounded collections in `src/` are: `state.decisions` (ring, capped `JRN_MAX = 400`, `src/bridge.js:446`), `state.decisionSkips` (object, no cap — pruned only when a window expires, `src/journal.js:218-223`), `state.findings` (array, pruned by `core.js:1132-1140` per plan 26 §A1), `state.seen` (object, pruned 24h by `core.js:1132-1140`), `state.farmsParsed` / `state.towns` (arrays), `state.txState` (object, no cap), `state.dodgeReturns` (object, no cap), `state.farmResources` (object, no cap).
- `gbEvidence()` (`src/stats.js:389-506`) already exposes `counts.findings`, `counts.seen`, `counts.farms`, `counts.towns`, `counts.decisions` (`stats.js:479-485`) — the *N* of each bounded map is already shipped to the user-facing evidence export. The leak detector adds the **delta over time** to that, not the absolute count.
- `preflightRun()` (`src/stats.js:12-267`) is the natural home for a `memory probe` row, after `cost reads` (`stats.js:188-209`) and before `attack` (`stats.js:210-214`).
- `gbListen(window, 'pagehide', …)` (`src/journal.js:306`) and the equivalent `visibilitychange` listener (`src/journal.js:307`) are the existing flush patterns to copy for saving the sample ring.

## 2. Gap

The user can see the journal ring holding steady at ~400 entries and assume nothing leaks. They cannot see the JS heap growing, and they cannot tell which of `state.dodgeReturns` / `state.txState` / `state.decisionSkips` (the three uncapped objects) is the source when it does. The detector adds a passive heap-size sample at 5-minute intervals plus a one-line `Map.size`-style tally of the uncapped objects, rendered into the existing Stats window. No new scheduler: the sample is taken from inside `jrnSave()`'s already-debounced `gbTimeout` (`src/journal.js:108`), so the cadence inherits from journal saves — zero new timers.

## 3. Design

Two pieces, one renderer, one Config toggle:

- **Heap sample.** `memSample()` reads `performance.memory.usedJSHeapSize` (Chromium-only) and `performance.memory.totalJSHeapSize`. If `performance.memory` is `undefined` (Firefox/Safari, or hardened Chromium), `memSample()` returns `{ blind: true }`. The sample ring is a fixed 24-entry FIFO (= 2 hours at 5min cadence) of `{ts, used, total}`.
- **Map-size tally.** A static list of the uncapped state objects (`state.dodgeReturns`, `state.txState`, `state.decisionSkips`, `state.farmResources`, plus any future ones added in `WORLD_SCOPED_BASES` whose default shape is an object — derived from the keys, not hand-listed) — counts `Object.keys(state.X || {}).length` at the same cadence. These are the maps that *could* leak; the bounded ones (journal, findings, seen) already have prunes and are reported only via `gbEvidence()`.
- **Sample cadence.** Reuse the existing `gbTimeout(() => { … jrnSave(true); }, JRN_SAVE_MS)` (`src/journal.js:108`, `JRN_SAVE_MS = 5000` — debounced 5s) as the host of the sample call: every time the journal would save, the heap+map sample is also appended. No new `gbInterval`. The 5s cadence is far above 5min — a `nextMemSample` field gates the actual append so the effective rate is one sample per `MEM_SAMPLE_MS = 300000` (5 min), matching plan 27's typical polling cadence.
- **Renderer.** A new block at the end of `renderStats()` before `box.textContent = …` (`src/stats.js:354`) prints `mem: used N Mb / total M Mb (delta +X Mb over 2h)` and `maps: dodgeReturns=N txState=N …`. When `performance.memory` is `undefined`, the row prints `mem: API no disponible (Chromium-only)` once via `gbLogT` — no dead guard.
- **Why best-effort, not gated by Config default.** Plan 27 §8 explicitly says the caveat is "best-effort". There is no spend or post surface here, so the toggle is a per-developer `memProbeOn` flag (default **OFF**, mirroring plan 8.3 — sampling is cheap but not free). The `preflightProbe('memory probe', …)` row reflects the toggle state so users can see whether it is on.

## 5. State & storage

- New state: `state.memSamples` (array of `{ts, used, total}`, capped `MEM_MAX = 24`); `state.memProbeOn` (boolean, default `false`); `memNextAt` (module-local, not persisted — resynced to `Date.now()` after reload, so the first sample lands 5 min after load, not 5 min after the last saved one).
- Storage: `STORE.MEM_SAMPLES` (`grepbot:mem-samples`) — world-scoped (entry in `WORLD_SCOPED_BASES`). The 24-entry ring at 5min cadence = 2h of history, which is enough to surface a linear leak of 5Mb/h without making `gbEvidence()` too heavy.
- Prune: in-ring FIFO at `MEM_MAX`. No separate TTL — the ring's purpose is "did the heap grow in the last 2h", not "long-term heap history".
- `configVer` bump: 10 → 11 (header.js:191). Coordinated with 8.3.

## 6. Config surface

- **Toggle:** `memProbeOn` (default **OFF**, like 8.3 — no spend, but adds two `performance.memory` reads + five `Object.keys(...).length` reads every 5 min when ON; cheaper than the profiler, but the default is OFF so the user opts in).
- **Surface:** same Actions-menu button pattern as 8.3, in the Stats tab. No Config checkbox.
- **No window selector needed.** The ring is its own 2-hour window; the Stats `1h`/`24h`/`7d` button only filters journal rollups (`STATS_WINDOWS[statsWindow]` is used at `stats.js:285,289-291`), not the memory ring.

## 7. Post surface & safety

Read-only. No `bridgePost` / `gameAjaxPost` / `gbAjaxWatch` / `gbLock` / dry-run. None of the post layer is touched. The `memSample()` call sits in the journal-save timer, which is already idempotent.

## 8. Failure modes

- **`performance.memory` undefined** (Firefox / Safari / hardened Chromium). This is the documented plan 27 caveat. The precondition invariant applies: `memSample()` *does* read the API (`typeof performance.memory`), and the read can return `undefined` — that is the value it read. Treat as `blind`: `gbLogT('mem-blind', 86400000, 'memory probe: performance.memory unavailable on this browser')` fires **once** per day, the renderer prints `mem: API no disponible (Chromium-only)`, the row stays in Preflight as a `warn`, and Stats renders the map-size tally regardless (those are vanilla `Object.keys(state.X).length` reads — always available). No dead guard: a missing API does not disable the map tally.
- **Heap delta noise.** `performance.memory.usedJSHeapSize` jitters ±2-5 MB per read on a healthy session (GC events, transient JSON serialisation). The renderer prints the **delta between the first and last sample** in the ring, not the last-vs-previous — over a 2-hour window the noise floor is small relative to a true leak.
- **Map-size drift.** `state.decisionSkips` is supposed to grow when errors fire and shrink when windows expire (`journal.js:218-223`). A monotonically increasing `txState` count after a session of no activity would be a real bug — but the detector only surfaces the count, it does not act. A future plan (8.1 circuit breaker territory) can act on the same data.
- **Preload save.** If the user reloads before 5 minutes elapse, the ring is empty after load — `memNextAt` resets to `Date.now()` and the first sample lands 5 min later. `evidenceCopy()` (`stats.js:511-531`) must **not** include `memSamples` — they are diagnostic, not part of the user-facing evidence export. If a key named `memSamples` or `memProbeOn` accidentally appears in `gbEvidence()` (`stats.js:432-506`), remove it.
- **Sample loss on reload.** Intentional. The 2-hour ring is meant to surface leaks in the current session — persisting it across reloads would conflate heap snapshots from two different user sessions (the heap can legitimately change between them).

## 9. Validation gate

Low risk → Preflight + one in-game session, no failure (plan 27 §11). The best-effort caveat from plan 27 §8 applies — if `performance.memory` is unavailable, validation is map-size only.

1. Toggle ON via Stats Actions menu → *Memory probe ON*. `preflightRun()` prints `! memory probe: recording — see Stats` and the `cost reads` row stays unchanged. Stats body prints the heap line and the map-size tally.
2. Wait 10 minutes with `autoFarm` ON and at least one `autoBandit` cycle: the heap line shows a non-zero sample count; the map-size tally shows `txState` ≥ 1, `dodgeReturns` = 0 if no dodge fired, `decisionSkips` ≥ 0.
3. In Chromium, observe `used JS heap size` in `chrome://memory-internals` (or DevTools Performance Memory panel) and confirm GrepBot's reported `used` is within ±10% of the dev-tools reading.
4. Toggle OFF → no more sample appends, the ring freezes at its current state for the rest of the session, then resets to empty on reload. No Log lines about the toggle (silent flip, same as 8.3).
5. **Unavailable path:** if the user is on Firefox (Tampermonkey + Firefox does not expose `performance.memory`), the Log shows the once-per-day `memory probe: performance.memory unavailable on this browser` line on the first toggle, and Stats renders `mem: API no disponible (Chromium-only)` with the map-size tally still present. No further Log spam.

## 10. Out of scope

- Storing `memProbeOn` to disk. Same rationale as 8.3 — the toggle is per-session. If users want persistence, add `STORE.MEM_PROBE` + world-scope later.
- Per-tab GC-forced sampling (`window.gc()` is a Chromium-only debug hook). Not needed for a 2-hour ring.
- Per-decision heap attribution (which feature's last run moved the heap). The journal already has feature keys; correlating heap snapshots to feature calls would need per-call heap sampling, which is 8.3's job.
- Leak remediation. The detector surfaces counts; it does not prune. `state.dodgeReturns` and `state.txState` are the obvious candidates for follow-up prune work, but that is a separate plan (belongs in §8 reliability, not §8 observability).
- 8.6 decision audit trail — already shipped in `src/journal.js` v1.1.0, no interaction.
- The `STORE.MEM_PROBE` key is intentionally *not* added in work item 1 — see §6 (per-session toggle). If the toggle later becomes persistent, that is a follow-up work item.
