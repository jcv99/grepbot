**Depends on:** none (data source `state.findings` is already populated; 2.1 will widen what is parseable but is not a prerequisite)

## 1. What exists today

- `parseReport(id, data)` (`src/parse-inline.js:33-93`) returns the canonical
  finding shape: `{id, ts, type, attacker, defender, town:{id,name,x,y}, units,
  resources, loot, outcome, wall, alliance, vill_id, vacation}`. Both
  `attacker` and `defender` go through `nameOf()` (`src/parse-inline.js:1-16`)
  and carry `{id, name, town_id, town_name, alliance, vacation}`.
- `state.findings[]` is the sole ingester target. `spy.js:249`
  (`state.findings.unshift(parsed)`) is the writer; `spy.js:250-253` caps it at
  500 rows; `spy.js:254` saves to `STORE.FINDINGS`. `core.js:1167-1171` does
  the same prune offline.
- `intelDossiers()` (`src/intel.js:34-71`) already aggregates findings into
  per-player dossiers and is the Intel-tab section "Fichas"
  (`src/intel.js:92-97`). It counts reports and the last-seen timestamp but
  does **not** compute loss/win ratios or per-village profitability — that is
  exactly the gap 2.5 fills.
- `intelPatternScan()` (`src/intel.js:206-245`) already counts ≥3 findings per
  attacker in a 24h window and emits a `pattern` webhook — that is the
  "attack pattern" feature shipped per plan 27 §9 and is not duplicated here.
- `findingsFilter` (`src/core.js:280`, persisted via `STORE.FINDINGS_FILTER`,
  key already in `WORLD_SCOPED_BASES`) is honoured by the Findings tab
  (`src/ui.js:1688-1693`). The Intel tab does **not** honour it (it is a
  summary view by design); 2.5 keeps that line.
- `unitMeta(id)` (`src/attack.js:31-...`) returns per-unit metadata including
  `population` and `attack`/`defense`/`hp`/`is_naval` — the natural weighting
  for loss ratio. `defenseLocalStrength` (`src/wonder.js:142`) already uses
  `unit population` as the weight when scoring a town's defensive power,
  so this codebase precedent is settled.
- Plan 27 §9 already lists "Battle report basics" as shipped at `intel.js
  (13.x)`. 2.5 is the **delta over** what plans 12 + 13 already shipped:
  support ETA + attack-pattern alert. Per plan 26 §B2 quality bar, treat
  that §9 row as confirmed but not as a synonym for 2.5.

## 2. Gap

The Intel tab shows a count of reports per player but no per-player **outcome
profile** (how much loot you extracted, how many losses you took, how often
you won), and no per-farm-village **profitability** ranking. Without these,
the "top farms" question is answered by inspection of every Findings row.

## 3. Design

Two derivations over `state.findings`, both pure read-mostly, both fire once
per Intel-tab render:

- **`intelLossRatio()`** — for each player in the dossier set, sum attacker-loss
  and defender-loss pop separately (where the player IS the attacker, count
  their losses; where they ARE the defender, count the losses they inflicted
  on the attacker). Use `unitMeta(id).population` for weight; unknown units
  are skipped, not estimated. Output: `{attacker, wins, losses, popLost,
  popKilled, ratio}`. Stored on the dossier object as `d.loss = {...}`,
  independent of the existing `reports`/`last` fields.
- **`intelFarmProfitability()`** — derive from `state.findings` rows where
  `vill_id` is set (farm-village raids) and `state.playerNotes[attacker]` or
  dossier shows the player was the attacker. Aggregate per `vill_id`: raid
  count, sum of `loot.wood+stone+iron` (or `resources` — same shape, see
  `parse-inline.js:25-31`), ratio of raids that returned loot > 0. Output:
  `[{vill_id, name, raids, haul, successRate}]` sorted by `(haul / max(raids,
  1)) desc`. Cut at top 20 for the panel; full list goes in the export.

Both depend only on `parseReport` output already captured. Nothing is fetched.
Both re-use `intelPlayerKey`/`intelPlayerLabel`/`intelActorIsMe`
(`src/intel.js:1-33`) — no new identity helpers.

The aggregate is computed when `renderIntel()` (`src/intel.js:75-114`) runs
(15s loop, `boot.js:108-115`) and stamped into the session snapshot
`state.intelSnapshot = { computedAt, lossByPlayer, topFarms }`. The snapshot
is **not** persisted — derived cheaply on demand, and any historical view
over `state.findings` already trims to 500 rows. Stats tab (`src/stats.js:480`
already reads `state.findings.length`) does not change.

## 5. State & storage

- **No new `state.*` field, no new STORE key.** Output is recomputed per
  render from existing `state.findings`. Plan 27 §9 already credits the
  surface to intel.js, and plan 26 §B6 warned us not to ship "Config-shaped
  boolean that does nothing" — same logic for state.
- `STORE.FINDINGS` (`src/header.js:25`) is already in `WORLD_SCOPED_BASES`
  (`src/header.js:194`); 2.5 inherits that.
- `STORE.FINDINGS_FILTER` is already loaded into `state.findingsFilter`
  (`src/core.js:280`). 2.5 does **not** consult it (the Intel summary is not
  the filtered Findings tab) and explicitly says so in §3 to avoid surprising
  the user.
- Bumping `configVer` is unnecessary: 2.5 adds a feature-toggle field but
  defaults it ON, with the absence behaving like a missing toggle being read
  as `true` (consistent with how `state.csAlert !== false` is treated at
  `src/intel.js:191`, `src/core.js:335`, `src/ui.js:1333`).
- No prune TTL — derived, not stored.

## 6. Config surface

- One toggle: `[data-cfg=intel-battle-stats]` default ON. Persisted to
  `STORE.FINDINGS_FILTER` would be wrong (semantically unrelated); instead
  co-store as a sub-key on the existing toggle pattern, but since the
  feature is **derived not stored**, the toggle is a UI switch bound through
  `bindToggle(sel, 'intelBattleStats', STORE.INTEL_BATTLE_STATS)` only if
  step 5 is implemented with persistence. If persistence is deferred (it is
  for this plan), the toggle is a per-session checkbox read at render time
  with no save call — that is honest and matches `csAlert`'s read-time
  default without a setter in scope.
- **HIGH-RISK?** No — read-only aggregation.

## 8. Failure modes

- **`parseReport` returns null** (`src/parse-inline.js:48-54`) — silently
  dropped at intake (`src/spy.js:237-241`); no impact on the aggregation.
- **Unit metadata missing for an attacker unit id** — `unitMeta(id)`
  (called via `wonder.js` style with `Object.entries`) returns `null` or
  `undefined`. The aggregator must `if (!m || m.is_naval) skip` (navel units
  do not appear in farm raids; the existing precedent is
  `wonder.js:defenseLocalStrength` which filters `m.is_naval`). Per CLAUDE.md
  "Precondition invariant": unreadable == unknown == skip, never estimate.
- **Identity loss** — `intelMyIdentity()` (`src/intel.js:17-27`) returns
  `{id:null, name:null}` on read failure; `intelActorIsMe()` (`src/intel.js:28-33`)
  then returns `false`, so "yours" filtering falls back to the unsorted
  export. Do not log a warning on every render — throttle via
  `gbLogT('intel-identity-blind', 300000, ...)`.
- **`state.findings` > 500** — already capped at intake (`src/spy.js:250-253`
  and `src/core.js:1167-1171`). Aggregation re-runs cleanly after the cap.
- **`vill_id` field absent** in older report shapes — `parseReport`
  (`src/parse-inline.js:90`) defensively falls back through `r.vill_id ???
  r.farm_town_id ?? null`; absent rows contribute zero raids to that farm.

## 9. Validation gate

Plan 27 §11 risk class Low: preflight + one in-game session, no failure.

- Preflight row `intel: battle stats`: pass when `state.findings.length`
  reads; warn (not fail) when `<5` findings (sample size too small to be
  meaningful).
- Manual: let one farm-cycle run with `intel-battle-stats=ON`, then visit
  the Intel tab. Expected: `=== Pérdidas ===` shows the player whose
  attacker appears most often, ranked by losses desc; `=== Granjas top ===`
  shows the farm villages sorted by haul-per-raid. Log shows no new entries
  (read-only).
- After a known-loss battle (loss to a CS or to a stronger player), the
  player's row in `Pérdidas` should reflect it within the next 15s render
  tick (`boot.js:108-115`).
- Export (Actions → Copy config): the snapshot must round-trip through
  `qolExportConfig`'s redaction contract (`qol.js:251-256`, `redact:true` in
  `src/core.js:347`). The aggregator's output is *not* part of the export;
  only the toggle state is, when persisted.

  only consumes what `parseReport` already returns. When 2.1 lands and adds
  building levels / hero roster, 2.5's `intelFarmProfitability` will get
  richer without a re-write — by reading `f.buildings` / `f.hero` from the
  same `parsed` shape it already walks.
- **Attack pattern alerts** (plan 13, `intel.js:206-245`): already shipped.
  2.5 adds losses + farms, not duplicate pattern emission.
- **Spy report timeline** (plan 27 §2.2): own plan, separate call site.
- **Counter-intel** (plan 27 §4.2 = this plan's sibling 4.2): entirely
  different signal — who is **spying you**, not who is attacking. 4.2 owns it.
- **Threat assessment engine** (plan 27 §5.3 = this cluster's 5.3): writes a
  score; 2.5 reads no risk field and emits none.
- **Persist the snapshot** — recomputing on every render (500 rows × 2
  passes) is well below the 250ms renderLog threshold
  (`src/intel.js:renderLog` flush, set in CLAUDE.md).
